# Agent Note: Session budgets as a durably enforced policy plugin

Status: proposed

[English](2026-09-05-budget-policy.md) | 中文

## Problem

长时间运行的 agent（智能体）会话对自身开销没有任何明示上限。harness 中没有任何地方规定单个会话允许消耗多少 token、多少挂钟时间或多少钱，也没有任何东西会在会话越过这样一个数字时停下它。现有的减压阀是相邻但不同的东西：`dsh-tool-call-timeout-policy` 约束单次工具调用，`dsh-repeat-tool-reminder` 把模型从重复循环中推出来，而目标的 `maxGoalRounds` 约束的是续行 Round 数量而非开销。因此，一个会话可以在单个 Goal Round 内耗尽运维方的预算，而运维方是从账单上才知道这件事的。

有两项性质让这件事不只是一个计数器。其一，驻留在进程内存中的强制执行会在重启时丢失：崩溃后恢复的会话会从零开始重新计账，并把预算再花一遍。其二，日志无法解释的强制执行是不可复核的——没有发出模型请求就停止的轮次（turn），看起来和本就无事可做的轮次完全一样。只有当停止会话的那个数字能够从回放所读取的同一批持久事件中重现，并且监督进程能够查明是哪一项上限停止了它时，预算才是可信的。

仅仅阻塞本身也不够。harness 已经自动化了续行：只要处于 active 且已启用续行的目标存在，续行驱动器就会预留下一个 Round。若只停止一个轮次而让目标保持启用续行，驱动器会立刻排入下一个，于是预算恰恰会从它本应约束的续行路径上被花光。

## Proposal

在 `packages/guard/` 中发布 `@deepseek-ai/dsh-budget-policy`，与既有的单次调用策略插件并列。它是一个函数插件，自身不提供服务：随部署而变的上限放在 `Config` 中，对会话日志做纯折叠，只有一个强制执行点。

**Config。** `maxInputTokens`、`maxOutputTokens`、`maxTotalTokens`、`maxWallMs` 与 `maxCostEur`，每项都可选、省略即不限；另有以 `provider/model` 为键的 `pricing` 表，给出每百万输入与输出 token 的欧元价格。空配置是合法的空操作策略。校验在插件加载时执行：上限值或价格不是有限非负数时抛出；`maxCostEur` 在 `pricing` 表为空时抛出，因为没有价格的路由没有成本上限，建立在空表之上的上限实际上什么都不会强制执行。非空表中缺失的路由，其 token 仍计入 token 上限。

**折叠。** 开销只从会话日志派生，绝不来自内存计数器，因此任何持有日志的一方都能重算该投影。`assistant/message` 是唯一的用量来源：它携带某个步骤（step）最终的提供方计量，因此同一步骤更早的 `assistant/chunk` 用量采样被忽略，而不是重复计入。计费输入是 `inputTokens`、`cacheReadTokens` 与 `cacheWriteTokens` 三项不相交计数之和。每条消息按其自身已携带的 `provider/model` 来源计价，因此会话中途切换路由时，每个步骤按服务它的那个路由的价格计费，折叠也就无需跨事件追踪路由。挂钟时间是日志首尾两条事件时间之间的跨度——它计入空闲间隔（包括跨重启的间隔），但不计入自最新事件以来流逝的时间；正是这一点让它成为日志的函数，而不是读取时刻时钟的函数。

**强制执行。** 一个以 `prepend: true` 注册的 `agent/pre-step` 监听器。该 waterfall（瀑布式事件）是下一次模型请求之前有文档记载的最早扩展点，而前置注册让预算判定先于任何会构建请求上下文或为无法执行的步骤预留续行工作的监听器。越限时该监听器不调用 `next()`，而是返回 `{ kind: 'reject' }`——这正是 `dsh-goal-round-driver` 已在使用的停止步骤方式；循环随后以 `blocked` 原因结束该轮次，且没有打开任何步骤。`agent-loop` 保持不变。

**持久记录。** 越限时追加 `budget/breach`，携带 `{ cap, measured, limit }`——触发的上限、从该记录之前那些事件度量出的开销，以及被该开销超出的配置值。上限按固定顺序 `maxInputTokens`、`maxOutputTokens`、`maxTotalTokens`、`maxWallMs`、`maxCostEur` 求值，因此该顺序是持久记录的一部分，而非实现细节。事件先于阻塞目标追加，读者因此先看到解释、再看到后果。

**持久计价。** 只存在于内存中的成本是事后无人能核对的数字，因此每条由有价格路由服务的 `assistant/message` 都会追加一条 `usage/priced`：它的轮次与步骤、该路由的 provider 与 model、计费输入与输出 token、所应用的两项价格、由此得出的 `costEur`，以及整张已配置价格表的摘要。价格随记录本身留存，因此每次会话的成本无需部署配置即可从日志回放；该摘要是对价格表的小写 SHA-256——路由键按代码单元排序，每个条目先序列化输入价格、再序列化输出价格——它说明是哪个版本的价格表为该步骤计价，任何一项价格改变都会改变它。哪些步骤仍需计价由日志读出而非记忆：在某条 `usage/priced` 携带某步骤的轮次与步骤之前，该步骤都算未计价；因此恢复的会话恰好为前一进程遗留的部分计价，且绝不会为同一步骤计价两次。记录写入于两个位置——步骤的计量此时已经持久、循环也正处于两次请求之间：同一个前置的 pre-step 监听器内部、读取上限之前，使越限前的最后一条消息由记录越限的那个步骤计价；以及 `agent/turn-stopping`，使正常结束的轮次的最后一个步骤同样被计价。以错误或中止结束的轮次不会到达这两个位置，它的最后一条消息会一直未计价，直到该会话的下一次 pre-step 或停止。

**阻塞目标。** `ctx.goals.block(agent, ref, { code: 'budget-exhausted', message })` 正是 goal seam 为此提供的操作：它是持久的、记录可供机器路由的代码，并会停用续行，因此 `dsh-goal-round-driver` 之后不会恢复该目标。goal 领域是可选的，通过 `ctx.get('goals')` 读取；因为硬性 `inject` 会让未满足的依赖静默停用整个预算，而不是响亮地失败。没有 `ctx.goals`、没有当前目标，或目标已离开 `active` 的组合，同样会得到越限记录和被停止的轮次。

开销只增不减，因此同一会话中之后的步骤会再次越限并记录自己的事件。持久日志因此说明了这份已耗尽的预算拒绝了多少次尝试。恢复运行的方式是提高上限并重新加载部署；不存在运行时授予。

**模型体验。** 模型看不到任何新内容。判定发生在步骤打开之前，因此不会添加任何提示词分区、工具 schema 或消息文本，也不会发出模型请求——越限记录和阻塞原因是给人和监督进程看的持久状态。经 loader 启动的 e2e 证明了这种"没有"：一条 assistant 消息、一个以 `blocked` 结束的轮次，以及没有任何 Goal Round。

## Alternatives considered

**改在 `agent/request` 上强制执行。** 请求 waterfall 离它所约束的开销更近，但它运行在已经打开的步骤内部，此时 `step/start` 和进入该步骤的 `user/message` 都已持久化。在那里停止会在日志中留下一个残缺的步骤，并需要一种回退它的手段；`agent/pre-step` 在这些东西存在之前就拒绝，并且已经有明确定义的轮次结果。

**在内存中累计开销。** 每次响应递增一个计数器更简单也更省，而且是朴素实现会首先想到的做法。它无法满足真正重要的性质：恢复的会话从零重新开始，而停止会话的那个数字也无从校验。折叠的代价是每个待执行步骤对日志做一次遍历，与循环为组装请求本就付出的量级相同。

**把 `assistant/chunk` 用量采样也计入折叠。** 分片采样到达更早，并且能在之后的请求失败中留存，这正是 `dsh-token-meter` 的投影两者都读的原因。在这里两者都计会让已完成的步骤被重复计数，而调和二者又会把一条同步骤替换规则塞进一个全部价值就在于算术显而易见的策略里。最终 `assistant/message` 的计量是保守的选择：响应从未完成的步骤不被本策略计费。

**暂停目标而不是阻塞它。** `pause` 同样停用续行，但它读起来像一次可逆的人工操作，也不携带原因代码。`block` 是 goal 领域为提供方限制和配置预算所记载的 phase，其 `GoalBlockReason` 正是监督方用来把耗尽的预算与其他各种停止区分开的手段。

**取消 agent 而不是拒绝步骤。** `agent.cancel` 会停掉进行中的工作，但它是驱动器拥有的生命周期动词，会丢弃运行中轮次的部分结果，并产生与用户中断无法区分的 `aborted` 结果。预算是关于*下一次*请求的判定，因此拒绝发出它才是诚实的机制。

**做成带运行时 `grant()` 操作的服务。** 允许运维方实时提高上限可以免去重新加载。但它也把被强制执行的上限变成日志无法解释的非持久进程状态，而这恰恰是本 Agent Note 要确立的性质。推迟到有消费方真正需要时再做，届时授予本身必须成为一个有日志记录的事件。

**在不变式配套模块中也折叠成本。** 配套模块会独立重算 token 与挂钟时间的度量，但 `maxCostEur` 越限记录中的 `measured` 是用部署 `pricing` 表算出的会话总额，而越限事件并不携带该表；因此配套模块对该上限只校验"超过自身上限"这一关系，README 也如此说明。价格真正属于按步骤的 `usage/priced` 记录——单个步骤的价格正是该步骤成本所依赖的事实——因此配套模块只用记录自身的字段重算每笔计价，完全不需要部署配置。

## Acceptance criteria

- 日志超出某项已配置上限的会话，每个被停止的步骤恰好记录一条 `budget/breach`，携带触发的上限、度量到的开销与上限值。
- 对每一项日志可推导的上限，记录的度量值等于本包对该记录之前那些事件的折叠结果；`./invariant` 配套模块会拒绝不满足此条件的事件流，也会拒绝任何度量值未超过自身上限的越限记录。
- 每条有价格路由上的 `assistant/message` 恰好记录一条 `usage/priced`，携带其计费 token、路由、所应用的价格、由此得出的成本与价格表摘要；表中未命名的路由不记录任何一条，对同一份日志再次执行 pre-step 或停止边界也不会新增。配套模块会拒绝与所引用消息矛盾的计价、其自身价格无法产生的计价，以及针对日志已计价步骤的第二条计价。
- 当前 phase 为 `active` 的目标会在同一步骤中、于越限事件之后被 `blocked`，代码为 `budget-exhausted`，并且已组合的 `dsh-goal-round-driver` 不会启动任何后续 Round。
- 被停止的步骤不发出模型请求，轮次以 `blocked` 原因结束。
- `maxCostEur` 在 `pricing` 表为空时于插件加载失败；任何非有限非负数的上限值或价格同样如此。
- 空配置可以加载，且从不停止任何步骤。
- 单元 spec 覆盖 `src/` 每个文件的全部分支，达到每文件 100%；一个基于 `examples/headless-agent/tests/fixtures/budget-policy/` 且经 loader 启动的 e2e，通过真实的 `cordis.yml` 与进程证明越限、阻塞、没有 Goal Round，以及只有一条 assistant 消息。

## Rollout

该插件发布时不被任何组合加载。它不在 `dsh-base` 中，也不在任何已发布 profile 中，因此现有部署的行为不发生变化；部署方通过在自己的 `cordis.yml` 中加入该配置项及其上限来选择启用。e2e fixture（测试前置数据）就是参考组合。

持久格式是增量的：`budget/breach` 与 `usage/priced` 是两个新的 `SessionEventMap` 成员，已登记到生成的持久化目录中，既有事件都不改变。不认识其中任一类型的构建会依据事件信封默认的"读取时必需"规则拒绝该日志，这正是正确的结果——静默跳过越限记录的读取方会重建出一个停止轮次无从解释的会话，而跳过计价记录的读取方会给出低于会话自身日志的成本。由于不涉及结构性格式变更，`SESSION_FORMAT_VERSION` 保持不变。

计价记录先于将要折叠它们的消费方落地：当 `dsh-scorekeeper` 开始读取它们之后，每次会话的成本才成为 scorekeeper 的字段；在此之前，这些事件是没有任何投影依赖的持久状态。

推广进已发布 profile 要等到有部署给出真实的上限与真实的价格。此后自然的下一步是下文推迟的建议性阈值。

## Risks

**过低的上限会在毫无预警的情况下停掉有用的工作。** 该策略没有在触及上限前提示模型收尾的建议性阈值，因此预算耗尽的第一个后果就是轮次结束。凭猜测设定上限的运维方会遭遇一次突兀的停止。目前的缓解是每项上限都需显式启用且默认缺失；预警阈值是之后单独的决策，因为它*确实*对模型可见，需要有自己的逐字固定文本。

**成本的准确度取决于价格表。** 部署未定价路由上的用量只增加 token、不增加成本，因此 `maxCostEur` 单独无法约束路由未全部定价的部署。空表这一情形由加载时失败覆盖；部分定价的表是合法配置，README 说明了它的含义。每个路由只有一个输入价格，也意味着缓存命中按未命中价格计费，对缓存密集的会话会高估成本。

**挂钟时间是日志属性，不是秒表。** 空闲一小时且无任何事件的会话，在下一条事件落地前不会记录到任何流逝时间。这保证了度量可重算，同时也意味着 `maxWallMs` 约束的是日志覆盖的跨度，而不是运维方等待的时间。

**被反复重新提示的耗尽会话会让日志增长。** 每个被阻塞的步骤都记录自己的越限事件。增长受人工重新提示的频率约束，且每条记录都是"一次尝试被拒绝"的持久陈述；但自动重试的监督进程会每重试一次就追加一条事件。

**预算按会话计。** subagent 会话各自持有自己的日志与彼此独立的预算，因此父级上限不会约束它派生的整个集群。需要集群级上限的部署在这里没有聚合点。
