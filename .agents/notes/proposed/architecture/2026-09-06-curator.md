# Agent Note: The curator — mandatory redaction and terms-gated export

Status: proposed

English | [中文](2026-09-06-curator.zh.md)

## Problem

The [Village note](2026-09-05-daliesk-village.md) makes two governance promises about data leaving the lab: the exporter refuses to run without a redaction profile, and the AI Village dataset — like every client transcript — enters only under terms scoped to what it may serve. The [four-goal note](2026-09-05-four-goal-workflows.md) hangs the Data Curator roster row on the same two facts, names `ExportManifest` as what an export must leave behind, and puts "shipped redaction rules and a curator that records rule hits" in its blocking rollout item; its W3 stage 3 row states the drop rule outright — a sample whose consent scope is unknown is dropped, never assumed.

Neither promise has a producer. [`dsh-trajectories`](../../../../packages/improvement/trajectories/README.md) writes `dsh-trajectory/1` lines straight from the fold: it withholds held-out and district sessions by the `environment/run` stamp and counts every withheld one, but it applies no redaction, reads no `dataUse/terms`, and leaves no manifest, so its own README lists "No redaction" as a limitation and points at the telemetry rules as precedent. [`dsh-data-use`](../../../../packages/governance/data-use/README.md) pins the terms at session creation and its README says outright that nothing enforces them; the [attributable-decisions note](2026-09-06-attributable-decisions.md) defers that enforcement to its rollout item 2. Meanwhile the [competitive-baselines note](2026-09-06-competitive-baselines.md) records that the Village dataset's research licence forbids training without written permission and concludes that no pipeline may ingest it until the withholding can be proven. Today a single `ctx.trajectories.export()` call writes a client transcript, its credentials, and its evaluation-only samples into one training file, and nothing in the repository says it was wrong.

## Proposal

One plugin, `@deepseek-ai/dsh-curator` (`ctx.curator`) in the `packages/governance/` group, wrapping the exporter rather than replacing it. It is the only export path that redacts, the only one that reads the pinned terms, and the only one that leaves a manifest; the trajectory exporter stays the unredacted primitive it already is.

### Redaction profiles, required by design

`Config.profiles` is a non-empty map of profile id to `{ shipped, rules }`. A rule is `{ id, pattern, flags?, replacement }`, where `pattern` is a JavaScript regular expression source. Every rule is compiled at load: an uncompilable pattern, an empty id, a duplicate id inside one profile, an unknown `defaultProfile`, a profile with no effective rule, and the sticky `y` flag are all load failures naming the profile and the rule. `shipped: true` prepends the rule set this package owns — email addresses, `Bearer` tokens of at least twenty characters, `sk-`-style API keys, dotted-quad IPv4 addresses, and E.164 telephone numbers — each with a fixture proving a hit and a fixture proving a non-hit, because a rule nobody has watched fail is a rule nobody knows the shape of.

`requireProfile: true` is fixed by design and is not a `Config` field. There is no configuration that exports without redaction: `export()` refuses with `CURATOR_PROFILE_REQUIRED` when the request names no profile and no `defaultProfile` is configured, and with `CURATOR_PROFILE_UNKNOWN` when it names one the deployment did not configure. The rule shape is the telemetry redaction precedent's — a pattern and a replacement applied to strings — but the mechanism is not: telemetry redaction is a waterfall a deployment may leave unmounted, and this one is a validated table the export cannot run without.

Replacements are applied through a replacer function, so a `$&` or `$1` in a configured replacement is written literally and can never splice the matched text back into the record. Every rule is compiled with the global flag whether or not the deployment wrote one, because a rule that replaced the first hit and left the rest would report a hit count that understates what it left behind.

### What is redacted, and what never is

The curator walks each `dsh-trajectory/1` record and redacts every string it reaches, except three explicitly enumerated exceptions. Redaction therefore fails safe: a field added to the record type is redacted until someone decides otherwise, rather than exported until someone notices.

The exceptions are the record's identifiers and its readers' discriminants. Four subtrees are never redacted — `environment` (the `environment/run` stamp: environment and group ids, content digests, repetition, district, route names, isolation), `steps` and `parity` (numbers), and `provenance` (component ids, tool names, isolation). Twenty key names are never redacted at any depth: `type`, `id`, `format`, `sessionId`, `parentSession`, `agentPreset`, `role`, `sourceKind`, `toolCallId`, `basis`, `phase`, `goalId`, `checkId`, `status`, `isolation`, `executor`, `provider`, `model`, `reasoningEffort`, `attachmentId` and `mediaType`; rewriting one of those would corrupt a record a consumer switches on rather than protect anything in it. Three paths keep a registered tool name readable: `tools[].name`, `messages[].content[].name`, and `messages[].toolCalls[].name`.

Everything else is redacted, which is what the four-goal note's field list asks for: the rendered system prompt (`system`), every tool schema's `description` and parameter text (`tools`), every message's content blocks (`messages[].content[]`, recursively through tool-result content, so text, reasoning, and nested results are covered), the raw model-produced argument strings (`messages[].content[].arguments` and `messages[].toolCalls[].arguments`), the working directory (`source.cwd`), the goal objective (`reward.goal.objective`), and the certificate's per-check run evidence (`reward.certificate.results[].evidence`). Directives reach the record as the count `reward.directives`, not as text; the record carries no directive prose to redact, and the note says so rather than implying a redaction that does not happen.

### The terms gate

`export({ purpose, ... })` states which `DataUsePurpose` the export serves. Before anything is written, the curator reads each candidate session's log and folds its terms with `termsOf(events)`. A session whose newest `dataUse/terms` does not list the export's purpose is withheld and counted in `withheldByTerms`; a session that carries no terms at all is withheld by the same rule, which is the four-goal note's drop rule made executable — no terms, no export, and in particular no terms, no training export. Withheld sessions are never handed to the exporter, so the refusal happens in the operation that makes the decision rather than in a filter over lines already written.

The curator injects `trajectories`, `sessionPersistence`, and `dataUse`. It reads the per-session terms through the pure `termsOf(events)` fold rather than through the service, because `DataUseService` exposes no reader for a persisted session's events — `pin` and `defaultTerms` both speak about a live agent. The injection is still required: a composition that curates exports without pinning terms would withhold every session it holds, and requiring the service turns that misconfiguration into a load failure instead of an empty export file.

`residency` from the same terms is copied onto each exported record's `curation` block, so a sink can partition an export by region without reading the session logs again.

### The curation block and the manifest

Each exported record gains one `curation` block: `redactionApplied: true`, `redaction: { profile, profileSha256, hits }` where `hits` counts this record's replacements per rule id, and `residency`. The four-goal note sketches these as `redaction_applied`, `redaction_profile_version`, `redaction_rule_hits`, and `residency_region`; they ship in camelCase inside a camelCase record, the way [`dsh-scorekeeper`](../../../../packages/improvement/scorekeeper/README.md) already ships that note's snake_case field group.

Every export writes one `ExportManifest`: `version`, `exportedAt`, `purpose`, `profile`, `profileSha256`, `records`, `withheld: { heldOut, districts, terms }`, `ruleHits` summed over the export, `recordsSha256` over the written lines in order, and `trajectoryFormat`. `profileSha256` digests the profile's effective rules in order, so a manifest states which rules ran rather than only which name they were filed under, and `recordsSha256` is the digest of exactly the bytes the sink received, so a file and its manifest can be checked against each other by anyone holding both.

The export is not a session, so the manifest is a file and not a session event: nothing in it belongs to any one session's log, it is written after the last line rather than during a turn, and a `curation/export` event would have to pick an arbitrary session to live in. The manifest is the durable artefact; the returned report carries the same counts plus the skips for the caller in the same process.

## Alternatives considered

**A redaction waterfall on the trajectory exporter, like `session-telemetry/record`.** Rejected: a waterfall with no listener mounted passes records through unchanged, which is exactly the failure this note exists to prevent. Redaction here must be a precondition of running, not a hook a deployment can forget; the telemetry seam's rule shape is worth reusing and its optionality is not.

**Reimplementing the fold instead of wrapping the exporter.** The curator could call `foldTrajectory` itself and skip the exporter entirely. Rejected: held-out and district withholding, skip accounting, and sink closure are the exporter's and would be duplicated, and the manifest's `withheld` triple is exactly the exporter's own report beside the curator's own terms count.

**Redacting a deny-list of known text fields.** Rejected as the wrong default: a new field on `Trajectory` would be exported unredacted until someone remembered it. The allow-list of identifiers and discriminants is longer to write once and safe every time the record type grows.

**Applying the profile each session's terms name rather than the export's.** Rejected for this slice: one manifest states one profile, and a per-session profile would make `profileSha256` unreadable. A deployment holding several clients' transcripts runs one export per profile, and the terms' `redactionProfile` names which profile that is.

**Deriving the manifest path from the sink.** Rejected: `TrajectorySink` is a `write`/`close` pair with no path, and guessing one would be the hidden default the package boundary rules forbid. The request states `manifestPath`, and the manifest is returned in the report whether or not one is given.

**A `curation/export` session event beside the manifest.** Rejected: an export spans many sessions and belongs to none, so the event would have to be written to an arbitrary one or to all of them, and neither states the fact honestly.

## Acceptance criteria

- A profile with an uncompilable pattern, an empty or duplicated rule id, a sticky flag, no effective rule, or an unknown `defaultProfile` fails at load with the profile and rule named; each rejection is proven by a fixture.
- Each shipped rule has one fixture proving a hit and one proving a non-hit, and a configured replacement containing `$&` is written literally.
- `export()` without a profile refuses with `CURATOR_PROFILE_REQUIRED` and writes nothing.
- A `training` export withholds every session whose terms omit `training`, and a session with no terms at all, counting both in `withheldByTerms`; an `evaluation` export of the same store admits the sessions whose terms list `evaluation`.
- Every exported record carries `curation.redactionApplied`, the profile and its digest, the per-record hit counts, and the residency its terms name; every never-redacted field survives a profile whose rules match it.
- `recordsSha256` is the digest of the sink's bytes in order and is stable for the same records; the manifest's `withheld` triple accounts for held-out, district, and terms withholding separately.
- A Loader-booted e2e composes the environment registration, the runner, the budget policy, persistence, the checkpoint policy, the trajectory exporter, data-use terms admitting `delivery` and `evaluation`, and the curator with the shipped rules; the scripted transcript carries a fake address and a fake `sk-` key, the `training` export writes no line, the `evaluation` export writes the record with both rule hits counted and neither string present, and the manifest's `recordsSha256` matches the file on disk.

## Rollout

1. This slice: the curator, the shipped rules, the terms gate, the curation block, and the manifest.
2. The trust-dossier export the Village note's rollout item 5 still needs, which is a second consumer of the same manifest.
3. `DatasetManifest`: the four-goal note's curated set with dedupe, decontamination against the held-out suite, and the merkle root over content hashes; the per-record `contentHash`, `dedupeClusterId`, `decontaminationStatus`, and `split` fields hang off it, not off this slice.
4. Refusing an unredacted export by composition: a village rule that rejects a district composing the trajectory exporter without the curator, once a district composition exists that needs it.

## Risks

- **The unredacted primitive is still callable.** `ctx.trajectories.export()` remains a service any plugin in the process can call, so the curator is the path that refuses rather than a barrier around the data. Closing that needs the composition rule in rollout item 4; until then the README says which call is the safe one.
- **Rules are regular expressions, and regular expressions miss.** A credential in a format nobody wrote a rule for is exported, and `redactionApplied: true` says a profile ran, never that the record is clean. The per-rule hit counts are what a reviewer reads to see whether a profile is doing anything at all.
- **A redacting rule can corrupt data.** An IPv4 rule rewrites a version string that looks like a dotted quad, and an aggressive custom rule can make a record unusable for training. The never-redacted set protects the identifiers a reader switches on; it does not protect meaning inside the text.
- **Terms are only as good as the pin.** A session pinned by a deployment whose configured terms are wrong is admitted or withheld by that error, and the curator cannot tell a wrong pin from a right one. It refuses the unpinned case, which is the one the log can see.
- **Two reads per admitted session.** The terms pass and the exporter's fold each read the session, so a large store is read twice. The cost is a batch export's, not the agent loop's, and the alternative was duplicating the exporter.
