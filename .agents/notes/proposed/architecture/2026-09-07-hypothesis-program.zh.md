# Agent Note: 建立在运营方订阅之上的假设验证计划

Status: proposed

[English](2026-09-07-hypothesis-program.md) | 中文

## 问题

这套 harness 已经有 Proving Ground、fleet、班次驱动器、带冻结配对计划的实验服务，以及三种把某个角色接上运营方 Claude Code 订阅的方式，却还没有产出任何关于自身质量的测得结果：实时区按固定节奏认证三个简单任务，这只证明了管道能在重启后存活，对能力毫无证明；也从未有配对实验晋升或否决过一次改动。与此同时，该领域上个季度测出的，恰恰是这套 harness 存在的理由所要回答的那些问题：harness 选择能让每个解决任务的 token 数相差最多 41.9 倍，而通过率只相差 0 到 8 个百分点；运行中途从廉价模型升级到强模型，挽回的差距不到一半，花费却比一开始就用强模型更高；5.37% 的 model-question cell 在相同条件下重新执行时会发生翻转；一张静态的任务类型表就能补上路由 oracle 差距的大部分；而 Sakana 的 Fugu 会在同一条轨迹内为每一轮派发不同的 worker 模型，封闭权重，且在欧盟不可用。实验室负责人提出的问题是对的：以这份订阅为引擎，这些结论中哪些能在我们自己的环境上站得住，在同一个模型上，harness 自身的循环是否优于产品自己的循环？

## 提案

把一套固定的假设作为冻结配对实验来运行，跑在一个由三十个零依赖编程任务组成、覆盖三个领域与三档、其中六个留出的基准之上，每条 arm（实验分支）都运行在运营方的 Claude Code 安装之上。该基准位于 `examples/headless-agent/tests/fixtures/proving-ground-bench/`：一个建立在 `environments/<task>/task.json` 之上的数据驱动注册器、一个在同一个提供方之下经 LLM 路由服务三个产品模型的组合、作为外部实现者的产品自己的循环、分别为一份实验计划与一份 fleet 计划提供的驱动器，外加一个对两次 fleet 运行做离线配对折叠的驱动器，以及一个证明每个任务的初始状态无法通过其自身测试、而其隐藏参考实现能够通过测试的准入脚本。结果记录在 `data/proving-ground/` 之下，与其他每一次运行一样；证伪的记录与确认同样审慎。

这套假设按运行顺序如下，各自带着自己的 arm、度量方式，以及能证伪它的条件：

- **E0，校准与翻转率。** 两条 arm 用同一条路由跑在同一批 cell 上，重复三次。度量的是证书在同一路由内的翻转率，以及此后每一个效应都要拿来对照的噪声基线。低于该基线的任何后续效应都报告为未有定论，而绝不是一次胜出。
- **E1，模型档位。** 中档对高档，低档对中档，跑在该基准的第 2、3 档上。度量证书率、尝试次数、每个已认证任务的 token 数。区间包含零即视为该档位被证伪。
- **E2，harness 循环对产品循环。** 同一个产品模型作为实现者，一边经 LLM 路由跑在 harness 自己的 agent loop 上，一边作为外部实现者跑在产品自己的循环上，二者在相同的 cell 上由 runner 一并认证。这正是「最好的 harness」这个问题落在同一个模型上时化简出的样子；一旦某条 arm 能够指名自己的实现者，它就成为一场冻结实验，在此之前则是两份离线折叠的 fleet 计划。
- **E3，尝试次数。** 一次尝试对三次带成簇指令的尝试，在两个组合上离线折叠得出。度量指令循环每次尝试新增了什么、又付出了什么代价。
- **E4，知识包。** 把 2026-q3 知识包挂载为其唯一 skill 根目录的 cell agent，对照不挂载该包的 cell agent，跑在该知识包所覆盖领域的任务上。度量有效输入、证书率。
- **E5，交接成本与降档，来自这两周的路由结果。** 一旦 runner 能在两次尝试之间切换模型，就有三条 arm：从头到尾用高档；从低档开始，在第二次尝试时升级到高档并保留 transcript；同样地升级但丢弃 transcript、保留 worktree；以及降档——第一次尝试用高档，随后用低档并保留 transcript。来自这些来源的预测：直接升级挽回的差距不到一半，花费却比一开始就用高档更高；丢弃低档的 transcript 优于保留它；降档能以高档一小部分的成本保住高档大部分的证书率。
- **E6，单一档位上的 k 次尝试对跨档位路由。** 在匹配的 token 预算下，用按证书挑选的重复高档尝试，对阵 E5 中路由效果最好的那条 arm。

每条 arm 的隔离级别都是 none，因为外部实现的那条 arm 撑不起更高的隔离声明；每一次路由决策都是一条已记录的会话事件；留出的六个任务，在有改动被提议晋升之前，绝不进入任何实验。

## 这套假设需要的切片

1. 一条实验 arm 能指名自己的实现者，使 E2 成为一场冻结实验（进行中）。
2. runner 与 fleet 计划上的一套尝试阶梯：按尝试序号配一个模型，外加 `keep` 或 `drop` 的 transcript 接口，并计入这份计划的摘要，使 E5 与 E6 成为冻结实验而不是离线折叠（[note](2026-09-08-attempt-ladder.md)）。
3. scorekeeper 中缓存正确的事实：原始输入、缓存读取与有效输入各自作为独立的事实，使 E4 与每一栏成本都能被正确读取。
4. 实验结果中的一个留出可靠性估计与一份按难度条件拆分的明细，使晋升与否不会只凭训练用的 cell 来判断。

## 曾考虑的替代方案

- **先导入一个公开基准。** 推迟，而非否决：Terminal-Bench 与 SWE-bench 的任务树需要这台主机不具备的容器隔离，它们经 gold 验证的切分是下一步要导入的东西，等一个 Harbor 适配器出现之后。本基准的任务是内部编写的，因此现在就能在这里运行，并能在三个档位上做出区分。
- **与已发布的排行榜比较。** 否决：由另一个验证者、在另一份 fixture 上、按另一种通过的定义产出的数字，比较的是记分牌，不是 agent；这里的每条 arm 都由同一个 runner 在同一份被恢复的 fixture 上认证。
- **先在循环内部按 step 路由，走 Fugu 式路线。** 作为第一场实验被否决：交接成本与翻转率的结果表明，带受控 transcript 接口的按尝试阶梯是更便宜、信息量也更大的检验，逐 step 路由则是等这套阶梯跑出数字之后的后续 arm。

## 验收标准

- 该基准准入三十个任务，其中六个留出；无密钥冒烟测试完成对它们的注册与准入。
- E0 报告一个翻转率与一条噪声基线，记录在 `data/proving-ground/` 之下，连同会话与导出文件一并留存。
- E1 到 E4 各自以一个判定与一个区间收尾，按同样的方式记录，本假设验证计划的结果章节点名每一次证伪。
- 尝试阶梯落地后，E5 与 E6 就以冻结实验的形式运行。

## 风险

- 这份订阅的速率限制给整个计划定了节奏：cell 一次运行两个，一场四十个 cell 的实验要花上数小时，因此这套假设要跑上数天，而不是一个下午。
- 人工编写的任务带着人工编写的错误；准入能抓住通过了的初始状态或失败了的参考实现，却抓不住把 prompt 定得过死的测试，因此一个在每条 arm 上都异常地零通过率的任务，要先经过审查，其结果才算数。
- 包在每次 LLM 路由查询外面的产品信封是模型可见的，却不在我们的日志里；路由上的每条 arm 都携带同一个信封，因此比较依然成立，但每个 cell 的绝对成本包含了它。
- 隔离级别为 none 意味着某条 arm 原则上可能读到它不该读的东西；每次运行上的不可变摘要与篡改裁决就是控制手段，任何被篡改的运行都算作其所属 arm 的一次失败。
