# Agent Note: OpenRouter 路由在单元首步之前挂起

Status: proposed

[English](2026-09-22-openrouter-route-prefirststep-hang.md) | 中文

## Problem

夜间基准台队列以 `e10-openrouter-nex-vs-laguna-t2` 打头，这是第一个两臂都跑在 OpenRouter 免费路由上的冻结配对——那是唯一条款允许其 transcript 进入 RLVR 语料的路由，因此通往开放权重模型的路正是从它经过。该实验从未产出记录。两次运行分别在相隔二十分钟和四分钟后启动，循环打印出 `=== loop nightly 1/2 ===` 表头后便再无动静：进程停在零 CPU，没有到 `:443` 的已建立连接，运行工作区和会话树下也没有写入任何文件。两个免费模型对一个平凡的 `chat/completions` 请求都在两秒内以 HTTP 200 作答,可见路由与账户都是活的;挂起发生在基准台的 agentic 负载之下、在单元首个模型请求之前,而非请求过程之中。

两个本应终结卡住单元的守卫在这里都没有触发。fleet 的路由断路器(`consecutiveErrors: 4`)统计的是错误,而一次静默的 await 不产生任何错误。组合的每单元墙钟上限在 agent 与 step 事件上折算,因此首步之前的挂起从不被它度量。路由上的请求超时(`timeoutMs`)会限制单次 HTTP 尝试,但零已建立连接表明没有请求在途可供超时——await 早于请求,发生在该路由为此单元所做的自身准备之中。

## Proposal

两处改动已落地以阻止挂起浪费自动化窗口,另有一处排队用于查明根因。

`e10-openrouter-nex-vs-laguna-t2` 从 `nightly` 队列移除,保留在 `openrouter-pairs` 中供有人看护的运行;夜间队列现在只有 `h3-baseline-sonnet-t5` fleet 一项,它可靠,且能扩大基线的噪声底。无人看护的夜间运行无法从一个逃过两个守卫的挂起中恢复,因此它绝不能以这样的条目打头。

`with-openrouter` overlay 中的 OpenRouter 路由 profile 现在把 `timeoutMs` 与 `streamIdleTimeoutMs` 都设为两分钟。这并不修复首步之前的挂起——挂起时没有请求在途——但对一个在途停滞的请求而言这是正确的界限,而免费层的队列确实会丢弃这种请求,因此把它作为路由卫生保留,而不是因其对此处不够用便删去。

根因尚未找到。下一步是为该路由的 fleet 与实验启动加装探针——provider 构造、凭证解析、implementer 可用性预检以及沙箱搭建——以点出被 await 的那个 promise,因为证据把挂起定位在首个 step 事件之前的其中一处。在此之前,循环没有逐条目的截止时间:一个配套改动应给每个循环条目一个总体超时,杀掉卡住的条目并把它记为失败,这样无论哪条路由导致挂起,一个挂起的计划都不能拖住整个队列。

## Alternatives considered

**为该路由降低单元墙钟上限。** 墙钟上限在 step 事件上折算;首步之前的挂起在任何取值下都不被它约束,因此降低它对此故障毫无作用。

**依赖路由断路器。** 它统计错误;静默的 await 不是错误。让它统计流逝的静默时间,会在错误的层次重复循环本应拥有的逐条目截止时间。

**把 e10 留在夜间队列里让它跑。** 最好的情况是它在许多小时里产出大多为超限的单元;最坏的情况,正如此处观察到的,它无限期挂起且无人终结。二者都不是一个夜间数字,且都会耗尽窗口。

## Acceptance criteria

`nightly` 队列在无人看护下产出一条已提交的记录与 ledger 行。`e10-openrouter-nex-vs-laguna-t2` 只在有人看护下、或在逐条目截止时间落地之后(以先到者为准),跑到一个已记录的裁定——一个真实的配对或一次诚实的快速失败。根因探针点出被 await 的 promise,修复由一个 openrouter 单元验证:它要么发出首个请求,要么在截止时间内失败。

## Risks

诊断依据的是进程的外在迹象——零 CPU、无连接、无文件——而非一份捕获的调用栈,因此被 await 的 promise 是推断出来的,不是看到的;探针步骤正是为取代这份推断而存在。在一条其失效并未被它覆盖的路由上保留 `timeoutMs`,有被读作「修复」的风险;队列注记与本注记都明确写出它是卫生措施,不是解药。把免费路由从夜间队列移除,会让 RLVR 语料在挂起解决之前失去一个自动化来源,这是排期代价,不是正确性代价:该路由仍在有人看护下运行,而模型计划本就受制于额度与提示词供给,而非这一节律。
