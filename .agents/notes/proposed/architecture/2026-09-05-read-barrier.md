# Agent Note: The read barrier as filesystem and process authority

Status: proposed

English | [中文](2026-09-05-read-barrier.zh.md)

## Problem

A certificate proves only what the implementer could not reach, and nothing in the repository decides that. [`dsh-verification`](../../../../packages/verification/verification/README.md) commits a `verification/certificate` only for a fully passing run and stamps it with a `CertificateIsolation` of `none`, `process`, or `host`, but its own Known Limitations name the missing read barrier: the standard's `run` instructions are readable by any in-process consumer of the log, and denying implementer reads is filesystem-policy work in a plugin that does not exist. The [four-goal-workflows note](2026-09-05-four-goal-workflows.md) states the requirement as principle P4, the read barrier as filesystem and process authority rather than a promise; this note is its design.

The implementer and the checks share one filesystem and one operating-system user. `EnvironmentRunner.run()` creates the implementer's agent with `meta.cwd = workspace` and then executes every check through `ctx.shell` with `workdir: workspace` from the same process ([`packages/improvement/environment-runner/src/index.ts`](../../../../packages/improvement/environment-runner/src/index.ts)); its README states that the read barrier is the deployment's. The standard is in the implementer's own session log, which [`dsh-session-persistence-jsonl`](../../../../packages/session/session-persistence-jsonl/README.md) keeps as ordinary files under its configured root. [`dsh-credentials-local`](../../../../packages/credentials/credentials-local/README.md) already records what that costs: owner-only modes stop other operating-system users and not the model, because tool processes run as the same user and the shipped file policy confines mutations rather than reads.

Composition decides what an implementer can read, and no composition is checked. A preset that mounts [`dsh-tool-session-query`](../../../../packages/session-query/tool-session-query/README.md) hands the model five tools that read the durable session log; one that mounts [`dsh-tool-cordis`](../../../../packages/extensions/tool-cordis/README.md) lets it define and mount a plugin into the live process. `tools.restrict()` and subagent `toolFilter` are visibility composition per [agent-scope-contexts](../../implemented/architecture/2026-07-08-agent-scope-contexts.md), not authority, and a certificate carries no durable record of which tools its session composed.

An isolation claim above `none` therefore has no evidence behind it. `recordRun()` writes the level its caller passes; the invariant companion validates revisions, append-only check growth, and certificate coverage, and never asks what the level asserts. Keeping only `process` and `host` runs — the reward-gaming mitigation the [trajectory-export note](2026-09-05-trajectory-export-and-environment-registry.md) names, and the column the [fleet leaderboard](../../../../packages/improvement/fleet/README.md) refuses to average across — filters on an unchecked field.

Nothing detects a workspace the implementer edited underneath its own checks. A task whose fixture supplies the tests it will be graded on is graded on whatever those files say at validation time, and the runner compares nothing between the overlay it wrote and the tree it measures.

## Proposal

Make the barrier authority at the executor: one policy owner, per-capability denial where each capability opens paths, and a certificate that may claim only what the composition recorded.

**A validator-owned root.** [`@deepseek-ai/dsh-read-barrier`](../../../../packages/verification/read-barrier/README.md) (`ctx.readBarrier`) at `packages/verification/read-barrier/` is the policy home for denied reads, in the role [`dsh-sandbox-policy`](../../../../packages/sandbox/sandbox-policy/README.md) plays for sandbox mode and workspace root. Its `root` config defaults to `dshHomePath('verification')` through [`dsh-home-paths`](../../../../packages/util/home-paths/README.md) and accepts any absolute or `~`-prefixed directory, as does every `denyRoots` entry; the service creates the root owner-only (`0700`) at construction and fails loud when it exists with wider modes or when a configured path is not absolute after expansion. `reserve(agent)` mints `<root>/runs/<sessionId>/` for one run and returns its absolute path, synchronously, so the role is in force the moment the caller returns; the environment runner calls it before appending the `environment/run` stamp and writes there the standard snapshot, one script per check at `checks/<checkId>`, and any fixture the environment marks held out, then resolves each check's `run` against that directory so the command line the implementer can observe in a process listing names a file whose content it cannot read. Because that reservation is what makes a session the implementer, the runner reads the barrier through `ctx.get('readBarrier')`: a composition without one reserves nothing and runs its checks inline, which is what its `isolation: none` claim already says. `protect(path)` registers one more denied directory and returns its disposer, so a plugin that owns a directory — `dsh-session-persistence-jsonl` with its session-store root — contributes it as an effect instead of a deployment repeating it in configuration; `denyRoots` remains a config field for directories no plugin owns. `resolve({ session? })` answers one `ReadBarrierPolicy { role, root, denied }`, and `denies(policy, target)` decides containment. Enforcement is not a field on that policy: `enforce(capability)` registers one capability's decision as an effect and `enforcementCensus()` reads the registrations back, so what a capability enforces lives as long as its listener rather than being recomputed per call. `declareComposition(agent, { presetId, role? })` is how the preset roster — the only caller — tells the barrier what a session composed.

| Field | Meaning |
|---|---|
| `root` (default `dshHomePath('verification')`) | Absolute or `~`-prefixed directory the barrier owns; created `0700`, rejected when it already exists with wider modes. |
| `denyRoots` (default `[]`) | Additional absolute directories denied alongside `root`, for directories no plugin registers through `protect()`. |
| `hostAttestation` (optional absolute path) | File an external account writes; without a verified one the barrier refuses a `host` claim. It arrives with the certificate invariant that reads it. |

The denied set for a role is not among them: which authorities an `implementer` may hold is a security invariant, not a deployment choice.

**The deny rule.** For a session whose role is `implementer`, a read is denied when the target's canonical path is a denied directory or a descendant of one. Containment is decided the way [`dsh-fs-sandbox`](../../implemented/feature/2026-07-14-cross-family-fs-sandbox.md) decides it: canonicalize first, then test identity or descent through `ctx.fs.contains(parent, child)` on resolved targets, so the policy parses no path strings and an ancestor symlink swapped since resolution is caught by re-canonicalizing immediately before the decision. A target whose containment cannot be decided is denied. Roles `validator` and `unrestricted` are denied nothing; `unrestricted` is the default and leaves every shipped preset exactly as it is today. Until a preset can declare a role, a session holding a reservation is the `implementer` and every other session is `unrestricted`, so the two open roles are indistinguishable at the decision and only the denied one is reachable.

**The fs policy plugin.** Add `@deepseek-ai/dsh-fs-read-barrier` at `packages/fs/fs-read-barrier/`, the read counterpart of the write and edit policy [`dsh-fs-observation-policy`](../../../../packages/fs/fs-observation-policy/README.md) contributes through the same event gate. It registers no service and declares no `Config`, because every deployment-varying value belongs to the barrier above: it injects `readBarrier` and decides one new event. [`dsh-fs`](../../../../packages/fs/fs/README.md) declares `fs/read-intent(target, actor, next)` beside `fs/write-intent` and `fs/edit-intent`, as a `@mode waterfall` returning `FsReadDenial { code: FsErrorCode; message: string } | undefined`; unlike the two single-slot intents this one delegates, because a barrier that owned the slot would stop every later read policy from deciding. The plugin returns a denial for a contained target and calls `next()` otherwise, and owns the exact message as `readBarrierDenialMessage`. `FsErrorCode` gains `FS_READ_BARRIER_DENIED`. `dsh-tool-fs` dispatches the event inside `resolveRegularReadTarget` before `ctx.fs.stat`, covering `read` and `read_image`, so a denied path never reveals presence or absence, and `dsh-tool-str-replace-editor` dispatches it on the `view` command. The tool layer adds no recovery instruction, because no retry of the same call succeeds; the model sees the policy's message verbatim inside the tool registry's ordinary `Error: ` framing.

##### Exact error

```markdown
read denied: "<path>" is validator-owned — it is not part of this task; continue without it
```

**What a denial records.** The barrier appends one log-only `read-barrier/denied` session event per refusal, carrying `{ version, role, capability, displayPath, root }`, where `capability` names the seam that refused (`fs`, `shell`, `subprocess`, `terminal`). The path is already in the log inside the model's own `tool/call` arguments, so the event adds evidence and no new disclosure. It is a `SessionEventMap` member registered in `KNOWN_SESSION_EVENT_TYPES` by `gen-persistence-catalog`, so this build reads it as a required event. The envelope's `ignorable` marker stays unused: `Session.append` has no parameter for it and no event in the repository sets it, so marking this one would be a core append change rather than a slice of the barrier.

**Tool authority and the composition-time guard.** `ToolDefinition` in [`dsh-tools`](../../../../packages/core/tools/README.md) gains `authority?: readonly ToolAuthority[]`, never model-visible, where `ToolAuthority` is a merge-extensible union declared by `dsh-tools` with three members at the start: `session-log` (the tool reads durable session events), `plugin-mount` (it mounts or evaluates code in the live runtime), and `runtime-introspection` (it reports the live composition). `dsh-tool-session-query` declares `session-log` on all five of its tools; `dsh-tool-cordis` declares `plugin-mount` on `cordis_define`, `cordis_run`, `cordis_stop`, and `cordis_undefine`, and `runtime-introspection` on the three tools it actually ships for the read-only report — `cordis_inspect_list`, `cordis_inspect_query`, and `cordis_inspect_self`. An `implementer` session may compose none of the three. Declaring authority at the tool, rather than a name list at the barrier, means a tool added later is covered by its own declaration.

**How a preset declares its role.** A preset's optional `preset.yml` gains `role: implementer | validator | unrestricted`, absent meaning `unrestricted`. It is the one authority claim that file carries, so [`dsh-agent-presets`](../../../../packages/preset/agent-presets/README.md) refuses `validator` from a `user`-trust preset and lists that preset as `broken` with the reason: a locally authored preset that could name itself `validator` would grant itself reads. This is the roster's first enforcing use of `trust`, and its README changes with it. `mountPreset` audits the role after `handle.await()` settles the subtree, beside `inactiveRows`, and rejects the mount when the declared role is `implementer` and any tool in the preset's scope layer declares a denied authority. Because the audit runs inside the agent factory's `setup`, a rejected composition rolls the whole session creation back, so the failure is loud and nothing half-composed survives.

##### Exact mount refusal

```markdown
agent-presets: preset "<id>" declares role "implementer" but composes "<tool>", which carries the "<authority>" authority
```

**The runtime guard.** The barrier also registers one `ctx.tools.guard()` through the agent's own context at session setup, denying any execution whose definition carries a denied authority for that session's role. Guards run after every `tools/pre-execute` listener and are monotonic, so no later listener can turn the denial back into permission ([`ToolGuard`](../../../../packages/core/tools/src/index.ts)). The mount audit covers the preset's composition; the guard covers a tool registered into the agent's own layer afterwards, including one a subagent driver contributes.

##### Exact guard denial

```markdown
"<tool>" carries the "<authority>" authority and is not callable in an implementer session
```

**Process-level denial.** The [sandbox seam](../../implemented/feature/2026-07-06-sandbox.md) expresses file effects only, which is why a confined subprocess can still read anything it reaches. `SandboxPolicy` and `SandboxExecutionPolicy` gain `deniedReadRoots: readonly string[]`; `ctx.sandboxPolicy.resolve()` fills it from `ctx.readBarrier.resolve({ session })`, so the fs fence and every process runner keep taking one owner-resolved policy per call. `dsh-sandbox-local` implements it per backend — a `bwrap` `--tmpfs` over each root, a Landlock ruleset that omits read access for them, a Seatbelt `(deny file-read* (subpath …))` clause, and the Windows ACL runner's equivalent deny entry — and reports `SANDBOX_UNAVAILABLE` when the selected backend cannot express the denial, so the claim fails rather than the barrier. [`dsh-bash-sandbox`](../../../../packages/shell/bash-sandbox/README.md), `dsh-pwsh-sandbox`, and [`dsh-terminal-bash`](../../../../packages/terminal/terminal-bash/README.md) inherit it without changes. [`dsh-tool-fs-search`](../../../../packages/fs/tool-fs-search/README.md) spawns ripgrep unconfined through `ctx.subprocess` today; it confines that spawn through `ctx.sandbox.confine()` whenever a barrier is in force, and additionally the barrier's tool guard denies a `glob` or `grep` whose `path` argument names a denied root directly.

**The executor of a run.** `RunEvidence.executor` already distinguishes a `runner` from an `agent-reported` run on the `verification/run` event, and `recordRun()` certified both identically. `VerificationCertificate` gains `executor`, copied from the run it cites, so a consumer reading a certificate alone can tell which it was; the scorekeeper's outcome facts expose it as `certificateExecutor`, which is what lets a leaderboard partition on it. `recordRun()` refuses any isolation above `none` for an `agent-reported` run — the implementer's own account of its checks is admissible evidence only at the level that asserts nothing — and the invariant rejects a certificate whose executor differs from the run it cites, or which claims `process` or `host` over an `agent-reported` run.

**Executors the barrier cannot confine.** Two composed capabilities open paths the harness cannot fence in-process. [`dsh-workflow-worker-thread`](../../../../packages/workflow/workflow-worker-thread/README.md) states that its worker is not a security sandbox and that an escaped script recovers Node capabilities with the host process's privileges. The out-of-process [subagent](../../../../packages/subagent/subagent/README.md) providers — `subagent-acp`, `subagent-claude-code`, `subagent-codex`, `subagent-dsh-sdk` — launch a foreign agent with its own tool stack and no harness policy. For an `implementer` session, both refuse to start under a claim of `process` or `host` and record `unenforced` under a claim of `none`. The in-process subagent drivers need no exception: a child joins its parent's standing composition through `composeFrom()`, so it inherits the same census, the same scope layer, and the same role.

**The scope census.** It arrives with `ToolAuthority`, whose declarations its `census` is made of. Before the session's first `request/header`, the barrier appends one log-only `read-barrier/scope` event carrying `{ version, role, presetId, root, denied, census, enforcement }`. `census` is one entry per tool visible to the agent, `{ name, authority }`, which makes the composition's authority durable rather than composition-time-only; the invariant cross-checks it against the tool names in each `request/header`'s assembled schemas, so a tool added after the census is caught. `enforcement` is one entry per path-opening capability the composition registered — `fs`, `shell`, `subprocess`, `terminal`, `subagent`, `workflow` — valued `denied-at-executor`, `unenforced`, or `not-composed`. A capability records `denied-at-executor` by calling `ctx.readBarrier.enforce(capability)` for the life of its enforcing registration, so the claim and the listener that backs it are disposed together.

**The certificate invariant.** `recordRun()` refuses to commit a certificate whose isolation exceeds what the session recorded, with `VERIFICATION_ISOLATION_UNPROVEN`; the [`./invariant`](../../../../packages/verification/verification/README.md) companion applies the identical rule to the durable stream, so a forged certificate fails replay wherever the companion is installed. Both read the session log alone rather than `ctx.get('readBarrier')`: everything a live barrier knows about a session is already in the census it appended, and one rule over one evidence source is what makes the live refusal and the replay refusal the same rule. Independently of level, both refuse a certificate on a session whose scope census carries a denied authority: composing a log-reading tool forfeits the certificate even when the guard was somehow bypassed. `CertificateIsolation`'s JSDoc changes with the rule: `process` means what the ladder below states rather than in-process read policy alone.

**The `host` marker.** `host` is accepted only from a `read-barrier/attestation` event the barrier wrote after verifying a file at the configured `hostAttestation` path: it must be a regular file, be owned by a uid other than the harness process's effective uid, and be unwritable outside its owner. An in-process component cannot produce that file without already holding another account's privileges, which is the property the level asserts. The barrier records the file's SHA-256 alongside its owner; comparing that digest against the run's environment content hashes waits for the `environment/run` stamp to reach the barrier, so the shipped check proves the owner rather than the run. Ownership is read through `process.geteuid()`, which Windows does not provide: an attestation there is refused with that reason rather than verified through `dsh-sandbox-windows-acl`. Absent or unverifiable, the barrier records no attestation, logs why, and the claim is refused.

**Tamper on check-owned paths.** Check-owned paths are the barrier's reserved directory plus the workspace paths an environment declares immutable: `EnvironmentDefinition.task` gains `immutable?: readonly string[]`, workspace-relative paths the fixture supplies and the implementer must not author — the tests, the reference outputs, and any overlaid check script; one that is not relative and normalized is refused at registration with `ENVIRONMENT_INVALID_IMMUTABLE`, because a path the registry cannot resolve must not reach the run it would decide. The runner already hashes a directory in `hashDirectory`; it records the digest of the check-owned set once the reservation is stocked and before the implementer's first turn, and again at each validation before the fixture overlay puts back exactly what the comparison is looking for. The `verification/run` event that the [environment-runner note's second slice](2026-09-05-environment-runner.md) adds carries the attempt's `treeHash`; this note adds `verdict: 'passed' | 'failed' | 'tampered'`, spelled apart from `CheckStatus`'s `pass` and `fail` so a run's verdict is never read as one check's result. A digest that differs from the baseline is `tampered`: the runner executes no check, records every result as not executed, and calls `recordRun` with `tampered: true` — the operation that certifies is the one that refuses, so it writes the verdict and issues no certificate for any verdict but `passed`, and `RunEvidence` states only the tamper because pass and fail already follow from the results. It then issues one directive naming tamper without naming a path, delivers it to the implementer as the last validation follow-up so the run's own transcript carries why it ended, and stops the attempt loop because the workspace no longer measures the task. Because each validation rewrites the reservation it owns, the runner re-establishes the baseline after materializing the attempt's scripts, so its own writes are never read as tamper. `foldTrajectoryReward` gains reward basis `tamper` with `outcome: 0`, which outranks any certificate in the same log, and the invariant companion rejects a certificate over a run whose verdict is not `passed`.

**A blind judge under one licence.** Cross-provider routing is the first answer to a judge whose label affects it, and a deployment with one model licence cannot take it. The second route is filesystem and process isolation plus a judge session that holds no implementer context, which means all of the following and nothing weaker. The judge session is created through `ctx.agents.create` with a fresh `SessionId`, no `parentSessionId`, and no resume or fork seed, so its log begins at its own creation. Its `meta.cwd` is a judge workspace holding a copy of the implementer's tree at the audited attempt's `treeHash`, never the implementer's workspace. Its derived history contains exactly the judge preset's system prompt, the environment's task prompt, and one user message carrying the evidence the auditor chose; no `assistant/message`, `tool/result`, or `verification/directive` from the audited session reaches it. Its preset is `system`-trust and declares `role: validator`, so the composition-time guard still denies it a log-reading tool: a judge that could read the audited log would reconstruct the implementer's reasoning and lose the independence this arrangement provides. The barrier appends a `judge/session` event naming the audited session id and asserting the empty lineage, and the invariant rejects a verdict from a session whose header carries a parent or a seed.

## The isolation ladder

| Level | What it asserts | Required enforcement | Durable evidence |
|---|---|---|---|
| `none` | Nothing. Implementer and validator share a filesystem. | None. | The certificate alone; a scope event when the barrier is composed. |
| `process` | No executor of the implementer's session opens a denied path. | Every composed path-opening capability records `denied-at-executor`; the session's sandbox mode is `workspace-write` or narrower; workflow workers and out-of-process subagent providers refuse to start. | A `read-barrier/scope` event before the first `request/header`, with role `implementer`, an empty denied-authority intersection, and no `unenforced` entry. |
| `host` | The checks and fixtures are outside the harness account's write reach. | Everything `process` requires. | Everything `process` requires plus a `read-barrier/attestation` event the barrier verified from a file the harness process cannot write. |

## Alternatives considered

**Omit the tools and trust the prompt.** Schema omission and instruction are not enforcement when another caller reaches the same operation, which is why the packages standard requires the decision in the operation that makes it. The barrier denies at the executor and the acceptance criteria test denial there.

**Deny reads through `SandboxMode` instead of a separate policy.** `SandboxMode` is a three-value file-effect vocabulary shared by every enforcing family; a fourth value meaning "and cannot read these paths" would make one enum carry two independent decisions, and every consumer that switches on the mode would have to learn the second. `deniedReadRoots` rides the same per-call policy without changing what a mode means.

**Subclass the filesystem provider the way `fs-sandbox` does.** One provider registers `ctx.fs` per context and `SandboxedFileSystem` already extends `LocalFileSystem`, so a second fence by inheritance would force a mixin or a fixed provider ladder. The `fs/*` event gate is the layer built for adding policy without a service dependency, and it degrades to the bare provider when the plugin is absent.

**Name the forbidden tools in the barrier's config.** A name list is stale the moment a package adds a log-reading tool, and a deployment could shorten it. Authority declared at the tool is carried by the tool, and the denied set for a role is a security invariant rather than a tunable.

**Derive the role from the session creator instead of the preset.** The creator knows the intent; only the composition knows what was actually mounted, and the failure this prevents is a preset that composes a tool its role forbids. The preset declares the role, the mount audit checks the composition against it, and the creator's request is refused when the resolved preset's role does not match.

**Infer `host` from configuration.** The environment runner already rejected inferred isolation for the same reason: nothing in-process can observe the deployment's arrangement, so an inferred value either devalues an isolated run or lies about a local one. A file another account owns is the smallest fact that cannot be produced from inside the process.

**Score tamper as a failing check.** A failed check means the work is incomplete; a modified test means the measurement is void. Folding them would let a trajectory earn partial credit for a workspace whose checks no longer describe the task, so tamper is its own verdict and its own reward basis.

**Give the judge the implementer's transcript for context.** A judge that reads the audited reasoning inherits its framing, and the same-lineage mislabeling the [seams note](2026-08-29-verification-improvement-oversight-seams.md) records is what the blind session exists to avoid. The judge receives the task, the tree, and the evidence the auditor selected.

## Acceptance criteria

- In a Loader-booted composition over `examples/headless-agent/tests/fixtures/read-barrier/`, a `read` of a file under the barrier root from an `implementer`-role session fails with `FS_READ_BARRIER_DENIED` and the exact message above, one `read-barrier/denied` event is appended, and the same call from a session the barrier denies nothing — one holding no reservation, and a `validator` once a preset can declare that role — returns the file's content in the same process.
- The denial is proved through the executor, not the schema: the implementer's `read` tool is registered and visible, and a direct `ctx.fs.readText` from a trusted plugin still succeeds, which the test asserts so the threat model stays explicit.
- Mounting the preset at `examples/headless-agent/tests/fixtures/read-barrier-guard/`, which declares `role: implementer` and composes `dsh-tool-session-query`, rejects with the exact mount refusal and leaves no session behind; a `user`-trust preset declaring `role: validator` is listed `broken` with its reason; and the invariant companion rejects a certificate on a hand-authored log whose scope census carries the `session-log` authority.
- `recordRun()` with `isolation: 'host'` on a session with no verified attestation refuses with `VERIFICATION_ISOLATION_UNPROVEN` and commits no certificate; the invariant companion rejects a hand-authored log carrying that certificate at the certificate record.
- `recordRun()` with `isolation: 'process'` on a session whose scope event records any `unenforced` capability refuses the same way, and succeeds once every composed capability records `denied-at-executor`.
- Over `examples/headless-agent/tests/fixtures/read-barrier-tamper/`, whose environment marks its test file immutable and whose scripted model overwrites it, the attempt's `verification/run` carries `verdict: 'tampered'`, no certificate exists, the goal stays out of `complete`, and the exported trajectory line has `outcome: 0` with basis `tamper`.
- A judge session created for an audited session has no `parentSessionId` and no seed, its derived history holds exactly the judge system prompt, the task prompt, and the evidence message, and the invariant rejects a verdict from a session that carries either.
- Two keyless snapshots record what the model sees: `examples/headless-agent/tests/snapshots/read-barrier-denied/` pins the denial text in the transcript and the session log, and `examples/headless-agent/tests/snapshots/read-barrier-tamper/` pins the tamper directive's `<validation_failed>` follow-up. Both replay on macOS and Linux per the [testing policy](../../../../docs/testing.md).

## Rollout

Each slice lands with its own tests and leaves the gates green on its own.

1. **Landed.** `@deepseek-ai/dsh-read-barrier` with the root, `reserve`, `protect`, `resolve`, `denies`, `recordDenial`, the `read-barrier/denied` event, and its invariant companion, which rejects a refusal for any role but `implementer`, one carrying an unknown payload version or capability, and one naming a second barrier root inside a session. The environment runner reserves through `ctx.get('readBarrier')` and materializes `standard.json` plus one `checks/<checkId>` script per attempt, running each as `. <script>` so the same shell executes the same instruction; a check id that is not one path segment, and a reservation path the command line cannot carry unquoted, fail the run with `ENVIRONMENT_RUN_UNSAFE_CHECK_SCRIPT`. `read-barrier/scope` and the enforcement census are not part of it: the census is one `{ name, authority }` entry per visible tool and enforcement is one entry per capability that records a decision, so both wait for the slice that supplies their content. `dsh-session-persistence-jsonl` does not yet call `protect()`, and no existing composition changes behavior.
2. **Landed.** `fs/read-intent` in `dsh-fs` as a delegating waterfall returning `FsReadDenial`, `FS_READ_BARRIER_DENIED`, the dispatches in `dsh-tool-fs` (`read` and `read_image`, inside `resolveRegularReadTarget` before the stat) and `dsh-tool-str-replace-editor` (`view`, before its own stat), and `@deepseek-ai/dsh-fs-read-barrier`, which owns the exact message. The `read-barrier` fixture proves the denial through the executor in a Loader-booted composition, and the `read-barrier-denied` snapshot pins the model-visible text and the durable record; both are keyless, the snapshot replaying a committed script through `dsh-llm-replay`.
3. **Landed.** `ToolAuthority` on `ToolDefinition`, the declarations in `dsh-tool-session-query` and `dsh-tool-cordis`, `role` in `preset.yml` with the `user`-trust refusal of `validator`, the `mountPreset` audit, `ReadBarrierService.declareComposition` as the roster's one way to set a role, and the per-agent tool guard. `read-barrier/scope` lands here too, with `enforce()` and `enforcementCensus()`, because the census is made of the authority declarations this slice adds and the enforcement registrations it needs a home for; `dsh-fs-read-barrier` is the first caller of `enforce()`. The audit reads the tool registry as the preset's scope resolves it, so a tool a restriction filtered out of that scope is not audited — that scope cannot call it either, and the guard covers what the audit cannot see.
4. **Landed.** The certificate invariant: the `recordRun` precondition, the companion's rule, `VerificationCertificate.executor` with the `agent-reported` ceiling and the scorekeeper's `certificateExecutor` fact, the `read-barrier/attestation` event and its file check, and the `CertificateIsolation` documentation change. `EnvironmentRunRequest.preset` is not part of it and is withdrawn: the census already records the session's role, so `isolationProblem` refuses a claim above `none` from a session that did not hold `implementer` — the refusal belongs to the operation that certifies, not to a second field on the run request. `verification-domain`'s `agent-reported` fixture moves from `process` to `none`, which is what its evidence supported all along.
5. `deniedReadRoots` on `SandboxPolicy` and `SandboxExecutionPolicy`, the `dsh-sandbox-local` backends, the `dsh-sandbox-policy` fill from the barrier, the confined ripgrep spawn in `dsh-tool-fs-search`, and the refusals in the workflow engine and the out-of-process subagent providers. This is the slice that makes `process` claimable.
6. **Landed.** Tamper: `task.immutable` in `dsh-environments` with its registration check, the runner's baseline and per-attempt digest over check-owned paths, `verdict` on `verification/run` with the `recordRun` refusal and the companion's rule, the `tamper` reward basis in `dsh-trajectories`, and the `read-barrier-tamper` fixture and snapshot, which drive the runner over an environment whose fixture supplies the test its implementer rewrites. A run payload that omits `verdict` reads as its results decide, since only tamper cannot be derived from them, so a hand-authored log that states no verdict replays as the run its results describe.
7. The blind judge: the shipped `system`-trust judge preset, the lineage-free creation path, the `judge/session` event, and the invariant that rejects a seeded judge. The judging Consumer itself belongs to the oversight seam of the [seams note](2026-08-29-verification-improvement-oversight-seams.md).

## Risks

The barrier is trusted code in the implementer's own process below `host`. A plugin with direct `Session` or `ctx.fs` access appends counterfeit events and reads any path, exactly as `dsh-verification` already states for its durable records. The ladder is honest about this: `none` claims nothing, `process` claims only that the composed executors deny, and `host` is the only level whose evidence comes from outside the process.

`process` costs enforcement a deployment may not want. Confining every ripgrep spawn, refusing workflow workers, and refusing out-of-process subagent providers removes capability from implementer sessions that claim it; a deployment that wants those capabilities runs at `none` and keeps a certificate that says so.

A check's command line stays observable. The barrier protects the script's content and the fixtures, not the argv a process listing shows, so an environment whose check name or arguments encode the assertion leaks it. Environment authors keep the assertion in the script.

The census is only as complete as the composition it was taken from. It is appended before the first request and cross-checked against each `request/header`'s tool names, which catches a tool added later but not a plugin that reads paths without registering a tool at all.

Tamper detection is a digest comparison, so it reports that the check-owned set changed and never who changed it or how. A legitimate build step that rewrites a file inside the immutable set fails the run; environment authors declare the immutable set narrowly, and a false verdict costs one run rather than a wrong certificate.

Making `trust` enforcing for one field changes what the roster promises. A deployment that configured a `user` root expecting presets to be ordinary compositions now finds one class of declaration refused there; the refusal is listed as a `broken` reason on the same roster page that offers to delete it.
