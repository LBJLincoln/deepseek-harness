# Agent Note: 委派给外部编码智能体的部门

Status: proposed

[English](2026-09-06-program-external-implementer.md) | 中文

## Problem

一个程序为它的每个目标配备一个部门：一个在自己的 git 工作树中、经由 LLM 缝合面被逐轮驱动的 harness agent，随后完成集成、发布与签署（[程序账本笔记](2026-09-06-program-ledger.md)）。这是配备部门的唯一方式。想知道自己的 harness 在同一项交付物上是否胜过另一个编码智能体的实验室，或者已经在为这样一个智能体付费的客户区，都没有办法把那个智能体放到一个部门背后：subagent 缝合面能把外部编码智能体作为子代运行（[`ctx.subagents`](../../../../packages/subagent/subagent/README.md)），但没有任何东西把它连到账本、工作树、上限、检查或证书上。缺了这条连接，比较就不成其为比较——外部智能体只会被它自己的说法所衡量，而一个 harness 部门是被验证者在它留下的树上跑过的检查所衡量。程序已经拥有的那一半——度量——才是有意思的那一半，而它恰恰是外部智能体无法提供的那一半。

## Proposal

`ProgramSpec.implementer` 指明一个程序的每个部门如何配备：`{ kind: 'route' }`，即本服务经由 LLM 缝合面驱动的 harness agent；或者 `{ kind: 'subagent', provider, label? }`，即每次尝试运行一次已注册 subagent provider 的子代。程序拥有的其余一切仍归程序所有：账本事件、部门工作树与分支、`program/member` 标记、`budget/caps` 记录、由目标 `checks` 编写的标准、轮次上限、证书、集成合并、发布，以及两份签名。程序仍然是验证者；改变的只是由谁写代码。

### 规格字段及其改变的身份

调用方省略该字段时，`resolveProgramSpec` 会把 `{ kind: 'route' }` 具体化，因此一份冻结的规格总是陈述它的配备方式，而 `programSpecDigest` 覆盖它。于是配备方式不同的程序就是不同的程序：同一组目标由 harness 交付与由外部智能体交付会得到不同的 id、不同的会话与不同的工作树，这正是让二者之间的比较成为两次运行、而不是一次被改动过的运行的原因。`program/start` 把解析后的 `implementer` 与 `baseRevision` 并列复制一份，供只读该事件的读者使用。

### 一次委派尝试是什么

部门的开启与今天完全相同——工作树、`meta.cwd` 位于工作树的会话、preset、`program/member`、`budget/caps`、目标、标准——随后，一次尝试不再是一次用户轮次，而是一次 `ctx.subagents.start(provider, { prompt, parent: departmentAgent, signal, label? })`。第一次尝试的 prompt 是目标的 objective，之后各次是被驱动的部门本会收到的同一段检查失败文本。进程内 provider 与每一个已交付的进程外 provider 都从委派父会话的 `cwd`（即部门工作树）推导子代的工作目录，因此子代无需程序传路径就在部门分支上工作。等待该次运行的结果后，向部门会话追加并冲刷 `program/delegation { goalKey, attempt, provider, runId, stopReason, structured?, usage? }`，释放该次运行，然后部门的检查就在子代留下的树上运行，与它们在被驱动的部门留下的树上运行时完全一样。轮次上限约束委派尝试，正如它约束轮次。

### 在做出决定的操作中拒绝

当 `ctx.subagents` 未被组合、或没有该名字的 provider 时，被委派的部门拒绝启动，`PROGRAM_IMPLEMENTER_UNAVAILABLE` 会指名该 provider；当目标声称高于 `none` 的隔离级别而 provider 在本进程之外运行其子代时，以 `PROGRAM_IMPLEMENTER_ISOLATION` 拒绝。第二条规则是诚实的那条：高于 `none` 的隔离是一项关于会话自身的读屏障普查对其执行器所证明之事的主张，而本进程的任何执行器都没有中介过另一进程中的子代。进程内 provider 加入父代既有的组合，保持同一份普查与同一角色，因此可以保留部署的隔离级别。两条拒绝都发生在启动部门的那个操作中、在其工作树存在之前，并以 `program/goal { failed, reason }` 落入账本。

### 重启后的对账

重启后的进程读取被委派的部门的方式与读取任何其他部门相同：部门自身的日志是权威，其中的证书意味着 `certified`，其余一切都是 `running` 并被恢复。委派事件是该日志的一部分，它们记录的最高尝试号就是恢复后的一遍所要继续的起点，因此已经结束的尝试永不会被跑第二次。不变量伴生插件维持同一关系：一条 `program/delegation` 跟在同一 key 的 `program/member` 之后，且携带的 attempt 严格大于该会话已记录的每一个 attempt。

### 一份委派证书证明了什么

程序经由 shell 执行器、在部门工作树中、在外部智能体留下的树上运行了目标的检查，并把该次运行与证书记录在部门自己的会话里。这就是全部主张。它不证明关于这棵树如何产生的任何事：对进程外 provider 而言，我们的日志里不存在实现者的任何模型可见历史，部门的轨迹不含任何步骤，而 `usage` 只对本进程发布过、且其自身会话日志核算了 token 的子代才被记录。把被委派的部门与被驱动的部门相比较的读者，比较的是关于树的证书——那才是有意义的比较——而不是转录。

## Alternatives considered

**按目标而非按程序设置 implementer。** 已拒绝：程序级字段正是让"同一项交付物、两种配备方式"成为同一组目标上的两个程序 id 的原因。一份在各目标之间混用实现者的规格会产生一个其部门无法归属的摘要，而今天也没有任何需求要求这样做；日后可以在不改动任何事件的前提下把该字段下推到目标层。

**用 `ProgramService` 的第二个配置字段而非规格字段。** 已拒绝：配备方式决定程序运行什么，因此它属于冻结的规格并处于摘要之内。作为部署配置它会落在身份之外，同一个程序 id 在一台主机上会意味着一件事、在别处又意味着另一件事——这正是冻结规格所要防止的。

**经由 subagent 工具而非缝合面委派。** 已拒绝：该工具是一个面向模型的消费者，让 agent 自己决定是否委派。这里由程序在任何轮次之前决定，且完全不涉及部门的模型；要用上该工具就需要一个唯一职责是调用它的被驱动部门，这既花掉一条路由，又添上一段什么也没说的转录。

**让被委派的部门自报结果。** 已拒绝：`agent-reported` 的运行只能在 `isolation: 'none'` 上签发证书，且它是实现者对自身检查的自述。程序本就以 `executor: 'runner'` 自行运行检查，而这恰恰是外部智能体唯一无法伪造的东西。

**在组合了读屏障时于此处拒绝一切进程外委派。** 因重复而拒绝：各 provider 已在会启动子代的那个操作中调用 `assertOutOfProcessAllowed`，因此一个拒绝该部门角色的屏障会自行拒绝这次启动。程序自己的规则针对的是证书将要声称的隔离级别，而屏障并不决定那件事。

**把 `program/delegation` 事件放在程序会话而非部门会话上。** 已拒绝：部门会话是其自身状态的权威，而账本是重启时读取的索引。把尝试放进账本会让程序会话随工作一起膨胀，也会给对账多出一个需要对账的权威。

## Acceptance criteria

- 一个由 Loader 引导的无密钥 e2e 组合一个继承父路由的进程内 provider 于 mock 路由之上，运行一个带 `implementer: { kind: 'subagent', provider: … }` 的单目标程序：部门签发证书，其日志携带一条 attempt 为 1 的 `program/delegation` 与一条 `verification/certificate`，程序发布。
- 同一个 fixture 换成 mock 无法满足的检查时，每次尝试记录一条 `program/delegation`，直到 `maxGoalRounds`，并使程序以 `failed` 结束。
- 指名一个无人注册的 provider 的组合会以指名该 provider 的 `PROGRAM_IMPLEMENTER_UNAVAILABLE` 使部门失败；委派给进程外 provider 的 `isolation: 'process'` 或 `'host'` 目标会以 `PROGRAM_IMPLEMENTER_ISOLATION` 失败，二者都在工作树被创建之前发生。
- 一份规格的摘要在其 `implementer` 改变时改变，在调用方省略该字段（解析为 `{ kind: 'route' }`）时不变。
- 日志中已记录一次已结束的委派尝试的部门，从下一次尝试恢复，且绝不重复已记录的那一次；不变量伴生插件拒绝没有对应 key 的 `program/member` 的 `program/delegation`，以及 attempt 未推进的 `program/delegation`。
- 一个带密钥风格的 fixture 把真实的 `claude-code` provider 与程序组合起来，运行一个其检查读取子代必须创建的文件的单目标程序；除非操作者显式选择加入，否则它自跳过，因为它在主机自身的认证下驱动一个真实的外部 CLI。

## Risks

- **树是唯一的证据。** 被委派部门的证书只陈述检查发现了什么，对产生它的过程只字不提。需要转录的部署只能使用进程内 provider——其子代会话是一个普通的持久化会话——或者接受记录到工作树为止。
- **不受 harness 策略约束的外部智能体。** 进程外子代自带工具栈、自带权限、自带网络可达范围；程序的沙箱、审批策略与读屏障只覆盖部门会话，不覆盖子进程。工作树约束的是它应当触碰什么，而不是它能够触碰什么。反过来也一样棘手：那些设置决定了无人值守的子代究竟能否写入，而无权写入的子代仍会正常结束运行，因此外部智能体被静默拒绝的部门与尝试过却做不到的部门无从区分——二者都在轮次上限之后读作 `failed`，唯一的解释只有检查证据。
- **程序看不见的花费。** 程序上限折叠的是携带 `program/member` 的会话，而被委派子代的花费要么在一个未打标记的独立会话中，要么完全在本进程之外。委派事件上的 `usage` 记录本地发布的子代花了多少；没有任何东西约束外部智能体自己的账单。
- **尝试比轮次更粗。** 被驱动的部门可以在一次尝试中途被引导；被委派的部门是一个 prompt 和一个结果，因此 `n` 的轮次上限买到的是 `n` 次机会而非 `n` 条消息。委派给外部智能体的程序会想要更小的上限与更大的单次尝试范围。
- **隔离规则取决于 provider 能力。** 进程外判定读取的是 provider 所宣告的启动期能力，而每一个已交付的进程外后端正是为此把它们声明为空。若将来有后端在另一进程中运行子代却宣告了某项启动期能力，就会击穿该判定，规则届时必须迁移到缝合面上的显式标记。
