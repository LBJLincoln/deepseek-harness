# Agent Note: A bench tier whose verdict comes from cases the implementer never sees

Status: proposed

[English](2026-09-07-bench-tier-5-hidden-cases.md) | 中文

## 问题

Proving Ground 基准此前收录三十个零依赖 JavaScript 程序任务，分布在第 2 至第 4 层，每个任务由随任务目录一同交付的测试套件校验。Claude Code 产品循环在三层全部 48 个非留出单元上各用一次尝试完成认证，每个单元耗时 58 至 406 秒。若某个实现者在首次尝试中通过基准的每一个单元，这套基准便无法排序：它分不出两个实现者，显示不出某项改动是否有帮助，也无法为一个单元的难度定价。

原因出在结构上，而不在于用同样的形式写出更难的任务。实现者在动笔之前就能读到 `test/*.test.js`，因此它实际面对的任务是"让这些断言通过"，而不是"实现这份规格"。套件没有断言到的每一处行为，实现者都可以随意写错；而大到足以补上这个缺口的套件，就是把答案交出去的套件。扩充可见套件只是把一种失败换成另一种。

## 提案

新增第 5 层：其主检查是在实现者从未见过的用例上，与隐藏的参考实现做差分比对；并为该层写入十个任务。校验缝已经具备所需的一切——`AuthoredCheck` 可以带 `cases: CheckCasesRef` 与 `caseBodies: CheckCase[]`，运行器把每个用例的 `argv` 追加到检查的 `run` 之后并喂入其 `stdin`，对被比对的通道取摘要，而校验失败后下发的指令只告诉实现者有多少个用例失败、哪些通道不一致。第 5 层复用这条缝，而不是另起一条。

### 用例存放在哪里

第 5 层的 `task.json` 检查新增一个可选字段 `"cases": "reference/cases.json"`。该路径必须位于 `reference/` 之下——运行器会把这个目录从每一层工作区叠加中剥离，并复制到校验者的屏障之内，因此写在那里的文件从构造上就无法从实现者的工作区触及，而不只是靠约定。`register-environments.ts` 在注册时读取该文件，用 `caseChannelDigest(…, ['crlf'])` 对每个用例的 `stdout` 与 `stderr` 取摘要，并把 `cases: checkCasesRef(bodies)` 连同 `caseBodies: bodies` 一起交给检查。只有引用会进入会话日志，用例主体留在校验者的预留区内。

该文件是一个朴素数组，因此易读且可重新生成：

```json
[{ "id": "corner-001", "weight": 3, "argv": ["normalize"], "stdin": "…\n",
   "exitCode": 0, "stdout": "…\n", "stderr": "", "channels": ["exit", "stdout", "stderr"] }]
```

遇到格式错误的文件、重复的用例 id、非正数的权重、需要 shell 引号的 `argv` 词、`exit`、`stdout` 与 `stderr` 之外的通道、声明了 `stderr` 通道却没有期望文本，以及离开 `reference/` 的 `cases` 路径，注册器都会让启动失败。这些条件都能在文件内部自证，因此在加载时即失败。

### 一个第 5 层任务是什么

每个任务都是一个命令 `src/cli.js`，由参数与标准输入驱动，按退出码与两条输出流评判。参数词只承载模式与小整数，因为运行器会把它们原样追加到检查的 `run` 之后；一切带结构的内容都走标准输入，那里没有引号规则。命令旁边是一套十二至二十条断言、只覆盖主路径的可见套件，一份隐藏的 `reference/src/` 解答，一个 `reference/generate-cases.mjs`——它在固定语料上运行该解答以产出 `reference/cases.json`，以及一个通不过可见套件的 `src/` 桩。

语料的两半都是确定的：手写的边角用例权重为 3，由带种子的线性同余流抽出的组合权重为 1。重跑生成器会写出完全相同的字节，因此用例文件是其参考实现的构建产物，可以在规格变动后重新生成，而不必手工维护。

让这件事保持公平的规则是：每一个隐藏用例都必须能从提示词中论证出来。提示词预测不到的用例是陷阱而不是测量，补救办法是把该边角写明或删掉该用例。提示词后缀从另一侧陈述了同一件事：带隐藏用例的任务会告诉实现者，校验者会在留存输入上运行程序并逐字节比对，应当实现的是写下来的规格而不是可见套件。没有隐藏用例的任务不带这句话，因为对它们而言这句话是假的。

### 准入

`admit.mjs` 增加用例文件必须满足的两个条件。每个用例都必须在 `reference/src/` 上复现，这证明该文件描述的正是它声称描述的那份参考实现。至少有一个用例必须在前置状态上不一致，这证明该文件测量到了可见套件尚未触及的东西：桩程序能全数满足的用例集，是一个会为无人写过的程序发证的用例集。准入会为每个通过的任务打印用例数。

### 难度闸门

每个任务都在一份删去 `reference/` 的目录副本中，以非交互方式对产品循环运行一次，接受编辑并放行 `node`，限时八分钟；随后把循环留下的成果对照可见套件与隐藏用例评分。这道闸门不是证书，而是该层究竟能否分出高下的证据。共跑了两轮：第一轮覆盖全部十个任务，第二轮覆盖那六个通过了全部隐藏用例的任务——在它们的语料补入这些任务所依赖的规格要点的边角用例之后。下文中每个任务的一行都对应其交付的语料，逐任务的细节见 [SUMMARY.md](../../../../examples/headless-agent/tests/fixtures/proving-ground-bench/SUMMARY.md)。

十个任务中有四个至少漏掉一个隐藏用例，七个通过了可见套件。只有 `lex-states` 在可见套件通过的同时漏掉了隐藏用例，160 个中命中 158 个，这正是该层要产生的形态；`glob-brace`、`conf-canon` 与 `sheet-eval` 都在八分钟预算耗尽时尚未留下可运行的成果，这是一种更粗钝的难度信号。重跑的六个任务——`uri-resolve`、`build-schedule`、`ranked-choice`、`rate-limit-sim`、`diff3-merge` 与 `wrap-justify`——两轮都命中了全部隐藏用例，耗时 201 至 417 秒，因此新增的边角对这个实现者没有产生影响。面对这个循环，该层目前靠的是任务承载的规格体量，而不是其边角的锋利程度。

## Alternatives considered

**扩充可见套件。** 对"48 比 48"最直白的解读是任务太容易，而最省事的答案是加断言。它按自身的标准就站不住：完整到足以钉住行为的套件，就是把行为陈述出来的套件，而实现者在动笔之前就会读它。测量的仍然是"你能不能满足给你看的东西"。

**留存第二套可见套件，事后再跑。** 由校验者拷入的 `test/hidden/*.test.js` 不需要任何新机制。它泄露的比测量的多：失败报告会带上断言文本，因此一次重试就把留存的规格一条一条交给实现者，该层在一次尝试之后便退化成可见套件层。带用例的检查所下发的指令只报告计数与通道名，这正是它经得起重试的原因。

**在运行时对照参考实现，而不是交付摘要。** 在新抽取的输入上让 `reference/src/` 与候选并排运行，可以不要用例文件。它会在一次计分运行中把参考实现放进运行器进程，放弃了让用例文件可审计的摘要绑定，还让一个单元的判定取决于当天抽到了什么，于是同一个计划的两次运行不再可比。冻结的用例让计划保持可复现。

**用基于性质的检查器取代用例。** 在生成输入上检查不变量，能抓住固定语料漏掉的一类错误。它同样需要为每条性质提供一个判定源，对这些任务而言那又是参考实现；而且它会报告反例，那正是留存套件方案已经栽过的泄露。

**把用例主体放进 `task.json`。** 每个任务一个文件更易读。但它会落在实现者的工作区里，于是整层都变成可见的；`reference/` 是运行器本来就会移除的唯一目录。

## Acceptance criteria

- 注册表与任务文件在四十个任务上相等，且每个第 5 层注册恰好带一个 `cases.count` 不小于 80 的带用例检查，由 `proving-ground-bench.e2e.ts` 经 `registry-driver.ts` 断言。
- `admit.mjs` 在全部四十个任务上以 0 退出：每个前置状态都通不过自身套件，每份参考实现都能通过，每个隐藏用例都能在参考实现上复现，且至少有一个在前置状态上不一致。
- 每个生成器重跑时都逐字节写出相同的用例文件，因此用例文件可从其参考实现复现。
- 在单次产品循环尝试中，十个任务里至少有四个至少漏掉一个隐藏用例，同时至少有六个通过可见套件。

## Risks

**这道闸门测的是某一天的某一个实现者。** 该层能分出当前形态的产品循环；一个更强的循环，或一份更长的预算，可能再次认证每一个单元，把基准打回原处。届时的答案是在规格里增加边角，而不是拉长套件，而用例文件正是为此而可重新生成的。

**提示词预测不到的用例就是陷阱。** 语料足够大，未经陈述的边角可以藏在其中，而实现者只看得到一个计数，因此陷阱的诊断代价很高。准入无法捕获这一点：它证明的是参考实现与用例一致，而不是提示词与用例一致。只有把提示词对着用例清单读一遍才能捕获，而两者中任何一个变动时，这遍阅读都得重做。

**参考实现是规格唯一的可执行副本。** 隐藏用例之所以正确，是因为参考实现正确。参考实现中的一处缺陷会变成一条没有任何可见测试与之矛盾的隐藏要求，而实现者无从申辩。

**八分钟的限制混淆了两种失败。** 预算耗尽的单元与做完了但做错的单元，都记为隐藏用例失败，而这两者对任务的含义并不相同。记录下来的结果保留了退出状态，因此两者可以区分，但验收规则并不区分它们。

**四份参考实现未达到 250 行的下限**——这是编写规格为第 5 层解答设定的：`ranked-choice` 170 行，`diff3-merge` 187 行，`wrap-justify` 191 行，`rate-limit-sim` 230 行。该层交易的是它们的规格面，往代码里填充也不会增加规格面，但这个缺口意味着这四个任务的纵深不及另外六个。
