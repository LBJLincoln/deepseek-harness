# Agent Note: Content-addressed identity and the composition manifest event

Status: proposed

English | [中文](2026-09-05-composition-manifest.zh.md)

## Problem

Every identity in the harness names a slot rather than the bytes in it. A `ComponentId` is "derived from its kind and the owning seam's stable name, never from mount order" ([`dsh-components`](../../../../packages/components/components/README.md)), a skill is addressed by its kebab-case name, a prompt section and a tool by their registered names, a preset by its directory name, and a plugin by its package name. Editing a skill body in place leaves all of those addresses unchanged, so a leaderboard cannot separate the generation before the edit from the generation after it, a rollback has no earlier address to return to, and a decontamination check has nothing to key on — the failure the [four-goal-workflows note](2026-09-05-four-goal-workflows.md) records under its rejected "single mutable knowledge store" alternative and forbids in principle P5.

Nothing durable records which components a session had in play. The `request/header` event carries each epoch's assembled system prompt text and tool schemas, which is enough to replay a request and not enough to name what produced it: it carries no component identity, provenance, lineage, or registry layer; a skill body loaded through the `skill` tool reaches the transcript as a tool result and never the header; and a dynamic package mounted through [`tool-cordis`](../../../../packages/extensions/tool-cordis/README.md) that registers no tool is invisible in it. The component registry itself is composition-time state that dies with the process, as [the component-registry seam note](2026-09-01-component-registry-seam.md) states outright.

Four consumers are blocked on that gap. [`dsh-scorekeeper`](../../../../packages/improvement/scorekeeper/README.md) ships no `composition_hash`, `component_ids`, or `skills_used` field because no event supplies one. W4 stage 1's invariant — a skill result whose digest is absent from the manifest fails — has no manifest to check against. The trajectory exporter can withhold a held-out environment but cannot tell a curated composition from one an agent mutated mid-session, so a synthesized skill body can reach a training set unannounced. And W4 stage 9's knowledge ledger has no address to mirror its entries against, which is what makes "a ledger entry with no matching manifest occurrence never counts as having been in play" enforceable rather than aspirational.

## Proposal

**One digest function, one address form.** [`dsh-components`](../../../../packages/components/components/README.md) gains `ComponentDigest` (a `Branded<'ComponentDigest'>` from `dsh-brand`) and two pure functions: `componentDigest(kind, canonical)` returns the lowercase SHA-256 hex of `` `${kind}\n${JSON.stringify(canonical)}` ``, and `componentAddress(id, digest)` returns `` `${id}@${digest}` ``. The kind is inside the hashed bytes so two kinds whose canonical values coincide never share an address. The digest is the full 64 hex characters everywhere it is stored or compared, matching `environmentContentHashes` in [`dsh-environments`](../../../../packages/improvement/environments/README.md); truncating it for a card or a table is a presentation choice that never enters a log or the ledger. `ComponentDescriptor` gains a required `digest: ComponentDigest` and a required `digestBasis: 'content' | 'registration'`. As landed, `canonical` is typed `ComponentCanonical` — a JSON value — so a producer cannot hand the hash a value `JSON.stringify` would drop, and `componentAddress` returns a plain string: an address is minted and compared, never received across a boundary that a brand would guard.

**Each producer owns its canonical value.** The registry ships no per-kind canonicalization for the same reason it ships no kind: each producer declares its `ComponentKindMap` member by declaration merging and exports the pure function that canonicalizes it, so a kind added later needs no change in the registry or in the manifest writer. The table below fixes the canonical value of every kind this note introduces. As landed, the exported function is the kind's digest rather than its bare canonical value — `agentProviderDigest(provider)`, and `skillDigest(definition)` as the skill row already names — so a consumer recomputing an address calls the producer instead of rebuilding the canonical value from the table.

**The registry becomes layered.** `ComponentRegistry` was one flat `Map`, so it could not answer "what does this agent see". It uses `ScopedLayers` from `dsh-scope`, exactly as [`ctx.tools`](../../../../packages/core/tools/README.md) and [`ctx.skills`](../../../../packages/skill/skill/README.md) already do: `register()` files into the calling context's scope, and `list({ kind, scope })` merges the global layer with the viewing scope's chain, the nearest layer's entry winning a duplicate id. A descriptor read back through a scope carries `layer: 'global' | 'agent'` — `global` when the winning registration sits in the global layer, `agent` when it sits in a layer of that agent's scope chain. A deeper chain still reads as `agent`, because a subagent writes its own manifest into its own session. Ids are unique per layer, so a duplicate in one layer still throws `COMPONENT_DUPLICATE_ID` while the same id in a different layer shadows.

The derived `layer` rides `ComponentView`, a distinct read type extending `ComponentDescriptor`, rather than an optional descriptor field: a producer registers a descriptor and cannot assert its own layer, and a reader always has one. `get(id, { scope })` takes the same viewing scope as `list({ kind, scope })`, the `SkillViewOptions` pattern `dsh-skill` already uses for its two reads. The registry publishes no change notification — the rejected `components/change` alternative below is why — so the `ScopedLayers` change callback is an explained no-op.

**The manifest writer reads one registry.** `@deepseek-ai/dsh-components-manifest` at `packages/components/components-manifest/` injects `agents` and `components` and nothing else. On `agent/pre-step` it calls `next()` first, recomputes `ctx.components.list({ scope: agent })` for the calling agent, compares the resulting `compositionSha256` with the last `composition/manifest` event in that session's log, and appends a new event through `agent.session.append()` only when the two differ — the shape [`dsh-budget-policy`](../../../../packages/guard/budget-policy/README.md) already uses to fold and append before a step opens. Recomputing rather than tracking incrementally is what keeps it correct across HMR disposal, a preset mounted after creation, and scope shadowing: the writer holds no subscription state that any of those three orderings could invalidate.

**Every other seam reaches the manifest through an adapter.** The one-adapter-per-seam rule [the component-registry note](2026-09-01-component-registry-seam.md) established is what keeps the writer from reading registries it does not own, and each adapter follows its seam's own change notification: `dsh-components-tools` follows `tools/change`, `dsh-components-prompt` follows `system-prompt/change`, `dsh-components-skills` follows `tools/result` for the `skill` tool, `dsh-components-presets` follows the `agent-preset/selected` Cordis event, and the shipped `dsh-components-subagents` already follows `subagent/provider-added` and `subagent/provider-removed`. One seam emits nothing today: the dynamic Cordis runner behind `tool-cordis` reports no change when a package is defined, run, stopped, or removed, so `dsh-cordis-host-runner` gains an unfiltered `cordis/dynamic-changed(agent, pluginId)` Cordis event — `@mode emit`, not scope-filtered, so no scope-scan metadata applies — and `dsh-components-packages` follows it.

**A skill is in play once its body is loaded, not once it is listed.** `ctx.skills.list()` returns summaries without bodies, so registering every discoverable skill would need a body load per catalog entry per step and would still address a summary rather than the knowledge. `dsh-skill` therefore exports `skillDigest(definition)` over the loaded definition, the `skill` tool's canonical output value gains a `digest` field (absent from `renderSkillContent`, so the model-facing text is unchanged, and durable in `tool/result`), and `SkillInvocationSource` gains the same field so the user-explicit `/name` injection records it too. `dsh-components-skills` registers a `skill` component from either durable record through `exec.agent.ctx`, never by re-parsing the rendered `<skill_content>` block. Skills that were reachable but never loaded stay out of the manifest; the catalog they came from is already durable as the `skill-catalog` message source.

**What slices 2 and 3 landed differently.** Five deviations, each the smallest the code admitted. The `tool` canonical value carries no output schema: `ToolSchema` — what `ctx.tools.schemas(scope)` projects and what the model receives — is name, description, and parameter schema, and the canonical output declaration is never model-visible, so addressing it would need the registry to project it beside the wire schema. The `prompt-section` adapter needs a registration read the prompt registry did not expose, so `SystemPrompt` gains `sections(scope?)`, the merged registrations in assembly order with each `text` as it stands. The `preset` adapter needs the trust, the composition path, and the resolved rows of a mount, none of which `PresetMount` carried, so `dsh-agent-presets` records `trust`, `path`, and `tree` on it; a row whose `config` does not survive the lossless-JSON boundary contributes `null`, exactly as an absent one does. That adapter also reconciles on `agent/created` beside `agent-preset/selected`, because a session that starts on the deployment default commits no selection event and the roster publishes no mount notification — `livePresetMounts()` reports a torn-down mount by pruning it, so reconciling against that reading is what removal is. And a `user`-trust preset is recorded with `provenance: 'synthesized'`: the roster records the root a preset was discovered under, never its author, and a locally authored composition carries the same trust as shell access.

**What slices 4 and 5 landed differently.** Seven deviations. The `skill` tool's `digest` is not durable in `tool/result`: the tool registry keeps a canonical value out of durable events by design, so the digest reaches `dsh-components-skills` through the settled `tools/result` and the durable record of a loaded generation is the manifest entry that load causes, plus `SkillInvocationSource.digest` on the user-explicit path. `dsh-components-skills` therefore observes two planes — `tools/result` for the model-driven load and `session/event` for the user-explicit injection — and it also follows `skills/change`, replaying each in-play skill's own lookup so a body edited in place is re-registered at its new address and a skill the registry lost leaves the inventory; the alternative, registering every listed skill, would address a summary rather than the knowledge. The `plugin` canonical value is `[specifier, config]` over the mounted Loader row, `registration` basis: `version` needs a package-manifest resolution the entry does not carry and `patchLayerSha256` needs the app-boot profile, which a components adapter must not read, and this note's own Risks already record that a name-and-version digest cannot move on a source edit. `dsh-components-packages` mirrors only a row with a live fiber, so a disabled or failed entry is out of the inventory, and it reconciles on `internal/status` and `loader/partial-dispose` because the Loader publishes no settled-tree notification. `cordis/dynamic-changed` carries `(agent, pluginId)` and is emitted through the agent registry, so a session whose agent is already gone notifies nobody; the dynamic descriptor is filed through `agent.ctx.get('components')`, and an agent whose service isolate cannot reach the registry is reported rather than filed elsewhere. The dynamic canonical value reads `inspectPackage`, not `inspectPlugin`, because only the package inspection carries source. The two fixtures are `examples/headless-agent/tests/fixtures/composition-manifest-mutation/` — one session that edits the body between turns, which proves the old address leaves the registry as well as that the next manifest differs — and `examples/headless-agent/tests/fixtures/composition-quarantine/`, whose assertions key on the entries (`kind: 'dynamic-package'`, `provenance: 'synthesized'`, `layer: 'agent'`) rather than on payload summary fields.

**The manifest payload landed narrower than this note states.** It carries `version`, `components`, and `compositionSha256` alone. `reason` names values only slices 4 and 5 can produce, `dynamicPackagesMounted` and `synthesized` summarize kinds slice 5 introduces, and `presetId` would make the writer read a registry it does not own — the writer injects `agents` and `components` and nothing else, and a consumer that needs the preset in play reads the `preset` entry in `components`. Each field arrives with the slice that produces its input.

## What each kind hashes

| Kind | Canonical value | Basis | Producer |
|---|---|---|---|
| `skill` | `[name, description, whenToUse ?? null, invocation.modelInvocable, invocation.userInvocable, metadata ?? null, content]` from the loaded `SkillDefinition` | content | `dsh-components-skills`, over `skillDigest()` in `dsh-skill` |
| `prompt-section` | `[name, order, complete === true, text]` when `PromptSection.text` is a string; `[name, order, complete === true, null]` when it is a provider evaluated per assembly | content, else registration | `dsh-components-prompt` |
| `tool` | the model-facing `ToolSchema` as `ctx.tools.schemas(agent)` projects it: name, description, parameter schema, output schema, in the registry's own field order | content | `dsh-components-tools` |
| `preset` | `[id, trust, rows]`, where `rows` is the preset's composition after `include` resolution as `[id, name, config, disabled]` per row, with every `name` that resolves to a path rewritten relative to the preset directory | content | `dsh-components-presets` |
| `plugin` | `[packageName, version, patchLayerSha256]`, the version from the resolved package manifest and `patchLayerSha256` the SHA-256 over the ordered `cordis.patch.yml` rows of the bundles in force | content | `dsh-components-packages`, over `ctx.loader.entries()` |
| `dynamic-package` | `[pluginId, packageId, hostSource, clientSource]` from `ctx.dynamicCordisRunner.inspectPlugin(agent, pluginId)` | content | `dsh-components-packages` |
| `agent-provider` | `[provider]` | registration | `dsh-components-subagents` |

A digest never covers the viewing scope, the working directory, a wall-clock time, an absolute path (`SkillDefinition.path`, `SkillResourceBase`'s directory, `AgentPreset.path`), a discovery `source` or `rank`, a provider name, or any value a registry computes per assembly. Two hosts that discovered the same skill under different roots, and the same body re-registered through a different provider, therefore address identically; one byte changed in a skill body, a tool parameter description, a static prompt section, or a preset row moves the digest. A `registration`-basis digest addresses the registration and not the bytes the model saw, which is the honest statement for a section whose text is a function of the assembly; the rendered bytes stay where they already are, in `request/header`.

## The `composition/manifest` event

`dsh-components-manifest` declaration-merges one member into `SessionEventMap` in `@deepseek-ai/dsh-session/types`. It is **log-only** and carries no `@mode` tag: a session log event has no dispatch mode, it rides the single `session/event` emit, and `gen-persistence-catalog` rejects the tag outright — the repo's `@mode` and payload-`@param` rules govern the Cordis bus event this note adds, not this one. It is **required-on-read**, without the envelope's `ignorable: true` marker, because every consumer below keys a refusal on it: a build that cannot interpret the type would otherwise fold a scoreboard row and write an export line for a session it cannot prove was unquarantined ([the version mechanism](../../implemented/architecture/2026-08-10-session-log-version-mechanism.md)). Its payload fields, each carrying its own JSDoc so [the generated catalog](../../../../docs/persistence-catalog.md) documents them:

- `kind: 'composition/manifest'` and `version: 1`, the self-declared payload version the environment stamp also carries.
- `reason`: why this manifest was written — `'session-start'`, `'preset-mounted'`, `'skill-loaded'`, `'tools-changed'`, `'prompt-changed'`, or `'package-mounted'`, decided by which kinds changed since the previous manifest.
- `presetId`: the preset the agent runs, resolved through `resolveSessionPreset()`; absent when the deployment composes none.
- `components`: one entry per component in play, ordered by `id`, each `{ id, digest, kind, provenance, lineage?, layer, digestBasis }`.
- `compositionSha256`: SHA-256 over the ordered `id@digest` addresses joined by newlines — the deduplication key and the `composition_hash` the scoreboard row wants.
- `dynamicPackagesMounted`: whether any entry has kind `dynamic-package`.
- `synthesized`: the ids of every entry whose `provenance` is `synthesized`, in the same order.

The four-goal note's sketch lists a `seq` field; the envelope already carries `seq`, so the payload does not repeat it. The first manifest is appended before the session's first `request/header`, because `agent/pre-step` runs before the step assembles its request and the preset has already settled by then — a preset chosen after creation commits `agent-preset/selected` while the session is still blank. Every later change to the set in play produces the next differing manifest at the next step, which is the first step whose model request that change can reach.

## Quarantine

A session is quarantined when its latest manifest reports `dynamicPackagesMounted` or a non-empty `synthesized`, and equally when its log carries no manifest at all: a session that cannot prove what was in play is exactly as unusable as one that mounted code an agent wrote. `SessionFacts.identity` in [`dsh-scorekeeper`](../../../../packages/improvement/scorekeeper/README.md) gains a `composition` group folded from the latest manifest — `compositionSha256`, the entry count, `presetId`, `dynamicPackagesMounted`, and `synthesized` — plus `skillsUsed`, the `id@digest` addresses of every `skill` entry any manifest of the session named. Its `./invariant` companion gains one relation beside the three it checks today: for every `tool/result` of the `skill` tool carrying a digest, some `composition/manifest` at or before that event's `seq` names a `skill` component with that digest, and a result whose digest appears in no manifest is reported as a record disagreeing with its own log. [`dsh-trajectories`](../../../../packages/improvement/trajectories/README.md) gains `includeQuarantined?: boolean` on `TrajectoryExportRequest` and a `quarantined` count on `TrajectoryExportReport`, symmetric with `includeHeldOut` and `heldOut`: absent, the export refuses every quarantined session and accounts for it in the count rather than dropping it silently. The complementary quarantine — a Harness Engineer proposal that touches an evaluator-owned path — belongs to W1 stage 7 and stays there.

## The knowledge ledger

`@deepseek-ai/dsh-archive` at `packages/improvement/archive/` (`ctx.archive`) holds the cross-session records over [`ctx.storage.domain`](../../../../packages/storage/storage-domain/README.md), through a `defineDomain` spec whose record schemas are zod, routed to whichever backend the deployment configures. Two tables: `variants`, keyed by the `HarnessVariant` id (base commit plus patch-set hash) with the fields the four-goal note fixes — `parent`, `operator`, `patch`, `scores`, `evaluations[]`, `children[]`, `status`, `proposer`; and `generations`, keyed by `id@digest` with `componentId`, `digest`, `kind`, `provenance`, `lineage` (the parent's address, absent for a root), `evidenceSessions[]`, `results`, and `status`. A mutation mints a new row rather than rewriting one, so a generation's bytes and its address never diverge.

`status` is `alive`, `dominated`, `promoted`, or `deprecated`. `alive` is evaluated or newly minted and still eligible for parent sampling; `dominated` lost to another generation of its lineage on every measured cell and stays sampleable and auditable, never deleted, which is the archive semantics the four-goal note's rejected best-only alternative exists to preserve; `promoted` carries the `PromotionDecision` that moved it into curated source; `deprecated` is what the department scoreboard writes once a paired present-versus-absent delta has stayed at or below zero over the configured number of runs. Lineage is stored on both ends — `lineage` on the child for the auditor walking up, `children[]` on the parent for the sampler's `1/(1+children)` weight — and a status change appends a revision rather than removing a row.

The ledger's `./invariant` companion owns the manifest-versus-ledger relation, an assertion over mutable data against the authoritative event stream the [package invariant rules](../../../../packages/AGENTS.md) require: for every generation row, each session named in `evidenceSessions` must carry a `composition/manifest` whose `components` hold that exact `id@digest`. A row that names an evidence session with no matching occurrence is reported and never counts as having been in play, so a promotion cannot rest on a session the component was not actually composed into.

## Alternatives considered

**Derive the manifest from `request/header`.** The header already records the assembled system prompt and every tool schema of each epoch, so a fold over it would need no new event. It is rejected because the header carries rendered text and no identity: provenance, lineage, and layer are absent, a loaded skill body never reaches it, and a dynamic package that registers no tool leaves it unchanged — precisely the three cases the quarantine has to catch.

**Keep the registry composition-time only, with no session event.** `ctx.components` is already the inventory, so a consumer could read it live. It is rejected because every consumer here reads persisted logs after the fact — the scorekeeper folds them, the exporter writes from them, the ledger invariant checks against them — and composition-time truth dies with the process.

**One manifest per session, written at creation.** A single record would be smaller and simpler to fold. It is rejected because a skill load, a preset switch, and a dynamic mount all change the set mid-session, and a start-of-session record would report a clean composition for exactly the sessions the quarantine exists to flag.

**Hash each component's rendered contribution.** Hashing what the model actually received would tie the digest to the bytes in the transcript. It is rejected because rendering depends on the working directory, the wall clock, and the viewing scope, so two identical compositions on two hosts would address differently and decontamination would key on noise; `request/header` already owns the rendered bytes, and the manifest owns identity.

**Put the per-kind canonicalization in the manifest writer.** One switch over kinds inside the writer would avoid an adapter per seam. It is rejected because the writer would then have to know every kind, which is the coupling `ComponentKindMap`'s declaration merging removes, and a kind added downstream could not be digested at all.

**A monotonic version counter per component instead of a content address.** A `skill@3` label is shorter and human-readable. It is rejected for the reason the four-goal note's "single mutable knowledge store" alternative was: a counter is authored rather than derived, so two hosts that refine the same body disagree on the number, a body restored from an ancestor gets a new number instead of its old address, and no consumer can verify the label against the bytes.

**A `components/change` event with an incremental writer.** Mirroring `tools/change` would let the writer maintain the manifest between steps instead of recomputing it. It is rejected because recomputation is one registry read and one hash per step and cannot be wrong, while an incremental writer would have to stay correct across HMR disposal, preset remounts, and scope shadowing; no consumer in this note needs a change notification, so the event is not added until one does.

**The ledger as session events rather than storage.** Recording generations in the log would keep everything on one plane. It is rejected because a ledger spans sessions and outlives every one of them, and because the manifest-versus-ledger invariant needs two planes to be a real check: an entry that is itself a session event could not be contradicted by the session events it cites.

## Acceptance criteria

- A Loader-booted composition at `examples/headless-agent/tests/fixtures/composition-manifest/` appends one `composition/manifest` before the session's first `request/header`; the event names the preset id, carries one entry per component in play with a `digest`, `provenance`, `layer`, and `digestBasis`, and its `compositionSha256` equals a recomputation from the ordered `id@digest` addresses in the persisted log.
- In the same fixture, the agent calls the `skill` tool once; a second manifest follows with `reason: 'skill-loaded'`, one added `skill` entry whose digest equals `skillDigest()` over that body, and a different `compositionSha256`. A step that changes nothing appends no third event.
- Two runs of that fixture under different temporary workspace roots and different `DSH_HOME` values produce byte-identical `compositionSha256` values, proving absolute paths, discovery roots, and timestamps are outside every digest.
- `examples/headless-agent/tests/fixtures/composition-manifest-mutation/` runs the same composition twice with one byte of the skill body changed between the runs; exactly one entry's digest differs, `compositionSha256` differs, and every other entry is unchanged.
- `examples/headless-agent/tests/fixtures/composition-manifest-quarantine/` composes `tool-cordis`, defines and runs a dynamic package, and proves the next manifest reports `dynamicPackagesMounted: true` with the package's id in `synthesized`; the trajectory export then withholds that session and counts it as `quarantined`, and the same export with `includeQuarantined` writes it.
- A keyless unit test over a synthetic log proves the scorekeeper invariant reports a `skill` tool result whose digest appears in no preceding manifest, and accepts the same result once a manifest names it; a second proves a session with no manifest at all folds to a quarantined record rather than a clean one.
- A keyless unit test in `packages/improvement/archive/tests/` proves the ledger invariant reports a generation row whose evidence session carries no manifest occurrence of its `id@digest`, and accepts the row once one exists.
- The persisted-log snapshot suite `examples/headless-agent` owns records the manifest events for the scenario that composes the manifest writer; the event is log-only and changes no model-visible text, so the required coverage is the persisted log rather than a transcript re-record ([testing policy](../../../../docs/testing.md)).

## Rollout

1. **Landed.** `dsh-components`: the `ComponentDigest` brand, `componentDigest()` and `componentAddress()`, the required `digest` and `digestBasis` on `ComponentDescriptor`, and the `ScopedLayers` layering with `list({ kind, scope })` and the derived `layer`. Updates `dsh-components-subagents` (the `agent-provider` canonical value `[provider]`, basis `registration`) and `dsh-command-components` (the invoking agent becomes the viewing scope; its rendered line still names no digest or layer, because no runnable example composes `/components` and a rendering change owes a keyless snapshot), [`docs/subsystems/components.md`](../../../../docs/subsystems/components.md), and the three package READMEs.
2. **Landed.** The composition-time adapters and their canonical values: `dsh-components-tools`, `dsh-components-prompt`, and `dsh-components-presets` at `packages/components/`, each following its seam's existing change event. Adds `SystemPrompt.sections(scope?)` and the `trust`, `path`, and `tree` fields on `PresetMount`.
3. **Landed.** `dsh-components-manifest`: the `composition/manifest` declaration, the `agent/pre-step` writer with `compositionSha256` deduplication, the regenerated `known-event-types.ts` and persistence catalog, the invariant companion over consecutive manifests and their addresses, and the `composition-manifest` fixture.
4. **Landed.** Skill generations: `skillDigest()` in `dsh-skill`, the `digest` field on the `skill` tool's canonical value and on `SkillInvocationSource`, `dsh-components-skills`, and the `composition-manifest-mutation` fixture.
5. **Landed.** Dynamic packages: `cordis/dynamic-changed` on `dsh-cordis-host-runner`, `dsh-components-packages` over `ctx.loader.entries()` and the dynamic runner, and the `composition-quarantine` fixture.
6. Quarantine consumers: the `composition` group and `skillsUsed` on `SessionFacts`, the scorekeeper invariant relation, and `includeQuarantined` with the `quarantined` count in `dsh-trajectories`.
7. `dsh-archive`: the domain spec, the `variants` and `generations` tables, the four statuses and their transitions, the two-ended lineage edges, and the manifest-versus-ledger invariant.

## Risks

A `registration`-basis digest cannot detect a change in what a provider-evaluated prompt section produced, so two runs whose dynamic sections differed share an address. `request/header` carries those bytes and a comparison that needs them must read it; a leaderboard keyed on the manifest alone will pool the two.

A `plugin` digest keys on package name and version, and every workspace package here is `0.0.1`, so a source edit does not move it. `HarnessVariant`'s base commit plus patch-set hash is what addresses harness source, and a comparison that keys on plugin digests alone will pool generations of the same package.

The manifest names components, not their transitive effects. An MCP server whose remote tool descriptions change without a re-registration, or a skill whose body references a file that changed, keeps its digest; only what the canonical value covers is addressed.

Required-on-read means a build that does not know `composition/manifest` refuses a log containing it. That is the intended trade — the alternative is a build silently treating a quarantined session as clean — and it is affordable only under the pre-release stance in the root [AGENTS.md](../../../../AGENTS.md).

A composition that churns its visible tool set every step writes one manifest per step. Deduplication by `compositionSha256` keeps a stable composition to exactly one event, and a churning one is paying for a real change in what the model can call, but a scoped restriction toggled per step would inflate a log with events no consumer distinguishes.
