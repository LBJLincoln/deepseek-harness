# Agent Note: Claude Code 路由上的原生工具调用

Status: proposed

[English](2026-09-07-claude-code-route-native-tools.md) | 中文

## Problem

[Claude Code 路由](2026-09-06-llm-claude-code.md)把 harness 工具以 prompt 文本的形式提供给安装，并以结构化输出索取答案——`{ content, toolCalls: [{ name, arguments }] }`，其中 `arguments` 是 JSON 字符串——轮次上限为两条助手消息。

受过原生工具调用训练的模型不会遵守该协议。当工具以散文形式提供时，它用一个点名其中之一的原生 `tool_use` 块作答；产品回以 `No such tool available: bash`，模型再次尝试同一次调用，第二次尝试耗尽轮次上限。SDK 随后在发布结果**之后**抛出 `Reached maximum number of turns (2)`，于是适配器的 catch 把该抛出归类为 `TRANSPORT`，结果自身的 `error_max_turns` 从未被读取。

实测数据：在同一批 prompt 材料上的三次探针查询产出零个可用答案，每次都终结于那个两次调用的循环；一个真实的 bench cell 以同样方式损失了 12 次查询中的 11 次。加入“结构化输出工具是唯一可用工具”的显式指令确实能让查询成功，但从不发生在第一条助手消息上——每次这样的运行仍要先花一次 API 调用在被拒绝的原生调用上——而所试的最小模型在一次查询中两度破坏协议：先是在 schema 要求字符串处发送对象形式的 `arguments`，随后发送根本无法解析为 JSON 的字节，查询失败。措辞无法恢复一个模型早已被训练越过的协议。

## Proposal

把 harness 工具作为真正的工具提供给产品，并从产品本就发布的回复中读取答案。

每次请求的 `GenerateOptions.tools` 成为一个名为 `dsh` 的进程内 MCP 服务器的工具，为该请求构建、作为查询唯一的 MCP 服务器挂载；查询只允许它所提供的名字，限定为 `mcp__dsh__<tool>`，产品自身的工具保持关闭。不提供工具的请求不构建服务器。结构化输出选项与 prompt 中的工具区一并去掉：prompt 只剩阅读指引加会话，其中没有任何内容描述工具。

该服务器不执行任何东西。它的调用处理器回以一句固定文本，因为产品会在查询结束前运行它刚请求的那次调用；真正的调用随后由 harness 在 agent loop 中执行，与其他每一个 provider 完全一致。正是这一点让本路由仍是 LLM 缝上的 Service Provider，而不是一个嵌套的 agent loop——这也是[路由自身的记录](2026-09-06-llm-claude-code.md)反对蹦床式做法的理由，它依然成立：此处没有任何东西给了产品一个 loop、一个会话，或第二次模型请求。

### 原样提供 schema

工具经 MCP 低层请求处理器（`ListToolsRequestSchema`、`CallToolRequestSchema`）提供，而不是走取 Zod 结构的高层注册。harness 工具定义携带 JSON Schema，而 `request/header` 记录的正是这些 schema，因此原样提供才能让“模型可见”等于“已记录”。Zod 往返会把一份转换后的 schema 摆在模型面前，而日志描述的是另一份。

### 一次查询一个轮次

`maxTurns` 变为一。发起工具调用的回复会触及该上限——产品作答、对着固定处理器运行所提供的调用，就再没有剩余轮次——SDK 报告携带该回复的 `error_max_turns`。对本路由而言，这一终止是发起工具调用的答案的正常结束，因此当查询发布过 `tool_use` 块时适配器交付答案，只有在没有发布时才给出 `MAX_TURNS`。纯文本回复以 `success` 结束查询。

### 读取答案

答案就是查询的 `assistant` 消息按顺序读取：text 块合并成 content，`tool_use` 块成为剥去 `mcp__dsh__` 限定的工具调用（直接使用 harness 原名同样接受），thinking 块被忽略。一条 API 消息可能拆成数条助手消息、每块一条，因此两者都跨整次查询读取。参数是 API 已解析输入的再序列化，这也是本缝每个适配器组装参数时的做法。请求未提供的名字为 `MALFORMED_RESPONSE`；完全没有助手消息的查询仍是 `EMPTY_RESPONSE`。

### 旧分类判错的两种失败

结果发布之后的抛出，是同一次查询的第二份交代，而结果是更好的那一份：适配器保留结果、丢弃抛出，只在没有结果、或 harness 自己停止了该查询时才对抛出作分类——后者的超时与取消 code 优先于产品已发布的任何内容。被产品标记 `is_error` 的 `success` 结果在 `result` 中携带产品自身请求的 API 失败（例如一次连接失败）；该文本并入被分类的细节，剩余情形为 `TRANSPORT`——默认重试策略会重试它——而不再是原先终局性的 `PRODUCT_ERROR`。

## Alternatives considered

**保留 prompt 协议，把指令写得更强。** 探针已经量过：“你恰好只有一个原生工具”的显式指令确实能产出结构化答案，但只发生在模型先用一条助手消息发起被产品拒绝的原生调用之后。那是每一步浪费一次 API 调用、永久更高的轮次上限，而所试的最小模型仍在一次查询中两度破坏该协议。原生工具调用正是这些模型受训所用的接口；顺着它比对抗它更便宜。

**提高 `maxTurns`，给拒绝循环留出恢复空间。** 已在四轮下试过：模型重复原生调用，查询依旧没有答案收场。更多轮次买到的是更多被拒调用，而不是不同的回复，而且它们还扩大了产品可以在轮次之间行动的窗口——这正是本缝必须禁止的。

**把每份 harness schema 转成 Zod，使用 SDK 的 `createSdkMcpServer` 工具辅助函数。** 这是有文档的路径，探针也用了它，但该转换是 `request/header` 所记录内容与模型所读内容之间有损的一步，而转换器无法表达的 schema 只能让请求失败。低层处理器直接接收 JSON Schema，因此这次转换并无必要。

**复用 `dsh-mcp-tool-server`，而不是在此构建服务器。** 那个包提供的是某个 **agent** 的注册表，并把每次调用通过 `ctx.tools.execute()` 在该 agent 会话的一个持久轮次中执行。本路由没有 agent，也绝不能执行任何东西：调用由 harness 自己的 loop 在一步之后执行，带着它自己的记录与审批。共用那个包意味着要么得到一个本路由必须设法废掉的执行型服务器，要么在一个“被提供的调用会真的运行”即为全部契约的包里塞进第二种不执行的模式。两者共用的 `mcp__<serverName>__` 限定属于消费端客户端的约定，而非共用实现。

**让产品执行这些调用并汇报所做之事。** 每一步更便宜，而错误的理由与从前相同：harness 的读取屏障、审批、预算策略以及 `tool/call`/`tool/result` 成对事件，才是工具结果可信的原因；绕过它们的路由会让会话日志无法完整交代 agent 做过什么。

## Acceptance criteria

- 提供工具的请求挂载一个名为 `dsh` 的 MCP 服务器，只允许 `mcp__dsh__<tool>`，并通过进程内传输向真实 MCP 客户端原样提供每条 harness 描述与 JSON Schema；不提供工具的请求不构建服务器、也不允许任何名字。
- 在轮次上限处结束查询的工具调用回复返回 text 与 tool-call chunk 并以 `tool-calls` finish；没有调用的轮次上限仍以 `MAX_TURNS` 失败；结果之后发布的抛出不改变这两种结果。
- 被产品标记为失败的 `success` 结果映射为携带产品 API 失败文本的可重试 code。
- 单元测试对 `src/` 保持逐文件 100% 覆盖，包含所提供的 MCP 表面、回复读取与每一种结果分类。
- 可选开启的真实安装 e2e（`DSH_E2E_CLAUDE_CODE=1`）在已挂载的路由上提供 `bash` schema，取回恰好一次参数可解析为 JSON 的工具调用；headless-agent 用例仍通过 harness 自己的工具写入并读回工作区文件。
- 本次改动不附带无密钥快照，理由[路由的记录](2026-09-06-llm-claude-code.md)已经写明：快照框架回放录制的 provider 记录，而本 provider 是一个答案未被录制的本地进程。

## Risks

**产品仍会运行所提供的调用。** 处理器不执行任何东西，但这次往返仍要花掉；请求了多次调用的回复，其全部调用都会在查询结束前以同样方式被回应。它在本就以秒计的查询里增加时延，也意味着产品的记录中留下一条没有任何模型会读的工具结果。

**轮次上限如今是工具调用答案的正常终止。** 路由把一个有文档的错误子类型读作成功，对本产品是对的，但也脆弱：若未来的产品以不同方式报告同一终止，或不再运行所提供的调用，交付答案的样子就会改变。该分类集中在一个函数里，而能发现这种变化的是真实安装的 e2e。

**工具 schema 每次查询都会重发。** 它们从前是 prompt 文本、如今是原生定义，token 成本相当，但在一条无跨轮缓存的无状态路由上，这仍是每一步都要付的。

**证据只有一代探针。** 四次探针查询全部在第一条助手消息里发起了工具调用，覆盖该安装家族的三个模型，每次 5–6 秒。相对于单一产品版本，这是一个很小的样本；产品更新后本路由的行为，只由维护者必须手动运行的可选 e2e 来保证。
