# Agent Note: Claude Code 路由上的会话连续性

Status: proposed

[English](2026-09-08-claude-code-route-session-continuity.md) | 中文

## Problem

[Claude Code 路由](2026-09-06-llm-claude-code.md)每个 harness 步骤跑一次无状态查询：它把整段会话渲染进一个 prompt 字符串，并新起一个 CLI 进程。把会话渲染进单条用户消息意味着每一步都在重写那条消息，于是上一步缓存的任何前缀都不再是下一步请求的前缀。什么都读不回来。

路由自身的 usage 事件在 Proving Ground bench 上量出了这一点。第 3 档上，harness 循环在 18 个 cell 的 200 次查询中花掉 352,494 输出 token 与 553,676 缓存读取 token，对应 3,005,288 缓存写入 token；第 4 档上是 214,397 输出对 4,024,446 缓存写入；第 5 档上是 860,596 输出对 4,778,361 缓存写入。产品自身的循环在同一批 cell 上以读取为主——一个受委派的 cell 报出 3,000,318 缓存读取对 68,193 缓存写入。在第 4 档上 harness 循环还比产品循环慢 20%，那里一个 cell 由许多短步骤组成，每一步都付一次全新的进程启动。

## The probe

一段脚本化的 10 步会话，规模贴近真实——600 字符的系统提示、2,000 字符的任务，随后十轮，每轮一次工具调用并以 1–3 KB 的预置结果作答，工具由进程内 MCP 服务器提供，与[原生工具那篇 note](2026-09-07-claude-code-route-native-tools.md) 所述完全一致——以三种方式驱动 Agent SDK。缓存计数取自每一步的 `result` 消息。

| 设计 | 步数 | 缓存写入 | 缓存读取 | 读取占比 | 墙钟 | 进程启动 |
|---|---|---|---|---|---|---|
| A —— 每步一次全新查询，渲染整段会话（今日实现） | 10 | 114,439 | 0 | 0% | 56.0s | 10 |
| A —— 重复一次 | 10 | 110,471 | 0 | 0% | 63.5s | 10 |
| B —— 每个 harness 会话一个产品会话，逐步 resume | 10 | 14,606 | 69,212 | 83% | 72.2s | 10 |
| B —— 重复一次 | 10 | 14,372 | 67,667 | 82% | 69.9s | 10 |
| C —— 一个持有的查询，会话以 SDK 用户消息推入 | 10 | 15,478 | 74,870 | 83% | 51.5s | 1 |

三个对照实验把机制与偶然分开：

- **两次相同 prompt，分处两个进程。** 第一次写入 13,450 token，第二与第三次各读取 13,450、写入 0。prompt 缓存本就跨越进程边界；设计 A 错过它，只是因为不断增长的会话每一步都在改动第一条用户消息。
- **不带工具的 resume。** 第一轮长回合写入 13,453；resume 后的第二轮读取 13,453、写入 111；第三轮读取 13,564、写入 147。仅凭 resume 就能得到以读取为主的形态。
- **限定作用域的 `CLAUDE_CONFIG_DIR`。** 让 CLI 指向一个空的配置目录要多付一次完整重写：冷目录之后的第一次 resume 读取 0，写入量还超过第一轮，再下一轮才开始读取。因此路由不去动操作者的配置目录。

设计 C 以每查询一轮的轮次上限运行。在该上限下，SDK 的流式输入查询并不会在上限处结束；它保持打开并接受下一条用户消息，而每一步都恰好报出一次 API 轮次。反过来把上限调高——即允许产品在所提供的调用返回后再次发言的那种形态——每推入一条用户消息就产生三到五条助手消息、每步两次 API 调用份额的未缓存输入，那正是本 seam 不得拥有的嵌套 agent 循环。

## Proposal

给路由一个显式的 `sessionContinuity` 配置字段，取值 `'per-session' | 'per-query'`，默认 `'per-session'`。

在 `'per-session'` 下，路由按 harness 会话保存它开启的产品会话 id，以及该会话已持有的会话前缀的摘要。前缀相符的请求以 `resume` 续上那个产品会话，只把最新一轮作为 prompt 发送；不相符的请求新起一次查询并替换该条目。在 `'per-query'` 下，每次请求都渲染整段会话并新起查询，也就是今日行为，作为 resume 表现异常的安装的退路。

`generate()` 的契约与 seam 的 `StreamChunk` 协议不变。轮次上限仍是一条助手消息，工具提供仍按请求重建、按查询挂载，答案仍从查询的助手消息中读出，usage 仍是产品对该步骤所报的数值——因此记分器看到的每步缓存读写与今天完全一致。

### 把产品会话绑到 harness 会话

`GenerateOptions.sessionId` 已经携带 harness 会话身份，seam 也把它记为适配器可用。路由以该值为键，因此无需改动 seam。不携带 `sessionId` 的请求——手工构造的一次性请求——没有可续的会话，始终作为全新查询运行。

`GenerateOptions.purpose` 把辅助调用与会话本身分开：同一 harness 会话上的压缩或会话标题请求属于另一段会话，因此键是会话 id 与 purpose 的组合。

### 等价性检查

被 resume 的产品会话必须让模型看到与 harness 日志完全一致的会话。因此路由在每个产品会话 id 旁记录一份摘要，覆盖一切抵达模型且不属于最新一轮的内容：系统提示、所提供的工具定义、模型条目，以及除最后一条以外的每一条已渲染消息。下一次请求时它从请求本身重算该摘要。相等意味着产品会话已持有这一模一样的前缀，可以只发送最新一轮。不等意味着 harness 编辑过历史——压缩把前缀换成了摘要、收件箱消息被插入、重试回退了一步——于是路由为该步骤跑一次全新查询，并由它开启新的产品会话。

这个回退是被记录的，而非无声的：请求的 `llm/route` 事件带上 `continuity` 字段，标明该步骤走了两条路径中的哪一条，以及回退时的原因。某一步的模型可见输入与上一步的前缀不同，正是日志读者必须能看见的情况。

产品自身的转录里有一样东西不在 harness 日志中：所提供的 MCP 服务器对一次调用回答的那句固定文本。它是本包的常量，插入位置完全由日志中的工具调用决定，因此被 resume 的模型所读到的会话，仍可由日志加该常量重建。README 陈述此点。

### 落盘的转录

resume 需要 `persistSession: true`，它会在操作者的配置目录下写入 `~/.claude/projects/<cwd-slug>/<session-uuid>.jsonl`。十步的探针会话留下 88.9 KB。路由通过 SDK 的 `deleteSession` 删除它开启的每个产品会话，时机是该条目离开表的时刻：等价性检查失败而条目被替换时，以及插件被销毁时。路由未曾开启的会话绝不触碰。

配置目录用操作者自己的，而非限定作用域的目录。探针量过限定作用域的代价——冷目录后第一次 resume 要付一次完整前缀重写——而且它还会对路由所驱动的 CLI 隐藏操作者的认证与设置。

## Alternatives considered

**设计 C：每个 harness 会话持有一个流式输入查询。** 它量出与 B 相同的缓存读取占比（83%），进程启动只有一次而非十次，墙钟少约 26%，而且它的一轮上限确实保住了每个 harness 步骤一次 API 轮次。它输在契约上，不是输在数字上。`systemPrompt`、挂载的 MCP 服务器、`model`、`effort` 与 `thinking` 都在查询创建时固定，而 `GenerateOptions` 是按请求携带它们的——于是改变工具集（计划模式、加载的技能）或系统提示的那一步，要么被喂以上一步的取值，要么仍旧被迫重建查询。它还依赖 SDK 让流式查询在自身轮次上限之后保持打开，这一点没有文档；并且它在每个 harness 会话的整个生命周期内持有一个 CLI 进程，而不是只在一步的时长内。resume 以有文档的接口、且不持有进程，买到同样的缓存；C 能省下的进程启动是后续工作，上面的数字正是重新审视它的依据。

**在 resume 的步骤上同样发送整段会话。** 这会让两种连续性模式的渲染保持一致，也不需要等价性检查。它同时原样复现了正在被修的故障：第一条用户消息每一步都会变，探针中设计 A 的各行就是代价。

**用消息条数比较来检测被编辑的历史。** 比摘要便宜，但在最要紧的情形下是错的：压缩把长前缀换成更短的摘要，重试则回退到更早的条数，于是条数比较会接受产品会话并不持有的前缀。摘要按内容计算，因为被检查的性质就是内容。

**让路由重新变回无状态：请产品什么都不存，把会话作为结构化历史重新上传。** SDK 的 `sessionStore` 会把转录镜像到调用方提供的存储中，但它不能与 `persistSession: false` 同用，而且它在 spawn 之前把会话具化成临时文件——它改变字节存放的位置，而非前缀是否被重发。相比本地转录加 `deleteSession`，它不带来任何新东西。

**保持路由原样，并建议部署优先选择带密钥的 provider。** 这是既有建议，且依然成立，但该路由存在正是为了没有密钥的主机，而在那样的主机上每个 bench cell 每一步都付全额输入。在这种量级下，83% 的缓存读取占比不是微优化。

## Acceptance criteria

- `sessionContinuity` 是经校验的 `Config` 字段，两个取值都能从 `cordis.yml` 到达，且 `resolveAdapterOptions` 在加载时拒绝任何其他取值。
- 在 `'per-session'` 下，同一 harness 会话上前缀与第一次相符的第二次请求会续上产品会话并只发送最新一轮；SDK 收到记录下来的 id 作为 `resume`，且 prompt 不包含更早的轮次。
- 在 `'per-session'` 下，系统提示、工具定义、模型或任一更早消息不同的第二次请求会以整段会话渲染跑一次全新查询，且先前的产品会话被删除。
- 在 `'per-query'` 下，每次请求都渲染整段会话，不记录也不删除任何产品会话。
- 不带 `sessionId` 的请求在任何模式下都不 resume。
- `llm/route` 事件标明每一步所走的连续性路径，使会话日志能区分被 resume 的步骤与全新步骤。
- 单元规格在 `src/` 上保持每文件 100% 覆盖，涵盖摘要、表的驱逐与销毁、增量渲染，以及两种模式的查询选项。
- 可选的真实安装 e2e（`DSH_E2E_CLAUDE_CODE=1`）在一个 harness 会话上以 `'per-session'` 跑两步，并断言第二步所报的缓存读取超过其缓存写入。

## Risks

**产品会话与 harness 日志可能在摘要察觉不到的地方分叉。** 摘要覆盖路由所发送的内容。它不覆盖产品自身信封所添加的内容，而那本就是路由既看不到也记录不了的——[路由那篇 note](2026-09-06-llm-claude-code.md) 已记下的限制。若产品更新在 resume 时往会话里注入文本，该检查将看不见它，只能表现为一次缓存未命中。

**清理是对操作者所拥有目录的尽力而为。** harness 进程在两步之间被杀，会为每个存活会话留下一份转录。路由在力所能及时删除它开启的东西；它不会为孤儿去扫操作者的目录，因为它没有开启过的转录可能是操作者自己的工作。

**每步多了一种失败模式。** 记录的会话 id 在盘上已不存在时，resume 会让查询失败而非让请求失败。路由把失败的 resume 当作一次全新查询的步骤并替换条目，从而把该失败变成一次被浪费的进程启动而非一次失败的 harness 步骤，但这条路径是全新查询模式所没有的。

**证据只有一代探针、一个安装。** 每种设计两次运行、每次十步，跑在一个产品版本上。问题陈述引用的 bench 数字是对设计 A 行为的独立佐证；设计 B 与 C 依赖该探针，以及维护者必须自行运行的可选 e2e。
