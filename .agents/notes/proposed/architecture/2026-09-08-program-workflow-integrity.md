# Agent Note: Program workflow integrity — a certificate over a commit, a confined integration, and an integration that resumes

Status: proposed

English | [中文](2026-09-08-program-workflow-integrity.zh.md)

## Problem

The first real program run of [`dsh-program`](../../../../packages/improvement/program/README.md) delivered its release, and the record of it — [`data/proving-ground/2026-09-08-self-assessment-program-artefacts`](../../../../data/proving-ground/2026-09-08-self-assessment-program-artefacts/manifest.json) — needed three operator interventions to get there. Each one is a hole in the workflow rather than a mistake the operator made.

**A department was certified over a worktree, and the branch it delivered was empty.** The department wrote `assessment.md`, its checks passed on the files on disk, and the program recorded it `certified`. Nothing it wrote was ever committed, so `git merge --no-ff` of that branch carried nothing and the integration's own check failed with "missing assessment.md". The integration agent then spent 22 steps trying to satisfy a check about a file no branch held, and the operator stopped the run, committed the department's tree by hand, and started the program again. The certificate had claimed a tree; only a commit is delivered.

**The integration was unconfined and edited a department's file.** Before that hand commit, the first integration attempt found the department worktree beside its own, and at step 20 it rewrote sentences of `assessment.md` with a python script. The text the department certified at 11:47:50 UTC survives only because the record reconstructs it from the department session's own write and edit calls (`assessment.certified.md`); the file the program released (`assessment.md`) carries the integration agent's edits. An integration that can write into a department worktree makes every department certificate a claim about a tree someone else may have changed since.

**The interrupted integration could not be resumed.** `driveIntegration` creates its session at the derived id `departmentSessionId(programId, INTEGRATION_KEY)`. After the operator's restart, `resume()` reached `close()` and then `integrate()`, which created that id a second time, and persistence refused it: `cannot publish session "program-…-@integration": persisted state already owns this identity` ([`resume-refusal.log`](../../../../data/proving-ground/2026-09-08-self-assessment-program-artefacts/resume-refusal.log)). The operator moved the first integration session aside under `sessions-superseded/` to get the program to finish. A program whose integration is killed mid-flight cannot finish without hand-editing the persistence root.

## Proposal

Three rules, all inside the service that already owns the ledger.

**A certificate covers a commit.** `attempts()` reads `git status --porcelain` in the workspace before it runs any check. A non-empty status means the attempt measures nothing: it spends its round, issues a directive whose root cause is `the worktree carries work that no commit on this branch carries`, and hands the session an `<uncommitted_work>` turn listing the porcelain lines and telling it that uncommitted work is not delivered. The round cap bounds those attempts exactly as it bounds failing checks, so a session that never commits ends `failed` instead of certifying something the integration cannot merge. The rule sits in `attempts()` rather than in the department path, so the integration session is held to it over its own worktree too.

**The record states what was certified.** A certified department records `revision` (`git rev-parse HEAD`) and `tree` (`git rev-parse HEAD^{tree}`) on its `program/goal`, carried together as one `CertifiedTree` in the run state so neither half can exist without the other. A reconciliation keeps what the ledger recorded and reads the worktree only when the ledger records nothing — a process that died between a department's certificate and the record of it. Before merging, the integration compares each branch head against the recorded revision and refuses a branch that moved, recording `program/integration { failed }` naming both revisions: a department that moved after certification is not what was certified. A branch the integration worktree already contains, which is what an interrupted integration leaves, is skipped through `git merge-base --is-ancestor` rather than merged again.

**The integration is sealed like a cell.** When `readBarrier` is composed, `driveIntegration` registers `denyFor(agent.session, <workspaceRoot>/<programId>)` for the length of the integration and disposes it when the integration ends — the same registration the [sealed cell](2026-09-08-sealed-cell-workspace.md) makes for an environment run, and for the same reason. The denied directory is the program's worktrees root: the barrier grants a session its own workspace beneath a denied strict ancestor, and every department worktree is a sibling of the integration's inside that root, so one registration reaches every department worktree and nothing of the integration's own. No per-department denial is added, because the layout `worktreePath` mints makes the parent denial exact. Both closing records carry `denied`, empty for a composition without a barrier, so the log states what the integration could not reach. `isolation` stays `none`: the denial is worth what the composed executors enforce, which is what that claim already says.

**An interrupted integration is taken back over.** A pass that reconciles a ledger whose last integration record is `running` and whose integration session persistence already holds resumes that session through `ctx.agents.resume`, resumes its goal, and continues at the attempt after the validation runs its own log records — so the round cap covers the whole integration rather than each process that drove it. The standing `running` record is what the pass owns; no second one is appended, which the package's own invariant does not admit either. A `running` record whose process died before the session existed opens it under that same record, and a session that carries no goal to resume records `failed` with `PROGRAM_INTEGRATION_UNRESUMABLE`.

## Alternatives considered

**Certify the tree the checks saw, and commit it for the department.** The program would commit whatever the worktree held before recording the certificate. It removes the refusal and the extra round, and it makes the program an author of the deliverable: the branch would then carry a commit no department wrote, made by a service whose whole claim is that it never writes into a worktree. The department is the one that knows what belongs in the commit; the program is the one that can tell it the work is not delivered.

**Record the tree digest and let the integration merge whatever the branch points at.** The `tree` alone tells a reader that two certificates delivered the same files, but nothing refuses a branch that moved: the integration would merge the new head and certify a merged revision no department certificate covers. Refusing at the merge is what makes the department record load-bearing.

**Deny each department worktree explicitly.** One `denyFor` per department, registered as each certifies, denies the same paths and needs a registration per department kept current while departments are still certifying. The worktrees root is one path known before any session exists, and it also covers whatever else a deployment puts beside the worktrees. Per-department denials would matter under a layout where the integration worktree's parent is not the worktrees root, which `worktreePath` does not mint.

**Give the resumed integration a fresh session id.** A suffixed id — `@integration-2` — would let the pass create rather than resume, and it drops the interrupted attempt's own log: the round cap would start over per process, the earlier attempts' runs would be in a session no ledger record names, and "one session per key" would stop being a property of the derived identity. Resuming keeps the id the ledger already published.

**Let the integration re-merge every branch and rely on git.** `git merge --no-ff` of an already-merged branch exits zero and merges nothing, so the skip is not needed for correctness. Asking `git merge-base --is-ancestor` states the intent instead of depending on that behaviour, and it keeps a resumed integration's command log free of merges that did nothing.

## Acceptance criteria

- A department whose worktree is dirty is not certified: the attempt runs no check, the department session's directive names the uncommitted work, and the next turn is an `<uncommitted_work>` block carrying the porcelain lines. Once the department commits, it certifies and the `program/goal` record carries the commit and its tree. A department that never commits ends `failed` on its round cap with no certificate in its log.
- The integration refuses a department branch whose head is no longer the recorded revision, records `program/integration { failed }` naming both, and merges nothing; a branch the integration worktree already contains is skipped rather than merged again.
- With a read barrier composed, the integration session is denied the program's worktrees root for the length of the integration, the registration is disposed when it ends, and both closing records carry that path in `denied`; a composition without a barrier records an empty list.
- Over [`examples/headless-agent/tests/fixtures/program/`](../../../../examples/headless-agent/tests/fixtures/program/cordis.yml), a Loader-booted keyless composition runs a program whose departments write before they commit and whose integration repairs a merged head no department branch could satisfy: the integration's `read` of a department worktree file appends one `read-barrier/denied` naming the `fs` capability, the certified department records carry a 40-hex revision and tree, and the released program's merged revision is a commit of the integration's own.
- In that same fixture, a boot killed after the integration's first run over the merged head is followed by one that takes the integration back over on the id it already owns: the program releases, its ledger carries exactly one `running` record before the `certified` one, and one `@integration` member session exists.

## Risks

- **A department that leaves ignored-but-untracked files stalls.** The porcelain status is the whole rule, so build output a check produced and the repository does not ignore reads as uncommitted work and burns the round cap. The deployment's own ignore rules are the only lever; the spec cannot state an exception.
- **The seal is only as strong as the executors under it.** `denyFor` binds the capabilities that refuse a read in the operation that opens paths. A deployment composing an unconfined shell beside the barrier leaves that seam able to reach a department worktree — which is exactly what the recorded run did — and the `denied` list on the record will still name the directory. A district that wants the seal enforced composes the sandbox-confined executor the [sealed cell](2026-09-08-sealed-cell-workspace.md) names.
- **A moved branch ends the program rather than re-certifying it.** An operator who moves a department branch on purpose — the recovery the recorded run performed — now gets a failed integration instead of a merge. Starting the program again reconciles that department from its own log and certifies the new head, which is a longer path than the operator took, and a truthful one.
