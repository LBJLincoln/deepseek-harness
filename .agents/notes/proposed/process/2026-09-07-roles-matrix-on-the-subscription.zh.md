# Agent Note: 每个 harness 角色都在运营方订阅上真实运行一次

Status: proposed

[English](2026-09-07-roles-matrix-on-the-subscription.md) | 中文

## 问题

Claude Code LLM 路由原则上把每个 harness 角色都放到了运营方的订阅上，但直到今天，除了单元实现者之外，没有任何角色在它上面真实运行过。验证者能否撰写标准、盲评审能否裁决、项目部门是否真的实现了什么、桥接模式是否把产品限制在所提供的工具之内，这些说法的依据都是使用脚本化模型的无密钥夹具，而不是真实路由上的真实模型。

## 提议

从各自的无密钥夹具出发，把脚本化路由替换为 Claude Code 路由，在订阅上把每个角色运行一次，保留组合、驱动、差异和会话日志作为证据，并逐角色记录结果。下表就是这份记录；角色 2 与 4 运行了两次，分别在路由开始以原生方式提供 harness 工具之前与之后（原生工具说明解释了这一变更）。

| 角色 | 夹具 | 原生工具路由之前 | 之后 |
| --- | --- | --- | --- |
| 经由 harness 循环的实现者 | `environment-run` | 是：一个环境一次尝试即获认证，不可满足的那个在两次尝试与两条指令后被正确拒绝，保留的那个获认证并被排除在奖励导出之外；三个共 165 s | 基准上 48 之 48 个获认证的单元可以代替 |
| 验证者（标准撰写者） | `recreation-instrument` | 否：`standard_author` 从未被调用；每次查询都在路由的两轮上限处失败，分别重试了五次与八次 | 是：带加权用例的标准在 137 s 内冻结，13 个步骤，40 次工具调用，没有重试 |
| 盲评审 | `blind-judge` | 是：一个无谱系的评审会话在 20 s 内给出 `upheld` 裁决并附有理由 | 未重跑 |
| 项目部门 | `program` | 编排发布并合并了两个目标，但两个部门的回合都在两轮上限处失败，目标之所以获认证只是因为夹具的检查在未改动的基线上就能通过 | 是：两个部门都完成了工作（13 次与 7 次 shell 调用），获认证，项目发布且没有重试 |
| 桥接模式 | `agent-bridge` | 是：产品只使用所提供的 `mcp__dsh__` 工具运行，调用了一次，harness 执行了它，三个桥接事件被记录；10 s | 不受影响，这一模式下产品本身就是模型 |
| 进程内子代理 | 已起草组合 | 未涉及 | 未运行 |
| Ralph 工作流 | 无 | 未涉及 | 未运行 |

证据目录（组合、差异、驱动、会话日志）是本会话暂存区的 `roles/` 树，其 `SUMMARY.md` 作了汇总；持久的事实是这张表中的内容。

## 矩阵暴露的缺口

1. 路由的两轮上限破坏了每一个对话超出简短交流的角色，而这几乎是所有角色；原生工具重写移除了这一上限，两次重跑就是证明。
2. 验证者从未被告知参考程序在哪里。人格说它被给予了一个参考，采样技能说先用 shell 探测，但没有任何模型可见的输入携带屏障根目录：作用域事件不会展示给模型，工具描述也没有给出路径。重跑之所以成功，是因为模型探测了工作区，所以这个缺口是一项成本，而不是一堵墙。
3. 桥接模式只能通过子代理服务到达：夹具的驱动从不启动产品，委派工具也没有请求桥接子代理的选项，因此代理无法从一次工具调用中请求它。
4. 两个角色没有证据：进程内子代理与 Ralph 工作流。

## 考虑过的替代方案

- 把无密钥夹具当作角色在路由上可用的证据：它们证明的是组合与协议，而不是模型行为；角色 2 与 4 在真实路由上失败，而它们的夹具却通过。
- 只运行一次矩阵并把最初的失败当作定论：这些失败在路由中只有一个根因，因此修复后重跑两个失败的角色比在角色内做任何变通都更便宜。

## 验收标准

- 表中每个角色都有组合、命令、墙上时间和一份会话日志，能在订阅上展示该角色自身的事件（冻结的标准、评审裁决、项目目标记录、桥接事件）。
- 在后续切片中，验证者的参考位置由一个模型可见的输入（任务提示或工具描述）携带，并有快照固定其文本。
- 两个尚无证据的角色各运行一次并加入表中。

## 风险

- 这个矩阵是在一个模型、一种努力程度下每个角色运行一次；它表明角色可用，而不是有多可靠。可靠性在基准的重复单元中度量。
- 证据目录位于仓库之外；只有这张表与所引用的夹具是持久的。
