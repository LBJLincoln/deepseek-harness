# Agent Note: Seeded-defect recall 在没有基准真值的目标上估计审查的召回率

Status: proposed

[English](2026-09-22-seeded-defect-recall.md) | 中文

## 问题

代码安全 program 的召回率只在两个带有已记载基准真值的公开目标上被度量过：NodeGoat（18 个问题）与 dvja（14 个问题）。客户自己的应用两者皆无，因此今天对它的一次审查会产出一个发现数与一组严重度，却没有任何东西可供比对——客户无法判断 40 条发现意味着审查找到了那里大部分的东西，还是漏掉了大部分，因为没有人数过那里究竟有什么。`docs/code-safety-poc.md` 的付费概念验证范围已经把"与他们的安全团队商定一份预埋的基准真值"点名为解法，但没有任何东西能产出这样一份基准真值：今天这意味着就哪些真实或植入的问题算数进行一次人工协商，且每次engagement都要重来一遍。

## 提议

Seeded-defect（canary）估计法：把已知数量的合成缺陷实例——属于各部门技能本就在寻找的类别——植入目标一份完整副本中记录在案的位置；在这份副本上运行审查，且不告知它这一点；用 `compare.mjs` 已经使用的同一条三行容差匹配规则，为已发布发现落在植入位置上的比例打分。这个比例是该代码库上、针对这些类别的一个召回率估计，并附带一个置信区间——而不是关于目标真实的、尚未被发现的缺陷的一种断言。

`data/code-safety/tools/seed-defects.mjs` 负责植入，取材于 `data/code-safety/tools/seed-catalogue.json` 里的一份**缺陷变异目录**。目录里每个条目都是数据：一个 CWE、一种语言、一个用于找到候选行的正则表达式（`sitePattern`）、可选的全文件 `fileRequirePattern`／`fileExcludePattern`，以及一个用于选出真实字段名的 `fieldHintPattern`，还有一个带 `{{indent}}`／`{{source}}`／`{{field}}`／`{{line}}`／`{{hex}}` 占位符的字符串模板（`insertTemplate`）。这个工具是架在这份数据之上的一个通用解释器，不是逐类别的代码分支。目录随附八个 JavaScript/Express 条目，对应 injection、access 与 secrets 技能所记载的每个类别各一个：eval 注入（CWE-95）、NoSQL `$where` 注入（CWE-943）、服务端请求伪造（CWE-918）、日志注入（CWE-117）、未验证重定向（CWE-601）、正则表达式拒绝服务（CWE-1333）、经由字符串拼接响应的反射型 XSS（CWE-79），以及硬编码凭证（CWE-798）。八个条目中的七个共用同一个位置模式——任何引用 `req.query`／`req.body`／`req.params.<field>` 的行——并在其后插入一行新代码，把同一个字段带入该类别的汇点（`eval()`、一个 `$where` 过滤器、`fetch()`、`console.log()`、`res.redirect()`、`new RegExp()`、`res.send()` 拼接）；凭证类别则改为锚定在文件自身的某一行 `require(...)` 上，添加一条形如 secrets 技能自身 `process.env.JWT_SECRET || 'literal'` 示例的兜底密钥声明。一次轻量的逐行扫描会跳过 `//` 注释、`/* */` 主体与跨行模板字面量，使插入永不落在其中；每一行插入的代码随即立即用 `node --check` 校验，事后解析失败的文件，其对应位置会被撤销，不计入 N。同一文件内没有两个植入位置的距离在 10 行以内。选取过程是对每个候选位置的一次带 seed 的 Fisher-Yates 洗牌（字段匹配某条目提示的位置优先），因此同一个 seed 与同一个目标总是植入同一批位置，换一个 seed 就会重新洗牌；`--max-per-entry` 为单个目录条目能贡献的位置数设置上限，使候选众多的类别不会在小目标上挤占其余类别；`--avoid <ground-truth.json>` 让植入位置与目标自身已记载的真实问题保持距离（三行容差，与 `compare.mjs` 自身的规则一致），因此审查对一个真实、已存在缺陷的命中绝不会被误认成对一个合成缺陷的命中。`--dry-run` 列出每一个候选位置，并标出 seeded 选取的结果，不触碰任何文件。

`data/code-safety/tools/seeded-recall.mjs` 用 `compare.mjs` 的精确匹配规则，把一份发现列表或一个记录目录，与一次 seeding 运行写出的 `seeded.ground-truth.json` 对比打分，并以 Wilson 95% 置信区间的形式，报告总体及逐 CWE 类别的「命中数/N」——选 Wilson 而不是正态近似区间，是因为它始终落在 [0, 1] 之内，且在一次 seeding 运行产生的小计数（`k = 0` 或 `k = n`）下不会收缩为零宽度。

### NodeGoat 上的 dry run

一次以 `--seed 1 --n 12 --avoid data/code-safety/targets/nodegoat.ground-truth.json` 针对基准真值自身修订版（`c5cb68a`）的 NodeGoat 副本运行的 seeding，从 37 个符合条件的候选位置中植入了全部 12 个请求的位置（6 个因落在另一个已接受位置 10 行以内而被拒绝，0 个被 `node --check` 拒绝），分布在 11 个文件里，没有一个落在 NodeGoat 18 个已记载问题中任何一个的 3 行以内。`--avoid` 与 NodeGoat 的小体量相互作用：排除 18 个已知问题位置后，七个请求数据流类别加在一起，整棵树里只剩下一个存活的候选位置（`app/routes/memos.js` 的 `req.body.memo`，因为 NodeGoat 其余的 `req.query`／`req.body` 读取全都落在某个已记载问题的三行以内），因此 12 个植入位置中有 11 个属于硬编码凭证类别——它不需要请求数据流，且有许多符合条件的 `require(...)` 行。一次使用只读工具（`Read`、`Grep`、`Glob`；提示词在 `/tmp/…/scratchpad/compare/t1-prompt.txt`，与针对未 seeded 目标那次运行完全相同，未作改动，因此审查从未被告知这份副本是 seeded 的）的单个 sonnet 通过，针对这份 seeded 副本在 265 s 内发布了 50 条发现，读出 12/12（召回率 1.0），Wilson 95% 区间为 [0.758, 1.0]；按类别看，硬编码凭证读出 11/11（95% 置信区间 [0.741, 1.0]），日志注入读出 1/1（95% 置信区间 [0.207, 1.0]）——每一个植入位置都被模型用它自己的措辞逐一点名，其输出中没有任何迹象表明它意识到这份副本是 seeded 的。这次只跑了单模型层，因为当晚六部门 program 的订阅份额被别的工作占用了；完整读数所需的命令记录在 `data/code-safety/README.md` 的 seeded-defects 小节，留待日后运行。

## 考虑过的替代方案

- **把两个公开基准的读数当作客户自身召回率的代理。** NodeGoat 与 dvja 对一个语言、框架与缺陷分布都与两者不同的代码库什么都说明不了，而这正是每一个真实客户应用的情形。
- **一份人工的、逐 engagement 的预埋基准真值**，正如 `docs/code-safety-poc.md` 已经点名的那样。它不可扩展（每次 engagement 都要重来），不可复现（没有 seed 可供重跑），并且把协商放在了任何可供协商的数字存在之前。
- **由 LLM 撰写 seeding，** 取代基于数据目录的正则表达式模板。它能让植入的缺陷比八个固定模板更多样，但其输出在给定 seed 下不会精确可复现，并且它自己需要一道验证步骤来保证语法有效性与放置的真实感——这正是本提议所解决的问题，在更高一层被重新引入了一遍。
- **在发布关口内为 seeded recall 打分。** 一个在每次运行中植入并为合成缺陷打分的关口，会让发布标准部分地变成关于这个工具自身的合成模式，而不是关于经过验证的真实发现；seeded recall 保持为一个独立的、可选的估计步骤，与 `recall.mjs` 对关口的关系完全相同。

## 验收标准

- `seed-defects.mjs` 从不修改原始目标（已验证：本记录中每次运行之后，`/root/targets/NodeGoat` 上的 `git status` 都为空）；每个植入缺陷所在的文件都能独立通过 `node --check`；同一文件内没有两个植入缺陷的距离在 10 行以内；同一个 seed 与目标在第二次运行时植入同一批位置。
- `seeded-recall.mjs` 精确复现 `compare.mjs` 的匹配规则，并报告总体及逐类别的 Wilson 95% 区间。
- 针对 NodeGoat 的一次 dry run 植入 N = 12 并报告上文的「命中数/12」读数；六部门 program 自身的读数，将在订阅份额不再被别的工作占用之后运行。
- Java 支持不在本记录范围内：NodeGoat 与 dvja 使用的 Java 框架（Struts 2、Spring）需要一套不同的位置模式与一种不同的语法检查（没有 `node --check` 的对应物），在这一阶段把它做对的成本并不低。

## 风险

- 一个 seeded-recall 数字，是**被植入的类别、在被植入的位置上**的召回率，不是目标中真实、尚未被发现的缺陷的基础比率；目标必定持有八个已建模类别之外的缺陷，这项估计对那些缺陷什么都说明不了。`data/code-safety/README.md` 的 seeded-defects 小节在每个读数旁边都陈述了这一点。
- 一个被 seeder 做得很明显的植入缺陷——一条点名该漏洞的注释、一个以该漏洞命名的变量、一个形如已记载占位符、会被审查自身技能当作已知非发现过滤掉的值（一个形如 `AKIA...EXAMPLE` 的密钥、一个字面的 `devsecret`）——会在不说明审查真实能力的情况下抬高这个数字。该目录通过以下方式避免这一点：每个模板都模仿一个已经记载在某个部门技能中、或已作为真实缺陷出现在某个公开目标里的模式；不携带任何注释或点名该缺陷的标识符；并且对唯一一个其值原本可能形似已知占位符的类别（硬编码凭证），使用一个带 seed 的伪随机十六进制字符串。
- 在像 NodeGoat 这样体量小、已被深入研究过的目标上，`--avoid` 可能只给一个类别留下真实的容量，使得较小的 N 主要读出那一个类别；客户体量大得多的代码库不会遇到同样的约束，但一个小型试点目标可能会，而 `seeded-recall.mjs` 输出中的逐类别拆分正是读者据以察觉这一点的地方。
