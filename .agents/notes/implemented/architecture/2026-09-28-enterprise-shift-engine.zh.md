# Agent Note: 企业班次：包管家经由程序工作流处理工单

Status: implemented

[English](2026-09-28-enterprise-shift-engine.md) | 中文

## Problem

[`data/enterprise/`](../../../../data/enterprise/README.md) 下的企业花名册定义了 147 个席位，[`data/enterprise/tickets/`](../../../../data/enterprise/tickets/README.md) 下的工单队列给了 Harness Core 的包管家 21 项针对各自软件包的小而可验证的修改，却没有任何东西让一个席位履行它的职能：没有一个流程会领一张工单、在本仓库的一个工作树里实现它、验证它、让它接受评审，并把它作为企业自己的提交落到开发分支上。[readme-rows 程序](../process/2026-09-27-program-builds-readme-rows.md)已经证明程序工作流可以指向本仓库的一个克隆，它的第一次真实运行也暴露了一个真实部门需要什么——已安装的工作区、在会话目录中工作的路由、按阅读本仓库的量级定下的上限——但它只交付过一份手写的任务陈述一次，由操作者手工准备克隆。工单需要的是一台引擎：一条可由定时任务无人值守运行的命令，对事业部通用，它的每个结果都是它所发运到的分支上的一条台账行与一份记录。

## Decision

[`examples/headless-agent/tests/fixtures/enterprise-shift/`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/README.md) 就是这台引擎，`pnpm run enterprise -- shift [--next <n> | --tickets <id,...>] [--implementer route|subagent] [--model <id>] [--push]`（[`scripts/enterprise.ts`](../../../../scripts/enterprise.ts)）发起它的一个班次。一个班次把开发分支的顶端克隆到一个临时目录，本地仓库不是浅克隆时就从它借用对象；读取并校验克隆中的队列、读取它的台账，于是选择跟随分支而从不跟随某个检出；运行一个部门即为所选工单的程序；评审每个已认证的部门；把获批的部门按每张工单一次 squash 提交装配到基准上；重新认证装配出的树；再连同班次自己的提交——携带台账行与记录——把分支快进推送出去。

**一个程序，工单即部门。** 每张工单是一个键为 `t-nnnn` 的目标，使用 `implementing` 预设，处于工单自己的预算之下，其标准是工单的验收命令，其后跟三项引擎检查：`engine-committed`（分支在基准之后有提交）、`engine-scope`（`git diff --name-only <base> HEAD -- . ':(exclude)<prefix>'…` 列不出任何路径，由 git 自己的 pathspec 决定什么算 scope 之内）与 `engine-whitespace`（`git diff --check`）。目标陈述工单、花名册中席位的名称、任务、scope、验收命令以及贡献者遵循的规则，把部门指向 `CLAUDE.md` 与包 README 而非粘贴它们。程序的每个工作树——每个部门一个，加上整合的——都在程序启动前添加并离线安装，因为部门的验收会在它的工作树里运行 `pnpm exec vitest` 与 `pnpm run typecheck`，而程序会复用已存在的工作树目录。程序的整合被保留：它合并每个已认证的部门，在合并后的头上重跑每张工单的验收，当所有部门都获批时，它的合并树就是装配结果所对照的摘要。

**一位按评审官方式构建的独立评审员，而不是评审官本身。** 部门认证之后，由一个从未见过它的会话作出裁定：全新的 id、没有父会话也没有种子、`reviewing` 预设——即随产品发布的 `judge` 预设的那套安排，一行 persona、`role: judge` 使读屏障拒绝它访问它所拥有的每个目录与每项权限——用 `tools.restrict({ allow: [] })` 限制掉所有全局工具、一个属于它自己的空工作目录，以及由三条消息派生的历史：常设指令、工单、证据（有上界的 `git diff <base> <revision>`、有上界的分支各提交信息，以及每项检查的状态与有上界的输出）。在这份组合里，让评审员失明的正是这个限制：部署的工具（`bash`、`read`、`edit`……）是没有声明任何权限的全局行，单凭 judge 角色一个也拒绝不了，第一个真实班次的评审员就是在班次的临时目录里创建的，它运行了 `bash`，读到了部门的工作树。提交信息是实现者对修改的自述，随修改一起提交，正是它让评审员得以分辨一句树早已满足的工单陈述与一个 diff 遗漏的步骤。回答的第一行 `verdict: approve|reject` 决定结论，其余是理由；两者都没写的回答视为驳回。没有使用 `ctx.judge.audit`：它会把被审工作区复制到一个新目录以复现该次尝试的树哈希，对本仓库已安装的工作树而言意味着复制 `node_modules`，而且它按设计对评审官隐去 diff 与检查输出，而工单评审恰恰是对照工单阅读 diff。也没有使用程序的 `signoff/recorded`：它记录的是某位主体对某个制品摘要的签名，是驱动在程序打开前就满足的规格冻结与发布关卡，不是模型依据证据得出的结论。评审员的会话日志是它读了什么、答了什么的持久记录，台账行写明了它。

**只有获批的工作到达分支，每张工单一次提交。** 获批的部门按工单顺序以 `git merge --squash` 压到基准上；squash 冲突的会被重置并记为 `conflict`，其余仍然装配。引擎自己的提交带 `--no-verify`：工作树的离线安装会把仓库的 git 钩子装进克隆，这对部门是对的——它们的提交是贡献者的提交——对引擎却是错的：它的 squash 已由工单的验收认证，它的台账提交是机器写出的数据——第一个真实班次正是死在那个钩子里。每次提交的信息写明工单、席位、程序 id、部门与评审会话、工单的来源，并以 `Co-Authored-By: <部门所用的模型>` 与操作者的 `Claude-Session:` 行结尾。当所有部门都获批时，装配出的树必须等于程序已认证的合并树；随后每张已装配工单的验收在克隆自身的检出里、在装配出的树上再跑一遍。推送是一次快进更新：顶端移动了就把装配的提交变基到它上面、在那里重新认证，并围绕新哈希重写台账；变基冲突则什么也不发运，但仍推送台账；循环最多三轮。在那一次推送之前没有任何东西到达远端，而每个部门经由的 `origin` 的推送 URL 都是不可达的。

**台账即状态，记录即证据。** `data/enterprise/ledger.jsonl` 每班次每工单新增一行，字段集与读取它的企业职能共用（`type, at, shift, ticket, seat, division, programId, implementer, model, department, checks, review, integration, shipped, reason, tokens, seconds`）；工单在已发运或已驳回的行上关闭，在其他任何行上保持开放。`data/enterprise/shifts/<UTC 日期>-<班次 id>/` 存放 `result.json`、`manifest.json` 与班次的每份会话日志，形似凭据的字符串已剪除并计数。两者都在装配的提交之后提交，在同一次推送中传播，因此什么也没发运的班次仍然汇报到下一个班次读取的地方。

**路由上限依据接缝的码停机。** 驱动监听第一个失败携带 `QUOTA` 的 `turn/end`——接缝赋予路由用量上限通知的码，重置时间作为 `providerRetryAfterMs`（[上限之墙](2026-09-27-route-limit-halts-the-run.md)）——在一个微任务里以 `route-limit` 阻塞该部门的目标——阻塞是对正在发布该事件的会话的又一次追加——于是程序在没有验证运行的情况下结束该次尝试，让之后的每个部门在第一个被拒的回合上阻塞，不评审不装配任何东西，把 `halted: limit (resets at <instant>)` 写进每张未完成工单的行，推送台账，以 3 退出。

**可安全地无人值守重跑。** 包装器持有写明其 pid 的 `<scratch>/shift.lock`；该 pid 存活期间第二个班次拒绝启动（退出码 4），已死亡班次留下的锁会被替换；满一天的克隆在下一个班次启动时清扫；工作树无法准备或程序抛出异常的班次仍然写出每张工单的行并推送。工单校验器把队列策略作为参数（`HARNESS_QUEUE_POLICY` 强制本仓库的 typecheck 与覆盖率运行，`OPEN_QUEUE_POLICY` 在工单自身的检查之外不作要求），因此播种的 e2e 仓库在同样的 schema、席位、来源与 scope 规则下通过校验。

## Alternatives considered

**每张工单一个程序。** 每张工单的程序会各自整合与发布，一张失败的工单不会阻止其他工单的整合。但班次的工单是一份席位花名册的一个交付物，程序的台账把它们归为一组，程序对全部工单的整合是工作流本身唯一认证合并树的地方；当程序无法整合时，班次装配获批的子集，这正是每工单一程序的设计会合并的同一个子集，却不必每张工单一个程序。

**在程序内部、评审之后才整合。** 程序在部门证书与整合之间没有钩子，为一个自己就能装配获批子集的消费者加一个，会改变工作流。程序的整合保持原样——对每个已认证部门的证书——班次的装配是对评审所批准内容的整合，在两个集合重合时对照程序的合并树校验。

**推送程序的合并修订。** 合并修订是覆盖各部门分支的合并提交，提交信息由模型撰写；推送它会把部门自己的提交与 `program/<id>/<key>` 合并信息落到分支上。每张工单一次 squash 提交携带企业应当写明的信息——工单、席位、程序、会话、模型的署名行——树摘要校验则保证它恰好是程序认证的那棵树。

**cherry-pick 部门的提交。** 部门可能多次提交、可能合并，它的提交信息是它自己的；`git merge --squash` 取分支的树而不问历史，把信息留给班次。

**让部门自己安装依赖。** 目标将以 `pnpm install` 开头，每个部门为此花费模型步骤与一个回合，忘记安装的部门会在每条验收命令上失败。引擎在程序启动前从存储安装每个工作树，目标禁止安装任何东西。

**在路由上限处销毁组合。** 销毁会拆掉部门仍在使用的 shell 与会话；程序自己的 `stopping` 标志只在部门之间结束一轮。阻塞目标在程序本就回读目标的地方结束尝试，代价是之后每个部门一个被拒的回合。

**新增 `USAGE_LIMIT` 结果或对通知文本做字符串匹配。** 接缝把通知连同重置时间一次性分类为 `QUOTA`；停机读的是这个码与这个延迟，从不读文本。

**用 `ctx.judge.audit` 评审。** 前文已述：评审官按设计复制工作区并隐去 diff；评审员保留评审官的独立性构造，同时阅读 diff。

**每班次一个分支加一个拉取请求。** 企业以自己的身份发运到开发分支；拉取请求需要一个人，而分支上的台账与记录就是评审轨迹。

## Consequences

Harness Core 包管家的工单由一条命令处理：`pnpm run enterprise -- shift --next <n> --push` 从分支携带的台账中选择、处理工单，并把独立评审批准的内容连同其余一切的记录推送出去。每个结果——验收失败的部门、改了 scope 之外路径的部门、驳回的评审、冲突的 squash、移动了的顶端、触及上限的路由——都是一条带原因的台账行与一份带会话日志的记录，未发运也未驳回的工单由后续班次再次尝试。

代价是时间与磁盘：一个班次为每个工作树（各部门、整合、克隆的检出）各安装一次工作区，并在每个部门的验收、程序的整合与重新认证中各运行一次 `pnpm run typecheck`。部门自己的模型回合仍花在阅读本仓库上；工单的预算限制它们，被阻塞的部门被记录而不被恢复。

无密钥 e2e 证明的是在播种仓库与裸远端之上的接线：选择、编译出的标准、评审、部分装配、重新认证、快进推送、向移动了的顶端变基、关闭的台账状态与停机。模型能从一张工单构建出什么，由真实班次记录。

- `pnpm run typecheck`、`pnpm run lint`、`pnpm run knip` 与 `pnpm run doc-sync` 覆盖夹具、脚本、README 对与本 note。
