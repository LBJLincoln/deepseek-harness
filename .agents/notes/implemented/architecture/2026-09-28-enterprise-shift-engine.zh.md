# Agent Note: 企业班次：包管家经由程序工作流处理工单

Status: implemented

[English](2026-09-28-enterprise-shift-engine.md) | 中文

## Problem

[`data/enterprise/`](../../../../data/enterprise/README.md) 下的企业花名册定义了 147 个席位，[`data/enterprise/tickets/`](../../../../data/enterprise/tickets/README.md) 下的工单队列给了 Harness Core 的包管家 21 项针对各自软件包的小而可验证的修改，却没有任何东西让一个席位履行它的职能：没有一个流程会领一张工单、在本仓库的一个工作树里实现它、验证它、让它接受评审，并把它作为企业自己的提交落到开发分支上。[readme-rows 程序](../process/2026-09-27-program-builds-readme-rows.md)已经证明程序工作流可以指向本仓库的一个克隆，它的第一次真实运行也暴露了一个真实部门需要什么——已安装的工作区、在会话目录中工作的路由、按阅读本仓库的量级定下的上限——但它只交付过一份手写的任务陈述一次，由操作者手工准备克隆。工单需要的是一台引擎：一条可由定时任务无人值守运行的命令，对事业部通用，它的每个结果都是它所发运到的分支上的一条台账行与一份记录。

## Decision

[`examples/headless-agent/tests/fixtures/enterprise-shift/`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/README.md) 就是这台引擎，`pnpm run enterprise -- shift [--next <n> | --tickets <id,...>] [--implementer route|subagent] [--model <id>] [--review-model <id>] [--push]`（[`scripts/enterprise.ts`](../../../../scripts/enterprise.ts)）发起它的一个班次。一个班次把开发分支的顶端克隆到一个临时目录，本地仓库不是浅克隆时就从它借用对象；读取并校验克隆中的队列、读取它的台账，于是选择跟随分支而从不跟随某个检出；运行一个部门即为所选工单的程序；评审每个已认证的部门；把获批的部门按每张工单一次 squash 提交装配到基准上；重新认证装配出的树；再连同班次自己的提交——携带台账行与记录——把分支快进推送出去。

**一个程序，工单即部门。** 每张工单是一个键为 `t-nnnn` 的目标，使用 `implementing` 预设，处于工单自己的预算之下，其标准是工单的验收命令，其后跟引擎自己的检查：`engine-committed`（分支在基准之后有提交）、`engine-scope`（针对工单的 scope 与队列策略的生成路径，`git diff --name-only <base> HEAD -- . ':(exclude)<prefix>'…` 列不出任何路径，由 git 自己的 pathspec 决定什么算 scope 之内）、`engine-whitespace`（`git diff --check`），`engine-lint`——队列策略的 `lintRun`（本仓库队列为 `node_modules/.bin/tsx scripts/run-oxlint.ts`），作用于 diff 新增或修改的每个 `.ts`、`.tsx` 与 `.mjs` 文件；`T-0007` 发运了三个 oxlint 错误，它的验收与评审员都没有运行 lint——以及 `engine-documentation`——队列策略的 `documentationRun`（本仓库队列为 `pnpm run verify-translation-pairing`），只要 diff 触及 Markdown 文档就执行，否则不执行即通过；整合的标准与重新认证对合并后与装配后的修改运行同一 linter 与关卡。这道关卡属于队列策略而非工单：部门可能编辑一份工单从未提及的 README，第二个真实班次的 `T-0012` 部门就在 README 点名了它删除的导出时这样做了，而工单的验收无法预见这一点。目标陈述工单、花名册中席位的名称、任务、scope、验收命令、如何让生成文件恢复一致，以及贡献者遵循的规则，把部门指向 `CLAUDE.md` 与包 README 而非粘贴它们。程序的每个工作树——每个部门一个，加上整合的——都在程序启动前添加并离线安装，因为部门的验收会在它的工作树里运行 `pnpm exec vitest` 与 `pnpm run typecheck`，而程序会复用已存在的工作树目录。程序的整合被保留：它合并每个已认证的部门，在合并后的头上重跑每张工单的验收，当所有部门都获批时，它的合并树就是装配结果所对照的摘要。

**一位按评审官方式构建的独立评审员，而不是评审官本身。** 部门认证之后，由一个从未见过它的会话作出裁定：全新的 id、没有父会话也没有种子、`reviewing` 预设——即随产品发布的 `judge` 预设的那套安排，一行 persona、`role: judge` 使读屏障拒绝它访问它所拥有的每个目录与每项权限——用 `tools.restrict({ allow: [] })` 限制掉所有全局工具、一个属于它自己的空工作目录，以及由三条消息派生的历史：常设指令、工单、证据（有上界的 `git diff <base> <revision>`、有上界的分支各提交信息，以及每项检查的状态与有上界的输出）。在这份组合里，让评审员失明的正是这个限制：部署的工具（`bash`、`read`、`edit`……）是没有声明任何权限的全局行，单凭 judge 角色一个也拒绝不了，第一个真实班次的评审员就是在班次的临时目录里创建的，它运行了 `bash`，读到了部门的工作树。提交信息是实现者对修改的自述，随修改一起提交，正是它让评审员得以分辨一句树早已满足的工单陈述与一个 diff 遗漏的步骤。回答的第一行 `verdict: approve|reject` 决定结论，其余是理由；两者都没写的回答视为驳回。没有使用 `ctx.judge.audit`：它会把被审工作区复制到一个新目录以复现该次尝试的树哈希，对本仓库已安装的工作树而言意味着复制 `node_modules`，而且它按设计对评审官隐去 diff 与检查输出，而工单评审恰恰是对照工单阅读 diff。也没有使用程序的 `signoff/recorded`：它记录的是某位主体对某个制品摘要的签名，是驱动在程序打开前就满足的规格冻结与发布关卡，不是模型依据证据得出的结论。评审员的会话日志是它读了什么、答了什么的持久记录，台账行写明了它。评审员运行在自己的路由与模型上，即组合中的 `enterprise-review-model` 条目，台账行在会话旁写明它们；被它驳回的工单留待人工分诊，而不是再次评审（[评审独立性](2026-09-29-enterprise-review-independence.md)）。

**只有获批的工作到达分支，每张工单一次提交。** 获批的部门按工单顺序以 `git merge --squash` 压到基准上；squash 冲突的会被重置并记为 `conflict`，其余仍然装配。引擎自己的提交与推送都带 `--no-verify`：工作树的离线安装会把仓库的 git 钩子装进克隆，这对部门是对的——它们的提交是贡献者的提交——对引擎却是错的：它的 squash 已由工单的验收认证，它的台账提交是机器写出的数据——第一个真实班次死在 pre-commit 钩子里，第三个死在 pre-push 钩子里，后者在克隆根目录里做类型检查，而什么也没装配时那里并未安装。周期自己的数据提交与推送出于同样的原因跳过钩子，转录捕获循环也是如此，它每五分钟一次的推送会在一个三分钟的钩子期间移动分支顶端。克隆中的每一次提交——部门的、squash 的、班次自己的——作者与提交者都是 `Claude <noreply@anthropic.com>`，这是仓库的规则，企业则写在正文里：每次工单提交的信息写明班次（`Shift: Daliesk shift <id>`）、工单、席位、程序 id、部门与评审会话、工单的来源，并以 `Co-Authored-By: <部门所用的模型>` 与操作者的 `Claude-Session:` 行结尾。当所有部门都获批时，装配出的树必须等于程序已认证的合并树；随后先移除程序的各个工作树，再让每张已装配工单的验收在克隆自身的检出里、在装配出的树上再跑一遍：这些工作树位于克隆的目录之内，班次 `081308-24b5` 的 `T-0016` 就因 `doc-sync` 的翻译配对遍历了一个部门的副本（`program-…/t-0016/python/sdk/README.md: missing language switcher`）而未能通过重新认证。推送是一次快进更新：顶端移动了就把装配的提交变基到它上面、在那里重新认证，并围绕新哈希重写台账；变基冲突则什么也不发运，但仍推送台账；循环最多 `ENTERPRISE_PUSH_ROUNDS` 轮（默认 3），从第一次抓取起，经每次变基与重新认证，直到推送，都持有推送锁（`ENTERPRISE_PUSH_LOCK`，默认 `/tmp/dsh-push.lock`，经由 [`scripts/enterprise-push-lock.ts`](../../../../scripts/enterprise-push-lock.ts) 取得，最多等待 `ENTERPRISE_PUSH_LOCK_WAIT` 秒，默认 1800）。开始行的推送、周期的拉取加推送、转录捕获循环的拉取、提交与推送都取同一把锁，因此它们都不会在引擎的窗口内移动顶端：第一次无人值守的发运——班次 `001527-881f` 的 `T-0007`，装配为 `50940d37a3`——三轮全输（`[rejected] … (fetch first)`），因为捕获循环每五分钟推送一次，而变基、重新认证与推送用时更长。在那一次推送之前，除了班次的开始行，没有任何东西到达远端：每个部门经由的 `origin` 的推送 URL 都是不可达的，每个程序工作树自己的配置（`extensions.worktreeConfig`，只在克隆升到仓库格式 1 之后才设置，因为本仓库的安装钩子拒绝带有任何扩展的格式 0 仓库——扩展先于格式设置时，班次 `021357-6546`、`041341-222d` 与 `061342-191b` 都死在每个工作树的安装上）还把推送到任何 URL——本地路径以及 git 所支持的每种传输——都改写为同一个不可达的 URL，因此按远端自己的 URL 推送也会失败，而引擎从不带这种改写的克隆检出推送。这防的是误推；把自己的配置改回去的部门不会被拦住，抓取也不受影响。

**一项检查可以用掉一个部门的墙钟预算，重型检查则取机器的锁。** 程序经由所组合的 shell 运行每项检查，检查的时限就是该 shell 解析出的值：不带超时的 `ctx.shell.resolve({ command, workdir })` 取的是 `dsh-bash-local` 两分钟的默认值，正是它在第三个班次的每一轮里杀掉了 `pnpm run doc-sync`。程序现在带一个可选且经校验的 `checkTimeoutMs`，字段与封顶语义同 `dsh-environment-runner` 的一致，组合把它设为 `2700000`，即部门的墙钟上限，并同时设置执行器的 `maxTimeoutMs: 2700000`，否则执行器会把它封顶在十分钟；执行器两分钟的默认值仍然约束部门自己的命令。重型验收运行——包含 `pnpm run typecheck`、`--coverage` 或 `pnpm run doc-sync` 的命令，即队列策略的 `heavyFragments`——在 `ENTERPRISE_HEAVY_LOCK` 指定一把锁时以 `flock <lock> bash -c '<命令>'` 运行，周期把它导出为 `/tmp/dsh-heavy.lock`：在部门的标准、整合的标准与重新认证中皆然，因此任何两个部门、以及任何取同一把锁的其他智能体的关卡，都不会同时运行其中之一。这个设计在检查运行之处成立：基于 `dsh-subprocess-local` 的 `dsh-bash-local` 不做任何限制（读屏障的 census 报告 shell 为 `unenforced`），因此 `flock` 能打开宿主机上的路径；子进程的环境清洗保留 `ENTERPRISE_HEAVY_LOCK`，它既不像凭据，也没有 `DSH_` 前缀；在时限处被杀的检查会连同它的 `flock` 一起被杀，从而释放锁；检查的时限也涵盖等待锁的时间。命令在 `bash -c` 下运行，因此带管道或引号的重型命令保持原意，驱动拒绝不是由普通字符构成的绝对路径的锁路径。班次本身绝不能在这把重型锁下启动，否则它自己的检查永远取不到锁。

**生成文件属于每张工单的 scope。** 队列策略的 `generatedPaths` 点名本仓库的生成器写出、其文档关卡对照源码校验的文件——`pnpm run doc-sync` 检查的各 `gen-*` 脚本的输出、`verify-type-equiv` 比对其 `type-equiv` 粘贴块的子系统页面，以及它们的中文侧与配对记录——`engine-scope` 在工单自身的 scope 之外也排除它们，因为让某个目录过期的包源码修改必须在该目录所在之处重新生成它，而没有哪张工单能事先知道那是哪个目录。目标写明这一点，也写明怎么做：运行 `doc-sync` 点名的生成器并提交它写出的内容，在两侧更新漂移的 `type-equiv` 块，重新记录两侧有改动的每个配对。评审员读到的工单带同一份清单，其指令把它算作 scope 之内。这份清单属于策略而非生成器：`doc-sync` 仍然逐字节对照生成器校验每个生成文件，因此手工编辑生成区域会使它失败，而在这类页面其他位置的手工编辑则出现在评审员阅读的 diff 里。一项 spec 保证清单中的每个 pathspec 都匹配某个已跟踪的文件。

**引擎作出决定之处不声称任何人。** 无人值守的班次没有人工发布关卡：程序打开前没有人阅读它的规格，推送前也没有人阅读它的装配结果。因此程序以 `requireSignoff: false` 组合，不经 `dsh-signoff` 记录任何东西——按契约，它的记录是一个人的签名，其[治理参考](../../../../docs/subsystems/governance.md)也说作出决定的规则"不是签名"——而 `result.json` 携带 `decisions`：规格冻结与发布，各自点名机器主体 `{ kind: 'machine', id: 'daliesk-enterprise-shift', decidedBy: 'the enterprise-shift engine, shift <id>' }`，覆盖所选工单的 SHA-256。同一周期无人值守运行的受理以同样方式在 `daliesk-enterprise-intake` 名下记录它的两个决定。以人类 `enterprise-operator` 名义的签名会点名一个什么也没决定的人；人所评审的是事后的分支，文档也如此说明。

**进行中的工作不会丢失。** 班次把它的开始行——班次、工单、基准、主机与 pid——追加到 `data/enterprise/shift-starts.jsonl`，在任何部门运行之前推送，并从这次提交切出每个工作树，因此最后的推送仍从远端所持有的内容快进。容器重置会杀掉班次、它的克隆以及每个未推送的提交，却杀不掉开始行：下一个班次发现一条其班次没有写下任何工单行的开始行，就在选择之前以一条 `abandoned: container reset` 行关闭它的每张工单，这条行在队列顺序中算作一次尝试。同一主机上 pid 仍存活的开始行是仍在运行的班次，保持不动。开始行有自己的文件，而不是 `ledger.jsonl` 里的第三种行类型，因为台账的每个读取者（花名册、报告、指挥台、周期记录）都把未知类型的行算作无法读取；abandoned 行则是每个读取者都已理解的普通工单行。无法推送的开始会让班次停止，因为它随后做的工作可能不留一行就消失。

**台账即状态，记录即证据。** `data/enterprise/ledger.jsonl` 每班次每工单新增一行，字段集与读取它的企业职能共用（`type, at, shift, ticket, seat, division, programId, implementer, model, department, checks, review, reviewer, integration, shipped, reason, tokens, seconds`，`reviewer` 只出现在由评审作出裁定的行上）；工单一旦任一行已发运、或最近一行为已驳回即告关闭，在其他任何情况下保持开放。`--next <n>` 按队列顺序取开放工单：尝试次数最少者优先，原因以 `halted: limit` 开头的行不算一次尝试；其次按优先级；再在尝试次数与优先级相同的工单之间让各部门轮流；最后按 id。因此失败过的工单要等每张未尝试的工单都轮到之后才会再被选中，一个部门的积压也不会挡住另一个部门同优先级的工单。引擎的读取器把没有 `type` 的行当作工单行，并跳过其他任何类型，因为企业职能把它们的 `function` 行写进同一个文件。`data/enterprise/shifts/<UTC 日期>-<班次 id>/` 存放 `result.json`、`manifest.json` 与班次的每份会话日志，已用 `data/transcripts/tools/secret-patterns.mjs` 的共用模式遮蔽——转录捕获与受理使用的正是这些模式，电子邮件地址包括在内——并计数。在暂存任何东西之前，已写出的记录会再用这些模式扫描一遍，残存的匹配会在班次提交之前让它停止：它什么也不推送并保留克隆，因为分支上的记录一经发布就无法收回。两者都在装配的提交之后提交，在同一次推送中传播，因此什么也没发运的班次仍然汇报到下一个班次读取的地方。

**路由上限依据接缝的码停机。** 驱动监听第一个失败携带 `QUOTA` 的 `turn/end`——接缝赋予路由用量上限通知的码，重置时间作为 `providerRetryAfterMs`（[上限之墙](2026-09-27-route-limit-halts-the-run.md)）——在一个微任务里以 `route-limit` 阻塞该部门的目标——阻塞是对正在发布该事件的会话的又一次追加——于是程序在没有验证运行的情况下结束该次尝试，让之后的每个部门在第一个被拒的回合上阻塞，不评审不装配任何东西，把 `halted: limit (resets at <instant>)` 写进每张未完成工单的行，推送台账，以 3 退出。

**可安全地无人值守重跑。** 包装器持有写明其 pid 的 `<scratch>/shift.lock`；该 pid 存活期间第二个班次拒绝启动（退出码 4），已死亡班次留下的锁会被替换；满一天的克隆在下一个班次启动时清扫；工作树无法准备或程序抛出异常的班次仍然写出每张工单的行并推送。工单校验器把队列策略作为参数（`HARNESS_QUEUE_POLICY` 强制本仓库的 typecheck 与覆盖率运行，`OPEN_QUEUE_POLICY` 在工单自身的检查之外不作要求），因此播种的 e2e 仓库在同样的 schema、席位、来源与 scope 规则下通过校验。

## Alternatives considered

**每张工单一个程序。** 每张工单的程序会各自整合与发布，一张失败的工单不会阻止其他工单的整合。但班次的工单是一份席位花名册的一个交付物，程序的台账把它们归为一组，程序对全部工单的整合是工作流本身唯一认证合并树的地方；当程序无法整合时，班次装配获批的子集，这正是每工单一程序的设计会合并的同一个子集，却不必每张工单一个程序。

**在程序内部、评审之后才整合。** 程序在部门证书与整合之间没有钩子，为一个自己就能装配获批子集的消费者加一个，会改变工作流。程序的整合保持原样——对每个已认证部门的证书——班次的装配是对评审所批准内容的整合，在两个集合重合时对照程序的合并树校验。

**推送程序的合并修订。** 合并修订是覆盖各部门分支的合并提交，提交信息由模型撰写；推送它会把部门自己的提交与 `program/<id>/<key>` 合并信息落到分支上。每张工单一次 squash 提交携带企业应当写明的信息——工单、席位、程序、会话、模型的署名行——树摘要校验则保证它恰好是程序认证的那棵树。

**cherry-pick 部门的提交。** 部门可能多次提交、可能合并，它的提交信息是它自己的；`git merge --squash` 取分支的树而不问历史，把信息留给班次。

**让部门自己安装依赖。** 目标将以 `pnpm install` 开头，每个部门为此花费模型步骤与一个回合，忘记安装的部门会在每条验收命令上失败。引擎在程序启动前从存储安装每个工作树，目标禁止安装任何东西。

**在路由上限处销毁组合。** 销毁会拆掉部门仍在使用的 shell 与会话；程序自己的 `stopping` 标志只在部门之间结束一轮。阻塞目标在程序本就回读目标的地方结束尝试，代价是之后每个部门一个被拒的回合。

**新增 `USAGE_LIMIT` 结果或对通知文本做字符串匹配。** 接缝把通知连同重置时间一次性分类为 `QUOTA`；停机读的是这个码与这个延迟，从不读文本。

**用 `ctx.judge.audit` 评审。** 前文已述：评审官按设计复制工作区并隐去 diff；评审员保留评审官的独立性构造，同时阅读 diff。

**经由 `dsh-signoff` 以机器身份签署。** `signoff/recorded` 中的 `kind: 'machine'` 主体会在程序会话里留下一条记录，但它会推翻该包"只有人才签署"的契约，而且每个 `requireSignoff` 关卡都必须分辨机器的记录与人的记录才能仍是人工关卡。班次自己的记录改为持有这些机器决定，程序也不组合一个无人能诚实满足的关卡。

**提高执行器的默认超时。** `dsh-bash-local` 的 `timeoutMs` 是所组合 shell 运行的每条命令的默认值，部门自己的 `bash` 调用也包括在内，因此在那里设定检查时限，会让部门回合里一条挂起的命令跑满整个墙钟预算。程序自己的 `checkTimeoutMs` 恰好约束程序作为检查运行的那些命令。

**在整个班次或每个部门外面取重型锁。** 那样班次会在每个模型回合里一直持有机器的锁，而模型回合占了部门的大部分时间，锁下的检查也再也取不到这把锁；只串行化重型命令，模型回合就能与其他智能体的工作重叠。

**把生成文件留在 scope 之外，让部门停下。** 部门的 diff 离开其 scope 时 `engine-scope` 会让它失败，于是第三个班次的 `T-0001` 部门——被告知只改自己的包、工单比写的大时就停下——在目录过期的情况下连续三轮停下；scope 检查与目标必须与关卡所要求的一致。

**每班次一个分支加一个拉取请求。** 企业以自己的身份发运到开发分支；拉取请求需要一个人，而分支上的台账与记录就是评审轨迹。

**用更多推送轮次代替推送锁。** 每一轮都要花几分钟变基与重新认证，而捕获循环每五分钟推送一次，所以每多一轮都输掉同一场竞争；锁为每个取得它的写入者消除了这场竞争，轮次则留给不取锁的写入者。

## Consequences

Harness Core 包管家的工单由一条命令处理：`pnpm run enterprise -- shift --next <n> --push` 从分支携带的台账中选择、处理工单，并把独立评审批准的内容连同其余一切的记录推送出去。每个结果——验收失败的部门、改了 scope 之外路径的部门、驳回的评审、冲突的 squash、移动了的顶端、触及上限的路由——都是一条带原因的台账行与一份带会话日志的记录，未发运也未驳回的工单由后续班次再次尝试。

代价是时间与磁盘：一个班次为每个工作树（各部门、整合、克隆的检出）各安装一次工作区，并在每个部门的验收、程序的整合与重新认证中各运行一次 `pnpm run typecheck`。部门自己的模型回合仍花在阅读本仓库上；工单的预算限制它们，被阻塞的部门被记录而不被恢复。

无密钥 e2e 证明的是在播种仓库与裸远端之上的接线：选择、编译出的标准、评审、部分装配、重新认证、快进推送、向移动了的顶端变基、关闭的台账状态与停机。模型能从一张工单构建出什么，由真实班次记录。

第一个真实班次 `171951-516d`，在 `sonnet` 上处理 `T-0012` 与 `T-0019`（[它的部分记录](../../../../data/enterprise/shifts/2026-09-28-171951-516d/result.json)），端到端地展示了这套工作流，也暴露了围绕它的三个引擎缺陷。两个部门都在第一次尝试就通过认证（21 步与 15 步；每条验收命令与每项引擎检查都通过），程序的整合在第二次运行时通过认证——第一次有一项 `typecheck` 在机器负载下短暂失败，整合会话花了 34 步调查却什么也没提交——`T-0012` 的评审批准，`T-0019` 的评审驳回：工单要求的测试导入改动树里早已存在，只读工单与 diff 的评审员把它的缺席当成了遗漏。随后引擎死在装配里：克隆的 pre-commit 钩子拒绝了 squash 提交，因为克隆根目录从未安装过，异常在写出任何台账行、记录或推送之前逃逸。批准 `T-0012` 的评审员是在对部门工作树运行过 `bash` 之后作出批准的，它自己会话的 census 表明了这一点：部署的工具以全局行的形式到达了它。引擎现在把评审员限制为没有任何工具、给它一个空目录与各提交信息、在自己的提交上带 `--no-verify`，并把装配或收尾中的失败记录下来；`T-0012` 与 `T-0019` 因为没有写出任何一行而保持开放，第二个班次再次领取了它们。

第二个班次 `182951-78a6` 在修好的引擎上处理同样两张工单（[它的记录](../../../../data/enterprise/shifts/2026-09-28-182951-78a6/result.json)随分支一起传播），两张都发运了。每个部门都在第一次尝试就通过认证；每次评审都在没有任何工具的情况下，凭 diff、提交信息与检查输出作出批准——`T-0019` 的评审员从覆盖率运行的输出中读出，一个仍在导入已删除根导出的测试不可能通过，这正是第一个班次的评审员跑去工作树里找的证据；装配出的树等于程序已认证的合并树；两项验收在其上再次通过；一次推送把分支从 `d2cc487f7` 移到 `52c56001d`：`1d6a5d343`（`T-0012`，部门与评审合计 1,047,317 token、547 秒）、`cfe0a75f7`（`T-0019`，475,850 token、376 秒）以及携带两条台账行与记录的班次自身提交，距克隆 35 分钟。企业以自己的身份发运的最初两个提交就是它们——而第一个 `1d6a5d343` 发运了一对两侧都改了、却没有重新记录 `README.i18n.yaml` 的 README，于是分支在记录被重新记录之前一直无法通过 `verify-translation-pairing`：工单的验收（一条 `grep`、包的覆盖率运行、typecheck）与一位不了解本仓库配对规则的评审员都抓不住它，这正是队列策略的文档关卡如今在部门标准、整合与重新认证中所做的事。

第三个班次 `221520-e979` 在 `sonnet` 上处理 `T-0001` 与 `T-0022`（[它的记录](../../../../data/enterprise/shifts/2026-09-28-221520-e979/result.json)），因引擎的三个缺陷什么也没发运。两个部门的每一轮都以 `doc-sync: terminated by SIGTERM` 结束：检查在执行器两分钟的默认值下运行，而它的关卡当时仍在通过，这是工单的任何修改都修不好的。`T-0001` 收窄的类型让 `gen-cordis-catalog`、`gen-doc-graphs` 与 `verify-type-equiv` 报告 `docs/subsystems/core.md`、`packages/extensions/tool-cordis/src/api-catalog.ts` 与 `docs/event-producer-consumer.md` 过期；指令携带了这段输出，生成器不需要构建好的 `lib/`，也没有任何东西给部门的 shell 加沙箱，但每个过期文件都在 `packages/core/agent/` 之外，而部门被告知只改这个 scope、工单比写的大时就停下，于是报告后停下——即便它没停，`engine-scope` 也会要求这样。班次的推送又在全部三轮里被克隆的 pre-push 钩子拒绝，钩子的 `pnpm run typecheck` 在克隆根目录里找不到 `node_modules`，于是记录只能由操作者亲手送到分支上。引擎现在给一项检查部门的墙钟预算，在机器的锁上串行化重型检查，把生成文件算进每张工单的 scope 并写明如何重新生成，推送时也不再运行钩子。
