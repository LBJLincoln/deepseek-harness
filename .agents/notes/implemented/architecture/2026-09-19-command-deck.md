# Agent Note: The Command Deck reads one feed and replays committed fixtures when it does not answer

Status: implemented

English | [中文](2026-09-19-command-deck.zh.md)

## Problem

A customer proof of concept has to show the Daliesk enterprise working — 147 defined agents, the workflows between them, live activity from harness runs, and a code-safety review placed on a target repository's code — on a laptop, in a meeting room, tomorrow. The repository could show the same facts as logs and generated catalogues, but a room full of executives reads a scene, not a JSONL file. Nothing in the repository rendered an agent roster, a program pipeline, or a code-safety result at all.

Three constraints shaped the design and pull against each other. The feed server that supplies this data is written by a different agent, in parallel, so the front end could not wait for it and could not discover its behaviour by running it. The demo must survive a room with no network and no API key, because a proof of concept that shows an empty screen is worse than no proof of concept. And nothing on screen may be mistaken for a live result when it is not, because a claim a client repeats is a claim the repository has to stand behind.

## Decision

**One contract file, two sources behind it.** `deck/contract.ts` is the only place the feed's paths and payloads are written down. `resolveFeed()` sends one `GET /roster` to `NEXT_PUBLIC_FEED_URL` with a 5-second timeout (a cold feed folds every recorded session before its first answer) and returns a base URL: the configured feed when it answers, and the committed fixtures under `public/fixtures` otherwise. Those static files hold the payloads the feed's paths return, and the feed client maps one to the other, so every reader downstream — the store, the three scenes, the panels — is written once against one contract and never learns which source it is reading. A failed probe is not an error state to recover from; it is the other half of a two-valued choice the status bar reports.

**Replay is paced, not dumped.** The stream client reads a recording once and delivers the first 55% immediately as history, then releases the rest a frame every 330 ms, then stays open and silent — the behaviour the live endpoint's own contract describes, produced in the browser so that replay needs no server. Interleaving the recorded phases (department sweeps, findings, the verifier's re-read, judging, integration) rather than laying them down in sequence is what keeps all four pipeline stages populated from the opening seconds. A keyless demo therefore shows an enterprise at work.

**Example data says so, on every view.** In replay mode the header badge reads `REPLAY`, the status footer names the feed it could not reach, and each view carries a standing notice. The notice sits inside the panel rather than once in the shell so that a screenshot of any single view carries the claim with it.

**The fixtures are a snapshot of the feed, never generated.** `scripts/snapshot-fixtures.ts` writes `public/fixtures/` from a running feed: the generated roster, five committed records under `data/`, their session logs folded into event streams, and the two code-safety reviews' details. It refuses a run directory outside `data/` because only committed records have their key material redacted. Every finding replay shows is one a department wrote and the committed examiner re-read at its line, at a named revision. A fabricated finding on a real, well-known target is the one thing in this demo a security-literate reader could catch, and the repository's own records make it unnecessary.

**Frame state never goes through React.** The store keeps `activity` and `bursts` as objects mutated in place and read from `useFrame`; only roster, runs, events and selection are React state. Each scene draws in a handful of calls — instanced meshes for nodes, file blocks and beacons, one additive point layer per glow, one line-segment layer per edge set — so 147 agents, 124 curved edges with their traffic, a pipeline of comets and a lit code city with a beacon per finding leave the frame budget to the grade.

**One grade, four choreographed stages, one keyboard.** `components/three/Stage.tsx` is the single canvas every view renders through: bloom, ACES tone mapping as its own effect (the composer forces `NoToneMapping` on the renderer), film grain and a vignette in one pass, then chromatic aberration, then SMAA on the graded image, over a shared atmosphere of dust and horizon glow. Each stage owns its choreography and nothing else: the enterprise opens on an establishing shot, runs traffic along an edge only while one of its agents has just acted, and flies to a selected node; the process pipeline releases every logged event as a comet from a queue through the Verification, Judging and Integration gates, so recorded history that arrives in one burst is still seen to travel; the code city lights a window grid keyed on each file's path and size, stands a beacon per finding sized by severity, sweeps a wall of light while a department is pending, and flies onto a selected finding; the workflow graph grows an edge as each session first reports and re-frames as tiers are added. `F` hides the panel and `P` walks the four views every thirty seconds behind a title card composed from what the deck has read; any key or click ends the tour. The shell's one keyboard handler in `components/shell/usePresentation.ts` owns every view-level shortcut, so `Esc` clears the selected agent and the selected finding wherever it is pressed and no stage listens for keys itself; the playback keys and `G` are the exceptions, bound by the playback hook and by the Safety view's findings-tour hook and live only on the views that mount them; `G` walks the loaded review's twelve worst findings four and a half seconds apiece by selecting each, so the city's own flight and callout do the work.

**The run's workflow is a fourth view, and time is the run's own.** `deck/layout-workflow.ts` builds a directed graph of the followed run's sessions from the admitted events alone: a program run's root is the session id without a suffix, a child is that id plus `-<name>`, the integration session is the `-@integration` child placed last, and a run without such a root (a fleet, an experiment) tiers its sessions by pipeline stage with no spawn edges, because nothing in it states who started whom. Certificates seal nodes, merges strand into integration, refusals rim red. The timeline cursor is an epoch-millisecond cap on `ts`, not a sequence number, because `seq` counts from one inside each session and orders nothing across them; `deck/playback.ts` advances that cursor from an anchor against `performance.now()` at 1× to 60× and hands back to head-following at the end, and the process view's comet queue releases at its rate multiplied by the speed. The stream client deduplicates on the pair of `sessionId` and `seq` for the same reason: keyed on `seq` alone it kept 404 of the 1,079 frames of a seven-session review and dropped three of its seven certificates.

**A live review has three moments, and each is a transition.** The code city resolves every admitted tool event to at most one inventory file by longest path suffix and flares that building in the acting department's colour, which is the palette's `departmentColor` and therefore the lane's colour in the process view. The launch sequence plays once per run id, on the first render that finds the review running with every department pending and a start inside ninety seconds; the verdict plays when a review the deck has already seen unfinished changes to verified, or ends unverified. A review loaded in its final state plays neither, because nothing happened while anyone was watching. `DeckState.refresh` re-reads a review once more on the refresh that first reports its run as no longer running, because the certificate lands after the last read made while it ran; without that read the deck held a finished review's running snapshot and no verdict could play.

**The cold open and the quality ladder are presentation, not data.** `O`, and the tour's first run, play an eighteen-second sequence whose progress lives in the store's `openingFrame` and is read by the enterprise layers in `useFrame`; the claim card composes its one line only from loaded data, any key or click ends the sequence with the graph whole, and it runs once per page load. The shared stage steps between three quality tiers from drei's `PerformanceMonitor` with hysteresis (two declines drop a tier, four inclines climb one, a tier holds five seconds, two drops fix the ceiling for the session); `?quality=` pins a tier and stops the monitor. Measured at device pixel ratio 2 under software rendering, `medium` costs 0.46× and `low` 0.28× of `high`, which is the "bloom and pixel ratio are the two knobs" consequence made operable. A `dispose={null}` on the tone-mapping primitive had replaced the effect's own `dispose` with `null`, so leaving any view threw in the stage's cleanup and blanked the whole deck; the reconciler never disposes a primitive, so the prop is gone and the hook alone owns disposal.

**The deck is a standalone Next.js program.** Its `tsconfig.json` is its own; it joins neither the host nor the client project-reference aggregate, because it is a browser application built by `next build` rather than a package the repository's `tsc -b` emits.

## Consequences

`pnpm run deck` and `pnpm --dir apps/command-deck build` work from a clean checkout with no key and no feed, and `pnpm run poc` builds the deck, starts the feed and serves the production build in one command for the demonstration machine. Because `pnpm --dir apps/command-deck fixtures` is a snapshot, replay shows what the recorded runs showed and a reviewer can diff `public/fixtures/` against `data/code-safety`; refreshing the fixtures after a new record is one command, not a generator edit.

`DECK_STATIC=1` builds the same views as a static export, and [`deck-pages.yml`](../../../../.github/workflows/deck-pages.yml) publishes it to the repository's GitHub Pages site on every push of the deck's branch: the replay deck at a public URL, with no feed, key or machine behind it. The deck is the whole Pages site, so the documentation workflow's deployment from master replaces it; folding the export into that build is how both would be kept.

Two facts the feed does not carry are derived deck-side and documented as such in the README: a finding's owning department, from its CWE through the table in `deck/departments.ts`, and its verification state, from whether the certificate's `unverified` list names it. If the feed later places a department on the finding, that table becomes dead code and should go.

`pnpm run constraints` reports four violations for this package that cannot be fixed from inside it. `scripts/check-workspace-constraints.ts` treats every `apps/*` directory as a release member — it must not be `private`, it must set `publishConfig.access`, its repository field must name its directory, and its name must appear in that script's `appPackageFiles` policy. A customer proof of concept is not a published package, so the manifest stays `private: true` and the gate stays red until the script grows a case for an app that is not published.

The scenes need WebGL 2 and have no 2D fallback. `prefers-reduced-motion: reduce` opens every stage at rest, cuts to a selection instead of flying, stands each process event as a still dot, holds the city's scan line still, and stops the traffic, the breathing, the pulsing and the chromatic aberration, which is the accessibility floor, not a full alternative rendering. The grade is the dominant frame cost. Measured under software rendering on this host, the shell's post stack costs about 1.4× the frame before it, almost all of it SMAA; the enterprise stage costs 1.15× its predecessor; the code city costs 0.96× because severity and selection moved from a per-frame typed-array rewrite into instanced attributes updated on change. The shared bloom threshold also catches the lit windows at the widest zoom, which softens the city slightly. Bloom and device pixel ratio are the two knobs to turn first on a weak GPU, and the quality tiers turn them on their own; a demonstration machine is pinned to the tier its rehearsal reached.

## Alternatives considered

- **Wait for the feed server, then build against it.** The two halves are written in parallel against one written contract precisely so neither blocks the other; a front end that cannot start without its server also cannot demo without it.
- **Bundle the fixtures as imported JSON.** Simpler, and it would lose the thing that makes the replay convincing: a paced stream exercised by the same subscription the live feed drives, and files a reviewer can read as data. Static files under `public/` keep both, and the pacing runs in the browser, which is what a static host needs.
- **A separate "demo mode" switch.** Two code paths through every view, one of which is only ever exercised in a meeting room. The fallback is instead a base URL, so the demo path is the production path.
- **Invent the code-safety findings.** Faster to write and indefensible in the room. The repository's own recorded reviews already place real findings on their lines at a named revision.
- **A 2D graph (SVG or canvas) for the enterprise.** It would carry the roster and the edges, and none of the reason a client believes the enterprise is real. The 3D scene is the deliverable, not decoration.
- **A grade per stage.** Each scene tuning its own bloom would let the code city sharpen its windows without dimming the enterprise beams, at the price of three grades that drift apart. The one shared composer is what makes the three scenes read as one instrument; a stage that needs a different look changes its materials.
