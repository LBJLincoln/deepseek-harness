# Agent Note：每个阶梯档位一份预算份额

Status: implemented

[English](2026-09-18-per-rung-budget-share.md) | 中文

## Problem

尝试阶梯的每个档位都在组合为整个 cell 设定的上限之下运行。`dsh-budget-policy` 在 `agent/pre-step` 上按会话的累计用量强制执行 `maxTotalTokens`、`maxWallMs` 与可选的成本上限，环境运行器则通过 `ctx.sessionBudgets`——`enforce`、`remainingWallMs` 与 `recordForeignSpend`——把同一批上限应用在每次委派尝试周围。没有任何东西把这份预算划分给各个档位，因此第一次尝试可以花光它。2026-09-08，路由实验的丢弃臂（记录 `data/proving-ground/2026-09-08-bench-e5-drop-candidate-t5`，一条 haiku 然后 opus 的阶梯对上一个 opus 臂，两者都委派给 spawn 实现者）丢掉了两个 cell：廉价的首个档位独自花掉了该 cell 1,500,000 个计费 token 中的 1,493,040 与 1,472,984 个来反复重读自己的记录稿，运行器随后在已被突破的上限上拒绝了强力的第二档位。只有当廉价档位留下足够预算时才会升级的阶梯，度量的是廉价档位，而不是路由。

## Decision

档位声明 `share`：一个位于 `(0, 1]` 的数，即其尝试可以消耗的每项已配置上限的比例；它以 cell 的各项上限为基准度量，而不是以上限剩余量为基准，因此廉价的首个档位无法花掉强力档位的预算。`resolveLadder` 以 `ENVIRONMENT_RUN_INVALID_LADDER` 拒绝落在该范围之外的份额，以及各份额之和超过 1 的阶梯；`run()` 则拒绝在没有预算策略可供分割份额的组合中出现的任何份额。被盖章的阶梯变为 `EnvironmentRunStampRung[]`——即 `EnvironmentRunModel` 加上可选的 `share`——于是 cell 的 arm 身份包含它如何划分自己的预算；`EnvironmentRunModel` 未被改动，stamp 仍保持 `version: 1`，因为档位上的一个可选字段不是结构性的格式变更。记分员的事实与行键、fleet 排行榜行及其 Markdown 单元格、天文台的发布行、其排序键与阶梯单元格，以及实验的计划摘要，都携带该份额。

该策略新增一个公开方法。`ctx.sessionBudgets.boundAttempt(agent, share)` 在会话上设置一组上限——每个都是已经产生的花费加上该项上限的 `share`——并返回这份工作可以消耗的挂钟预算，以及释放该界定的清理函数。界定生效期间，`enforce` 先度量会话自身的上限，再度量这些上限；突破其中一个会记录携带 `scope: 'attempt'` 的 `budget/breach`、驳回该步骤，并让目标保持活跃。运行器恰好围绕一次尝试设置该界定，并在验证之前释放它：route 尝试由该策略自身的 pre-step 检查停止；委派尝试在 cell 剩余挂钟预算与其挂钟上限份额中较小的那个处被取消，随后在子进程的花费被计入之后，再按其上限度量一次。`usage/foreign` 的折叠不变，并且份额只存在于阶梯之中。

## Alternatives considered

- **用一条 `budget/caps` 记录按尝试收紧会话的上限。** 拒绝：该记录只能收紧，因此 cell 永远无法为下一档位取回剩余预算；而且突破被收紧的上限会阻塞目标——那正会结束该 cell，恰是份额要避免的行为。
- **让运行器自带一个 token 计数器并自行停止尝试。** 拒绝：route 尝试正是在 pre-step 检查处被停止的，而对同一份日志的第二次度量会与该策略的折叠产生分歧。决定属于做出它的那个操作。
- **把份额定义为 cell 剩余量的一个比例。** 拒绝：那样一来阶梯的各份额就取决于此前档位碰巧花掉多少，于是同一个臂的两个 cell 会以不同方式划分预算，该臂度量的就会是首个档位的胃口连同它的路由。
- **把预算在阶梯各档位之间平均切分。** 拒绝：阶梯存在的意义是升级，而升级比它所跟随的廉价档位值得更多预算。由部署固定的切分，也是把一个可调参数硬编码在本应属于计划文件的位置。

## Consequences

一份计划可以陈述 cell 的每个档位可以花多少；超出的档位以 attempt 作用域的 `budget/breach` 结束，而本次运行在 cell 保留下来的预算上转入下一档位。仅在份额上不同的两份计划是两场实验，因为 `planDigest` 覆盖了它们；`EXPERIMENT_PLAN_VERSION` 因被摘要的字段变化而升到 `6`。`budget/breach` 的读者现在能区分会话自身的上限（它会阻塞目标）与上限的一份份额（它不会）；未声明作用域的记录就是会话的上限，本次改动之前写出的每一条记录都是如此。被委派档位的 token 与成本份额只在其子进程返回后才被度量，因为这里没有任何环节能观察带外子进程运行期间的花费；挂钟份额是唯一能中途截断这类尝试的上限，运行器 README 陈述了这一限制。

## Testing

运行器的单元测试覆盖了解析边界处以及经由 `run()` 的份额拒绝、在自己 token 份额处被停止并随后转入下一档位的 route 尝试、被计费超出其份额的委派子进程、在自己挂钟上限份额处被取消的委派尝试，以及改为在 cell 剩余量处被取消的委派尝试。预算策略的测试覆盖了这些上限、它们以各项上限而非剩余量为基准的度量、挂钟份额、会话上限的优先次序，以及被驳回的步骤。无密钥的 `attempt-ladder` fixture 运行第三个 cell，其首个档位持有组合 token 上限的千分之五，其 e2e 把该 cell 日志读回：一条 attempt 作用域的越限、没有目标阻塞、第二档位自己的两次请求，以及一份携带该份额的 stamp。
