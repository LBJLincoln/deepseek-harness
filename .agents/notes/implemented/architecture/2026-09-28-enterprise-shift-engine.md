# Agent Note: The enterprise shift: stewards work tickets through the program workflow

Status: implemented

English | [中文](2026-09-28-enterprise-shift-engine.zh.md)

## Problem

The enterprise roster under [`data/enterprise/`](../../../../data/enterprise/README.md) defined 147 seats and the ticket queue under [`data/enterprise/tickets/`](../../../../data/enterprise/tickets/README.md) gave the Harness Core stewards 21 small, verifiable changes to their own packages, but nothing made a seat do its function: no process took a ticket, implemented it in a worktree of this repository, verified it, had it reviewed, and landed it on the development branch as the enterprise's own commit. The [readme-rows program](../process/2026-09-27-program-builds-readme-rows.md) had shown that the program workflow can be pointed at a clone of this repository, and its first real run had exposed what a real department needs — an installed workspace, a route that works in the session's directory, a cap sized for reading this repository — but it delivered one hand-written task statement once, by an operator preparing a clone by hand. The tickets needed an engine: one command a schedule can run unattended, generic over division, whose every outcome is a ledger line and a record on the branch it ships to.

## Decision

[`examples/headless-agent/tests/fixtures/enterprise-shift/`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/README.md) is that engine and `pnpm run enterprise -- shift [--next <n> | --tickets <id,...>] [--implementer route|subagent] [--model <id>] [--push]` ([`scripts/enterprise.ts`](../../../../scripts/enterprise.ts)) launches one shift of it. A shift clones the development branch tip into a scratch directory, borrowing objects from the local repository when it is not shallow; reads and validates the clone's queue and reads its ledger, so selection follows the branch and never a checkout; runs one program whose departments are the selected tickets; reviews every certified department; assembles the approved ones onto the base as one squash commit per ticket; recertifies the assembled tree; and pushes the branch fast-forward with the shift's own commit, which carries the ledger lines and the record.

**One program, the ticket as the department.** Each ticket is one goal keyed `t-nnnn`, on the `implementing` preset, under the ticket's own budget, with a standard of the ticket's acceptance commands followed by three engine checks: `engine-committed` (the branch carries a commit past the base), `engine-scope` (`git diff --name-only <base> HEAD -- . ':(exclude)<prefix>'…` lists nothing, git's own pathspecs deciding what is inside the scope) and `engine-whitespace` (`git diff --check`). The objective states the ticket, the seat's name from the roster, the task, the scope, the acceptance commands, and the rules a contributor follows, pointing the department at `CLAUDE.md` and the package README rather than pasting them. Every worktree of the program — one per department and the integration's — is added and installed offline before the program starts, because a department's acceptance runs `pnpm exec vitest` and `pnpm run typecheck` in its worktree and the program reuses a worktree directory that exists. The program's integration is kept: it merges every certified department and repeats every ticket's acceptance over the merged head, and its merged tree is the digest the assembly is checked against when every department was approved.

**An independent reviewer built the judge's way, not the judge itself.** After a department certifies, a session that never saw it decides: a fresh id with no parent and no seed, the `reviewing` preset — the shipped `judge` preset's arrangement, one persona row, `role: judge` so the read barrier denies it every directory and authority it owns — every global tool restricted away with `tools.restrict({ allow: [] })`, an empty working directory of its own, and a derived history of three messages: the standing instruction, the ticket, and the evidence (the bounded `git diff <base> <revision>`, the bounded messages of the branch's commits, and every check's status and bounded output). The restriction is what makes the reviewer blind in this composition: the deployment's tools (`bash`, `read`, `edit`, …) are global rows carrying no declared authority, so the judge role alone denies none of them, and the first real shift's reviewer, created in the shift's scratch directory, ran `bash` and read the department's worktree. The commit messages are the implementer's own account of the change, committed with it, and are what lets a reviewer tell a ticket sentence the tree already satisfied from a step the diff left out. The answer's first `verdict: approve|reject` line decides and its remainder is the rationale; an answer naming neither rejects. `ctx.judge.audit` was not used: it copies the audited workspace into a fresh directory to reproduce the attempt's tree hash, which for an installed worktree of this repository means copying `node_modules`, and by design it withholds the diff and the check output from the judge, while a ticket review is exactly a reading of the diff against the ticket. The program's `signoff/recorded` was not used either: it records a principal's signature over an artefact digest and is the spec-freeze and release gate the driver satisfies before the program opens, not a verdict a model reaches over evidence. The reviewer's session log is the durable record of what it read and answered, and the ledger line names it.

**Only approved work reaches the branch, as one commit per ticket.** The approved departments are squashed onto the base in ticket order with `git merge --squash`; a squash that conflicts is reset away and recorded as `conflict` while the rest still assemble. The engine's own commits pass `--no-verify`: the offline install of the worktrees installs the repository's git hooks into the clone, which is right for the departments, whose commits are a contributor's, and wrong for the engine, whose squash was certified by the ticket's acceptance and whose ledger commit is machine-written data — the first real shift died in that hook. Each commit's message names the ticket, the seat, the program id, the department and review sessions, the ticket's source, and ends with `Co-Authored-By: <the department's model>` and the operator's `Claude-Session:` line. When every department was approved, the assembled tree must equal the program's certified merged tree; every assembled ticket's acceptance then runs again over the assembled tree in the clone's own checkout. The push is one fast-forward update: when the tip moved, the assembled commits are rebased onto it, recertified there, and the ledger is rewritten around their new hashes; a rebase that conflicts ships nothing and still pushes the ledger; the loop tries three rounds. Nothing reaches the remote before that one push, and every department pushes through an `origin` whose push URL is unreachable.

**The ledger is the status, the record is the evidence.** `data/enterprise/ledger.jsonl` gains one line per ticket per shift with the field set shared with the enterprise functions that read it (`type, at, shift, ticket, seat, division, programId, implementer, model, department, checks, review, integration, shipped, reason, tokens, seconds`); a ticket closes on a shipped or rejected line and stays open on any other. `data/enterprise/shifts/<UTC date>-<shift id>/` holds `result.json`, `manifest.json` and every session log of the shift, credential-shaped strings cut and counted. Both are committed after the assembled commits and travel in the same push, so a shift that shipped nothing still reports where the next shift reads.

**A route limit halts the shift on the seam's code.** The driver listens for the first `turn/end` whose failure carries `QUOTA`, the code the seam gives the route's usage-limit notice with the reset as `providerRetryAfterMs` ([the limit wall](2026-09-27-route-limit-halts-the-run.md)), blocks that department's goal with `route-limit` in a microtask — the block is one more append to the session that is publishing the event — so the program ends the attempt without a validation run, lets every later department block on its first refused turn, reviews and assembles nothing, writes `halted: limit (resets at <instant>)` into every unfinished ticket's line, pushes the ledger, and exits 3.

**Safe to rerun unattended.** The wrapper holds `<scratch>/shift.lock` naming its pid; a second shift refuses to start while that pid is alive (exit 4) and replaces the lock of a shift that died; clones a day old are swept when the next shift starts; a shift whose worktrees cannot be prepared or whose program throws still writes every ticket's line and pushes it. The ticket validator takes its queue policy as a parameter (`HARNESS_QUEUE_POLICY` mandates this repository's typecheck and coverage runs, `OPEN_QUEUE_POLICY` nothing beyond the ticket's own checks), so the seeded e2e repository validates under the same schema, seat, source and scope rules.

## Alternatives considered

**One program per ticket.** Each ticket's program would integrate and release on its own, and a failing ticket would not stop the others' integration. But the shift's tickets are one deliverable of one seat roster, the program's ledger groups them, and the program's integration over all of them is the only place the combined tree is certified by the workflow itself; the shift assembles the approved subset when the program could not integrate, which is the same subset a per-ticket design would have merged, without a program per ticket.

**Integrate only after the review, inside the program.** The program has no hook between a department's certificate and its integration, and adding one would change the workflow for a consumer that can assemble the approved subset itself. The program's integration stays what it is, a certificate over every certified department, and the shift's assembly is the integration of what the review approved, checked against the program's merged tree when the two sets coincide.

**Push the program's merged revision.** The merged revision is a merge commit over department branches whose commit messages the model wrote; pushing it would land the department's own commits and `program/<id>/<key>` merge messages on the branch. One squash commit per ticket carries the message the enterprise owes — ticket, seat, program, sessions, the model's trailer — and the tree-digest check keeps it exactly the tree the program certified.

**Cherry-pick the department's commits.** A department may commit several times, may merge, and its messages are its own; `git merge --squash` takes the branch's tree whatever its history and leaves the message to the shift.

**Let the department install its own dependencies.** The objective would start with `pnpm install`, each department would spend model steps and a round on it, and a department that forgot would fail every acceptance command. The engine installs every worktree from the store before the program starts, and the objective forbids installing anything.

**Dispose the composition on the route limit.** Disposing tears down the shell and the sessions the department is still using; the program's own `stopping` flag ends the pass only between departments. Blocking the goal ends the attempt where the program already reads the goal back, and costs one refused turn per later department.

**A new `USAGE_LIMIT` outcome or a string match on the notice.** The seam classifies the notice as `QUOTA` with its reset once; the halt reads that code and that delay and never the text.

**Reviewing with `ctx.judge.audit`.** Discussed above: the judge copies the workspace and withholds the diff by design; the reviewer keeps the judge's independence construction and reads the diff.

**A per-shift branch and a pull request.** The enterprise ships to the development branch as itself; a pull request needs a person, and the ledger and the record on the branch are the review trail.

## Consequences

The Harness Core stewards' tickets are worked by one command: `pnpm run enterprise -- shift --next <n> --push` selects from the ledger the branch carries, works the tickets, and pushes what an independent review approved together with the record of everything else. Every outcome — a department that failed its acceptance, one that changed a path outside its scope, a review that rejected, a squash that conflicted, a tip that moved, a route that hit its limit — is one ledger line with a reason and one record with the session logs, and a ticket that was not shipped or rejected is tried again by a later shift.

The cost is time and disk: a shift installs the workspace once per worktree (departments, integration, and the clone's checkout) and runs `pnpm run typecheck` in every department's acceptance, in the program's integration, and in the recertification. A department's own model turns still spend on reading this repository; the ticket's budget bounds them and a blocked department is recorded, not resumed.

What the keyless e2e proves is the wiring over a seeded repository and a bare remote: selection, the compiled standard, the review, partial assembly, recertification, the fast-forward push, the rebase onto a moved tip, the closed ledger status, and the halt. What a model can build from a ticket is what the real shifts record.

## Verification

- `pnpm exec vitest run --config vitest.e2e.config.ts examples/headless-agent/tests/enterprise-shift.e2e.ts` runs four shifts against a seeded bare remote: `T-0001,T-0002,T-0004` (one shipped with its commit message and trailers, one failed on its acceptance, one failed on `engine-scope`; the remote carries the ticket commit, the shift commit, the ledger and the record), `T-0003` (certified, rejected, closed), `T-0005` (the tip moved, rebased, recertified, shipped) and the `QUOTA` halt over two tickets (both blocked on their first turn, `halted` lines, exit 3).
- `pnpm exec vitest run examples/headless-agent/tests/enterprise-shift.spec.ts scripts/enterprise.spec.ts scripts/enterprise-tickets.spec.ts` pins ticket selection from the ledger, the compiled checks, the verdict line, the commit message, the redaction, the command line, the lock and the sweep, and the queue policy parameter.
- `pnpm run typecheck`, `pnpm run lint`, `pnpm run knip` and `pnpm run doc-sync` cover the fixture, the script, the README pair and this note.
