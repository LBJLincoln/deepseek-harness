# Agent Note: The enterprise shift: stewards work tickets through the program workflow

Status: implemented

English | [中文](2026-09-28-enterprise-shift-engine.zh.md)

## Problem

The enterprise roster under [`data/enterprise/`](../../../../data/enterprise/README.md) defined 147 seats and the ticket queue under [`data/enterprise/tickets/`](../../../../data/enterprise/tickets/README.md) gave the Harness Core stewards 21 small, verifiable changes to their own packages, but nothing made a seat do its function: no process took a ticket, implemented it in a worktree of this repository, verified it, had it reviewed, and landed it on the development branch as the enterprise's own commit. The [readme-rows program](../process/2026-09-27-program-builds-readme-rows.md) had shown that the program workflow can be pointed at a clone of this repository, and its first real run had exposed what a real department needs — an installed workspace, a route that works in the session's directory, a cap sized for reading this repository — but it delivered one hand-written task statement once, by an operator preparing a clone by hand. The tickets needed an engine: one command a schedule can run unattended, generic over division, whose every outcome is a ledger line and a record on the branch it ships to.

## Decision

[`examples/headless-agent/tests/fixtures/enterprise-shift/`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/README.md) is that engine and `pnpm run enterprise -- shift [--next <n> | --tickets <id,...>] [--implementer route|subagent] [--model <id>] [--review-model <id>] [--push]` ([`scripts/enterprise.ts`](../../../../scripts/enterprise.ts)) launches one shift of it. A shift clones the development branch tip into a scratch directory, borrowing objects from the local repository when it is not shallow; reads and validates the clone's queue and reads its ledger, so selection follows the branch and never a checkout; runs one program whose departments are the selected tickets; reviews every certified department; assembles the approved ones onto the base as one squash commit per ticket; recertifies the assembled tree; and pushes the branch fast-forward with the shift's own commit, which carries the ledger lines and the record.

**One program, the ticket as the department.** Each ticket is one goal keyed `t-nnnn`, on the `implementing` preset, under the ticket's own budget, with a standard of the ticket's acceptance commands followed by the engine's checks: `engine-committed` (the branch carries a commit past the base), `engine-scope` (`git diff --name-only <base> HEAD -- . ':(exclude)<prefix>'…` over the ticket's scope and the queue policy's generated paths lists nothing, git's own pathspecs deciding what is inside the scope), `engine-whitespace` (`git diff --check`), `engine-lint`, the queue policy's `lintRun` (`node_modules/.bin/tsx scripts/run-oxlint.ts` for this repository's queue) over every `.ts`, `.tsx` and `.mjs` file the diff adds or modifies — `T-0007` shipped three oxlint errors that neither its acceptance nor its reviewer ran — and `engine-documentation`, the queue policy's `documentationRun` (`pnpm run verify-translation-pairing` for this repository's queue) executed whenever the diff touches a Markdown document and passed without execution otherwise; the integration's standard and the recertification run the same linter and gate over the merged and the assembled change. The gate belongs to the queue policy rather than to the ticket: a department may edit a README its ticket never mentioned, as the second real shift's `T-0012` department did when the README named the export it removed, and the ticket's acceptance cannot anticipate it. The objective states the ticket, the seat's name from the roster, the task, the scope, the acceptance commands, how to bring a generated file back in line, and the rules a contributor follows, pointing the department at `CLAUDE.md` and the package README rather than pasting them. Every worktree of the program — one per department and the integration's — is added and installed offline before the program starts, because a department's acceptance runs `pnpm exec vitest` and `pnpm run typecheck` in its worktree and the program reuses a worktree directory that exists. The program's integration is kept: it merges every certified department and repeats every ticket's acceptance over the merged head, and its merged tree is the digest the assembly is checked against when every department was approved.

**An independent reviewer built the judge's way, not the judge itself.** After a department certifies, a session that never saw it decides: a fresh id with no parent and no seed, the `reviewing` preset — the shipped `judge` preset's arrangement, one persona row, `role: judge` so the read barrier denies it every directory and authority it owns — every global tool restricted away with `tools.restrict({ allow: [] })`, an empty working directory of its own, and a derived history of three messages: the standing instruction, the ticket, and the evidence (the bounded `git diff <base> <revision>`, the bounded messages of the branch's commits, and every check's status and bounded output). The restriction is what makes the reviewer blind in this composition: the deployment's tools (`bash`, `read`, `edit`, …) are global rows carrying no declared authority, so the judge role alone denies none of them, and the first real shift's reviewer, created in the shift's scratch directory, ran `bash` and read the department's worktree. The commit messages are the implementer's own account of the change, committed with it, and are what lets a reviewer tell a ticket sentence the tree already satisfied from a step the diff left out. The answer's first `verdict: approve|reject` line decides and its remainder is the rationale; an answer naming neither rejects. `ctx.judge.audit` was not used: it copies the audited workspace into a fresh directory to reproduce the attempt's tree hash, which for an installed worktree of this repository means copying `node_modules`, and by design it withholds the diff and the check output from the judge, while a ticket review is exactly a reading of the diff against the ticket. The program's `signoff/recorded` was not used either: it records a principal's signature over an artefact digest and is the spec-freeze and release gate the driver satisfies before the program opens, not a verdict a model reaches over evidence. The reviewer's session log is the durable record of what it read and answered, and the ledger line names it. The reviewer runs on its own route and model, the composition's `enterprise-review-model` entry, which the ledger line names beside the session, and a ticket it rejected is held for human triage rather than reviewed again ([review independence](2026-09-29-enterprise-review-independence.md)).

**Only approved work reaches the branch, as one commit per ticket.** The approved departments are squashed onto the base in ticket order with `git merge --squash`; a squash that conflicts is reset away and recorded as `conflict` while the rest still assemble. The engine's own commits and its push pass `--no-verify`: the offline install of the worktrees installs the repository's git hooks into the clone, which is right for the departments, whose commits are a contributor's, and wrong for the engine, whose squash was certified by the ticket's acceptance and whose ledger commit is machine-written data — the first real shift died in the pre-commit hook, the third in the pre-push hook, which typechecks the clone's root, uninstalled when nothing was assembled. The cycle's own data commits and pushes skip the hooks for the same reason, as the transcript capture loop does, whose five-minute pushes move the tip during a three-minute hook. Every commit of the clone — a department's, a squash, the shift's — is authored and committed as `Claude <noreply@anthropic.com>`, the repository's rule, and the enterprise is named in the body: each ticket commit's message names the shift (`Shift: Daliesk shift <id>`), the ticket, the seat, the program id, the department and review sessions, the ticket's source, and ends with `Co-Authored-By: <the department's model>` and the operator's `Claude-Session:` line. When every department was approved, the assembled tree must equal the program's certified merged tree; every assembled ticket's acceptance then runs again over the assembled tree in the clone's own checkout, once the program's worktrees are removed: they live inside the clone's directory, and shift `081308-24b5` failed `T-0016`'s recertification because `doc-sync`'s translation pairing walked a department's copy (`program-…/t-0016/python/sdk/README.md: missing language switcher`). The push is one fast-forward update: when the tip moved, the assembled commits are rebased onto it, recertified there, and the ledger is rewritten around their new hashes; a rebase that conflicts ships nothing and still pushes the ledger; the loop tries `ENTERPRISE_PUSH_ROUNDS` rounds (default 3), holding the push lock (`ENTERPRISE_PUSH_LOCK`, default `/tmp/dsh-push.lock`, taken through [`scripts/enterprise-push-lock.ts`](../../../../scripts/enterprise-push-lock.ts) and waited for up to `ENTERPRISE_PUSH_LOCK_WAIT` seconds, default 1800) from its first fetch through every rebase and recertification to the push. The start push, the cycle's pull-and-push and the transcript capture loop's pull, commit and push take the same lock, so none of them moves the tip inside the engine's window: the first unattended ship, `T-0007` of shift `001527-881f`, assembled as `50940d37a3`, lost all three rounds (`[rejected] … (fetch first)`) because the capture loop pushes every five minutes and the rebase, the recertification and the push took longer. Nothing but the shift's start line reaches the remote before that one push: every department pushes through an `origin` whose push URL is unreachable, and every program worktree's own config (`extensions.worktreeConfig`, set only after the clone is raised to repository format 1, because this repository's install hook refuses a format-0 repository carrying any extension — shifts `021357-6546`, `041341-222d` and `061342-191b` died at every worktree's install while the extension came first) rewrites a push to any URL — a local path and every transport git speaks — to that same unreachable URL, so a push by the remote's own URL fails too, while the engine pushes from the clone's checkout, which carries no such rewrite. It contains a mistaken push; a department that rewrites its own config back is not stopped, and fetching is untouched.

**A check may take a department's wall budget, and a heavy one takes the machine's lock.** The program runs every check through the composed shell, and a check's time limit is whatever that shell resolves: `ctx.shell.resolve({ command, workdir })` with no timeout took `dsh-bash-local`'s default of two minutes, which killed `pnpm run doc-sync` in every round of the third shift. The program now carries an optional validated `checkTimeoutMs`, the same field and cap semantics `dsh-environment-runner` has, and the composition sets it to `2700000`, the department wall ceiling, beside the executor's `maxTimeoutMs: 2700000`, without which the executor would cap it at ten minutes; the executor's two-minute default still bounds a department's own commands. The heavy acceptance runs — a command containing `pnpm run typecheck`, `--coverage` or `pnpm run doc-sync`, the queue policy's `heavyFragments` — run as `flock <lock> bash -c '<command>'` when `ENTERPRISE_HEAVY_LOCK` names a lock, which the cycle exports as `/tmp/dsh-heavy.lock`: in the department's standard, in the integration's and in the recertification, so no two departments and no other agent's gate taking the same lock run one at the same time. That design holds where the checks run: `dsh-bash-local` over `dsh-subprocess-local` confines nothing (the read barrier's census reports the shell `unenforced`), so `flock` opens the host path; the subprocess scrub keeps `ENTERPRISE_HEAVY_LOCK`, which is neither credential-shaped nor `DSH_`-prefixed; a check killed at its limit takes its `flock` with it and so releases the lock; and the check's limit covers the wait for the lock. The command runs under `bash -c` so a heavy command with pipes or quotes keeps its meaning, and the driver refuses a lock path that is not an absolute path of plain characters. A shift must never be started under the heavy lock itself, because its own checks could then never take it.

**The generated files are inside every ticket's scope.** The queue policy's `generatedPaths` name what this repository's generators write and its documentation gates verify against the source — the outputs of the `gen-*` scripts `pnpm run doc-sync` checks, the subsystem pages whose `type-equiv` pastes `verify-type-equiv` compares, and their Chinese sides and pair records — and `engine-scope` excludes them beside the ticket's own scope, because a change to a package's source that makes a catalog stale must regenerate it wherever the catalog lives, and no ticket can know in advance which catalog that is. The objective says so and says how: run the generator `doc-sync` names and commit what it writes, update a drifted `type-equiv` block on both sides, re-record every pair whose sides changed. The reviewer's ticket carries the same list, which its instruction counts inside the scope. The list belongs to the policy rather than to the generators: `doc-sync` still verifies each generated file byte for byte against its generator, so a hand edit of a generated region fails it, and a hand edit elsewhere in such a page is in the diff the reviewer reads. A spec keeps every listed pathspec matching a tracked file.

**No person is claimed where the engine decided.** An unattended shift has no human release gate: no person reads its spec before the program opens or its assembly before the push. The program is therefore composed with `requireSignoff: false`, nothing is recorded through `dsh-signoff` — whose record is by contract a person's signature, and whose [governance reference](../../../../docs/subsystems/governance.md) calls a rule that decides "not a signature" — and `result.json` carries `decisions`: the spec freeze and the release, each naming the machine principal `{ kind: 'machine', id: 'daliesk-enterprise-shift', decidedBy: 'the enterprise-shift engine, shift <id>' }` over the SHA-256 of the selected tickets. The intake, which the same cycle runs unattended, records its two decisions the same way under `daliesk-enterprise-intake`. A signature in the name of a human `enterprise-operator` would name a person who decided nothing; what a person reviews is the branch afterwards, and the documentation says so.

**Nothing in flight is lost.** A shift appends its start line — the shift, its tickets, the base, the host and the pid — to `data/enterprise/shift-starts.jsonl` and pushes it before any department runs, and cuts every worktree from that commit, so the final push still fast-forwards from what the remote holds. A container reset kills the shift, its clone, and every unpushed commit, but not the start line: the next shift finds a start whose shift wrote no ticket line and closes each of its tickets with an `abandoned: container reset` line, which counts as an attempt in the queue order, before it selects. A start on the same host whose pid is alive is a shift still running and is left alone. The start lines have their own file rather than a third line type in `ledger.jsonl`, because every reader of the ledger (the roster, the report, the deck, the cycle record) counts a line of an unknown type as unreadable; the abandoned lines are ordinary ticket lines every reader already understands. A start that cannot be pushed stops the shift, since work it then did could vanish without a line.

**The ledger is the status, the record is the evidence.** `data/enterprise/ledger.jsonl` gains one line per ticket per shift with the field set shared with the enterprise functions that read it (`type, at, shift, ticket, seat, division, programId, implementer, model, department, checks, review, reviewer, integration, shipped, reason, tokens, seconds`, `reviewer` only on a line a review decided); a ticket closes on a shipped or rejected line and stays open on any other. `--next <n>` takes the open tickets in queue order: fewest attempts first, a line whose reason starts `halted: limit` not counting as one; then priority; then each division in turn among tickets of the same attempts and priority; then id. A ticket that failed therefore waits until every untried ticket had its turn, and one division's backlog does not hold back another division's tickets of the same priority. The engine's reader takes a line without `type` as a ticket line and skips every other type, because the enterprise functions write their `function` lines into the same file. `data/enterprise/shifts/<UTC date>-<shift id>/` holds `result.json`, `manifest.json` and every session log of the shift, masked with the shared patterns of `data/transcripts/tools/secret-patterns.mjs` — the ones the transcript capture and the intake use, e-mail addresses included — and counted. The written record is scanned again with those patterns before anything is staged, and a match that survived stops the shift before its commit: it pushes nothing and keeps the clone, because a record on the branch is published and cannot be taken back. Both are committed after the assembled commits and travel in the same push, so a shift that shipped nothing still reports where the next shift reads.

**A route limit halts the shift on the seam's code.** The driver listens for the first `turn/end` whose failure carries `QUOTA`, the code the seam gives the route's usage-limit notice with the reset as `providerRetryAfterMs` ([the limit wall](2026-09-27-route-limit-halts-the-run.md)), blocks that department's goal with `route-limit` in a microtask — the block is one more append to the session that is publishing the event — so the program ends the attempt without a validation run, lets every later department block on its first refused turn, reviews and assembles nothing, writes `halted: limit (resets at <instant>)` into every unfinished ticket's line, pushes the ledger, and exits 3.

**Safe to rerun unattended.** The wrapper holds `<scratch>/shift.lock` naming its pid; a second shift refuses to start while that pid is alive (exit 4) and replaces the lock of a shift that died; clones a day old are swept when the next shift starts; a shift whose worktrees cannot be prepared or whose program throws still writes every ticket's line and pushes it. The ticket validator takes its queue policy as a parameter (`HARNESS_QUEUE_POLICY` mandates this repository's typecheck and coverage runs, `OPEN_QUEUE_POLICY` nothing beyond the ticket's own checks), so the seeded e2e repository validates under the same schema, seat, source and scope rules.

## Alternatives considered

**One program per ticket.** Each ticket's program would integrate and release on its own, and a failing ticket would not stop the others' integration. But the shift's tickets are one deliverable of one seat roster, the program's ledger groups them, and the program's integration over all of them is the only place the combined tree is certified by the workflow itself; the shift assembles the approved subset when the program could not integrate, which is the same subset a per-ticket design would have merged, without a program per ticket.

**Integrate only after the review, inside the program.** The program has no hook between a department's certificate and its integration, and adding one would change the workflow for a consumer that can assemble the approved subset itself. The program's integration stays what it is, a certificate over every certified department, and the shift's assembly is the integration of what the review approved, checked against the program's merged tree when the two sets coincide.

**Push the program's merged revision.** The merged revision is a merge commit over department branches whose commit messages the model wrote; pushing it would land the department's own commits and `program/<id>/<key>` merge messages on the branch. One squash commit per ticket carries the message the enterprise owes — ticket, seat, program, sessions, the model's trailer — and the tree-digest check keeps it exactly the tree the program certified.

**Cherry-pick the department's commits.** A department may commit several times, may merge, and its messages are its own; `git merge --squash` takes the branch's tree whatever its history and leaves the message to the shift.

**Let the department install its own dependencies.** The objective would start with `pnpm install`, each department would spend model steps and a round on it, and a department that forgot would fail every acceptance command. The engine installs every worktree from the store before the program starts, and the objective forbids installing anything.

**Dispose the composition on the route limit.** Disposing tears down the shell and the sessions the department is still using; the program's own `stopping` flag ends the pass only between departments. Blocking the goal ends the attempt where the program already reads the goal back, and costs one refused turn per later department.

**A new `USAGE_LIMIT` outcome or a string match on the notice.** The seam classifies the notice as `QUOTA` with its reset once; the halt reads that code and that delay and never the text.

**Reviewing with `ctx.judge.audit`.** Discussed above: the judge copies the workspace and withholds the diff by design; the reviewer keeps the judge's independence construction and reads the diff.

**Sign as a machine through `dsh-signoff`.** A `kind: 'machine'` principal in `signoff/recorded` would keep a record in the program session, but it would reverse that package's contract that only a person signs, and every `requireSignoff` gate would then have to tell a machine's record from a person's to stay a human gate. The shift's own record holds the machine decisions instead, and the program composes no gate that nobody could honestly satisfy.

**Raise the executor's default timeout.** `dsh-bash-local`'s `timeoutMs` is the default of every command the composed shell runs, the department's own `bash` calls included, so a check limit set there would let a hung command in a department's turn run for the whole wall budget. The program's own `checkTimeoutMs` bounds exactly the commands the program runs as checks.

**Take the heavy lock around the whole shift, or around each department.** The shift would then hold the machine's lock through every model turn, which is most of a department's time, and a check under it could never take the lock again; serializing the heavy commands alone lets model turns overlap every other agent's work.

**Leave the generated files out of scope and let the department stop.** `engine-scope` fails a department whose diff leaves its scope, so the third shift's `T-0001` department, told to change only its package and to stop when the ticket turned out larger, stopped three rounds in a row with the catalogs stale; the scope check and the objective have to agree with what the gates require.

**A per-shift branch and a pull request.** The enterprise ships to the development branch as itself; a pull request needs a person, and the ledger and the record on the branch are the review trail.

**More push rounds instead of a push lock.** Every round rebases and recertifies for minutes while the capture loop pushes every five minutes, so each added round loses the same race; the lock removes the race for every writer that takes it, and the rounds remain for a writer that does not.

## Consequences

The Harness Core stewards' tickets are worked by one command: `pnpm run enterprise -- shift --next <n> --push` selects from the ledger the branch carries, works the tickets, and pushes what an independent review approved together with the record of everything else. Every outcome — a department that failed its acceptance, one that changed a path outside its scope, a review that rejected, a squash that conflicted, a tip that moved, a route that hit its limit — is one ledger line with a reason and one record with the session logs, and a ticket that was not shipped or rejected is tried again by a later shift.

The cost is time and disk: a shift installs the workspace once per worktree (departments, integration, and the clone's checkout) and runs `pnpm run typecheck` in every department's acceptance, in the program's integration, and in the recertification. A department's own model turns still spend on reading this repository; the ticket's budget bounds them and a blocked department is recorded, not resumed.

What the keyless e2e proves is the wiring over a seeded repository and a bare remote: selection, the compiled standard, the review, partial assembly, recertification, the fast-forward push, the rebase onto a moved tip, the closed ledger status, and the halt. What a model can build from a ticket is what the real shifts record.

The first real shift, `171951-516d` over `T-0012` and `T-0019` on `sonnet` ([its partial record](../../../../data/enterprise/shifts/2026-09-28-171951-516d/result.json)), showed the workflow end to end and three faults of the engine around it. Both departments certified on their first attempt (21 and 15 steps; every acceptance command and every engine check passed), the program's integration certified on its second run after one transient `typecheck` failure under machine load that the integration session spent 34 steps investigating without committing anything, the `T-0012` review approved and the `T-0019` review rejected — the ticket asked for a test import change the tree already had, and a reviewer reading only the ticket and the diff took its absence as an omission. The engine then died in the assembly: the clone's pre-commit hook refused the squash commit because the clone root was never installed, and the exception escaped before a ledger line, a record, or a push. The reviewer that approved `T-0012` had done so after running `bash` over the department's worktree, which the census of its own session shows: the deployment's tools reached it as global rows. The engine now restricts the reviewer to no tool, gives it an empty directory and the commit messages, passes `--no-verify` on its own commits, and records a failure in the assembly or the finalize; `T-0012` and `T-0019` stayed open, because no line was written, and the second shift took them again.

The second shift, `182951-78a6` over the same two tickets on the fixed engine ([its record](../../../../data/enterprise/shifts/2026-09-28-182951-78a6/result.json) travels on the branch), shipped both. Each department certified on its first attempt; each review approved with no tool, from the diff, the commit messages and the check outputs — the `T-0019` reviewer read from the coverage run's output that a test still importing the removed root export could not have passed, which is the evidence the first shift's reviewer went to the worktree for; the assembled tree equalled the program's certified merged tree; both acceptances passed again over it; and one push moved the branch from `d2cc487f7` to `52c56001d`: `1d6a5d343` (`T-0012`, 1,047,317 tokens and 547 s of department and review time), `cfe0a75f7` (`T-0019`, 475,850 tokens and 376 s) and the shift's own commit with the two ledger lines and the record, 35 minutes after the clone. The first commits the enterprise shipped as itself are those two — and the first, `1d6a5d343`, shipped a README pair edited on both sides without its re-recorded `README.i18n.yaml`, so the branch failed `verify-translation-pairing` until the record was re-recorded: neither the ticket's acceptance (a `grep`, the package's coverage run, the typecheck) nor a reviewer with no knowledge of the repository's pairing rule could catch it, which is what the queue policy's documentation gate now does in the department's standard, the integration and the recertification.

The third shift, `221520-e979` over `T-0001` and `T-0022` on `sonnet` ([its record](../../../../data/enterprise/shifts/2026-09-28-221520-e979/result.json)), shipped nothing, for three faults of the engine. Every round of both departments ended with `doc-sync: terminated by SIGTERM`: the check ran under the executor's two-minute default while its gates were still passing, which no change of the ticket's could fix. `T-0001`'s narrowed type made `gen-cordis-catalog`, `gen-doc-graphs` and `verify-type-equiv` report `docs/subsystems/core.md`, `packages/extensions/tool-cordis/src/api-catalog.ts` and `docs/event-producer-consumer.md` stale; the directive carried that output, the generators need no built `lib/`, and nothing sandboxed the department's shell, but every stale file was outside `packages/core/agent/`, and the department, told to change only that scope and to stop when the ticket turned out larger, reported it and stopped, which `engine-scope` would have required anyway. And the shift's push was refused in all three rounds by the clone's pre-push hook, whose `pnpm run typecheck` found no `node_modules` in the clone's root, so the record reached the branch only by the operator's hand. The engine now gives a check the department's wall budget, serializes the heavy ones on the machine's lock, counts the generated files inside every ticket's scope and says how to regenerate them, and pushes without the hook.

## Verification

- `pnpm exec vitest run --config vitest.e2e.config.ts examples/headless-agent/tests/enterprise-shift.e2e.ts` runs four shifts against a seeded bare remote whose every offline install runs this repository's install hook in its `--check` mode, every clone carrying a pre-push hook that refuses every push, which the test shows by a push that runs it, and every shift under a heavy lock of its own, which the seeded heavy check of `T-0001` passes only while held; the first shift's program session carries no `signoff/recorded` and its record names the machine principal of both decisions: `T-0001,T-0002,T-0004` (one shipped with its commit message and trailers, one failed on its acceptance, one failed on `engine-scope`; the remote carries the ticket commit, the shift commit, the ledger and the record), `T-0003` (certified, rejected, closed, and a start line from another host without an end closed as abandoned while a live one on this host is left alone), `T-0005` (the tip moved, rebased, recertified, shipped) and the `QUOTA` halt over two tickets (both blocked on their first turn, `halted` lines, exit 3).
- `pnpm exec vitest run examples/headless-agent/tests/enterprise-shift.spec.ts scripts/enterprise.spec.ts scripts/enterprise-tickets.spec.ts` pins ticket selection from the ledger, the compiled checks with the heavy lock and the generated paths, the objective and the reviewer's ticket, the verdict line, the commit message, the redaction, the command line, the lock and the sweep, the queue policy parameter, and that every generated pathspec matches a tracked file.
- `pnpm exec vitest run packages/improvement/program/` pins that every check and gate runs under `checkTimeoutMs` and every `git` command under the executor default; `pnpm exec vitest run scripts/enterprise-cycle-record.spec.ts` runs the cycle script past a pre-push hook that refuses every push and checks that the shift receives the heavy lock and the push lock and that a final ship whose push lock another writer holds pushes nothing; `pnpm exec vitest run scripts/enterprise-push-lock.spec.ts` shows that a writer holding the push lock from its fetch to its push is not overtaken by a pusher that takes the lock as the cycle does, while the same pusher overtakes a writer that does not hold it.
- `pnpm run typecheck`, `pnpm run lint`, `pnpm run knip` and `pnpm run doc-sync` cover the fixture, the script, the README pair and this note.
