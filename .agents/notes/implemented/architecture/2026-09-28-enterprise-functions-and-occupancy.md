# Agent Note: The enterprise's ticketless functions and the occupancy rule

Status: implemented

English | [中文](2026-09-28-enterprise-functions-and-occupancy.zh.md)

## Problem

The roster under `data/enterprise/` defines 147 seats, and until this change only 19 had ever been occupied — every one of them by a recorded session a code-safety review or a bench run happened to produce — and `counts.active` was fixed at `0`. Nothing made a Verification, Judging, Observatory or Curation seat do its job on a schedule, nothing recorded such work when it happened, and the two counts a viewer reads first, occupied and active, had no rule behind them that a deliverable could satisfy. The operator's goal for the enterprise was to exist: seats doing their real functions on this repository on a schedule, every deliverable recorded, occupancy counted only from evidence, and all of it visible in public. The engine that ships tickets through programs covers the Harness Core stewards; the divisions whose work is not a ticket — running a gate, ruling on a CI lane, folding telemetry, keeping score — needed their own runner, one record for both kinds of work, one rule that turns that record into occupancy, and a public view that reads the same record.

## Decision

**One ledger, two line types.** `data/enterprise/ledger.jsonl` is the organisation's record, append-only under [the ledger gate](../process/2026-09-29-tamper-evident-enterprise-ledger.md). The engine appends a *ticket line* per worked ticket (`type: "ticket"`, or no `type` at all) with the department's outcome, the acceptance checks, the review verdict, the integration outcome and the shipped commit or `null`; `scripts/enterprise-functions.ts` appends a *function line* per seat that performed a function on a commit (`type: "function"`) with the function's name, the target commit, `pass` | `fail` | `error`, the evidence as a repository path it wrote or a URL it read, and its duration. `scripts/enterprise-ledger.ts` owns both types: it reads the file as the durable boundary it is, keeping every line that carries the fields a reader relies on and reporting the rest by line number, and it derives a ticket's status from its line — `shipped` by a commit, `rejected` by a failed check or a non-approving verdict, `halted` otherwise, `queued` with no line.

**The occupancy rule counts deliverables and nothing else.** A seat is occupied only by a recorded deliverable: a ledger line naming its id exactly, or a recorded session `scripts/roster-evidence.ts` attributes to it. A seat is active when its newest deliverable — a line by its `at`, a session by the newest time its record logged — falls inside the 24 hours ending at the moment the occupancy is computed. `occupancyOf` in `scripts/enterprise-ledger.ts` is the one implementation; the roster generator, the functions runner's telemetry snapshot and the deck's published report all call it. The generated roster carries each seat's `ledger: { lines, lastAt? }` beside its session `evidence`, a top-level `ledger` naming the file, the lines read and the lines naming no seat, `activeWindow` (the 24 hours ending at `generatedAt`), `counts.occupied` and `counts.active` by the rule, and `status: "active"` for exactly the active seats. The window is measured at `generatedAt`, not at read time, so the file is a snapshot with a stated moment that regenerates byte-identically over unchanged inputs; every new line or record restamps it and measures the window afresh. The feed's `GET /roster` keeps its own meaning — status and `counts.active` from discovered sessions alone, a seat no session occupies reading `"defined"` whatever the file says — because the feed is the live view and the file is the record.

**Each ticketless division has one function, run by one command.** `pnpm run enterprise:functions -- [--commit <sha>] [--shift <id>] [--branch <name>] [--only <divisions>] [--lock <file>]` runs on the checked-out commit and appends progressively, so a division that fails after another recorded its lines loses nothing; on a shared machine `--lock` makes each gate take the named `flock` file only while it runs, so the run never holds the machine's heavy-command lock for a whole shift:

- *Verification*: each verifier seat runs the root package script its `source` names, one after another — a gate that judges nothing without a build, `verify-doc-site-fragments`, through `docs:build:mpa`, the script that builds and then verifies as CI's static lane does — with a gate's exit code as its outcome, a spawn failure or timeout as `error`, and the command, commit, outcome and output tail written under `data/enterprise/functions/<shift>/<seat>.log` as the evidence. A seat whose script the root `package.json` lacks fails the run before anything is recorded.
- *Judging*: the judges read the Branch CI run of the commit from GitHub's REST API without credentials, through the proxy `HTTPS_PROXY` names when the environment names one (Node's `fetch` honours it only under `NODE_USE_ENV_PROXY=1`, which the package script sets; a read that bypasses the proxy goes out unauthenticated from a shared address whose limit is soon spent, and the judges then stay vacant with that hint) — the newest completed run whose lanes rendered a verdict, so a run cancelled by a later push is passed over, and the branch's newest such run when the commit has none, its commit then named in `target.commit` with the asked-for one in `target.requested`. A job maps to the seat of the gate mode its log opens with; a gate group a job's log shows by name (`GATE_GROUPS`: `ci-lint-contracts-ready`, `ci-snapshot`, `ci-artifacts`) maps to that group's seat, `pass` when every gate passed, `fail` when one failed, `error` when one was skipped after a failed dependency, and no line when the log does not show them all. The job's page is the evidence and its completion time the line's `at`; a verdict already in the ledger for the same seat and job is not appended again. A judge with no lane on this fork (the primary and Windows lanes) is vacant with the reason, and an API failure leaves every judge vacant with the failure as the reason while the other divisions run.
- *Observatory*: the session-stats observer folds its package's real `sessionStats` projection unit over every recorded session — the committed records and any shift records under `data/enterprise/shifts/` — and publishes `data/enterprise/telemetry.json`: sessions and tokens in the last 24 hours and in total, the unit's turns, steps, model and tool wall time, and seats occupied and active per division by the rule over the ledger as it stands, this run's earlier lines included. The other five observer seats are vacant with the reason each package's function needs a running backend, collector, store or registry that nothing here composes over committed records.
- *Curation & Data*: the scorekeeper folds the scorekeeper package's session facts and scoreboard over the same sessions into `data/enterprise/scoreboard.json`. The note and fixture curators are vacant: curation is ticketed work.

**The public view reads the record.** `pnpm run enterprise:publish` regenerates the deck's static data from the roster, the ledger and the ticket queue: the roster fixture as a byte copy, and `enterprise.json`, which the Enterprise view's Ledger tab shows — seats occupied and active per division, the day's tickets by status, the day's function runs by shift, and the latest shipped commits with the CI verdicts recorded on them. The deck lights a seat by the same rule (`isOccupied` reads sessions and ledger lines), rings an active one through the status the roster already carries, and leads with what the window delivered before the seats defined, occupied and active, the active ones split by the kind of work their deliverables were ([the headline figures note](../process/2026-09-29-headline-figures-and-daliesk-identity.md)). The report is a pure function of its inputs, rewritten only when its bytes change, and `deck-pages.yml` republishes the Pages site on every push of the deck's branch that touches `apps/command-deck/**`.

## Verification

`scripts/enterprise-ledger.spec.ts` pins the line parsing, the tolerant read, the ticket status reading and the occupancy rule at its edges (a line at the window's start is active, one a millisecond after its end is not; a session older than the window occupies without activating). `scripts/enterprise-functions.spec.ts` runs the functions against a scripted gate runner and a recorded GitHub reader built from the real lanes' logs: every verifier's script runs and its real outcome and log are recorded; the commit's run yields one verdict per lane and per gate group shown by name and none for the lanes this fork lacks; the branch fallback names the requested commit; a cancelled run is passed over; an unreadable API leaves the judges vacant with the failure while the observatory still publishes; a verdict is never appended twice; the telemetry and scoreboard snapshots fold a committed record and count the ledger's seats. `scripts/enterprise-roster.spec.ts` proves the roster counts ledger lines exactly by seat id, activates by the window against the stamp, reproduces the committed file over exactly the records and lines it names, and keeps an unchanged file byte-identical. `scripts/enterprise-publish.spec.ts` builds the report from a fixed ledger and proves the publisher rewrites nothing on an unchanged input. The deck's `next build` typechecks the contract, the feed client, the store and the Ledger tab.

## Alternatives considered

**Counting a seat as active when its function ran, dated at the run.** A judge whose newest verdict is three days old would then read as active every night the runner re-read it. The function line's `at` is the deliverable's own time — the gate's end, the verdict's rendering — so a seat is active only when it delivered inside the day, and re-reading an old verdict appends nothing.

**Measuring the roster's window at read time.** The count would then differ between two reads of one file and the generator could not keep an unchanged file byte-identical, which the roster spec and the idempotent regeneration depend on. Measuring at `generatedAt` keeps the file a snapshot with a stated moment; the operator regenerates after every shift, so the stamp is never far behind.

**Filtering the ledger to lines dated at or before the roster's stamp.** It would make the file reproducible without naming the lines it read, but the generator first rebuilds under the previous stamp to detect change, and that build would exclude every new line — the roster would never take a new line in. Naming the count of lines covered, as `evidence.records` names the records, keeps both reproduction and change detection.

**Extending the seat's `evidence` with the ledger count.** The feed recomputes `evidence` from discovered sessions and its spec asserts the exact session evidence; a ledger field inside it would have been dropped or faked on the live path. A separate `ledger` field beside `evidence` travels through the feed untouched.

**Ruling a gate-group seat from its own CI lane only.** `ci-lint-contracts-ready`, `ci-snapshot` and `ci-artifacts` have no lane on this fork, so their judges would be permanently vacant although every gate of each group runs by name inside the consumers lane. Mapping the group from the gates the log shows by name gives each judge a verdict that is exactly the conjunction of what ran, and no verdict when the log does not show them all.

**Running every observer through a composed Cordis context.** Composing the projection registry, a session store, the telemetry seam and an OTLP exporter over committed records would light six seats with functions nothing consumes. The one fold that has a real output over committed records — the session-stats unit — runs directly, and the rest are vacant with the reason, which is what the honesty rule requires.

**A telemetry snapshot without seats.** Sessions and tokens alone would not say whether the enterprise exists; the snapshot carries seats occupied and active per division by the same rule the roster applies, so the observatory publishes the figure the operator's goal is measured by.

## Consequences

The enterprise has a record that any seat's work enters as one line, and a rule that turns the record into occupancy the same way in three places. The ticketless divisions do their functions on every commit the command is run on: 14 gates, up to 6 CI verdicts, one telemetry snapshot and one scoreboard per shift, each with evidence a reader can open. Occupancy is now honest in both directions: a seat lights only by a deliverable, and a seat with no deliverable in a day goes dark whatever it did before. The roster's `active` count is meaningful and time-stamped, and the deck shows it beside the ledger's day.

The cost is a growing record: a shift appends 14 gate logs under `data/enterprise/functions/` and about 22 lines to the ledger, so the committed tree grows by a few hundred kilobytes per day of unattended shifts. The roster's `active` is as fresh as its last regeneration, which the shift order guarantees and a stale checkout does not. Five judge seats and five observer seats are vacant by construction on this fork, and the vacancy table in `data/enterprise/README.md` is the place that changes when a Windows runner, a primary pool, an OTLP collector or a session store is composed. The ticket line's status reading is the deck's and the report's, not the engine's; an engine that records a verdict vocabulary outside the approving set reads as rejected until the set is extended here.
