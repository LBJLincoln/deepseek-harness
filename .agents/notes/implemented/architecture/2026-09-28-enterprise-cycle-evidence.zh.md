# Agent Note: 企业无人值守周期的证据

Status: implemented

[English](2026-09-28-enterprise-cycle-evidence.md) | 中文

## Problem

`scripts/enterprise-scheduler.sh` 在无人操作的情况下每两小时运行一次 `scripts/enterprise-cycle.sh`，而每个周期的输出只写入容器内的一个日志文件：仓库从未见过它，2026-09-28 22:07Z 的容器重置也把它抹掉了。分支对一个周期所保留的，只是它的提交碰巧带上的内容——一份受理记录、一个班次的记录与台账行、职能的台账行——没有任何陈述说明哪些步骤运行了、哪些失败了、周期是否跑完，也无法区分一个什么都没做的周期和一个从未运行的周期。操作员必须得到一份诚实、可复现的企业无人值守最初 24 小时的记述，其中每个数字都必须来自已提交的内容。

## Decision

**每个周期提交它自己的记录。** 在最后一个数据步骤（`publish`）之后、最后一个提交之前，周期运行 `pnpm run enterprise:cycle-record`，写出 `data/enterprise/cycles/<cycle id>.json`，最后一个提交包含它。shell 保持精简：`step()` 向周期锁旁边的一个临时文件追加 `<name> <exit> <UTC time>`，脚本记下 `start`（周期开始时的 HEAD，即运行的周期脚本所在的修订）、`pulled`（首次拉取之后的 HEAD）以及那次拉取之后的远程跟踪分支顶端。`scripts/enterprise-cycle-record.ts` 由这些信息和检出构建记录：按顺序的每个步骤、自 `pulled` 以来台账新增的行（按多重集合比较；工单行按状态计数，职能行按结果计数，工单行所属的班次 id，无法读取的行）、`firstFailure`，以及 `end`，即构建记录时所在的提交。同一个校验器 `cycleRecordProblems` 同时把守写入和每一次读取。无法写出的记录是失败的步骤 `record`，推送照常运行，因此周期的数据从不等待它的记录。

**最后一次推送由下一个周期报告。** 一条记录无法包含送达它的那次推送的结果。下一个周期的记录写明其检出中较早记录里最新的一条，以及首次拉取时远程分支是否已包含它（`previous.recordOnRemote`）：`false` 恰好表示最后一次推送没有落地，此时检出保留的那个提交会随下一个周期的推送一起送出。

**没有记录的周期从 git 计数，并加以标注。** 记录出现之前的周期、记录失败的周期、被容器重置中断的周期，以及因锁或检出不干净而退出的周期，至多留下它推送过的提交，其主题带有周期 id（`chore(enterprise): <cycle id> intake`、`chore(enterprise): <cycle id> functions, roster and deck`）；读取方把它们计为只在 git 历史中可见的周期，从不计为干净或失败。

**任意时间窗上的同一份报告。** `pnpm run enterprise:report`（`scripts/enterprise-report.ts`）对一个两端都包含的时间窗陈述：由记录和指名周期的提交得出的周期、按状态与事业部统计的工单行及已交付的不同工单、每个已交付提交的 Branch CI 裁决、在时间窗结束时刻运行花名册生成器得出的各事业部席位、按事业部与结果统计的职能行，以及各行陈述的 token 数与秒数。`enterpriseReport` 以仓库读取器、GitHub 读取器和某一时刻的花名册作为参数，因此指挥台的发布器和任何其他采集器都在同样的输入上调用同一个函数。已交付提交的裁决是以该提交本身为 head 的运行；否则是在该提交之后创建、且在检出历史中 head 包含它的第一个已完成运行，回答会说明是哪一种；班次把它的工单提交推送在自己的提交之下，因此工单提交很少是某次运行的 head。`no run` 也是一个回答；API 失败或检出中缺少运行的 head，则是带有原因的未知；来自后续运行的裁决在每一处显示时都会如此标注。报告以试点精确计数的标题开头——周期、班次、工单行、评审结果、已交付提交及其裁决、职能运行——席位放在最后陈述。每个周期都写明启动者：记录的 `startedBy`（周期脚本从其父进程得出），或者对于早于调度器脚本首次提交的周期，为操作员。班次来自其记录；没有记录时来自台账行；两者都没有留下的班次则来自损失登记 `data/transcripts/LOSSES.md`。开销按来源各给一个标明覆盖内容的总计——工单行、受理协调人、由 `sessionFiguresIn` 折叠的各记录树的已记录会话、职能行、已记录周期——从不相加，因为工单行的计数包含了日志同样被折叠的会话。输入未显示的每一项事实都进入 `unknowns`。

**指挥台用同一份报告展示最近 24 小时。** `pnpm run enterprise:publish` 写出 `apps/command-deck/public/fixtures/enterprise-day.json`，即报告在花名册时间窗（截至其 `generatedAt` 的 24 小时）上的 JSON，并以花名册本身作为该时间窗结束时刻的席位。企业视图的 24 hours 标签页读取它：运行过的周期及其结果、按事业部列出的已交付工单及每个提交的 Branch CI 裁决（链接到其运行）、按事业部的活跃席位，以及未知项；其他任何视图都可以读取同一个文件。`deck-pages.yml` 在分支上每一次触及 `apps/command-deck/**` 的推送时重新发布 Pages 站点，而每个周期的最后一个提交都带有重新生成的 fixture，因此每个周期都会重新发布指挥台。

## Alternatives considered

**提交周期的日志。** 日志是调度器对每条命令原始输出的重定向：提交它会让树每两小时增长一段未经审阅的文本，而且仍然不陈述任何程序可读的结果。记录陈述结果；日志仍是本地的调试手段。

**在 shell 中构建记录。** bash 写出的 JSON 无法自我校验，而且周期会拉取分支，分支可能在脚本运行期间改写脚本本身。每个步骤追加一行、只调用一条命令，使 `main() {…}; main "$@"` 保持简短，并把解析与校验放在测试能覆盖的地方。

**按位置或按时间计数周期的台账行。** 按位置（拉取时台账的行数）计数，会在变基重排追加的行时出错；按时间过滤是错的，因为职能行的 `at` 是交付物自身的时间，一个在周期开始之前给出的 CI 裁决仍然是本周期的行。把前后的行按多重集合比较，恰好计入周期检出所新增的行。

**在周期结束时对照远程检查上一条记录。** 到那时本周期自己的推送可能已经带上了上一个周期未推送的提交，这样的检查会把一次失败的推送报告为已送达。

**从裁判的台账行获取 CI 裁决。** 裁判记录的是职能运行所在提交的运行，或分支上最新的运行；工单的提交通常两者都不是，因此按提交匹配裁决会让大多数已交付提交没有裁决。先向 API 询问该提交本身，再询问包含它的第一个后续运行，就能回答每一个已交付提交，并说明回答属于哪一种。

**从已提交的花名册文件获取席位。** 该文件的时间戳是它最后一次变化的时刻，而不是时间窗的结束时刻；在 `until` 时刻、以不晚于该时刻的台账行与会话运行生成器，能为任意时间窗陈述那一时刻的在岗情况。

**在发布之前写出记录。** 这样指挥台的数据会包含正在发布的周期的记录，但记录会缺少 `publish` 步骤，一次失败的发布将无处可见。记录保留最后一个提交之前的每个步骤；指挥台把正在发布的周期显示为没有记录的周期，这正是那一时刻的数据所显示的。

## Consequences

分支保存着每一个最后推送落地的周期，连同它的步骤、退出码和它产生的台账行，下一条记录会说明上一条是否落地；容器本地的日志不再是一个周期唯一的记述。代价是每个周期一个小 JSON 文件和一次 `tsx` 启动。在写出记录之前终止的周期只留下它的提交，读取方会标注这样的周期，而不是猜测它的结果。操作员得到的记述是 `pnpm run enterprise:report -- --since <start> --until <end> --write`，可从它写明的提交与 GitHub 的回答复现；时间窗内早于记录出现的周期，报告会逐个如实说明。

## Verification

`scripts/enterprise-cycle-record.spec.ts` 固定了步骤文件的解析、在新增了工单行、职能行和残缺行的台账上的记录计数、`firstFailure`、校验器的拒绝理由、读取方对命名错误和残缺文件的处理，以及 `previous.recordOnRemote` 对照临时 origin 的三种状态。其中一个测试在临时克隆中用一个替身 `pnpm` 两次运行真实的 `scripts/enterprise-cycle.sh`，替身的 roster 步骤第一次失败：第一条记录按顺序列出八个步骤并带有 `firstFailure: { step: "roster", exit: 1 }`，它被提交在 origin 上的最后一个提交中，该提交的父提交是记录的 `end`；第二个周期的记录在远程找到了它。

`scripts/enterprise-report.spec.ts` 在一个含有残缺行的固定台账、三条周期记录、指名一个无记录周期的提交，以及一个录制的 Branch CI API 上构建报告：周期按来源计数并标注，每条记录的推送取自下一条记录；工单行按状态与事业部统计；四个已交付提交分别得到本提交上的运行、包含它的后续运行、无运行，以及因检出缺少运行 head 而未知的裁决；无法读取的 API 让每个裁决都成为带原因的未知，而报告的其余部分照常成立；席位来自时间窗结束时刻的花名册生成器；未知项被逐条准确列出；相同输入上的 Markdown 完全相同；`--write` 在时间窗结束时刻的名下写出两个文件。同一个测试还固定了：由记录或调度器脚本首次提交得出的每个周期的启动者、一个有记录的班次、一个只有台账行的班次与一个丢失的班次、评审结果、标明覆盖内容的开销总计，以及标题。`scripts/enterprise-publish.spec.ts` 证明发布器在花名册时间窗上以花名册的席位写出 24 小时报告，且在输入未变时不重写任何文件；指挥台的 `next build` 对契约、fixture 读取函数与该标签页做类型检查。
