# Agent Note: Evidence of the enterprise's unattended cycles

Status: implemented

English | [中文](2026-09-28-enterprise-cycle-evidence.zh.md)

## Problem

`scripts/enterprise-scheduler.sh` runs `scripts/enterprise-cycle.sh` every two hours without an operator, and each cycle's output went only to a log file inside the container: the repository never saw it, and the container reset at 22:07Z on 2026-09-28 erased it. What the branch kept of a cycle was whatever its commits happened to carry — an intake record, a shift's record and lines, the functions' lines — with no statement of which steps ran, which failed, or whether the cycle finished, and no way to tell a cycle that did nothing from one that never ran. The operator must receive an honest, reproducible account of the enterprise's first 24 hours unattended, and every figure in it has to come from something committed.

## Decision

**Every cycle commits its own record.** After its last data step (`publish`) and before its final commit, the cycle runs `pnpm run enterprise:cycle-record`, which writes `data/enterprise/cycles/<cycle id>.json`, and the final commit includes it. The shell stays thin: `step()` appends `<name> <exit> <UTC time>` to a temporary file beside the cycle's lock, and the script captures `start` (HEAD when the cycle began, the revision whose cycle script ran), `pulled` (HEAD after the initial pull) and the remote-tracking tip after that pull. `scripts/enterprise-cycle-record.ts` builds the record from those and the checkout: every step in order, the ledger rows gained since `pulled` compared as a multiset (ticket lines by status, function lines by outcome, the shift ids of the ticket lines, unreadable rows), `firstFailure`, and `end`, the commit the record was built on. One validator, `cycleRecordProblems`, guards the write and every read. A record that cannot be written is the failed step `record`, and the push still runs, so the cycle's data never waits on its record.

**The final push is reported by the next cycle.** A record cannot contain the outcome of the push that delivers it. The next cycle's record names the newest earlier record in its checkout and whether the remote branch held it when the initial pull fetched (`previous.recordOnRemote`): `false` is exactly a final push that did not land, and the commit the checkout kept then travels with the next cycle's push.

**Cycles without a record are counted from git, and labelled.** A cycle before the record existed, one whose record failed, one a container reset cut short, or one that exited on the lock or a dirty checkout leaves at most its pushed commits, whose subjects carry the cycle id (`chore(enterprise): <cycle id> intake`, `chore(enterprise): <cycle id> functions, roster and deck`); readers count those as cycles seen only in git history, never as clean or failed.

**One report over any window.** `pnpm run enterprise:report` (`scripts/enterprise-report.ts`) states, for a window with both ends inclusive, the cycles from their records and from the commits naming them, the ticket lines by status and division with the distinct tickets shipped, each shipped commit's Branch CI verdict, the seats by division from the roster generator run at the window's end, the function lines by division and outcome, and the tokens and seconds the lines state. `enterpriseReport` takes the repository reader, the GitHub reader and the roster at a moment as arguments, so the deck's publisher and any other collector call the same function over the same inputs. A shipped commit's verdict is the runs whose head is that exact commit, else the first completed run created after the commit whose head contains it in the checkout's history, and the answer names which; a shift pushes its ticket commits beneath its own commit, so a ticket commit is rarely a run's head. `no run` is an answer; an API failure, or a run head the checkout lacks, is an unknown with its reason. Every fact the inputs do not show goes to `unknowns`.

**The deck shows the last 24 hours from the same report.** `pnpm run enterprise:publish` writes `apps/command-deck/public/fixtures/enterprise-day.json`, the report's JSON over the roster's window (the 24 hours ending at its `generatedAt`), with the roster itself as the seats at that window's end. The Enterprise view's 24 hours tab reads it: the cycles run with their outcomes, the tickets shipped by division with each commit's Branch CI verdict linking to its run, the seats active by division, and the unknowns; any other view can read the same file. `deck-pages.yml` republishes the Pages site on every push of the branch that touches `apps/command-deck/**`, and each cycle's final commit carries the regenerated fixture, so every cycle republishes the deck.

## Alternatives considered

**Committing the cycle's log.** The log is the scheduler's redirect of every command's raw output: committing it would grow the tree with unreviewed text every two hours and still state no outcome a program can read. The record states the outcome; the log stays the local debugging aid.

**Building the record in the shell.** JSON written by bash cannot validate itself, and the cycle pulls the branch that may rewrite the script while it runs. One appended line per step and one command keep `main() {…}; main "$@"` short and put parsing and validation where tests reach them.

**Counting the cycle's lines by position or by time.** A position (the ledger's row count at the pull) breaks when a rebase reorders appended rows; a time filter is wrong because a function line's `at` is the deliverable's own time, and a CI verdict rendered before the cycle began is still this cycle's line. Comparing the rows before and after as a multiset counts exactly the rows the cycle's checkout gained.

**Checking the previous record against the remote at the end of the cycle.** By then this cycle's own pushes may have carried the previous cycle's unpushed commit, and the check would report a failed push as delivered.

**Taking CI verdicts from the judges' ledger lines.** The judges record the run of the commit the functions ran on, or the branch's newest; a ticket's commit is usually neither, so matching verdicts by commit would leave most shipped commits without one. Asking the API for the exact commit and then for the first later run containing it answers every shipped commit and says which kind of answer it is.

**Seats from the committed roster file.** The file is stamped at its last change rather than at the window's end; the generator run at `until` over the lines and sessions dated at or before it states the occupancy at that moment for any window.

**Writing the record before publishing.** The deck's data would then include the publishing cycle's record, but the record would lack the `publish` step, and a failed publish would appear nowhere. The record keeps every step before the final commit; the deck shows the publishing cycle as one without a record, which is what the data at that moment shows.

## Consequences

The branch holds every cycle whose final push landed, with its steps, exit codes and the ledger lines it produced, and the next record says whether the previous one landed; the container-local log is no longer the only account of a cycle. The cost is one small JSON file and one `tsx` start per cycle. A cycle that dies before its record leaves only its commits, and readers label such a cycle instead of guessing its outcome. The account the operator receives is `pnpm run enterprise:report -- --since <start> --until <end> --write`, reproducible from the commit it names and GitHub's answers; a report over a window whose cycles predate the record says so for each of them.

## Verification

`scripts/enterprise-cycle-record.spec.ts` pins the step-file parsing, the record's counts over a ledger that gained ticket, function and torn rows, `firstFailure`, the validator's rejections, the reader's handling of misnamed and torn files, and `previous.recordOnRemote` against a temporary origin in its three states. One test runs the real `scripts/enterprise-cycle.sh` twice in a temporary clone with a stand-in `pnpm` whose roster step fails the first time: the first record lists the eight steps in order with `firstFailure: { step: "roster", exit: 1 }` and is committed in the final commit on the origin, whose parent is the record's `end`, and the second cycle's record finds it on the remote.

`scripts/enterprise-report.spec.ts` builds a report over a fixed ledger with a torn row, three cycle records, commits naming a cycle without a record, and a recorded Branch CI API: the cycles are counted and labelled by source, each record's push taken from the next record; the ticket lines are tallied by status and division; the four shipped commits get a run on the exact commit, a later run containing it, no run, and an unknown whose run head the checkout lacks; an unreadable API leaves every verdict unknown with the reason while the rest of the report stands; the seats come from the roster generator at the window's end; the unknowns are listed exactly; the Markdown is identical over identical inputs; and `--write` writes both files under the window's end. `scripts/enterprise-publish.spec.ts` proves the publisher writes the 24 hours report over the roster's window with the roster's seats, and rewrites nothing on an unchanged input; the deck's `next build` typechecks the contract, the fixture reader and the tab.
