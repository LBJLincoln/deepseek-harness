# Agent Note: The enterprise roster is generated from real sources; the feed computes liveness, never invents it

Status: implemented

English | [中文](2026-09-19-enterprise-roster-and-harness-feed.zh.md)

## Problem

A customer proof of concept needs to present a large, structured "enterprise" of agents — divisions, departments, specializations — without pretending the harness runs 147 concurrent agents today. Two failure modes were both live risks: a hand-authored roster JSON that drifts from the repository the moment a package is renamed or removed, and a status field that reports "active" for seats nothing is actually running. Either one turns a proof of concept into a fabrication the first time someone checks it against the repository.

## Decision

**The roster is generated, not authored, and every entry cites a real, checked path.** `scripts/enterprise-roster.ts` composes exactly 147 agents as role x division x specialization. Every division's agent count is a fixed quota (`DIVISION_QUOTAS`, summing to 147), not a directory listing's length: `takeQuota()` slices exactly that many entries from a pool sorted for deterministic iteration, throwing an error naming the division and the shortfall when the tree defines fewer real sources than the quota needs. Each division's pool is one enumerable, real source: `packages/core`, `packages/llm`, and `packages/subagent` leaf directories for `harness-core`; task environments under the Proving Ground bench fixture (`examples/headless-agent/tests/fixtures/proving-ground-bench/environments`) for `proving-ground`; `scripts/verify-*.ts` for `verification`; the CI gate ids in `scripts/run-gates.ts` for `judging`; `.agents/notes/implemented/<class>` directories plus the token-meter package for `curation-data`; ten package group READMEs for `program-departments`; six departments' real review knowledge packs under `data/knowledge/code-safety` crossed with six language specializations for `code-safety`; `.agents/skills/<id>` directories for `knowledge`; eight process-standard files for `governance`; and six telemetry/query sources for `observatory`. A `cite()` helper resolves every hardcoded relative path against `existsSync` before the generator emits it, so a renamed or deleted source fails the generator immediately, naming the missing path, rather than shipping a roster entry nothing backs. Every code-safety reviewer's OpenRouter model, and the free-tier model list itself, come from a regular expression over the Proving Ground bench's `with-openrouter.cordis.yml` overlay (`openRouterFreeModels()`), cycled across the 36 reviewers with `pickCyclic()`, never a hardcoded model list.

**`generatedAt` is the tree's last commit timestamp, not the wall clock.** Reading `git log -1 --format=%cI` instead of `Date.now()` is what makes `buildRoster()` produce byte-identical JSON on repeated runs against the same commit — a real idempotency property, not merely a stable field count. A tree with no git history falls back to a fixed epoch rather than breaking the guarantee.

**The generated file's `status` is always `"defined"` and `counts.active` is always `0`.** This module describes what the repository defines; it has no session data and must not guess. `scripts/harness-feed.ts` is the only place liveness is computed: its `GET /roster` handler reads the committed roster, then maps each agent to a live session (best-effort, by the provider/model its stamped `request/header` names, then by its role or division appearing in the session's system-prompt text) to decide `active` (a matching session is still running), `certified` (that session logged a `verification/certificate`-shaped event before ending) or `failed` (it ended without one), and only then are the counts recomputed. The committed file and the served response are never the same object; the served response is derived and discarded per request.

**Code-safety specializations name a target, not an implemented scanner.** This repository is TypeScript/JavaScript and has no Java, Go, PHP, or mobile static-analysis tooling, so every one of the 36 department x specialization reviewer seats cites its department's real review knowledge pack (`data/knowledge/code-safety/<department>/SKILL.md`) regardless of which language the seat names; the specialization records what the seat is *for*. Every reviewer, integrator, and the program lead also draw on that pack (the lead additionally on the cross-cutting `review-method` and `severity-and-evidence` packs) as a `code-safety/<id>` skill, alongside a bare `.agents/skills/<id>` id for every other division. `data/enterprise/README.md` states the "defined" vs "implemented" distinction plainly so a reader does not mistake one for the other.

**The event fold in `harness-feed.ts` is written against the real session-event vocabulary, with a small forward-looking remainder.** `packages/core/session`'s generated `KNOWN_SESSION_EVENT_TYPES` includes `turn/start`, `turn/end`, `step/start`, `step/end`, `tool/call`, `tool/result`, `agent/inbox/spliced`, `hook/*`, `tool-workflow/*`, `tool/code-dispatch*`, `verification/certificate`, and `program/integration` — all real, currently-emitted types the fold maps to `step`, `tool` (or `delegation` when the tool name is one of the subagent tools), `directive`, `certificate`, and `merge` respectively. Only `agent/step`, a `finding`-prefixed type, and `code-safety/finding` remain forward-looking, recognized ahead of the not-yet-shipped code-safety scanner emitting them for real. Every reader of a decoded line's `type` goes through a shared `typeOf()` guard rather than assuming the field is a string: a run directory's non-session JSONL records (`facts.jsonl`, `trajectories.jsonl`) and a session's own header line both carry no `type`, and a line the fold does not recognize is dropped from the stream, never a crash and never a placeholder record.

**A discovered run's kind and status come from what its driver actually writes, never from a field no driver populates.** A `.proving-ground/runs/<id>/plan.json` is a verbatim copy of the user-authored plan file (`scripts/proving-ground.ts` never adds a `kind`, `status`, or `endedAt` to it), so `classifyPlanKind()` infers `fleet` from a `models` array, `experiment` from a `baseline`/`candidate` pair, and `program` from a `goals` array (`packages/improvement/program`'s `ProgramSpec`), mirroring `scripts/proving-ground.ts`'s own `planKind()`. Status and `endedAt` come from `run.log`'s terminal JSON line instead: every fleet and experiment driver prints exactly one `type: "result"` line carrying `endedAt` right before exiting, which `run.log` tees, so that line's presence (or a `type: "error"`/`"refused"` line) is what distinguishes `completed`/`failed` from `running`. A recorded `data/proving-ground/<id>` run classifies the same three kinds from `result.json`'s `report.goals` (program), `result.arms` (experiment), or `report.group`/`report.cells` (fleet), falling back to the directory name or the manifest's fixture path when the shape is not one of those three. A code-safety run (live `.code-safety/<id>` or recorded `data/code-safety/<id>`) is always kind `code-safety`; the live run's status comes from `stdout.jsonl`'s single terminal `type: "result"` line the same way, checked against `scripts/code-safety.ts`'s own success criterion (`report.outcome === "released" && verifier.exitCode === 0`).

**`GET /runs/:id/events` streams a run's session files one at a time and one event at a time, never buffering a whole file into an array first.** `streamJsonlLines()` reads each file through `node:readline`, folding and sending each line's event as soon as it decodes; `resolveFileIdentity()` makes one lightweight pass over a file to find its `session` header and `request/header` line before the real replay pass, so a file's agent-id attribution needs no more than those two lines held at once. This keeps the recorded 32-session `data/proving-ground/2026-09-19-bench-e3-attempts-t5` replay starting in well under a second, because `sessionFilesForRun()` also scopes its `*.jsonl` search to the run's `sessions`/`.sessions` subdirectory rather than walking the whole run directory: a run directory's own top-level `facts.jsonl`/`trajectories.jsonl` carry none of a session line's fields, so an unscoped recursive walk would still hand either to the fold as if it were one.

## Consequences

- `pnpm run roster` regenerates `data/enterprise/roster.json` deterministically; a diff in that file after a clean regeneration means a cited source moved, and the generator's own error names which one.
- `pnpm run feed` serves `GET /roster`, `GET /runs`, `GET /runs/:id/events` (SSE), `GET /safety/:id`, and `POST /safety` on port 4711 (`--port` to override) or against a `--fixtures <dir>` directory for the front end's own tests. It discovers runs under four independent paths at request time, each tolerated absent: `.proving-ground/runs/*` and `.code-safety/*` are gitignored runtime output a fresh checkout does not have; `data/proving-ground/*/sessions/*.jsonl` and `data/code-safety/*` are committed historical records a fresh checkout does have, with whichever runs have actually been recorded into them (`data/proving-ground/2026-09-19-bench-e3-attempts-t5`, `data/code-safety/2026-09-19-nodegoat`, …).
- `POST /safety` checks `package.json` for a `code-safety` script on every request rather than caching the answer, answering 501 with a clear message when it is absent and 202 with a run id once `scripts/code-safety.ts` starts it detached. `GET /safety/:id` serves both a live `.code-safety/<id>` run — reading its report repository's `repo/<programId>/@integration` worktree once departments have merged into it — and a recorded `data/code-safety/<id>` run's flat `findings.json`/`SAFETY-REPORT.md`/`verifier.txt`. A finding carries no `department` field in either shape, only an id prefixed with one (`access-idor-allocations`); `certificate.counts` is tallied from `findings` directly rather than trusted to a verifier reading, which carries no per-severity counts in either real format.
- The honesty rule this note exists to enforce: 147 is always the defined count; the active count is whatever `GET /roster` computes from real session directories at the moment of the request, including zero.

## Alternatives considered

- **Hand-authoring `roster.json` once and committing it as static data** — the first package rename or removal would silently strand entries pointing at nothing, with no mechanism to notice. Generation with a checked `cite()` turns that into a build failure instead of a silent lie.
- **Wall-clock `generatedAt`** — makes every regeneration a diff even when nothing sourced from the tree changed, which defeats the point of an idempotency check.
- **Keying the fold on the aspirational event names instead of the real ones** — would make the fold's happy path untestable against any session log this repository can currently produce. Folding the real vocabulary first, with the still-forward-looking names (`agent/step`, a `finding`-prefixed type) as additional recognized prefixes, keeps the keyless test suite exercising real behavior while staying forward-compatible for the one scanner not yet shipped.
- **Treating a missing `.proving-ground/`, `.code-safety/`, `data/proving-ground/`, or `data/code-safety/` as an error** — the first two are runtime directories a real machine populates and a fresh checkout or CI runner commonly lacks; the latter two are committed records that can still lack any given run id. Absence at any of the four is the common case, not a misconfiguration.
- **Deriving a run's kind or status from `plan.json`'s own `kind`/`status`/`endedAt` fields** — no driver ever writes them (`scripts/proving-ground.ts` only copies the user-authored plan file verbatim), so trusting them would silently report the same wrong kind and status for every run. Deriving both from the arms a plan actually declares and from `run.log`'s/`stdout.jsonl`'s terminal line ties the answer to what a driver provably wrote.
