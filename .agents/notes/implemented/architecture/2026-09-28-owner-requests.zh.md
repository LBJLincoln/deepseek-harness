# Agent Note: 所有者的请求在下一次受理时成为工单

Status: implemented

[English](2026-09-28-owner-requests.md) | 中文

## Problem

企业每两小时自行运转一次：协调人受理在队列见底时补充队列（[协调人受理 note](2026-09-28-coordinators-intake.md)），班次处理队列（[班次引擎 note](2026-09-28-enterprise-shift-engine.md)）。它的所有者却没有任何通向它的渠道：工作只能经由协调人在自己包族中找到的事项、或操作者会话手工提交的工单进入队列，所有者想知道某个心愿后来怎样，只能去问操作者。这样的渠道必须能在手机上用 GitHub 网页编辑器写入，不能等到队列见底才起作用，必须让所有者的工作排在企业自身的工作之前，并且必须用仓库已经记录的内容回答每个请求后来怎样。

## Decision

**请求就是一个 Markdown 文件。** 所有者提交 `data/enterprise/requests/<name>.md`：第一行为 `# <title>`，其下是自由文本，别无其他（[请求 README](../../../../data/enterprise/requests/README.md)）。只有对该分支有推送权限的人才能添加请求，因此请求是受信任的输入，会逐字送达答复它的部门。当一张工单的 `source.path` 就是某个请求的文件时，这张工单即答复了该请求；它的 `source.anchor` 是请求的标题行，因此队列"source 必须存在且包含其锚点"的规则对请求的工单原样成立。

**每次受理都先答复请求，且与补充互不相干。** [`scripts/enterprise-intake.ts`](../../../../scripts/enterprise-intake.ts) 读取尚无工单答复的请求，按文件名顺序为前 `--max-requests` 个（默认 2）各设一个部门，与负责补充的协调人同在一个 program 中并排在它们之前。请求的部门以 `request-<文件名>` 为键，由协调人从开放工单最少的那位起轮流担任，逐字得知请求原文，并在 `.intake/<key>.json` 提交恰好一张工单。它的验证者是同一个 `admit` 形式另加 `--request`，由同一套准入裁决，并先检查新增的一条规则：请求的部门提交的工单须带有该请求的 source 与优先级 `0`，其他部门都不得以请求作为 source。第一行不是 `# <title>` 的请求不设部门即被拒绝，也不占 `--max-requests` 的名额。队列已有 `--min-open` 张开放工单时，这次运行仍会答复请求，只跳过补充；周期本来就每两小时运行一次受理，并在班次之前提交 `data/enterprise/`，因此周期无需改动。

**优先级 0 就是先后次序。** [`validateTickets`](../../../../scripts/enterprise-tickets.ts) 只允许 `source.path` 为请求的工单取优先级 `0`，准入则要求每张答复请求的工单都取这一优先级。引擎的队列顺序——尝试次数最少者优先，其次是优先级，再次是各事业部轮流，最后是编号——因此无需改动引擎，就会把请求的工单排在每一张未尝试过的工单之前；请求的工单一旦失败，也会像其他工单一样排到未尝试过的工单之后。

**被拒的请求会被记录并重试。** 受理记录的 `requests` 写明这次运行处理过的每个请求及其结果：`admitted` 附上工单；`refused` 附上准入给出的每条原因，或其部门没有提交任何工单，或缺少标题行；`unanswered` 表示它的部门在完成之前就被截断，且其已提交内容没有因自身原因被拒。下一次运行会处理每个尚无工单答复的请求，因此所有者修改被拒的请求后就会得到一次新的尝试。每个部门的职能行写明担任该部门的协调人。

**状态只推导，从不存储。** `pnpm run enterprise:requests`（[`scripts/enterprise-requests.ts`](../../../../scripts/enterprise-requests.ts)）从队列、台账的工单行与受理记录推导每个请求的文件、标题与状态：由答复它的工单的最近一行得出 `queued`、`halted`、附带提交的 `shipped` 或 `rejected`；否则，最近一份提到该请求的受理记录拒绝了它时为附带原因的 `refused`，没有拒绝时为 `waiting`。

## Alternatives considered

**单独的请求命令或 program。** 它会重复克隆、检出、driver、准入、路由隔断与记录，而每个周期的第二个 program 还要再花一次克隆与一次安装；一个让请求的部门先运行的 program 把这些全部复用，并保留用量上限停止及其退出码 3。

**以 GitHub issue 作为请求。** 读取它们需要每个周期都有凭据与网络，还要对每位作者做一次信任判断；分支上的文件由谁能推送来确立信任，像其他任何工单来源一样被读取，并按原样满足校验器的 source 规则。

**由准入替工单填写 source 与优先级。** 部门将永远不知道自己工单的 source 写错了，准入也会成为唯一一处在编号之外改写拟议工单的地方。以确切的期望 source 拒绝，能让准入保持裁判的身份：目标写明这些值，拒绝在部门的第二轮中再次点明它们。

**为请求设状态文件。** 每种状态都已经是已提交文件的函数：工单凭 source 路径答复请求，台账关闭工单，受理记录说明请求为何仍未获答复。状态文件会成为第二份副本，被中断的周期可能让它过时。

**任何操作者认为紧急的工单都可取优先级 0。** 校验器把它留给请求，使这一先后次序归所有者所有；操作者的紧急工作写成请求即可。

**在被拒请求的文件改动之前跳过它。** 这会埋没因暂时原因（例如耗尽预算的部门）被拒的请求，还需要记录每次拒绝时看到的内容；每次运行都重试，代价是每个等待中的请求占一个部门，并受 `--max-requests` 限制。

## Consequences

所有者的渠道就是一次提交：在某个周期之前提交的请求会由该周期的受理处理，一旦被接纳，它的工单就是同一周期的班次领取的第一张未尝试过的工单。请求按文件名顺序处理，被拒的请求每次运行都会重试，因此一个屡被拒绝的请求会一直占着排在后续文件之前的位置，直到所有者修改或删除它；`--max-requests` 限定了请求每次运行所花的模型会话数。即使队列已满，每次运行也要为每个等待中的请求花一个部门。请求的部门是一位协调人在为另一个席位写工单，因此请求的范围划定得好坏，取决于这位协调人读得如何；准入与班次的独立评审仍是把关。请求涉及的内容若没有任何花名册席位覆盖，就会以席位归属规则的原因被拒，状态命令会打印这一原因。

## Verification

[`scripts/enterprise-requests.spec.ts`](../../../../scripts/enterprise-requests.spec.ts) 固定了请求的发现（标题行、略过 README 这一对文件与其他文件、文件名顺序）、答复判定、每种状态以及工单相对拒绝的优先、对已提交记录的读取（略过损坏的记录）、打印与 JSON 输出，以及引擎的 `queueOrder` 把优先级 0 的工单排在每一张未尝试过的工单之前。[`scripts/enterprise-tickets.spec.ts`](../../../../scripts/enterprise-tickets.spec.ts) 固定了优先级 0 规则；[`scripts/enterprise-intake-admission.spec.ts`](../../../../scripts/enterprise-intake-admission.spec.ts) 固定了两个方向上的请求规则；[`scripts/enterprise-intake.spec.ts`](../../../../scripts/enterprise-intake.spec.ts) 固定了该选项、部门键与担任者、请求的目标、program 中的部门顺序与加引号的验证命令，以及每种请求结果。[`examples/headless-agent/tests/enterprise-intake.e2e.ts`](../../../../examples/headless-agent/tests/enterprise-intake.e2e.ts) 在一个含四个请求、无需补充的种子仓库上无密钥地运行该命令：以优先级 0 接纳一张，因优先级拒绝一张，拒绝一个没有标题行的请求，让第四个保持等待，并通过状态命令读回这四个状态。
