# Agent Note: 客户简报：每个数值都从记录计算得出，并附来源

Status: implemented

[English](2026-09-28-client-briefing.md) | 中文

## Problem

运营者要向一家客户的高管——首席信息官、首席信息安全官与首席财务官——介绍 Daliesk 企业，而仓库里没有任何内容是为这样的读者写的。指挥台的四个视图是为演示搭建的舞台：它们展示企业在运转，却没有陈述主张，没有安全负责人可以核对的控制措施，也没有成本。这类读者需要的事实都在分支上——花名册、台账、班次、受理与周期记录、Proving Ground 的冻结配对实验、代码安全记录及其真值、实时对话记录捕获，以及 GitHub 的 Branch CI 运行——但它们分散在十几份为贡献者撰写的 README 与 Agent Note 中，其中若干说法已被后来的记录修正。手写的幻灯片只会把这些数字重述一遍，到下一个周期就已过时；对早期草稿的一次审计也发现了这类文档容易滑向的说法：无人值守的周期在交付工作（实际一张也没有），已交付的工作经 CI 验证（两个已交付提交都没有自己的运行，包含它们的运行失败了），客户代码从不离开审查机器（各部门以操作员的登录把代码发往 Anthropic 的模型 API，对话记录也被公开发布），由人员签署发布（签署由引擎写入），以及不附匹配规则与分母的召回率。

## Decision

**由一个构建器计算每个数值，页面只负责格式化。** [`scripts/enterprise-briefing.ts`](../../../../scripts/enterprise-briefing.ts)（`pnpm run enterprise:briefing`）读取已提交的输入，并通过 GitHub 的 REST API 读取本分支的 Branch CI 运行与仓库的可见性，写出 [`apps/command-deck/public/fixtures/briefing.json`](../../../../apps/command-deck/public/fixtures/briefing.json)。每个数值要么是 `{ value, source: { paths, urls?, computation } }`，要么是 `{ value: null, unknown, source }`：读取它的路径或页面，以及一句说明计算方式的话。席位与事业部来自花名册；按状态分列的工单、token 与秒数来自台账；班次来自其记录；冻结配对实验来自各记录的 `result.json`，若有重读 fold 则附上其读数；召回率来自每条代码安全记录的发现与其目标真值的比对，采用 `compare.mjs` 的规则，即发现落在问题行范围或某个 `alsoAt` 位置的三行以内，三层对比也按同样方式重新计算；治理数值直接来自记录本身（固定了 `dataUse/terms` 的会话；班次或受理记录所载的批准，即其会话日志中的 `signoff/recorded` 事件或其 `result.json` 所列的 `decisions`，各带主体 id 与所声明的类型；审阅者的 `tool/call` 事件）。它读取的输入集连同其 SHA-256 一并列出。指挥台的 `/briefing` 路由在构建时导入该文件并渲染。

**试点按单元逐一列出。** 一个单元是周期脚本的一次运行——由周期提交的标题、台账中的职能行、`data/enterprise/cycles/` 下的周期记录或实时捕获保存的周期日志在分支上指名——或者是所有周期之外的一条班次记录。构建器为每个单元说明启动者及其依据：周期记录所载的启动者——当 `scripts/enterprise-scheduler.sh` 是周期脚本的父进程时，周期脚本记录为 scheduler，否则记录为 operator；对于记录未载明启动者的周期，调度器，当捕获到的调度器日志报告运行了该周期，或宣布了该周期作为第一个启动的时段；操作员，当周期开始于 `scripts/enterprise-scheduler.sh` 进入分支之前，以及任何周期之外的班次；否则为未知。随后它统计该单元的班次记录所列的工单、这些班次按状态分列的台账行及失败的检查、没有任何台账行记录的所列工单，以及这些行的 token；运行了班次却没有记录进入分支的单元，或其步骤无从得知的单元，尝试数与丢失数记为未知。捕获的日志从实时捕获的 gzip 分块中读取；较早的周期脚本只记录时刻的步骤时间，被放在上一步之后。页面第一节与执行摘要按启动者报告已交付的工单，因此记录会说明哪些工作由操作员启动、哪些由调度器启动。

**CI 裁决写明每次运行测试了什么。** Branch CI 在每次推送的末端提交上运行。对每个已交付提交，构建器读取恰好在该提交上的最新一次运行、包含运行（其 head 包含该提交的最早一次运行，即携带它的那次推送，`git merge-base --is-ancestor`）及其各个 job、班次 base 提交上的运行，以及包含该提交的第一次成功运行，并把包含运行中失败的关卡——由职能运行器的 `parseJobLog` 从每个失败 job 的日志中解析——分为 base 运行已经失败的与这次推送引入的两类。页面把这两种读数分别标为“确切提交”与“包含运行”，不把已交付的工作称为已验证。运行列表无法读取时，所有 CI 数值都记为未知并附原因；某一次交付的运行无法读取时，只有那一次交付记为未知。

**数据处理如实陈述。** 治理一节以数据流向图开头：分支被克隆到审查机器上；每个部门、审阅者与受理请求在操作员的 Claude Code 登录下发送到 Anthropic 的模型 API，其中包括文件内容；班次记录的会话日志随每个班次提交；实时捕获每五分钟把操作员与各部门的对话记录推送到本仓库，其可见性由构建器从 GitHub 读取。图下列出在读取客户代码之前合作所需的条件：一个签有数据处理协议并启用零数据保留的 Anthropic API 组织、一个存放记录的私有仓库，以及在每个会话上固定的数据使用条款。签署一行读取记录所载的两种形式：引擎在较早的班次与受理记录中写入的签署事件（在程序启动时写入，间隔以毫秒计，主体类型标为 `human`），以及较新记录以引擎的机器主体列出的决定；它说明在推送之前没有任何人员签署变更。

**未知是一个值，从不是估计。** 输入缺失的数值记为未知并附原因，页面显示 `unknown`。一张工单的货币成本在构造上就是未知的：班次运行在包月订阅的路由上，没有任何记录带有价格。

**声明清单为页面把关。** [`scripts/enterprise-briefing-claims.ts`](../../../../scripts/enterprise-briefing-claims.ts) 在子进程中用 React 的服务端渲染器渲染页面（[`apps/command-deck/scripts/render-briefing.ts`](../../../../apps/command-deck/scripts/render-briefing.ts)，经 tsx 并使用 `apps/command-deck/tsconfig.render.json`，把指挥台的 JSX 编译为自动运行时），用 jsdom 读取，并把每个段落、列表项、表格行与 KPI 拆成句子，每句带上它引用的注释，否则取其段落的注释，再否则取其上方标题的注释。当页面文本（包括注释与悬停卡片）以任意大小写包含 "unattended cycles ship"、"CI-verified"、"never leaves" 或 "(human)"，或某个句子陈述了数字却没有注释时，构建器拒绝写出清单并以 1 退出；否则写出 [`apps/command-deck/public/fixtures/briefing-claims.md`](../../../../apps/command-deck/public/fixtures/briefing-claims.md)：每个句子连同其章节与注释，然后是每条注释及其计算方法与读取的内容。清单与 `briefing.json` 放在一起，因此周期会同时提交二者；当已提交的清单不是已提交页面的渲染结果时，[`scripts/enterprise-briefing-claims.spec.ts`](../../../../scripts/enterprise-briefing-claims.spec.ts) 会在 Branch CI 中失败。

**页面是指挥台中的一份文档。** `/briefing` 是一个基于所导入文件的 Server Component，另有三个客户端部件：主题切换、打印按钮，以及在简报打开期间拦下指挥台舞台快捷键的按键守卫。它的样式表 [`components/briefing/briefing.css`](../../../../apps/command-deck/components/briefing/briefing.css) 限定在 `.bf` 之下；隐藏指挥台页眉页脚、让页面可以滚动的规则通过 `:has([data-briefing])` 生效，因此不修改任何共享的外壳文件。八个章节——试点现状、运营模式、试点记录、实测质量、数据处理与治理和审计、经济性、局限与风险、路线图与建议的合作方式——都按阅读顺序引用各自的数值，并以编号的来源注释结尾，屏幕上折叠、打印时展开；标签在悬停或聚焦时显示其注释。图表用 HTML 与 CSS 绘制，每张只有一个刻度，直接标注数值，颜色在两种主题下都经过校验。打印样式表按 A4 或 Letter 排版（`@page { size: auto }`），每一节另起一页，在页边框中打印页码，在各节之下打印来源注释，并强制使用浅色色板。

**发布步骤会运行构建器。** `pnpm run enterprise:publish` 最后运行 `enterprise:briefing`，因此周期会重新生成简报及其清单而无需修改 `scripts/enterprise-cycle.sh`，周期对 `apps/command-deck/public/fixtures` 的提交会同时带上二者。默认运行不会写入该目录以外的任何文件。`--summary` 从同一份简报渲染一页纸的执行摘要双语对（`docs/client/daliesk-executive-summary.md` 及其中文版）（[`scripts/enterprise-briefing-summary.ts`](../../../../scripts/enterprise-briefing-summary.ts)），`--check-summary` 则把已提交的双语对与该渲染结果相比较。摘要模块与清单模块在运行时不从构建器导入任何内容，因为构建器在自身顶层求值尚未完成时加载它们。

**页面只有英文。** 指挥台没有语言层（`<html lang="en">`）；法文执行摘要属于代码安全项目为其审查对象撰写的报告，页面会引用它。仓库自身的双语规则适用于执行摘要，它由同一份简报渲染为英文与中文。

## Alternatives considered

**把数值直接写进页面。** 写起来最快，但一个周期内就会出错：席位、工单、周期与 CI 数值每两小时变化一次，而一个没有计算方法的数字无法审计。已否决，改用构建器。

**由页面在运行时从原始 fixture 计算。** 指挥台已经发布 `roster.json` 与 `enterprise.json`，但基准、代码安全、会话日志、捕获日志与 CI 的数值不在任何 fixture 中；在浏览器里计算它们，意味着要把 400 MB 的记录与 GitHub API 的读取交给每一位访问者。构建器在记录所在之处运行。

**只凭开始时间判断周期由谁启动。** 调度器在每个偶数 UTC 小时的第 13 分钟启动周期，所以分钟数可以暗示启动者；但手动启动的周期可能恰好落在这一分钟，而定时的周期会等待正在运行的周期。构建器改为读取周期记录所载的启动者，否则读取调度器自己的日志与脚本的历史，都不涵盖某个周期时就说未知。

**把丢失工作的记述解析成计数。** `data/transcripts/LOSSES.md` 依据操作员会话的日志写明了被重置中断的工单。它是写给人读的行文；试点表格把这些计数记为未知，并引用该记述。

**API 失败时沿用上一次构建缓存的 CI 裁决。** 已完成运行的结论不会改变，因此缓存本身是可靠的，但它会让输出依赖于上一次的输出，并用过时的数据掩盖一次无法读取的 API。附带原因的未知才是如实的状态，下一个周期会再次读取。

**从 Next.js 静态导出渲染清单。** 它读取的正是发布出去的内容，但需要完整构建指挥台，而周期与单元测试都不运行这一构建。服务端渲染器在数秒内就能为页面主体生成相同的标记。

**为 `/briefing` 建立带独立根布局的路由组。** 这样可以干净地脱离外壳，但需要把其他所有路由移入一个分组，改写指挥台上其他工作正在修改的文件。限定作用域的 `:has()` 规则只用简报自己的文件就能达到同样效果。

**页面的法文版。** 客户可能使用法语，代码安全报告也以法文开头。但指挥台没有做任何本地化；为一个路由添加语言层将是指挥台的第一个语言层，应当与指挥台的其他视图一起完成。

**在每次发布时生成执行摘要。** 这能让摘要保持最新，但周期只提交 `data/enterprise` 与指挥台的 fixture，重新生成的摘要会让周期的工作副本留下未提交的改动，从而使下一个周期停止运行。执行摘要是一份注明日期的快照，在寄出时用 `--summary` 重新生成。

## Consequences

简报对企业弱点的陈述与对其长处的陈述同样醒目，因为二者出自同一次计算：哪些单元有交付、由谁启动，每次 CI 运行测试了什么，数据流向何处，由谁签署，哪些会话固定了条款，哪些工作在沙箱之外运行，以及模型路由有多集中。记录变化时，页面、清单与试点表格会在下一个周期随之变化；新数据若会让某个句子失去来源，或出现被禁止的短语，发布步骤就会停止，而不是照常发布。

构建器会读取已提交记录中的每一份会话日志（约 400 MB）以及捕获的周期日志，耗时数秒，并在子进程中渲染一次页面。简报文件会随每一次 Branch CI 运行而变化，因此周期对指挥台的提交每个周期都会改变它，连同清单。

数值周围的行文凡是数据可能变化之处都依数据用模板生成：单元、已交付的工单、CI 裁决、签署的主体及其类型、仓库的可见性与各项计数。与某一事件绑定的陈述——第一张已交付工单引入的 translation pairing 失败、被容器重置抹去的班次——引用陈述该事件的记录，对该事件而言始终成立。关于合作所需条件的陈述是要求而不是记录，清单列出它们但不附注释。

## Verification

- `pnpm exec vitest run scripts/enterprise-briefing.spec.ts` 在 fixture 数据上计算每一类数值：按事业部的在岗情况、由最新一行得出的工单状态、班次时长、试点的各个单元及其启动者（记录所载的启动者、捕获的调度器时段、调度器的运行行、调度器存在之前的周期、所有周期之外的班次、没有运行班次的已记录周期）以及尝试、交付、失败、丢失与 token 计数、实验臂标签、每个实验臂的证书与重读 fold、带 `alsoAt` 的三行以内召回率、三个层级、固定的条款、班次与受理记录中带主体类型的签署事件与所载决定、审阅者的工具调用、确切提交运行、包含运行、base 运行与第一次通过的 CI 运行及其引入与既有的关卡、仓库的可见性、API 无法读取与单次交付无法读取时的未知处理、缺失的输入、逐字节一致的序列化、摘要分组，以及执行摘要双语对的结构一致且不含任何被禁止的短语；它还从已提交的发现重新计算已提交对比的得分，并重组已提交的调度器日志。
- `pnpm exec vitest run scripts/enterprise-briefing-claims.spec.ts` 从一个合成页面读取句子、其注释及其继承的注释，拒绝悬停卡片中的被禁止短语与没有来源的数字，并把已提交的页面无问题地渲染为已提交的清单。
- `DECK_STATIC=1 NEXT_PUBLIC_BASE_PATH=/deepseek-harness pnpm --dir apps/command-deck run build` 导出 `/briefing`；Playwright 通过无头 Chromium 在 1440×900 与 390×844 下截取页面，没有横向溢出，也没有页面错误，并按 A4 与 Letter 打印为 PDF。
- `pnpm run typecheck`、`pnpm run lint`、`pnpm run knip` 与 `pnpm run doc-sync` 覆盖构建器、页面、README、执行摘要双语对与本注记。
