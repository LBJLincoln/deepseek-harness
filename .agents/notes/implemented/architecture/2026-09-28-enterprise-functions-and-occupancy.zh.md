# Agent Note: 企业无工单职能与在岗规则

Status: implemented

[English](2026-09-28-enterprise-functions-and-occupancy.md) | 中文

## Problem

`data/enterprise/` 下的花名册定义了 147 个席位，而在本次变更之前只有 19 个曾被占据——每一个都是因为某次代码安全审查或基准测试运行恰好产生了一个已记录的会话——`counts.active` 则固定为 `0`。没有任何机制让验证、裁决、观象台或策展席位按计划做它的工作，这类工作发生时没有任何东西记录它，而读者最先看到的两个数字——在岗与活跃——背后没有一条交付物能够满足的规则。运营者对企业的目标是让它存在：席位按计划在本仓库上执行真实职能，每条交付物都被记录，在岗只凭证据计数，且全部公开可见。把工单送过项目的引擎覆盖了 Harness Core 的包管家；那些工作不是工单的事业部——运行一道关卡、裁决一条 CI lane、折叠遥测、记分——需要自己的运行器，两类工作共用一份记录，一条把记录变成在岗的规则，以及一个读取同一份记录的公开视图。

## Decision

**一份台账，两种行类型。** `data/enterprise/ledger.jsonl` 是组织的记录，只追加、从不改写。引擎为每张处理过的工单追加一条*工单行*（`type: "ticket"`，或根本没有 `type`），带部门结果、验收检查、评审结论、整合结果以及已交付的提交或 `null`；`scripts/enterprise-functions.ts` 为每个在某个提交上执行了职能的席位追加一条*职能行*（`type: "function"`），带职能名称、目标提交、`pass` | `fail` | `error`、作为它写出的仓库路径或它读取的 URL 的证据，以及耗时。`scripts/enterprise-ledger.ts` 拥有这两种类型：它把该文件当作它本来就是的持久边界来读取，保留每一条带有读取方所依赖字段的行并按行号报告其余的行，并从工单行推出工单状态——有提交即 `shipped`，有失败的检查或非批准的结论即 `rejected`，其余为 `halted`，没有行即 `queued`。

**在岗规则只计交付物，不计其他。** 一个席位只能被一条已记录的交付物占据：一条精确指名其 id 的台账行，或一个由 `scripts/roster-evidence.ts` 归属给它的已记录会话。当席位的最新交付物——按 `at` 计的行、按其记录最新日志时间计的会话——落在计算在岗时刻之前的 24 小时内时，该席位为活跃。`scripts/enterprise-ledger.ts` 中的 `occupancyOf` 是唯一的实现；花名册生成器、职能运行器的遥测快照与指挥台发布的报告都调用它。生成的花名册在每个席位的会话 `evidence` 旁带有 `ledger: { lines, lastAt? }`，顶层的 `ledger` 指明文件、读取的行数与未指向任何席位的行数，`activeWindow`（以 `generatedAt` 结束的 24 小时），按规则计得的 `counts.occupied` 与 `counts.active`，以及恰好为活跃席位设置的 `status: "active"`。时间窗按 `generatedAt` 而非读取时刻度量，因此该文件是一份写明时刻的快照，在未变的输入上逐字节复现；每一条新行或新记录都会重新盖章并重新度量时间窗。feed 的 `GET /roster` 保留自己的含义——状态与 `counts.active` 只来自被发现的会话，没有会话占据的席位无论文件怎么写都读作 `"defined"`——因为 feed 是实时视图，文件才是记录。

**每个无工单事业部有一项职能，由一条命令运行。** `pnpm run enterprise:functions -- [--commit <sha>] [--shift <id>] [--branch <name>] [--only <divisions>] [--lock <file>]` 在已检出的提交上运行并逐步追加，因此某个事业部在另一个事业部记录了它的行之后失败，什么也不会丢；在共享机器上，`--lock` 让每道关卡只在运行期间持有所指定的 `flock` 文件，因此一次运行绝不会在整个班次里占住机器的重型命令锁：

- *验证*：每个验证员席位逐一运行其 `source` 所指的根包脚本——没有构建就无从判断的关卡 `verify-doc-site-fragments` 通过 `docs:build:mpa` 运行，即像 CI 的 static lane 那样先构建再验证的脚本——以关卡的退出码为结果，启动失败或超时为 `error`，并把命令、提交、结果与输出尾部写到 `data/enterprise/functions/<shift>/<seat>.log` 作为证据。根 `package.json` 中缺少其脚本的席位会在记录任何东西之前让运行失败。
- *裁决*：裁判通过 GitHub 的 REST API 无凭据读取该提交的 Branch CI 运行，环境指定了代理时经由 `HTTPS_PROXY` 所指的代理（Node 的 `fetch` 只在 `NODE_USE_ENV_PROXY=1` 下遵守它，包脚本设置了该变量；绕过代理的读取会以共享地址无凭据外发，其配额很快耗尽，裁判随即带着这一提示空缺）——各条 lane 作出过裁决的最新已完成运行，因此被后一次推送取消的运行会被跳过；该提交没有时取分支上最新的此类运行，其提交写入 `target.commit`，被请求的提交写入 `target.requested`。job 映射到其日志开头所报关卡模式的席位；job 日志按名称显示出的关卡组（`GATE_GROUPS`：`ci-lint-contracts-ready`、`ci-snapshot`、`ci-artifacts`）映射到该组的席位，所有关卡通过为 `pass`，有一个失败为 `fail`，有一个因依赖失败被跳过为 `error`，日志未全部显示时不写行。job 的页面是证据，其完成时间是该行的 `at`；台账中已有的同一席位、同一 job 的裁决不会再次追加。在本 fork 上没有 lane 的裁判（primary 与 Windows 各 lane）带原因空缺，API 故障则让每位裁判以该故障为原因空缺，其他事业部照常运行。
- *观象台*：会话统计观察员把其所属包真实的 `sessionStats` 投影单元折叠在每个已记录会话上——已提交记录以及 `data/enterprise/shifts/` 下的任何班次记录——并发布 `data/enterprise/telemetry.json`：最近 24 小时与总计的会话数与 token，该单元的轮次、步数、模型与工具耗时，以及按规则在当下台账（含本次运行此前的行）上计得的按事业部在岗与活跃席位。其余五个观察员席位空缺，原因是各自包的职能需要运行中的后端、collector、存储或注册表，而这里没有任何东西在已提交记录上组合它们。
- *策展与数据*：记分员把记分员包的会话事实与记分板折叠在同一批会话上，写入 `data/enterprise/scoreboard.json`。笔记与夹具策展员空缺：策展是工单化的工作。

**公开视图读取记录。** `pnpm run enterprise:publish` 从花名册、台账与工单队列重新生成指挥台的静态数据：作为逐字节副本的花名册 fixture，以及企业视图的台账标签页所展示的 `enterprise.json`——按事业部的在岗与活跃席位、当天按状态分列的工单、当天按班次的职能运行，以及最近已交付提交及其上记录的 CI 裁决。指挥台按同一规则点亮席位（`isOccupied` 读取会话与台账行），通过花名册已带的状态为活跃席位加环，并以 `defined · occupied · active today` 为标题。报告是其输入的纯函数，只在字节变化时重写；`deck-pages.yml` 在指挥台分支上每一次触及 `apps/command-deck/**` 的推送时重新发布 Pages 站点。

## Verification

`scripts/enterprise-ledger.spec.ts` 钉住行解析、容错读取、工单状态读取以及在岗规则的边界（时间窗起点的行为活跃，终点之后一毫秒的行则不是；比时间窗更旧的会话占据但不激活）。`scripts/enterprise-functions.spec.ts` 用脚本化的关卡运行器与由真实 lane 日志构建的录制 GitHub 读取器运行各项职能：每个验证员的脚本都运行且其真实结果与日志被记录；该提交的运行对每条 lane 与每个按名称显示的关卡组各给出一个裁决，对本 fork 缺少的 lane 不给出；分支回退指明被请求的提交；被取消的运行被跳过；无法读取的 API 让裁判以该故障空缺而观象台仍然发布；裁决绝不追加两次；遥测与记分板快照折叠一条已提交记录并统计台账的席位。`scripts/enterprise-roster.spec.ts` 证明花名册严格按席位 id 统计台账行、按相对于盖章时刻的时间窗激活、在恰好它所指明的记录与行上复现已提交文件，并保持未变文件逐字节一致。`scripts/enterprise-publish.spec.ts` 从固定台账构建报告并证明发布器在未变输入上不重写任何东西。指挥台的 `next build` 对契约、feed 客户端、store 与台账标签页做类型检查。

## Alternatives considered

**在职能运行时把席位计为活跃，以运行时刻为日期。** 那样一位最新裁决已有三天之久的裁判，会在运行器每晚重读它时都读作活跃。职能行的 `at` 是交付物自身的时间——关卡结束、裁决作出——因此席位只有在当天交付过才活跃，重读旧裁决不追加任何东西。

**在读取时刻度量花名册的时间窗。** 那样同一文件的两次读取会得出不同的计数，生成器也无法保持未变文件逐字节一致，而花名册规格与幂等的重新生成都依赖这一点。按 `generatedAt` 度量使文件成为一份写明时刻的快照；运营者在每个班次后重新生成，因此盖章从不落后太多。

**把台账过滤为日期不晚于花名册盖章时刻的行。** 这能让文件无需指明读取了哪些行即可复现，但生成器先在上一次的盖章下重建以检测变化，而那次重建会排除每一条新行——花名册永远无法纳入新行。像 `evidence.records` 指明记录那样指明覆盖的行数，同时保住了复现与变化检测。

**把台账计数扩展进席位的 `evidence`。** feed 从被发现的会话重新计算 `evidence`，其规格断言的是精确的会话证据；放在其中的台账字段在实时路径上要么被丢弃要么被伪造。放在 `evidence` 旁的独立 `ledger` 字段原样穿过 feed。

**只从其自身的 CI lane 裁决关卡组席位。** `ci-lint-contracts-ready`、`ci-snapshot` 与 `ci-artifacts` 在本 fork 上没有 lane，其裁判会永久空缺，尽管每组的每道关卡都在 consumers lane 内按名称运行。从日志按名称显示的关卡映射关卡组，给每位裁判一个恰好是所运行之物的合取的裁决，日志未全部显示时则不给裁决。

**通过组合好的 Cordis 上下文运行每个观察员。** 在已提交记录上组合投影注册表、会话存储、遥测接缝与 OTLP 导出器，会用没人消费的职能点亮六个席位。唯一在已提交记录上有真实输出的折叠——会话统计单元——直接运行，其余带原因空缺，这正是诚实原则的要求。

**没有席位的遥测快照。** 仅有会话与 token 说不出企业是否存在；快照带有按花名册同一规则计得的按事业部在岗与活跃席位，因此观象台发布的正是运营者目标据以衡量的数字。

## Consequences

企业有了一份记录，任何席位的工作都以一行进入其中，也有了一条在三处以同样方式把记录变成在岗的规则。无工单的事业部在该命令运行到的每个提交上执行职能：每班次 14 道关卡、至多 6 个 CI 裁决、一份遥测快照与一份记分板，每一项都带有读者可以打开的证据。在岗如今在两个方向上都诚实：席位只因交付物点亮，一天内没有交付物的席位无论此前做过什么都会熄灭。花名册的 `active` 计数有了意义并带有时间戳，指挥台把它与台账的一天并排展示。

代价是一份不断增长的记录：每个班次在 `data/enterprise/functions/` 下追加 14 份关卡日志并向台账追加约 22 行，因此无人值守班次的每一天让已提交的代码树增长几百 KB。花名册的 `active` 与其最后一次重新生成一样新，班次顺序保证了这一点，而陈旧的检出不能。在本 fork 上有五个裁判席位与五个观察员席位按构造空缺，`data/enterprise/README.md` 中的空缺表是组合了 Windows runner、primary 池、OTLP collector 或会话存储时要改的地方。工单行的状态读取属于指挥台与报告，而非引擎；若引擎记录的结论词汇在批准集合之外，在此处扩展该集合之前都会读作 rejected。
