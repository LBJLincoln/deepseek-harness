# Agent Note: 运营中心的周期时间线、班次看板与下一步行动

Status: implemented

[English](2026-09-29-ops-cycles-and-shift-board.md) | 中文

## Problem

[运营中心](2026-09-28-operations-center.md)显示了什么正在工作、什么需要处理，却没有显示企业自身的节奏。周期步骤只是 24 小时泳道图里的匿名色条，运营者读不出哪个周期的哪一步失败、退出码是多少。下一个周期只是卡片里的一个钟点，没有倒计时。正在运行的班次只以 agent 卡片的形式出现，没有工单列表，也没有每个部门所处的阶段。转录捕获的时长取自检出的历史，因此比捕获真实的推送最多晚一次抓取。已交付的提交显示 `cancelled`，而 `pnpm run enterprise:verdicts` 显示 `failure`：采集器从它唯一一次读取的 50 次运行中取第一个任意结论的后续运行，而报告会跳过没有给出结论的运行，并向更早翻页。最紧急的行动在手机宽度下位于首屏之外。

## Decision

**采集器报告周期、班次与已交付工单。** [`scripts/enterprise-ops.ts`](../../../../scripts/enterprise-ops.ts) 为 `OpsSnapshot`（[`contract.ts`](../../../../apps/command-deck/deck/contract.ts)）增加三个可选字段。较早的采集器写出的快照没有这些字段，deck 仍然读取它，因此模式版本仍为 2。这些字段是：

- `cycles`：窗口内的每个周期，最新的在前，取自它的日志，没有时取自已提交的记录，再没有时取自它的提交。每一步带有退出码和耗时。正在运行的周期还加上它正在运行的步骤，以及尚未到达的步骤。调度器的 `<cycle> exit=<n>` 行把在已记录步骤之后终止的周期标为失败。
- `shift`：持有班次锁的班次，没有时取最新的班次。正在运行的班次从它的暂存运行中读取。program 账本的 `program/goal` 事件给出每个部门的阶段，审查会话的 `verdict:` 行把已认证的工单推进到审查、集成或被拒。已结束的班次从已提交的 `result.json` 读取，并给出每个未交付工单到达的最远阶段。运行日志末尾的结果带有 `error` 时，该班次无法完成收尾或推送。它组装好的工单停在集成阶段，以该错误为原因，绝不算作已交付；关注队列标出该班次（`shift-unpushed:<id>`），附上保留的克隆和它需要的决定：手工推送该克隆，或把这些工单留给下一个班次。账本是真正到达分支的内容，因此账本为该班次记录的工单行优先于暂存运行的陈述，并清除这两个标记。事后写入的行带有 `recordedBy`，看板与已交付列表将其显示为补救推送。
- `big.shippedTickets`：最新交付的工单，各自附带其提交和 Branch CI 结论。

**同一条结论规则。** 当周期的 24 小时报告（`fixtures/enterprise-day.json`，即 `enterprise:verdicts` 给出的答案）对某个已交付提交给出了结论时，就采用该结论。否则，结论依据同一规则从采集器读取的运行中得出：提交自身最新的运行；没有时取头部包含该提交、且给出 `success` 或 `failure` 的最早后续运行，被取消的运行不给出结论。`running` 表示仍有一个包含该提交的后续运行正在进行。

**捕获的推送在发生之处读取。** `parseCaptureLog` 从 `transcripts-capture.log` 读取最新的 `pushed <commit>` 行，以及此后任何没有推送的轮次。心跳携带 `lastPush`，分支历史作为后备。

**视图。** 顶部横条以一行“Do next”结束：关注队列的第一项，附其下一步行动与证据链接。大厅上有调度器的时钟。两个周期之间，它倒数到已公布的时段，外圈从最近一次周期开始逐渐填满。周期运行时，它显示正在运行的步骤及步骤进度。大厅下方的周期矩阵每个周期一行、每个步骤一列。每个单元格的颜色表示该步骤的状态，失败的单元格印出退出码。矩阵旁边，班次看板为每个工单画出轨道：排队 → 工作中 → 已认证 → 审查 → 集成 → 交付，点亮到它所处的阶段，并标出未交付工单停下的位置。面板中的已交付列表按工单列出。在手机宽度下，“Do next”行紧跟模式标记，时钟位于大厅下方，矩阵在其面板内滚动，外壳的席位计数换行而不是撑宽页面。除非观看者要求减少动态效果，正在运行的单元格与当前阶段会脉动。

## Alternatives considered

**每次采集都向更早翻页读取 Branch CI。** 采集器以未认证方式读取 GitHub。它每两分钟一次的列表读取已经用掉每小时限额的一半。周期报告每个周期翻页一次，它给出的结论不会再变，因此采集器复用它们。

**提升快照的模式版本。** 新的模式版本会让已部署的 deck 拒绝新采集器的快照，让新的 deck 拒绝旧的快照，直到两者都被替换。可选字段让 deck 与中继的循环可以按任意顺序更新。

**每行一组步骤标签。** 每一行都写上十个步骤名称，无法放进清晰可读的宽度。矩阵只在列标题中给每个步骤命名一次。

## Consequences

运营者可以在一个页面上读到每个周期的步骤、下一个时段的倒计时、每个部门的阶段以及每个已交付工单的结论，而且这些结论与 `enterprise:verdicts` 一致。已经结束、但其记录尚未被检出抓取到的班次，从其暂存运行末尾的 `result` 行读取。暂存班次的证据只以标签点名它的运行日志，因为没有公开页面保存它。

## Verification

`pnpm exec vitest run scripts/enterprise-ops.spec.ts` 覆盖调度器退出码、捕获日志、program 账本、审查结论，覆盖包含运行中、已记录、被拒绝启动和被调度器判为失败的周期的时间线，覆盖运行中、已记录与未能推送的班次，覆盖包含被取消运行、报告答案和进行中的后续运行的结论规则，以及捕获的推送。`pnpm exec vitest run apps/command-deck/tests/ops.spec.ts` 覆盖倒计时、外圈进度与班次轨道。
