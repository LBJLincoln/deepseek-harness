# Agent Note：指挥台镜像从一台不接受入站连接的机器发布 feed

Status: implemented

[English](2026-09-21-command-deck-mirror.md) | 中文

## Problem

客户概念验证需要一个此刻就能展示企业运转的 URL：deck 读取的 feed 里的运行正在进行，而不是一段录制。运行 harness、feed 与审查的机器是一个不接受入站连接的托管容器，隧道会用到的出站路径也是关闭的：Cloudflare 的快速隧道需要 QUIC 或 TCP 的 7844 端口，而出口代理会重置它；会话可用的托管连接器无法创建任何 Vercel 项目、部署或沙箱。feed 是一个普通的 HTTP 与 Server-Sent Events 服务端，所以问题是：如何在不建立任何进入这台机器的连接的情况下，让它的应答能从一个公开来源被访问。

## Decision

**把 feed 的应答推出去；从中继提供它们。**feed 旁边的一个 pusher 读取 `GET /runs`、`GET /roster` 与每个代码安全的 `GET /safety/:id`，跟随每个运行的事件流，并把变化写入托管在 Supabase 项目上的中继：一张按 feed 路径键控的 JSON 快照表、一张在运行、会话与 `seq` 上唯一的折叠事件表、一张审查请求表。公开的 `feed` 函数从这些行提供 deck 的全部契约，包括事件流：它先从行回放，再每 500 毫秒轮询，并在运行时的挂钟上限之前关闭；浏览器的 `EventSource` 带着 `Last-Event-ID` 重连，函数从那一行续传。deck 除了 `deck/feed.ts` 里的一处新增外没有改动：页面 URL 上的 `?feed=` 为该浏览器标签页指定一个 feed，保存在会话存储中，因此托管的 deck 无需重新构建就能跟随中继。

**写入由一个中继从未明文存储的令牌鉴权。**`ingest` 函数接受它在 `POST /bootstrap` 上看到的第一个令牌，把其 SHA-256 保存在 `feed_config` 中，并用它比对之后的每个请求。令牌在推送机器上生成到仓库之外的文件里，不出现在任何源码、日志或转录中；anon 角色在任何镜像表上都没有策略，两个函数都用自身环境里的 service role 写入。

**每次写入都以 base64 内的 gzip 传输。**项目前面的 Web 应用防火墙拒绝了带有已记录 NodeGoat 发现的最初几个快照：它们的片段引用了 SQL 注入与路径遍历字符串，而这正是防火墙匹配的内容。`{ "gz": … }` 信封让载荷对它不透明；响应不会被检查，所以 deck 读到的是普通 JSON。

**事件从每个运行一个队列发出，运行中的优先。**五十四个已记录运行约有六万八千个事件；一个共享队列用了二十五分钟才排空，而实时运行排在它们后面等待。按状态、类别与开始时间排序的每运行队列、四个并发批次，以及被拒绝时减半、三次拒绝后丢弃一个事件的批次，让实时审查排在最前，并在约一分钟内清空了积压。流客户端使用 `node:http` 而不是 `fetch`：后者的响应体超时每五分钟就结束一次安静的已记录流，并把整个运行重新回放一遍。

**中继也能启动审查。**`feed` 函数上的 `POST /safety` 保存一个请求并最多等待 25 秒；pusher 认领它，拒绝位于 `TARGET_ROOT` 之外的目标或 `sonnet`、`opus`、`haiku` 之外的模型，在本地 feed 上启动审查并把运行 id 报告回去，因此托管 deck 的表单会在推送机器上启动一次真实审查。URL 的任何观看者都能做同样的事，这就是为什么演示结束时要停止 pusher。

## Consequences

任何提供 deck 导出的静态主机都能展示推送机器的实时运行：GitHub Pages 工作流现在把中继烘焙为页面的 feed（`vars.DECK_FEED_URL` 可覆盖它），观看者可以用 `?feed=` 指定任何中继。已在无头 Chromium 中针对本地提供并指向中继的导出验证：每个视图都报告 `LIVE`，页脚给出中继与运行中的审查，Process 视图在审查事件到达时逐一计数。

中继无法托管页面本身。Supabase Storage 以 `text/plain` 和 `default-src 'none'; sandbox` 策略应答 HTML，函数网关对浏览器导航也是如此，即使函数设置了 `text/html`，而普通 HTTP 客户端能收到页面。`deck` 函数保留为导出文件的存储前端，页面则从 GitHub Pages 或另一个静态主机发布。

镜像是一件演示工具，不是产品接缝：它复制 feed 的应答而不是其折叠，除令牌摘要外不保存任何密钥，在项目的免费计划上不产生费用。镜像要保持实时，其 pusher 必须运行；它停止后，中继保留最后的快照与收到的每个事件，因此托管 deck 退化为最后一次运行的忠实记录，而不是一个空页面。

## Alternatives considered

- **到本地 feed 与 deck 的 Cloudflare 快速隧道。**不需要账号也不需要中继代码，但隧道需要到边缘的 7844 端口，而这台机器的出口关闭了它。
- **运行真实 feed 的 Vercel 沙箱或项目。**被账号权限拒绝，而且 feed 的云端副本需要同步整个工作区与运行目录，重复本地 feed 已经完成的折叠。
- **从存储桶或 `deck` 函数提供导出。**两者都在沙箱策略下以纯文本应答浏览器；平台禁止在其共享域名上托管页面。
- **用 anon 密钥直接写入 PostgREST。**每条写入策略都会是公开的；经令牌校验的函数把写入限定在一台机器上。
- **提交实时运行的会话文件。**公开原始文件会被缓存数分钟，而每隔几秒一次数据提交会污染分支；中继以数秒延迟、不留历史地承载事件。
