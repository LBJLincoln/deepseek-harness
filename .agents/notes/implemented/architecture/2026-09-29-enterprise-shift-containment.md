# Agent Note: Containing the enterprise shift's acceptance commands and checks

Status: implemented

English | [中文](2026-09-29-enterprise-shift-containment.zh.md)

## Problem

A security review of the [enterprise shift](2026-09-28-enterprise-shift-engine.md) found three openings in how an unattended shift runs a ticket. A ticket's acceptance commands are written by a model at [intake](2026-09-28-coordinators-intake.md) and run with `bash -c` three times: in the department's worktree, over the program's merged head, and in the engine's recertification in the clone's own checkout, which is where the engine pushes from. Admission checked that each own check fails on the clean tip and nothing about what the command is, so a ticket could carry `git push`, `curl` or `gh`, and the engine would run it. The recertification spawned its checks, and the offline installs their lifecycle scripts, with the engine's whole environment, which on the operator's host carries `GH_TOKEN`, `GITHUB_TOKEN`, cloud keys, `GIT_ASKPASS` and the proxy variables. The Claude Code route overlay pre-approved `Bash(pnpm exec:*)` for a `--implementer subagent` department, and `pnpm exec` runs any installed binary, `tsx -e` and `node -e` among them.

## Decision

**Acceptance commands take a closed set of forms.** [`scripts/enterprise-acceptance.ts`](../../../../scripts/enterprise-acceptance.ts) lexes a command line the way bash would and accepts it only as commands joined by `&&`, `||` and `|`, each optionally opened by `!`, every word literal — no `$`, backquote, `~`, unquoted glob or brace, redirection, subshell, `;`, `&`, comment or line break — and none an absolute path or a `..` segment. Each command must be one of `pnpm run <script>` for a root script the queue names, `pnpm exec vitest run …`, `pnpm exec tsc …`, `grep …`, `test …`, or `git diff …` without `--output`, `--ext-diff` or `--textconv`; the open queue of the keyless seed adds `node <file>` and `sh <file>` over a repository file. This repository's queue names `typecheck`, `doc-sync`, `lint`, `test:snapshot` and the `verify-*` scripts: its root also carries `enterprise`, `enterprise:publish`, `release:publish` and `dsh`, which push, publish or start an agent, so "any root script" is not a form. The forms are the queue policy's `acceptanceForms` field, beside the heavy fragments and the generated paths.

**Admission and the engine both enforce them.** Admission refuses a proposal whose acceptance breaks the forms with the stable code `acceptance-form`, after `invalid` and before any command runs, and the coordinators' objective lists the forms. The engine checks again after selection, because a queue file can change after admission: a selected ticket that breaks the forms gets a ticket line with `department.outcome: "blocked"`, no check, and a reason starting `refused: acceptance <check id>:`; the program is composed of the other selected tickets, or not run when none is left. `blocked` is an outcome every ledger reader already understands, so the refusal needs no new value in the ledger's field set, and the line counts as an attempt, so a refused ticket moves behind every untried one instead of taking a slot in every shift.

**The engine's own spawns get an allowlisted environment.** The recertification's acceptance, linter and documentation runs and every offline install run with [`checkEnvironment`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/shift.ts): `PATH`, `HOME`, the `NODE_*`, `npm_config_*`, `NPM_CONFIG_*`, `PNPM_*` and `COREPACK_*` variables, `ENTERPRISE_HEAVY_LOCK`, which the heavy runs take, and `DSH_E2E_INSTALL_LOG`, which the keyless e2e's seeded postinstall appends to — filtered through the intake's existing `scrubbedEnvironment`, so a credential-named `npm_config__authToken` is dropped too, and with every proxy variable removed. The installs are included because they run the checkout's lifecycle scripts, which a department may have changed. The department's standard and the program's integration already run through the composed shell, whose subprocess seam applies the repository's one shared scrub (`scrubbedParentEnv`: every name carrying `KEY`, `PASSWORD`, `SECRET` or `TOKEN` and every `DSH_*` name), so no second scrub was added there: the e2e now gives the engine a credential-named variable that the seeded heavy check fails on, and `T-0001` still certifies in its department and ships through the recertification.

**The subagent grant names the binaries.** The overlay pre-approves `Bash(pnpm exec vitest:*)` and `Bash(pnpm exec tsc:*)` in place of `Bash(pnpm exec:*)`. Every `pnpm exec` the recorded shift sessions ran was `vitest` (214 `vitest run`, 2 `vitest related`) apart from one `eslint`, which this repository does not install, and `tsc` is the other binary an acceptance form may run, so a department can still run every acceptance command it is given.

**The README states what is not confined.** The [fixture README](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/README.md#what-is-confined-and-what-is-not) lists, beside what the forms and the environment confine: nothing controls a department's or a check's network egress; the composed shell's scrub goes by name, so `GIT_ASKPASS`, the proxy variables and a credential under another name reach a department's shell and the program's checks; `HOME`, and with it a git credential helper or SSH keys the host keeps there, reaches every check; the push rewrite stops a mistaken push and a department's `git config` undoes it, and the recertification's checkout carries none; the read barrier's census counts `dsh-bash-local` `unenforced` and `isolationClaim: none` lets it run, so a shell reads whatever the host user can; and the forms bound the command line, not the test files and root scripts it runs, which a department may have written inside its scope.

## Alternatives considered

**Allow any root script for `pnpm run`.** The candidate form was `pnpm run <root script>`. The root names scripts that push (`enterprise`), publish (`enterprise:publish`, `release:publish`) or start an agent session (`dsh`), and a ticket naming one would pass that form, so the queue names its gates instead.

**Allow command substitution whose inner commands are allowed.** Three queued tickets count matching lines as `test "$(grep -l … | wc -l)" = 2`. Admitting `$(…)` when its content parses under the forms would keep them, but every expansion the lexer admits is one more place a later rule has to be right, and the same checks are expressible as `grep -q` per file. The tickets are reported for rewriting rather than the forms widened.

**Put the forms into `validateTickets`.** The validator already runs over the committed queue and inside the engine's `readQueue`, which throws on any invalid ticket. Four queued tickets break the forms, so every shift would stop at selection; refusing per ticket keeps the rest of the queue working and records why the four are not.

**Allowlist the composed shell too.** A fixture executor over `dsh-bash-local` could hand every command the allowlisted environment, a department's own shell included, which would take `GIT_ASKPASS` and the proxy variables away from it. That changes what every route department's shell can do between two cycles of an unattended enterprise and was left to the operator; the README states the gap.

## Consequences

Four open tickets carry acceptance commands outside the forms and are refused whenever a shift selects them, each with a ledger line naming the command: `T-0025`, `T-0028` and `T-0034` count matching lines through `$(…)`, and `T-0031` reads a JSON value with `node -e`. Each can be rewritten into allowed forms — `grep -q <text> <file>` once per file for the counts, and a `grep -qE` over `scripts/doc-budgets.manifest.json` for the ceiling — by an operator or a later intake. [`scripts/enterprise-acceptance.spec.ts`](../../../../scripts/enterprise-acceptance.spec.ts) pins those four as the only refused tickets of the committed queue, so a rewrite or a new ticket that breaks the forms shows up there.

## Verification

[`scripts/enterprise-acceptance.spec.ts`](../../../../scripts/enterprise-acceptance.spec.ts) accepts every form and rejects `git push`, `curl`, `gh`, command substitution, expansion, separators, redirection, a path outside the checkout, and chaining or piping into a disallowed command, and runs the forms over every committed ticket. [`scripts/enterprise-intake-admission.spec.ts`](../../../../scripts/enterprise-intake-admission.spec.ts) refuses a proposal that chains a push with `acceptance-form` before any of its checks runs. [`enterprise-shift.spec.ts`](../../../../examples/headless-agent/tests/enterprise-shift.spec.ts) covers the engine's refusal and shows that a spawned check under `checkEnvironment` sees neither `GH_TOKEN` nor `GIT_ASKPASS` and still sees the heavy lock. [`enterprise-shift.e2e.ts`](../../../../examples/headless-agent/tests/enterprise-shift.e2e.ts) runs the seeded `T-0006`, whose acceptance chains a `git push`, beside three worked tickets and alone, where no program runs and the refusal is pushed, and carries the credential-named variable through every shift; given a variable whose name carries no credential word in its place, `T-0001` fails its department's check, which is the name-based gap the README states. A fresh offline install of this repository, a ticket's coverage run (`pnpm exec vitest run packages/llm/llm-retry/ --coverage …`), `pnpm run typecheck` and `pnpm run doc-sync` passed under `checkEnvironment` on the operator's host, so the recertification's heavy runs keep working without the engine's environment.
