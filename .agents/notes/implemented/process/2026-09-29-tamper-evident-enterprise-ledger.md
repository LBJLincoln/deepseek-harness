# Agent Note: The enterprise ledger is append-only, and a gate checks it over any commit range

Status: implemented

English | [中文](2026-09-29-tamper-evident-enterprise-ledger.zh.md)

## Problem

[`data/enterprise/ledger.jsonl`](../../../../data/enterprise/README.md#the-ledger) is the enterprise's durable record: the shift engine's ticket lines, the cycle seats' and the intake's function lines. A client's auditor needs to check that, since a given commit, the file was only ever appended to and that every commit a line names is real. Nothing checked either. Before this change five commits did more than append: `d46e02bd9`, `d1aec806b` and `1f669dbf9` inserted lines before the end, in time order, `8a4dd9c02` merged 70 recovered lines into it in time order, and `dae1babd0` changed T-0007's line in place after a rebase moved its commit from `3d5210654` to `cba8e4682`. 57 lines name a commit the branch does not carry. Two runs that never wrote their own lines, a shift that crashed and a shift a container reset destroyed, left the ledger silent where the repository holds evidence of them.

## Decision

**Four rules over a commit range.** [`scripts/verify-enterprise-ledger.ts`](../../../../scripts/verify-enterprise-ledger.ts) (`pnpm run verify-enterprise-ledger -- --base <rev> [--head <rev>]`) walks every commit in `base..head` whose ledger differs from a parent's. A commit with one parent must keep the parent's lines as a prefix of its own. A merge must keep each parent's lines as a subsequence, which is what the `merge=union` driver produces when two writers append. Every added line must parse under `parseLedgerLine`. Every commit an added line names, as listed by `commitReferences` in [`scripts/enterprise-ledger.ts`](../../../../scripts/enterprise-ledger.ts) (`shipped.commit`, `target.commit`, `target.requested`, `target.via`), must be a full 40-hex id that exists and is an ancestor of the commit that added the line. A base the head does not contain fails as a rewritten branch, and a base missing from the clone fails loudly. Violations are reported per commit and line, and lines a failed commit kept from its parent are not reported a second time as added.

**The reference rule stays strict for every field.** Each unreachable reference in the real history came from a local checkout or clone whose history was rebased or never pushed: the intake's checkout commit `4a1f22151`, a judging re-run's checkout commit `3ed95172e` in `target.requested`, the diverged cycle checkout's `73a7727b5`, `2231af791` and `e1678940d`, and the T-0007 clone's pre-rebase `3d5210654`. Legitimate writers meet the strict rule: the shift engine rebases its assembled commits before its final push and rewrites its ledger lines around the new hashes ([the driver's `pushRounds`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/driver.ts)), and a cycle's function lines name the checkout it pulled from the branch. A recovery of a clone's unpushed work does the same before it pushes, or merges that history so the commits its lines name stay reachable. `target.requested` is checked too, although the verdict does not cover that commit, because a requested commit off the branch shows a run from an unpushed checkout, which is what the auditor needs to see.

**Wiring.** The gate is the `enterprise-ledger` leaf of `ci-static` in [`scripts/run-gates.ts`](../../../../scripts/run-gates.ts), reading its base from `DSH_LEDGER_BASE_REF`. The Branch CI static job sets that variable from `github.event.before` unless it is empty (a manual run) or all zeros (a push that created the branch); the job already checks out the full history, and its concurrency settings are unchanged. Without a base the gate checks only that every line of the head's ledger parses, and says so. The roster seats one verifier per `verify-*.ts` script, taking the first 14 in sorted order, so a new script would displace `verify-mermaid`'s seat; [`scripts/enterprise-roster.ts`](../../../../scripts/enterprise-roster.ts) excludes this gate by name, because it checks a range from a base the push names rather than the tree of the commit a seat covers.

**Lines written after the fact.** A line may carry `recordedBy` and `recordedAt`, both or neither. `recordedBy` is a closed set whose one member is `supervisor`, the session that operates the enterprise; `recordedAt` is when the line was written and may not precede `at`, which on such a line is when the event happened or the earliest moment the evidence establishes it. `parseLedgerLine` rejects any other combination, so the gate rejects it in an added line. The engine's `ticketStatuses` in [`shift.ts`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/shift.ts) still takes each ticket's last line in file order, except that a line with `recordedAt` replaces the current one only when its `at` is not earlier, so recording an old shift never reopens or recloses a ticket a later shift settled. Four such lines are appended, each citing its evidence in `reason`: shift `171951-516d`'s T-0012 (review approved, then the driver crashed in the assembly) and T-0019 (review rejected), from that shift's partial record and review sessions under `data/enterprise/shifts/2026-09-28-171951-516d/`; and shift `201448-94fd`'s T-0001 and T-0005, abandoned with the engine's `abandoned: container reset` reason, from `data/transcripts/LOSSES.md` and the restored orchestrator log (the shift's start at 20:14:48Z, its scratch directory last seen at 21:08:23Z and gone at 22:07:53Z). They leave `checks` empty and omit `model`, `tokens` and `seconds`, which only the lost or partial records could have totalled.

## Alternatives considered

- **Accept a reference whose patch matches a commit on the ancestry.** A pre-rebase commit is absent from a fresh clone, which is what CI and an auditor hold, so its patch cannot be computed there; matching on author, date and subject instead accepts any reference a writer chooses to forge.
- **A committed allowlist of disclosed violations that the gate honours.** It would make the historical range pass, but a list the same push can extend checks nothing. The README discloses the history instead, and an auditor's range that starts at `dae1babd0` or later passes.
- **Exempt `target.requested` from the reference rule.** Its only off-branch values come from checkouts that were not pushed, which is exactly the provenance gap the rule exists to expose.
- **Base CI on a fixed anchor commit instead of the push's `before`.** It would also cover pushes whose runs GitHub dropped as superseded pending runs, but it re-walks the whole history on every run and moves the question of which anchor to trust into the workflow; the per-push base is what the push itself asserts, and the gap is documented with the one-command audit that closes it.
- **Name the script outside the `verify-` prefix.** The file then reads as something other than a gate; the named exclusion in the roster keeps both the name and the roster's seats.
- **Take each ticket's status from its line with the newest `at`.** T-0007's shipped line, pushed late with `at` 02:04Z, is older than the halted attempt of 04:14Z, so ordering by `at` alone would reopen a shipped ticket; file order with after-the-fact lines placed by `at` keeps every current status.
- **Sign the engine's commits.** Signing needs a key the operator provisions and keeps out of the repository; it is not part of this change.

## Consequences

A push that inserts, deletes or changes a ledger line, or appends a line naming a commit off its ancestry, now fails the Branch CI static job. The gate proves that the history an auditor holds is consistent with append-only writing from a base the auditor chooses; it does not prove who wrote a line, and a force push that replaces the whole branch is detected only against a base the auditor recorded before it. Commit signing, which would bind lines to the engine, needs a key the operator must provision and decide on. GitHub keeps only the newest pending run of the workflow, so a push whose run was superseded has no run of its own; `pnpm run verify-enterprise-ledger -- --base <rev>` over any stretch checks all of it. The four after-the-fact lines give T-0001 and T-0005 a second attempt in the queue order, which places them after tickets tried once; the statuses of all four tickets, the roster's counts and the briefing's ticket statuses are unchanged, and the report now lists `201448-94fd` as a shift the ledger records with two halted tickets instead of a lost one.

## Verification

`scripts/verify-enterprise-ledger.spec.ts` builds real git repositories and proves that the gate rejects a line inserted before the end, a deleted line, a changed line, a reference off the adding commit's ancestry, a missing and an abbreviated reference, an unparsable line and an invalid `recordedBy`, a merge that drops a parent's line, and a head that no longer contains its base, and accepts pure appends, the first ledger a range creates, and a union merge of two branches that both appended. `scripts/enterprise-ledger.spec.ts` covers the `recordedBy`/`recordedAt` validation and `commitReferences`; `examples/headless-agent/tests/enterprise-shift.spec.ts` covers the placement of after-the-fact lines in `ticketStatuses`; `scripts/run-gates.spec.ts` keeps the gate in `ci-static`. Over the branch from `6fb91bb11` (2026-09-28T00:40Z) to `148490ce5` (2026-09-29T09:54Z) the gate reported 62 violations in the 16 commits that changed the ledger: the five non-append commits above and 57 lines naming `3ed95172e`, `4a1f22151`, `73a7727b5`, `2231af791`, `e1678940d` or `3d5210654`. From `dae1babd0` to the same tip it passed over two commits and 24 added lines. The engine's selection over the ledger with and without the four lines gave the same statuses for T-0001, T-0005, T-0007, T-0012 and T-0019 and the same first ten tickets in queue order.
