# Agent Note: The bench loop and its machine ledger

Status: implemented

English | [中文](2026-09-19-bench-loop-and-machine-ledger.zh.md)

## Problem

[The improvement log](../../../../data/proving-ground/improvement-log.md) listed four parts of the improvement loop that a person supplies. Two of them were mechanical work rather than judgment: a run was launched one plan at a time, and the reading it produced was copied into the log by hand. Launching one plan at a time meant an operator sat through each run to start the next, so a night's worth of comparisons needed a night's worth of attention, and nothing recorded what had been queued or why. Copying the reading by hand meant the log's numbers were a transcription of `result.json`, with no file between the record and the row that any later reader could replay: an iteration that ran but never gained a row left no trace of its verdict outside the record directory, and a row's numbers could drift from the record without any gate noticing.

## Decision

`pnpm run bench -- loop <queue>` runs an ordered queue of checked-in plans unattended. A queue is JSON — a checked-in name under [`queues/`](../../../../examples/headless-agent/tests/fixtures/proving-ground-bench/queues/) or a path — holding an array of `{ plan, overlay, note }` entries: `overlay` is an overlay name or `null` for the fixture's base composition, and `note` says why the entry is queued. `nightly-tier5.json` is the checked-in example. Every entry resolves through the same `resolvePlanPath` and `resolveOverlayPath` the `fleet` and `experiment` subcommands use, and the whole queue resolves before the first driver starts, so an unknown plan or overlay anywhere in the file refuses the command rather than stopping it halfway. An entry's driver follows from the plan itself: a `models` array is a fleet, a `baseline`/`candidate` pair is an experiment, and a plan declaring both or neither is refused.

Each entry runs into a run directory under the wrapper's runs root, exactly as `fleet` and `experiment` do, then is recorded by the same `record-run.mjs` a hand-recorded run uses, under `<UTC date>-bench-<plan>` with `-2`, `-3`, … appended when that name is taken, then summarized, then written as one line of `data/proving-ground/loop/ledger.jsonl`. The line carries `ranAt`, `queue`, `index`, `plan`, `overlay`, `kind`, `record`, `head`, `verdict`, `delta`, `interval`, `certified` per arm, `decision`, `elapsedSeconds`, `outcome`, and `reason` on a failure. Every number on it is read back out of the record that was just written — an experiment's verdict, delta, and interval from its `result.json`, each arm's certificates from that result's per-environment rates and pair counts, a fleet's certificates per model from its leaderboard, the elapsed seconds from the manifest — so the ledger states what the record states and invents nothing.

The decision rule is fixed in code and documented with it: verdict `promote` decides `adopt-candidate`, `reject` and `inconclusive` decide `keep-baseline`, a fleet carries no verdict and decides `recorded`, and a failed entry decides `none`. `adopt-candidate` names a decision, not an edit. Nothing in the loop writes a composition, because an arm cannot name one: carrying a promoted arm into `cordis.yml` or an overlay stays the human act the improvement log's third limitation describes.

A failed entry — a driver that exited non-zero, a recording `record-run.mjs` refused, a record whose result carries neither a verdict nor a leaderboard — is written to the ledger as `outcome: "failed"` with its reason, and the queue continues to the next entry; the command exits non-zero once the queue ends. `--dry-run` resolves everything, prints the schedule, and runs and writes nothing. `--from <n>` and `--only <plan>` resume a queue after an interruption, and both narrow the resolved queue rather than the parsed one, so a typo in a skipped entry is still refused.

The ledger is machine-owned and append-only: the loop writes it, nothing else does, and it is absent until the first iteration runs. [`build-dashboard.mjs`](../../../../data/proving-ground/tools/build-dashboard.mjs) reads it when it exists and renders a Loop section — when, queue and position, plan, overlay, kind, per-arm certificates, delta with interval, verdict, decision, wall time, and a link to the record — which stays hidden while the ledger is absent or empty, like the page's Running-now section. The records' own lanes, cards, and rows are untouched. [The improvement log](../../../../data/proving-ground/improvement-log.md) remains hand-written and remains the ledger a reader reads; what changed is that its rows now read a durable, replayable machine line instead of a record directory alone.

## Alternatives considered

- **Generate the improvement log's rows from the ledger.** Rejected for the same reason [the improvement-log note](2026-09-19-improvement-log-as-the-loop-ledger.md) rejected generating them from the records: the proposed change, the reason a decision was taken, and the default that moved are in no file the loop writes. The ledger carries a decision label, not the sentence that weighs a verdict against its cost, and generating the two columns a machine can fill would leave the log's actual subject in a hand-maintained sidecar.
- **Extend the improvement log itself with machine-appended rows.** Rejected: a Markdown table that both a person and a command write has no owner, and a machine append would conflict with the editorial rewriting a row's decision column needs. Keeping the machine ledger in its own JSONL file gives each artifact one writer and makes the machine's half diffable line by line.
- **Let the loop apply an adopted candidate to the composition.** Rejected: an experiment arm names a route and a ladder, not a composition, so there is no mechanical translation from a promoted arm to a `cordis.yml` edit, and a verdict on sixteen cells is not by itself a reason to move a shipped default. The rule names the decision and stops there.
- **Stop the queue at the first failure.** Rejected: the failures worth surviving are per-run — a driver that died on one plan, a container restart, a record name already taken — and the remaining entries are independent runs. Stopping would forfeit a night of runs to one bad entry; the non-zero exit at the end keeps the failure visible.
- **Schedule the queue as well, with cron or a verdict trigger.** Rejected for now: a schedule needs a policy for what to queue and when to stop, and the bench runs on the operator's own subscription. The loop closes the launching gap; the improvement log still records that a schedule and a verdict-driven trigger are absent.

## Consequences

- One command runs a night of comparisons: a queue of three tier-5 plans records three runs, decides three times, and leaves three ledger lines, where an operator previously started each run and read each result.
- The machine's half of the loop is replayable. Every ledger line names its record, its head, and its queue position, so a row of the improvement log can be checked against the record it claims to read, and an iteration that never gained a row is still on file.
- The ledger is a new durable format with no compatibility promise, in line with the pre-release stance: it is append-only JSONL, read by `build-dashboard.mjs` and by people, and a field added to the line changes the page's Loop section in the same change.
- Failure states are recorded rather than lost: a driver that exits non-zero leaves a line naming its run directory, and a record the reading cannot interpret leaves a line naming the record.
- `scripts/proving-ground.spec.ts` covers queue parsing and its refusals, plan and overlay resolution, plan classification, record-name suffixing, the decision rule, the reading of two checked-in records, the ledger line, and the end-to-end `--dry-run` over the checked-in queue. A real queued run needs the operator's Claude Code subscription, so no test runs a driver.
