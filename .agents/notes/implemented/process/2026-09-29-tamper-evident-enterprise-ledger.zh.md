# Agent Note: 企业台账只可追加，并由一道关卡在任意提交范围上检查

Status: implemented

[English](2026-09-29-tamper-evident-enterprise-ledger.md) | 中文

## Problem

[`data/enterprise/ledger.jsonl`](../../../../data/enterprise/README.md#the-ledger) 是企业的持久记录：班次引擎的工单行，以及周期席位与受理的职能行。客户的审计方需要核实：自某个给定提交起，该文件只被追加过，且每一行所指明的每个提交都真实存在。此前两者都无人检查。在这次改动之前，有五个提交做的不只是追加：`d46e02bd9`、`d1aec806b` 与 `1f669dbf9` 按时间顺序在末尾之前插入了行，`8a4dd9c02` 把恢复出的 70 行按时间顺序合入其中，`dae1babd0` 则在一次变基把 T-0007 的提交从 `3d5210654` 移到 `cba8e4682` 之后就地改动了它的行。有 57 行指明了分支上不存在的提交。还有两次运行从未写下自己的行——一个崩溃的班次，以及一个被容器重置销毁的班次——使台账在仓库持有其证据之处保持沉默。

## Decision

**在一个提交范围上的四条规则。** [`scripts/verify-enterprise-ledger.ts`](../../../../scripts/verify-enterprise-ledger.ts)（`pnpm run verify-enterprise-ledger -- --base <rev> [--head <rev>]`）遍历 `base..head` 中台账与某个父提交不同的每个提交。只有一个父提交的提交，必须把父提交的各行作为自身的前缀保留下来。合并提交必须把每个父提交的各行作为子序列保留下来，这正是两个写入方都做了追加时 `merge=union` 驱动产生的结果。每条新增行都必须能被 `parseLedgerLine` 解析。新增行所指明的每个提交——即 [`scripts/enterprise-ledger.ts`](../../../../scripts/enterprise-ledger.ts) 中 `commitReferences` 列出的 `shipped.commit`、`target.commit`、`target.requested`、`target.via`——都必须是存在的完整 40 位十六进制 ID，并且是添加该行的提交的祖先。若头提交不包含基准提交，按分支被改写判为失败；若克隆中缺少基准提交，则明确报错失败。违规按提交与行号报告；某个失败提交从父提交保留下来的行，不会再作为新增行重复报告。

**引用规则对每个字段都保持严格。** 真实历史中每一个不可达的引用，都来自一个其历史被变基或从未推送的本地检出或克隆：受理所在检出的提交 `4a1f22151`，一次评判重跑所在检出的提交 `3ed95172e`（位于 `target.requested`），分叉的周期检出中的 `73a7727b5`、`2231af791` 与 `e1678940d`，以及 T-0007 所在克隆变基之前的 `3d5210654`。正当的写入方都满足这条严格规则：班次引擎在最后一次推送前把组装好的提交变基，并围绕新的哈希改写其台账行（[驱动程序的 `pushRounds`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/driver.ts)）；周期的职能行指明的是它从分支拉取的检出。恢复某个克隆中未推送的工作时，在推送前也这样做，或者合并那段历史，使其各行指明的提交保持可达。`target.requested` 同样受检，尽管裁决并不覆盖该提交，因为不在分支上的被请求提交表明有一次运行来自未推送的检出，而这正是审计方需要看到的。

**接线。** 该关卡是 [`scripts/run-gates.ts`](../../../../scripts/run-gates.ts) 中 `ci-static` 的 `enterprise-ledger` 叶节点，从 `DSH_LEDGER_BASE_REF` 读取基准。Branch CI 的静态作业用 `github.event.before` 设置该变量，除非它为空（手动运行）或全为零（创建分支的推送）；该作业本就检出完整历史，其并发设置保持不变。没有基准时，关卡只检查头提交台账的每一行都能解析，并如实说明。花名册为每个 `verify-*.ts` 脚本设一个校验员席位，按排序取前 14 个，因此新脚本会挤掉 `verify-mermaid` 的席位；[`scripts/enterprise-roster.ts`](../../../../scripts/enterprise-roster.ts) 按名称排除这道关卡，因为它检查的是推送所指明的基准起的一个范围，而不是某个席位所覆盖提交的文件树。

**事后写入的行。** 一行可以带有 `recordedBy` 与 `recordedAt`，二者同时出现或同时缺省。`recordedBy` 是一个封闭集合，唯一成员是 `supervisor`，即运营该企业的会话；`recordedAt` 是写下该行的时间，不得早于 `at`，而在这样的行上 `at` 是事件发生的时间，或证据所能确立的最早时刻。`parseLedgerLine` 拒绝任何其他组合，因此关卡会拒绝带有这种组合的新增行。[`shift.ts`](../../../../examples/headless-agent/tests/fixtures/enterprise-shift/shift.ts) 中引擎的 `ticketStatuses` 仍按文件顺序取每张工单的最后一行，只是带 `recordedAt` 的行仅在其 `at` 不早于当前那一行时才取而代之，因此补记一个旧班次绝不会重新打开或重新关闭一张已由更晚班次定论的工单。追加了四条这样的行，每条都在 `reason` 中引用其证据：班次 `171951-516d` 的 T-0012（评审通过，随后驱动程序在组装中崩溃）与 T-0019（评审拒绝），依据该班次位于 `data/enterprise/shifts/2026-09-28-171951-516d/` 的部分记录与评审会话；以及班次 `201448-94fd` 的 T-0001 与 T-0005，按引擎的 `abandoned: container reset` 原因记为放弃，依据 `data/transcripts/LOSSES.md` 与恢复后的编排器日志（该班次于 20:14:48Z 开始，其临时目录最后一次出现在 21:08:23Z，到 22:07:53Z 时已不存在）。它们让 `checks` 保持为空，并省略 `model`、`tokens` 与 `seconds`，这些只有丢失的或不完整的记录才能汇总出来。

## Alternatives considered

- **接受补丁与祖先链上某个提交相同的引用。** 变基之前的提交在全新克隆中并不存在，而 CI 与审计方持有的正是全新克隆，因此无法在那里计算其补丁；改为按作者、日期与主题匹配，则会接受写入方任意伪造的引用。
- **提交一份由关卡认可的已披露违规白名单。** 它会让历史范围通过检查，但同一次推送就能扩充的名单什么也检查不了。README 转而披露这段历史；审计方从 `dae1babd0` 或更晚处开始的范围能够通过。
- **把 `target.requested` 排除在引用规则之外。** 它仅有的不在分支上的取值都来自未推送的检出，而这正是该规则要揭示的来源缺口。
- **让 CI 以一个固定的锚点提交而非推送的 `before` 为基准。** 它也能覆盖 GitHub 作为被取代的待运行任务而丢弃的那些推送，但每次运行都要重新遍历整段历史，并把信任哪个锚点的问题搬进工作流；按推送取基准，是推送本身所声明的内容，而这一缺口连同弥补它的一条审计命令已写入文档。
- **给脚本起一个不带 `verify-` 前缀的名字。** 那样文件读起来就不像一道关卡；在花名册中按名称排除，既保住了名字，也保住了花名册的席位。
- **取 `at` 最新的那一行作为每张工单的状态。** T-0007 的交付行推送得晚，其 `at` 为 02:04Z，早于 04:14Z 那次被停下的尝试，因此仅按 `at` 排序会重新打开一张已交付的工单；按文件顺序、并把事后写入的行按 `at` 放置，则保留了每一个现有状态。
- **为引擎的提交签名。** 签名需要一把由运营方配置并存放在仓库之外的密钥；这不属于本次改动。

## Consequences

凡是插入、删除或改动台账行，或追加一条指明其祖先链之外提交的行的推送，现在都会让 Branch CI 的静态作业失败。该关卡证明，审计方持有的历史与从其自选基准起的只追加写入相一致；它不证明某一行由谁写下，而替换整个分支的强制推送，只有相对于审计方事先记下的基准才会被发现。为提交签名能把各行与引擎绑定，但这需要一把运营方必须配置并做出决定的密钥。GitHub 对该工作流只保留最新一次待运行的任务，因此运行被取代的推送没有属于自己的运行；在任一时间段上执行 `pnpm run verify-enterprise-ledger -- --base <rev>` 即可检查全部。四条事后写入的行让 T-0001 与 T-0005 在队列顺序中多了一次尝试，从而排在只尝试过一次的工单之后；这四张工单的状态、花名册的计数以及简报的工单状态都没有改变，而报告现在把 `201448-94fd` 列为台账记录的、带两张被停下工单的班次，而不再列为丢失的班次。
