# Agent Note: 程序工作流构建软件

Status: implemented

[English](2026-09-19-program-workflow-builds-software.md) | 中文

## Problem

程序工作流只被端到端跑通过一次，而它交付的是一份文档。2026-09-08 的[自评估运行](../../../../data/proving-ground/README.md)在 Claude Code 路由上配备了一个部门，让它写出 `assessment.md`，并用一个已提交的结构验证器为其签发证书。于是这套工作流提出的每一条主张——部门在一次提交上被认证、分支只在仍指向已认证修订版时才被合并、对合并后 head 的整合证书才是发布的依据——都只在单个文件上被检验过，而那个文件的考官只会数章节与引用。

交付软件才是这套工作流存在的场景，而它从未被运行过。一个构建程序的程序，也正是工作流自身那些规则不再只是仪式的地方：多个部门写出的文件必须能组合起来，合并是各部分第一次相遇的时刻，而验证器是一套要么能把结果跑起来、要么不能的测试套件。

## Decision

[`examples/headless-agent/tests/fixtures/program-csv-tools/`](../../../../examples/headless-agent/tests/fixtures/program-csv-tools/README.md) 是一个交付物为 `csv-tools` 的程序：一个零依赖的 Node.js 命令行，带 `stats`、`filter` 与 `join` 三个子命令。三个部门各拥有一个子命令；第一个部门还拥有共享的 RFC 4180 读写器，而 `filter` 与 `join` 依赖它。程序交付进入的仓库就是 fixture 的 `seed/`，由 driver 提交并打上 `base` 标签：`SPEC.md`——引号规则、表头处理、空输入与畸形输入的行为、退出码以及 stdout/stderr 纪律——外加 `bin/csv-tools.js`、`package.json` 和 `test/` 下的一套 `node:test` 套件。发布树中的每一个源文件都由某个部门写成。

每个部门依据已提交套件中覆盖其自身模块的那部分被认证，外加 `test ! -e node_modules`。整合在合并后的 head 上运行整套套件，随后是两道门禁：`test -z "$(git status --porcelain)"` 以及同一条零依赖规则，于是"要么提交、要么拒绝"这条规则进入了证书，而不只停留在程序拒绝测量脏工作树这一层。账本本来就记录每份部门证书所覆盖的修订版与 `HEAD^{tree}`，e2e 会把这三对都从中读出来。

组合沿用自评估那一份，预算、持久化、检查点与程序条目都相同，只增加一项：读屏障。那次运行的整合会话未被约束，找到了部门的 worktree 并改写了已认证文件中的句子。这里，程序在整合会话运行期间对它拒绝整个工作树根。

`cordis.yml` 是无密钥的：部门跑在 `cli-mock` 路由上，其脚本化回合读 `SPEC.md`、写出提交在 `scripted/src/` 下的模块并提交；`overlays/claude-code.cordis.yml` 是同一份文件，禁用该路由并换上操作者的 Claude Code 安装。两者的 `implementer` 都保持 `route`，而路由不属于规格摘要，因此两次运行是同一组目标上的同一个程序 id。`examples/headless-agent/tests/program-csv-tools.e2e.ts` 在 e2e 泳道中运行无密钥的那一半；fixture 的 README 对则为真实运行给出启动命令、产物清单与 `record-run.mjs` 调用。

### 基线版本决定了软件的形态

每个部门 worktree 都从 `baseRevision` 切出，因此一个部门永远看不到另一个部门的文件。这决定了布局：`src/filter.js` 与 `src/join.js` 不 import 任何东西并各自重述规格中的数字规则，`bin/csv-tools.js` 归 seed 所有、是读写器与子命令唯一相遇的地方，而每个子命令模块都接收并返回一个表。端到端套件 `test/cli.test.js` 因此只在合并后的 head 上通过、在任何部门分支上都不通过——正是这一点使整合证书成为发布，而不是在三条已经通过的分支之上走个过场。

于是依赖边的作用是给工作排序，而不是给它供料：`filter` 与 `join` 只在拥有读写器的那个部门持有证书之后才启动，因为与未认证读写器组合出的合并 head 不值得整合。

## Alternatives considered

**把解析器放进 seed，每个部门只做一个子命令。** 那样每个部门在构造上就彼此独立，依赖边也就成了摆设。它还把交付物中最难的部分直接交给部门，而那恰恰是程序最希望被测量的部分。

**让被依赖方的部门 worktree 从其依赖的分支切出。** 那样模块之间就能直接 import。程序从 `baseRevision` 创建每一个 worktree，改动这一点将意味着某个部门的证书覆盖了另一个部门所做的工作，而整合合并也不再是各部分第一次相遇。规则保持不变，软件的形态围绕它调整。

**让脚本化 implementer 在适配器内部以字符串形式给出模块内容。** 那样交付的代码就无法作为代码被评审、检查或运行。它以真实文件的形式放在 `scripted/src/` 下，由 fixture 自己的检查执行，而适配器通过 `write` 工具写出这些字节，因此部门会话所携带的与分支上的完全一致。

**让脚本化 implementer 用 `cp` 拷贝文件。** 更短，但记录下来的将是一次拷贝而不是源代码——部门会话对所交付内容一无所示，正是外部 implementer 路由已有的失效模式，没有理由在不存在该问题的路由上复制它。

**扩展 `fixtures/program/` 而不是新增 fixture。** 那个 fixture 回答的是账本、跨终止开关的协调以及屏障拒绝；给它加上真实交付物会让一个 fixture 同时回答两个问题，也会让两者都更难读。

**把交付物做成对本仓库的改动。** 那样基线版本就是 harness，检查就是仓库自己的关卡，而失败的运行无法区分是工作流的问题还是关卡的问题。一个独立的小交付物让工作流成为唯一变量；等这一个有了已记录的判定，仓库就是下一个值得一试的场景。

**为程序的 transcript 增加一个快照场景。** 这套工作流放到模型面前的文本只有目标描述与验证方的指令；e2e 已从持久日志中逐字断言了该指令，而目标描述提交在 driver 里。driver 打印的是一份 JSON 报告而不是会话事件流，因此快照需要第二种输出模式，换来的覆盖却是 e2e 已有的。

## Consequences

工作流现在有了一个判定为"一个能运行的程序"的场景：无密钥 e2e 约五秒完成发布，随后从整合 worktree 中把三个子命令各执行一遍。它还钉住了文档型交付物几乎没有检验到的两条规则——`join` 部门故意让第一次尝试不提交，挣得 `the worktree carries work that no commit on this branch carries`，并由提交了的那次尝试获得证书；以及账本中三个已认证的修订版与树被断言为与合并后的 head 不同。

无密钥运行不能证明的，是模型能构建出什么。它证明的是规格被冻结、部门被配备与设限并在已提交的树上被认证、分支被合并，以及已提交的验证器决定发布。回答另一半的是 Claude Code 路由上的真实运行；在它被记录到 `data/proving-ground/` 之前，本 fixture 只是一份接线证明。

`SPEC.md` 与那套套件都提交在本仓库中，因此见过本仓库的模型也就见过考官。真实运行度量的因而是工作流，而不是任务的新颖度；能力主张所需要的是一个留出的交付物。

由于干净的合并会直接通过整合标准，整合会话不会被给予任何回合、不会拒绝任何读取，本次运行的拒绝清单为空，而 `program/integration` 仍记录了被拒绝的目录。e2e 对两者都做了断言，因此这份空清单是被解释过的伴生物，而不是缺失。
