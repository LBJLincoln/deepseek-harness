## Executive summary

This review covered the locked source tree at `/root/targets/NodeGoat` (111 files, sha256 `78ac112b7bd5083bb065086c4642dcd8a3932a8d3052f9405503124c90a70fe3`), the OWASP NodeGoat training application. Six departments (access, data, dependencies, injection, platform, secrets) each read a slice of the repository, grounded by the Semgrep 1.177.0 static scanner and, for dependencies, by `npm audit` against the live npm registry; the integration then merged their 48 raw findings into 47 unique findings, deduplicated by file, line and CWE. The review found 4 critical, 18 high, 17 medium, 7 low and 1 informational finding. The three most important: (1) server-side arbitrary code execution via `eval()` on the request-body fields of `POST /contributions` (`app/routes/contributions.js:32`), reachable by any authenticated user; (2) an admin account seeded with the plaintext password `Admin_123` (`artifacts/db-reset.js:18`), letting anyone log in as an administrator without ever signing up; (3) persistent script injection through unfiltered Markdown rendering of memos, visible to every logged-in user (`app/views/memos.html:31`). The review covered HTTP entry points, authentication, session handling, sensitive-data storage, rendering templates and the dependency manifest; it did not cover git history, dynamic testing against a running instance, vendored front-end libraries used as-is, or deployment infrastructure (see "What was not covered"). Method: entry points read before any conclusion, data traced from source to sink, one finding per sink, the exact line quoted and mechanically checked by the program's examiner, and a stated confidence level for each.

## Scope and method

Target: `/root/targets/NodeGoat`, locked in `target.json` to 111 files under sha256 `78ac112b7bd5083bb065086c4642dcd8a3932a8d3052f9405503124c90a70fe3`. The target is read-only for this program; `verify-safety-report.mjs` re-hashed every locked file against that lock before this report was written, and reported the tree unchanged.

Six departments ran, each on its own branch, each committing `findings/<department>.json` and `report/<department>.md`: **access** (authentication, session handling, authorization, CSRF), **data** (sensitive data exposure, logging, cryptography, transport), **dependencies** (manifest and lockfile advisories), **injection** (SQL/NoSQL/code injection, XSS, open redirect), **platform** (security headers, cookies, CORS, error handling, rate limiting, Docker/Compose), and **secrets** (hard-coded credentials and leaked configuration). The integration is a seventh pass that merges their output and adds no new source reading of its own beyond what was needed to check the union and this report.

Tools that ran: **Semgrep 1.177.0**, run independently by five of the six departments (access, data, dependencies, injection, platform) with the local `program-code-safety` rule pack plus the registry pack `p/owasp-top-ten` (`--metrics off --json`), covering 72 git-tracked files with 113 rules and returning 29 hits each run; every hit was read as a place to look, never counted as a finding on its own. **`npm audit --json`**, run by the dependencies department against the reachable npm registry (`npm ping` returned `PONG`), resolving 1,479 packages and reporting 145 vulnerable packages, condensed to 15 findings on the 24 vulnerable direct dependencies plus two maintenance-only packages. The committed mechanical examiner, **`verify-safety-report.mjs`**, was run by every department against its own `findings/<department>.json` before commit (`--findings`, all six returned `ok` with no invalid ids under `--list-invalid`), and was run again here against the merged `findings.json` and this report (`--report`).

Files actually read, by department, per their own committed reports: `server.js` in full; every route handler under `app/routes/` (`index.js`, `session.js`, `profile.js`, `contributions.js`, `allocations.js`, `benefits.js`, `memos.js`, `research.js`, `tutorial.js`, `error.js`); every DAO under `app/data/` (`user-dao.js`, `profile-dao.js`, `allocations-dao.js`, `benefits-dao.js`, `contributions-dao.js`, `memos-dao.js`, `research-dao.js`); the views `app/views/profile.html`, `app/views/memos.html`, `app/views/layout.html`, `app/views/error-template.html`; `config/config.js` and every file under `config/env/`; `artifacts/db-reset.js` and `artifacts/cert/server.key`/`server.crt`; `docker-compose.yml`, `Dockerfile`, `app.json`, `Procfile`; `package.json` and `package-lock.json`; CI configuration (`.travis.yml`, `.github/workflows/*.yml`); and the credential-bearing test fixtures under `test/e2e/fixtures/users/` and `test/security/profile-test.js`. This is a static, offline review by a language model: no department started the application, attempted a login, forged a session cookie, or sent a crafted payload against a running instance.

## Findings

### critical

- `deps-mongodb` — mongodb driver (`^2.1.18`, installed 2.2.36) pulls a critically vulnerable bson deserializer (`package.json:18`, CWE-502, likely) — an attacker who can influence BSON bytes the driver deserializes can trigger memory corruption or a crash across every route that touches MongoDB; upgrade to a maintained 7.x driver line.
- `injection-eval-contributions` — server-side code injection via `eval()` on request body fields (`app/routes/contributions.js:32`, CWE-95, confirmed) — any authenticated user can submit a body that runs arbitrary Node.js code on the server via `POST /contributions`; replace `eval()` with `Number()`/`parseInt()` and reject non-numeric input.
- `injection-xss-memos-marked` — stored XSS visible to every user via unescaped Markdown rendering of memo content (`app/views/memos.html:31`, CWE-79, likely) — a crafted memo can run script in the browser of every user who opens `/memos`, including an admin; render Markdown through a maintained sanitizer (DOMPurify/sanitize-html) rather than relying on `marked`'s deprecated `sanitize` option.
- `secrets-admin-seed-password` — admin account seeded with a hard-coded plaintext password compared by strict equality (`artifacts/db-reset.js:18`, CWE-798, confirmed) — any unauthenticated visitor can log in as `admin`/`Admin_123` on a deployment that ran the seed script; generate a random password per deployment, hash it, and force a change on first login.

### high

- `access-csrf-missing-profile-update` — no CSRF protection anywhere in the app; profile update (bank account, SSN, address) is forgeable from a cookie-authenticated session (`app/routes/index.js:48`, CWE-352, confirmed) — a cross-site form can silently overwrite a victim's bank/SSN/address data; re-enable `csurf()` and include the token in every state-changing form.
- `access-idor-allocations-userid` — allocations page is an IDOR: any logged-in user can read any other user's allocation data by changing the URL (`app/routes/index.js:63`, CWE-639, confirmed) — walk `:userId` to enumerate other users' financial records; load allocations for `req.session.userId` only, or verify ownership before querying.
- `access-missing-admin-check-benefits-update` — admin-only benefits update has no role check; any logged-in user can change any other user's benefit start date (`app/routes/index.js:56`, CWE-862, confirmed) — full vertical privilege escalation on a state-changing route; apply the existing `isAdmin` middleware to both the GET and POST `/benefits` routes.
- `access-password-compare-not-constant-time` — login compares passwords with plain string equality on plaintext-stored passwords, not a constant-time hash verify (`app/data/user-dao.js:61`, CWE-916, confirmed) — timing leakage plus plaintext-at-rest disclosure on any DB read; hash with bcrypt and verify with `bcrypt.compareSync`.
- `data-cleartext-http-transport` — the application only ever listens over plain HTTP; the HTTPS path is fully commented out (`server.js:145`, CWE-319, confirmed) — credentials, session cookies and SSN/bank data travel in the clear on the wire; enable the existing `https.createServer` path and redirect HTTP to HTTPS.
- `data-plaintext-password-storage` — passwords are stored and compared in cleartext, never hashed (`app/data/user-dao.js:25`, CWE-256, confirmed) — any read access to the `users` collection discloses every account's real password; hash with bcrypt on signup and verify with `bcrypt.compareSync`.
- `data-secrets-logged-on-startup` — session-signing secret and crypto key are printed to stdout on every application start (`config/config.js:13`, CWE-532, confirmed) — anyone who reads process logs recovers the exact secret used to sign session cookies and can forge one for any user; remove the config dump or redact secret-bearing keys before logging, and rotate the current values.
- `data-ssn-bank-cleartext-storage` — SSN, date of birth and bank account/routing numbers are stored in the database unencrypted (`app/data/profile-dao.js:55`, CWE-312, confirmed) — read access to the `users` collection discloses PII and financial data enabling identity theft/fraud; encrypt at rest with an authenticated cipher keyed from a KMS/secrets manager.
- `deps-marked` — `marked` pinned to `0.3.5` (exact, no range) renders user-supplied memo text with none of six later sanitization/ReDoS fixes applied (`package.json:17`, CWE-79, likely) — enables the memo XSS path above and a ReDoS on crafted memo bodies; upgrade to at least `marked@0.3.19`, pin with a range going forward.
- `deps-swig` — `swig` (installed 1.4.2, the last release ever published) is the app's view engine and carries an unfixed path-traversal advisory (`package.json:22`, CWE-22, likely) — a request path that influences which template renders could read arbitrary server-readable files, with no upstream fix available; replace swig with a maintained template engine.
- `deps-underscore` — `underscore` (`^1.8.3`, installed 1.9.1) is below the version that fixes a template code-execution advisory (`package.json:23`, CWE-94, likely) — attacker-influenced data reaching `_.template` or the affected recursive functions yields code execution or a DoS; upgrade to `underscore@1.13.7` or later.
- `injection-nosql-where-allocations` — NoSQL injection via unescaped `$where` clause built from a query-string threshold (`app/data/allocations-dao.js:78`, CWE-943, confirmed) — a crafted `threshold` triggers a MongoDB-side infinite loop or breaks out of the intended comparison to read other users' records; build queries from typed, bounds-checked fields instead of a `$where` string.
- `injection-xss-profile-reflected` — reflected XSS via unescaped `firstName` echoed back on profile validation failure (`app/views/profile.html:41`, CWE-79, confirmed) — a crafted `firstName` executes script in the submitting user's browser, and can exfiltrate the session cookie because CSRF is disabled and the cookie is not httpOnly; re-enable Swig autoescape or HTML-encode the field.
- `injection-xss-profile-stored` — stored XSS via unescaped profile fields persisted to MongoDB and re-rendered (`app/views/profile.html:45`, CWE-79, confirmed) — a payload in `lastName` (and five sibling fields on the same page) executes on every later profile view, enabling account takeover via cookie theft; re-enable autoescape and validate/sanitize before persisting.
- `platform-cookie-flags-missing` — session cookie is configured with no httpOnly, secure or sameSite attribute and keeps the default cookie name (`server.js:78`, CWE-1004, confirmed) — the session id is readable via XSS, sent over plain HTTP, and attached on cross-site requests; set `cookie: { httpOnly: true, secure: true, sameSite: 'strict' }` once served over HTTPS.
- `platform-csrf-disabled` — CSRF protection is installed as a dependency but never mounted (`server.js:104`, CWE-352, confirmed) — every state-changing POST route accepts forged cross-site requests; uncomment the `csurf()` middleware and wire the token into every form.
- `platform-no-tls` — server only listens over plain HTTP; the HTTPS setup is fully commented out (`server.js:144`, CWE-319, confirmed) — the same cleartext-transport exposure as `data-cleartext-http-transport`, confirmed independently by reading the same middleware stack; terminate TLS and redirect HTTP to HTTPS.
- `secrets-cookie-secret` — Express session-signing secret is hard-coded in committed configuration and applies to every environment including production (`config/env/all.js:8`, CWE-798, confirmed) — anyone who has read the repository can forge a validly-signed session cookie for any user id; read the secret from a required environment variable with no literal fallback, and rotate it.

### medium

- `access-login-no-session-regenerate` — login does not regenerate the session id, allowing session fixation (`app/routes/session.js:116`, CWE-384, confirmed) — a session id fixed before login inherits the victim's post-login privileges; call `req.session.regenerate()` before setting `req.session.userId`, as signup already does.
- `access-session-cookie-insecure-config` — session cookie is configured with no httpOnly, no secure flag, and no maxAge (never expires) (`server.js:78`, CWE-614, confirmed) — a stolen or fixed session id remains valid indefinitely; set a bounded `cookie` block and serve over HTTPS.
- `data-hardcoded-creds-logged` — seed script logs hard-coded plaintext admin and user passwords to stdout on every container start (`artifacts/db-reset.js:99`, CWE-532, confirmed) — anyone who reads container/CI logs recovers the admin password; never log a user object containing a password field.
- `data-verbose-error-to-client` — internal error objects are rendered directly to the client on every unhandled error (`app/routes/error.js:10`, CWE-209, confirmed) — any triggered server error discloses internal message text/paths that help an attacker map the backend; render a generic message and log detail server-side only.
- `deps-body-parser` — `body-parser` (installed 1.18.3) is below the version that fixes a request-parsing DoS (`package.json:9`, CWE-405, likely) — a crafted urlencoded body can consume disproportionate CPU/memory on any route accepting a body; upgrade to `1.20.6` or later.
- `deps-express` — `express` (installed 4.16.4) is below the versions that fix an open-redirect and an XSS advisory (`package.json:13`, CWE-601, likely) — a malformed URL can be redirected to an attacker host by any route that echoes a path segment into a redirect; upgrade to at least `4.21.3`.
- `deps-forever` — `forever` (installed 2.0.0) carries the largest transitive advisory tree of any direct dependency (`package.json:15`, CWE-1321, possible) — prototype-pollution issues in its config/argument-parsing chain matter if it is run against untrusted config; upgrade to `forever@4.0.3` or replace it with a maintained process supervisor.
- `deps-grunt` — `grunt` itself (not just its dependencies) carries a code-execution advisory (`package.json:45`, CWE-1188, likely) — running `npm test`/`db:seed`/the precommit hook against an untrusted Gruntfile is a build/CI-risk path; upgrade to the latest 1.x, which npm audit reports as a non-major fix.
- `deps-helmet` — `helmet` (installed 2.3.0) is four major versions behind and its transitive chain carries a ReDoS advisory (`package.json:16`, CWE-400, likely) — a crafted string can tie up the event loop via `debug`, and the app misses seven generations of hardened defaults; upgrade to `helmet@8.x`.
- `injection-nosql-login-operator` — NoSQL operator injection in login lookup via JSON request body (`app/data/user-dao.js:91`, CWE-943, confirmed) — a JSON `userName` object such as `{"$regex":"^a"}` lets an unauthenticated caller enumerate valid usernames; reject any `userName`/`password` that is not a string before the DAO call.
- `injection-open-redirect-learn` — open redirect via unvalidated `url` query parameter (`app/routes/index.js:72`, CWE-601, confirmed) — a crafted `/learn?url=` link redirects an authenticated victim to a phishing site under the trusted domain; validate the destination against an allowlist.
- `platform-default-env-is-development` — config defaults to the development environment when `NODE_ENV` is unset, injecting a live-reload script and debug settings into every page (`config/config.js:5`, CWE-1188, confirmed) — a deployment that forgets to set `NODE_ENV=production` has every page fetch and execute a live-reload script from the requesting host; fail closed instead of defaulting to development.
- `platform-missing-security-headers` — all Helmet security headers (frameguard, CSP, HSTS, MIME-sniffing, X-Powered-By) are commented out (`server.js:38`, CWE-693, confirmed) — responses carry none of the standard hardening headers and fingerprint the framework; uncomment and mount Helmet with an explicit configuration before routes are registered.
- `platform-no-rate-limit-auth-routes` — no rate limiting or lockout on the login and signup routes (`app/routes/index.js:32`, CWE-307, confirmed) — unlimited password guessing against any known username; add a rate limiter keyed by IP and by submitted username.
- `platform-open-redirect-learn` — the `/learn` route redirects to an attacker-supplied URL taken straight from the query string (`app/routes/index.js:70`, CWE-601, confirmed) — independently confirmed instance of the same sink as `injection-open-redirect-learn`, read from the platform department's own pass over `server.js`'s route wiring; validate the destination against an allowlist.
- `platform-session-unbounded-lifetime` — sessions are created for every visitor and never expire (`server.js:82`, CWE-613, confirmed) — sessions accumulate indefinitely in the in-memory store and a stolen session id remains valid far longer than necessary; set `saveUninitialized: false` and a bounded `cookie.maxAge`, back the store with a persistent session store.
- `secrets-committed-private-key` — RSA private key is committed to the repository alongside its matching certificate (`artifacts/cert/server.key:1`, CWE-321, likely) — if HTTPS is enabled by uncommenting the disabled code path, any deployment reusing this key lets anyone who ever cloned the repository impersonate the server or decrypt captured traffic; remove the key from source control and generate a fresh pair per environment.

### low

- `deps-bcrypt-nodejs-unmaintained` — `bcrypt-nodejs`, used for password hashing, has had no release since 2013 (`package.json:8`, CWE-1104, confirmed) — a security-critical function rests on a package with no maintainer response path; migrate to `bcrypt` or `bcryptjs`.
- `deps-csurf` — `csurf` is archived upstream and only carries a low-severity transitive cookie advisory (`package.json:11`, CWE-1104, confirmed) — no currently known high-impact issue, but no future CSRF-handling bug in csurf itself will be patched; plan a migration to a maintained CSRF middleware.
- `deps-cypress` — `cypress` (devDependency) is 12+ majors behind and carries 22 transitive advisories, but is test/CI-only (`package.json:44`, CWE-1104, likely) — exposure is to the local/CI runner, not the deployed server; upgrade during a planned test-tooling refresh.
- `deps-express-session` — `express-session` (installed 1.15.6) pulls two low-severity cookie/header advisories (`package.json:14`, CWE-565, likely) — real-world impact is rated low by the advisory database itself; upgrade to resolve the transitive `cookie`/`on-headers` versions.
- `deps-mocha` — `mocha` (devDependency) is 10 majors behind and carries 8 transitive advisories, dev/CI-only (`package.json:57`, CWE-1104, likely) — same class of risk as cypress, not the running server; upgrade as part of a test-tooling refresh.
- `secrets-e2e-admin-fixture` — admin credential is duplicated as a plaintext Cypress e2e test fixture (`test/e2e/fixtures/users/admin.json:3`, CWE-798, confirmed) — anyone reading the fixture also learns the real seeded admin password; once the seed password is randomized, pull the test credential from a CI secret instead.
- `secrets-zap-api-key` — OWASP ZAP proxy API key is hard-coded in committed dev/test configuration (`config/env/development.js:6`, CWE-798, confirmed) — grants access only to a local ZAP instance on a private lab network, not the deployed app; move it to an environment variable and rotate it.

### info

- `deps-node-esapi-unmaintained` — `node-esapi`, used for output encoding, has had exactly one release, in 2014 (`package.json:20`, CWE-1104, confirmed) — no known advisory, but a decade-abandoned encoding library backs part of the app's XSS defense; replace it with a maintained, actively-updated encoding library.

## What was not covered

- **Dropped finding**: `platform-error-handler-leaks-error-object` was removed from `findings.json` only because it is an exact duplicate — same file, line and CWE (`app/routes/error.js:10`, CWE-209) — of `data-verbose-error-to-client`, which the union keeps under the file+line+CWE deduplication rule; both departments independently read and confirmed the same sink at the same line, at tied `confirmed` confidence. No finding from any department was rejected by the mechanical examiner: `node verify-safety-report.mjs --findings <file> --list-invalid` printed no ids for any of the six `findings/*.json` files.
- **Git history** was not scanned by any department (no `git log -p`/gitleaks pass over prior commits); only the current tree state locked in `target.json` was reviewed. A secret rotated out of `HEAD` but present in an earlier commit would not be caught by this review.
- **Dynamic and penetration testing** were not performed by any department: no department started the application, attempted the `admin`/`Admin_123` login, forged a session cookie, sent a crafted `eval()` or `$where` payload, or exercised the SSRF path below against a running instance. Every finding rests on a static read of the source and a traced code path, not on an exploited proof-of-concept.
- **SSRF in `app/routes/research.js:16`** (`needle.get` against a URL built from `req.query.url`/`req.query.symbol`) was read and flagged as a real risk by the injection department, but SSRF was outside that department's assigned sink list (SQL/NoSQL, eval, shell commands, template injection, HTML sinks, path traversal) and no other department claimed it either, so it was never written up as a numbered finding; it should be picked up in a follow-up pass.
- **MFA** — NodeGoat has no multi-factor authentication anywhere in the files read; there is nothing to evaluate for CWE-308, so no finding was written for its absence, and this is not the same as having checked an implementation.
- **JWT-specific pitfalls** do not apply: every route read uses `express-session`/cookie sessions, not JWTs.
- **Vendored, unmodified third-party code** (`app/assets/vendor/*` — bootstrap, jquery, morris, raphael, html5shiv, font-awesome) was not read line-by-line for injection or platform sinks by any department; it ships unmodified and is a dependency-management concern already covered at the manifest level by `npm audit`, not an application-code one.
- **`node_modules` was absent from the read-only checkout**, so `marked@0.3.5`'s actual `sanitize: true` implementation could not be inspected directly; `injection-xss-memos-marked` is marked `likely` rather than `confirmed` for exactly this reason, and no department verified it by other means.
- **Command injection, path traversal via `fs`/`sendFile`, and `new Function`/string-bodied-timer sinks** were not found reachable from any route in the files the injection department read; this is an absence in what was read, not a proof that none exists elsewhere in the tree.
- **Client-side/browser JavaScript that ships to the browser** (`app/assets/js/chart/chart-data-morris.js`, `app/assets/js/tour/redirects-steps.js`) was only spot-read for obvious `postMessage`/DOM-URL sinks by the platform department; no dedicated front-end/DOM-XSS pass was performed.
- **~47 of npm audit's 145 flagged packages** were read during triage but not written up as individual findings, per the dependencies department's instruction not to report one finding per transitive package; their advisories roll up under the 15 direct-dependency findings above or under packages whose `effects` chain does not resolve to a single direct dependency (mostly hoisted dev-tool-internal packages such as `ajv`, `ws`, `handlebars`, `yargs`, `tap`, `nodeunit`).
- **`grunt-env@latest`** (a floating tag) and **`grunt-if`** (installed from a GitHub tarball URL rather than a registry version) were noted as textbook pinned-vs-floating problems but carried no `npm audit` advisory at review time and were not written up as findings; a provenance/typosquatting check of the tarball source was not performed.
- **Non-JavaScript supply chain** — the `Dockerfile`'s base image and the images named in `docker-compose.yml` — was not audited; `npm audit` only covers the Node.js dependency graph.
- **Runtime/deployment configuration** — the actual `NODE_ENV` a real deployment sets, whether `docker-compose.yml`'s `MONGODB_URI` is overridden, where container logs are actually shipped, and any WAF/network-topology controls in front of the app — was not observable from a static read and was not assumed either way.
- **CORS, file uploads, source maps, and nginx configuration** were checked by the platform department and found not to apply to this codebase (no `cors` package or cross-origin API, no upload endpoint, no client bundler/build step, no nginx config present) rather than left unexamined; this is recorded as a checked absence, not a gap.
- **The commented-out `cryptoKey` encryption path** in `app/data/profile-dao.js` and the duplicate seeded users (`User1_123`, `User2_123`, and `test/e2e/fixtures/users/user.json`) were read and recognized as the same class of issue as findings already filed, but were not filed again as separate findings, to avoid padding the count with duplicates of an already-reported sink or an unreachable, commented-out path.
- **Timing side channels and memory safety in native modules** (for example `bcrypt-nodejs`'s C++ addon) were not checked by any department; this review is a source read, not a binary or hardware-level analysis.
- **Mobile, native, and infrastructure-as-code review** do not apply: this is a server-rendered Node.js/Express web application with no mobile client and no Terraform/CloudFormation in the reviewed tree.
