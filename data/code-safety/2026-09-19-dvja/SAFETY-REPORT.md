## Executive summary

This integrated review covers dvja (Damn Vulnerable Java Application), a Java Struts2/Spring/Hibernate app, over the tree locked at `/home/user/targets/dvja` (174 files, sha256 `014b5713f91d7c23181b282f75b1e8220f54f5d5de5e0ea36f28e1c456a80982`). Six departments (access, data, dependencies, injection, platform, secrets) each read the code and produced their own findings; this integration merges their 43 findings into 40, after removing 3 exact duplicates (same file, line and CWE) and with no finding invalidated by the mechanical examiner. Breakdown: 9 critical, 10 high, 13 medium, 7 low, 1 info. The three most important: (1) a password-reset key that is nothing more than MD5 of the login, with no secret or expiry, giving unauthenticated account takeover (`src/main/java/com/appsecco/dvja/services/UserService.java:90`); (2) full export of every user's data via `/api/userList`, authorized purely by a caller-forged `admin=1` cookie on a route that also passes through no authentication interceptor at all (`src/main/java/com/appsecco/dvja/controllers/ApiAction.java:39-44` and `src/main/resources/struts.xml:156-159`); (3) three confirmed SQL/JPQL injections and one OS command injection, each traced end-to-end from request parameter to sink (`src/main/java/com/appsecco/dvja/services/UserService.java:75`, `src/main/java/com/appsecco/dvja/services/ProductService.java:48`, `src/main/java/com/appsecco/dvja/controllers/PingAction.java:45`). Coverage included the Struts entry points, the Java controllers and services, the data model, the JSP views cited by a finding, the Struts/Spring/Log4j2/Docker configuration, and `pom.xml`; it did not cover actual runtime behavior, git history, vendored third-party front-end libraries (jQuery, Font Awesome), full transitive-dependency resolution, or any dynamic testing (see "What was not covered"). Method: entry points first, data traced from source to sink, one finding per sink, exact line quoted, confidence stated, then every finding mechanically verified against the locked tree by `verify-safety-report.mjs`.

## Scope and method

Target: `/home/user/targets/dvja`, locked in `target.json` to 174 files (only `.git` excluded) under sha256 `014b5713f91d7c23181b282f75b1e8220f54f5d5de5e0ea36f28e1c456a80982`. Six departments ran on their own branches and each committed `findings/<department>.json` and `report/<department>.md`: **access** (authentication, session handling, authorization, CSRF), **data** (sensitive-data exposure, crypto misuse, logging), **dependencies** (`pom.xml` manifest review against the OSV advisory database), **injection** (SQL/JPQL, OS command, XSS, open redirect), **platform** (security headers, cookies, error handling, devMode, container configuration) and **secrets** (hard-coded credentials). This integration is itself a language-model review: it read every department's `findings/*.json` and `report/*.md` in full and is grounded by two mechanical checks — `verify-safety-report.mjs` (the committed examiner, which re-hashes the locked tree and checks every citation and snippet), and, for the dependencies department only, live queries against the OSV API (`api.osv.dev`, ecosystem Maven) for each directly declared `pom.xml` coordinate. **No static-analysis scanner (e.g. semgrep) was run by any department in this engagement** — every report says so explicitly, and this integration repeats it rather than implying a scanner ran: all findings below come from a department reading source code directly, not from pattern-matched tool output.

Files the six departments state they actually opened and traced (not merely the full 174-file list that exists in the tree): `src/main/resources/struts.xml` and `example.xml`; every controller under `src/main/java/com/appsecco/dvja/controllers/`; every service under `src/main/java/com/appsecco/dvja/services/`; `AuthenticationInterceptor.java`, `Constant.java`, `models/User.java`, `models/Product.java`; `src/main/webapp/WEB-INF/web.xml`, `config.properties`, `applicationContext.xml`; `src/main/resources/log4j2.xml`, `persistence.xml`; `pom.xml`; `Dockerfile`, `docker-compose.yml`, `scripts/start.sh`; a sample of the JSP views directly implicated by a finding (`UserEdit.jsp`, `UserSearch.jsp`, `ProductList.jsp`, `ProductEdit.jsp`, `Ping.jsp`, `Home.jsp`, `index.html`); and the `com.appsecco.example` tutorial package (read, found to hold no sink). Method follows the review-method skill throughout: entry points first, each attacker- or user-controlled field traced from its Struts action binding to its sink (a query, a shell command, a log statement, an HTML render, a redirect, or a stored/declared credential), one finding per sink, the exact cited line quoted and re-checked against the target's own text by the examiner, and a stated confidence (`confirmed`, `likely`, or `possible`) per finding. This is a static, read-only review: the target tree was never modified, and no department stood up a running instance of the application.

## Findings

### critical

- `access-reset-password-predictable-token` — Password-reset token is a deterministic MD5 of the public login name, not a server-issued secret (`src/main/java/com/appsecco/dvja/services/UserService.java:90`, CWE-640, confirmed) — anyone who knows or guesses a login can compute a valid reset key themselves and take over that account, including an administrator's; fix by generating a random, stored, single-use, expiring token instead.
- `data-006` — Bulk export of every user's PII is gated only by a client-supplied cookie (`src/main/java/com/appsecco/dvja/controllers/ApiAction.java:40`, CWE-602, confirmed) — any caller who sends `Cookie: admin=1` receives the full user directory; fix by deleting the cookie check and requiring a server-side session role check behind an authentication interceptor.
- `dependencies-struts2-core` — Apache Struts2 2.3.30 carries multiple pre-authentication RCE advisories, including the Equifax-breach CVE-2017-5638 (`pom.xml:22`, CWE-20, confirmed) — an unauthenticated attacker can execute arbitrary code with a single crafted HTTP request; fix by upgrading to a currently supported Struts 6.x (or at minimum 2.5.33) release.
- `dependencies-log4j-core` — log4j-core 2.3 is vulnerable to Log4Shell (CVE-2021-44228) and is wired in as the framework's active logger (`pom.xml:47`, CWE-502, likely) — if any Log4j2-backed log statement ever carries attacker text, unauthenticated remote code execution follows; fix by upgrading to 2.17.1 or later and removing the conflicting `slf4j-log4j12` binding.
- `injection-sqli-user-search` — SQL injection in user login search via string-concatenated JPQL (`src/main/java/com/appsecco/dvja/services/UserService.java:75`, CWE-89, confirmed) — any authenticated user can inject JPQL to dump arbitrary rows; fix by using the parameterized query the file already has two methods above.
- `injection-sqli-product-search` — SQL injection in product listing search via a string-concatenated JPQL LIKE clause (`src/main/java/com/appsecco/dvja/services/ProductService.java:48`, CWE-89, confirmed) — enumerates or exfiltrates arbitrary rows; fix by binding the value as a parameter.
- `injection-cmdi-ping` — OS command injection in the ping diagnostic feature (`src/main/java/com/appsecco/dvja/controllers/PingAction.java:45`, CWE-78, confirmed) — any authenticated user can run arbitrary shell commands as the application's OS user; fix by validating the address as a strict IP/hostname and executing without a shell.
- `platform-001` — Struts2 developer mode (devMode) is enabled, exposing debug diagnostics and potentially the OGNL debugging console (`src/main/resources/struts.xml:7`, CWE-489, likely) — unauthenticated requests that trigger an error can leak internals or worse; fix by setting `struts.devMode` to `false` for any non-developer deployment.
- `platform-006` — Admin user-list API trusts a client-supplied cookie instead of a server-side authorization check (`src/main/java/com/appsecco/dvja/controllers/ApiAction.java:39`, CWE-602, confirmed) — any unauthenticated client sending `Cookie: admin=1` receives the full user directory; fix by authorizing from server-side session/role state instead.

### high

- `access-api-userlist-noauth` — `/api/userList.action` has no authentication interceptor at all (`src/main/resources/struts.xml:158`, CWE-862, confirmed) — the admin user-list handler is reachable with zero session state; fix by adding the authentication interceptor stack to the `api` package.
- `access-adminshowusers-cookie-privilege` — Admin capability is self-assigned via a client-supplied cookie, not the user's stored role (`src/main/java/com/appsecco/dvja/controllers/ApiAction.java:40`, CWE-863, confirmed) — any caller can grant themselves the admin branch of the handler; fix by gating on the session user's stored role.
- `access-edituser-missing-csrf` — `editUser` (password/email change) has no CSRF token, enabling forced password change (`src/main/resources/struts.xml:62`, CWE-352, confirmed) — a single clicked link changes a victim's password to a value the attacker knows; fix by adding a token interceptor and a CSRF hidden field.
- `data-001` — Passwords hashed with unsalted MD5 instead of a slow, salted hash (`src/main/java/com/appsecco/dvja/services/UserService.java:109`, CWE-327, confirmed) — a leaked `users` table is trivially crackable; fix by moving to BCrypt/Argon2id.
- `data-005` — Unauthenticated API endpoint discloses any user's email address (`src/main/java/com/appsecco/dvja/controllers/ApiAction.java:79`, CWE-200, confirmed) — enables account enumeration and phishing with no login required; fix by requiring authentication and not returning another user's email.
- `injection-xss-stored-product-name` — Stored XSS in product name rendered with escaping disabled (`src/main/webapp/WEB-INF/dvja/ProductList.jsp:42`, CWE-79, confirmed) — a malicious product name executes in every viewer's browser; fix by removing `escape="false"`.
- `platform-007` — The `/api` Struts package has no authentication interceptor, so every action in it runs unauthenticated (`src/main/resources/struts.xml:156`, CWE-306, confirmed) — any future action added to this package inherits no login requirement; fix by adding the authentication interceptor to the package.
- `dvja-secrets-001` — MySQL root password hard-coded in committed `docker-compose.yml` (mysql service) (`docker-compose.yml:8`, CWE-798, confirmed) — anyone with repository access has the database container's root credential; fix by moving it to an untracked `.env`/secret and rotating it.
- `dvja-secrets-002` — Same MySQL root password re-declared for the app service and used by `start.sh` to run schema DDL as root (`docker-compose.yml:17`, CWE-798, confirmed) — the running app container's own DB credential is committed in plaintext; fix by using a low-privilege account and externalizing the value.
- `dvja-secrets-003` — MySQL root password hard-coded in the deployed application's `config.properties` and wired into the live Spring DataSource (`src/main/webapp/WEB-INF/config.properties:4`, CWE-798, confirmed) — the credential the running application actually uses for every query is recoverable from the WAR/source; fix by externalizing via environment/secrets manager and using least privilege.

### medium

- `access-addeditproduct-missing-csrf` — `addEditProduct` (create/update product) has no CSRF token (`src/main/resources/struts.xml:79`, CWE-352, confirmed) — a cross-site form can create/overwrite products as any logged-in user; fix by adding a token interceptor and CSRF field.
- `access-login-no-session-regeneration` — Session id is not regenerated after successful login (session fixation) (`src/main/java/com/appsecco/dvja/controllers/Login.java:50`, CWE-384, likely) — a pre-login fixed session id becomes fully authenticated once the victim logs in; fix by invalidating and reissuing the session id on login.
- `access-logout-session-not-invalidated` — Logout removes the user attribute but never invalidates the underlying session (`src/main/java/com/appsecco/dvja/controllers/Login.java:39`, CWE-613, confirmed) — the container session and its id survive logout; fix by calling `HttpSession.invalidate()` on logout.
- `access-login-no-rate-limit` — Login has no attempt limit, lockout or delay (`src/main/java/com/appsecco/dvja/controllers/Login.java:49`, CWE-307, confirmed) — online brute-forcing is practical against any known login; fix by adding a per-account attempt counter with backoff/lockout.
- `data-002` — New password logged in cleartext during password reset (`src/main/java/com/appsecco/dvja/services/UserService.java:93`, CWE-532, confirmed) — anyone with log access obtains a user's plaintext new password; fix by removing the password value from the log statement.
- `data-004` — Struts2 devMode is enabled, exposing debug information to clients (`src/main/resources/struts.xml:7`, CWE-215, likely) — verbose stack traces reach error responses; fix by disabling devMode for deployment.
- `dependencies-mysql-connector` — mysql-connector-java 5.1.42 is affected by multiple Connector/J privilege-management advisories (`pom.xml:135`, CWE-269, likely) — exploitable primarily by a malicious/compromised database server; fix by upgrading to at least 8.2.0.
- `injection-xss-reflected-product-search` — Reflected XSS in product search results via raw scriptlet output (`src/main/webapp/WEB-INF/dvja/ProductList.jsp:23`, CWE-79, confirmed) — a crafted search link runs attacker JavaScript in a victim's session; fix by using the auto-escaping `<s:property>` tag.
- `injection-open-redirect` — Unvalidated open redirect via the `url` request parameter (`src/main/resources/struts.xml:101`, CWE-601, confirmed) — a trusted-domain link can send victims to an attacker site; fix by validating `url` against an allowlist.
- `platform-002` — Struts2 config-browser debug plugin is shipped in the production build (`pom.xml:26`, CWE-489, likely) — an unauthenticated visitor can enumerate the app's action/interceptor configuration; fix by removing the plugin or scoping it to test.
- `platform-003` — No security-headers filter is mounted: CSP, X-Frame-Options, X-Content-Type-Options and HSTS are all absent (`src/main/webapp/WEB-INF/web.xml:13`, CWE-1021, confirmed) — responses can be framed, MIME-sniffed, or served without HSTS; fix by adding a security-headers filter ahead of the Struts2 filter.
- `platform-004` — Session cookie has no explicit Secure, HttpOnly or SameSite configuration (`src/main/webapp/WEB-INF/web.xml:32`, CWE-614, likely) — the session cookie can be sent over plain HTTP and is more exposed to cross-site delivery; fix by adding an explicit `<session-config><cookie-config>` block.
- `platform-005` — Raw exception message from a database query is returned to the client on the user-search form (`src/main/java/com/appsecco/dvja/controllers/UserAction.java:115`, CWE-209, confirmed) — discloses the internal query shape and confirms the injection point; fix by returning a generic message and logging the detail server-side.

### low

- `access-password-compare-non-constant-time` — Password hash comparison uses `String.equals()`, not a constant-time comparison (`src/main/java/com/appsecco/dvja/services/UserService.java:52`, CWE-208, confirmed) — a secondary weakness on top of unsalted MD5 storage; fix by using `MessageDigest.isEqual()` and a salted adaptive hash.
- `access-api-ping-unauth-identifier-trust` — `/api/ping.action` trusts a caller-supplied login and discloses the account's email with no authentication (`src/main/resources/struts.xml:157`, CWE-862, confirmed) — enables login/email enumeration; fix by requiring authentication and scoping to the caller's own account.
- `dependencies-slf4j-log4j12` — slf4j-log4j12 1.5.2 is a 2008-era, unmaintained binding that transitively pulls end-of-life Log4j 1.x (`pom.xml:53`, CWE-1104, possible) — no upstream fix path for that classpath component; fix by removing it and routing logging through Log4j 2.
- `dependencies-gson` — gson 2.8.1 matches CVE-2022-25647, but the app's own code only calls the serializing `toJson`, not the vulnerable `fromJson` sink (`pom.xml:141`, CWE-502, possible) — not currently reachable through this app's own code; fix by upgrading to 2.8.9+ regardless.
- `dependencies-hibernate-3x` — hibernate-core/entitymanager/annotations pin a 2009-2010 Hibernate 3.x line with no upstream support (`pom.xml:99`, CWE-1104, possible) — any future ORM issue has no vendor fix path; fix by migrating to a maintained 5.6.x/6.x line.
- `platform-008` — Open redirect: the redirect action forwards to an attacker-supplied URL with no validation (`src/main/resources/struts.xml:100`, CWE-601, confirmed) — aids phishing from a trusted domain; fix by validating `url` against an allowlist.
- `platform-010` — Application container has no `USER` directive and runs as root (`Dockerfile:17`, CWE-250, confirmed) — widens the blast radius of any code-execution vulnerability reached through the app; fix by adding an unprivileged `USER` before `CMD`.

### info

- `dependencies-spring-3x` — spring-tx and spring-orm are pinned to Spring Framework 3.0.5.RELEASE (2011), a line with no upstream support (`pom.xml:122`, CWE-1104, possible) — no specific CVE was found for this exact coordinate, reported as a maintenance concern only; fix by upgrading to a supported Spring 5.x/6.x release.

## What was not covered

- **Dropped as an exact duplicate**: `data-003` (`src/main/java/com/appsecco/dvja/services/UserService.java:90`, CWE-640) reported the identical file, line and CWE as `access-reset-password-predictable-token`; both were `confidence: confirmed` and both passed the examiner individually. - **Dropped as an exact duplicate**: `data-007` (`src/main/webapp/WEB-INF/config.properties:4`, CWE-798) reported the identical file, line and CWE as `dvja-secrets-003`; both were `confidence: confirmed` and both passed the examiner individually. The union keeps the `secrets` department's entry and drops `data-007`.
- **Dropped as an exact duplicate**: `platform-009` (`docker-compose.yml:8`, CWE-798) reported the identical file, line and CWE as `dvja-secrets-001`; both were `confidence: confirmed` and both passed the examiner individually. The union keeps the `secrets` department's entry and drops `platform-009`.
- No finding from any department's `findings/*.json` was invalidated by the mechanical examiner (`node verify-safety-report.mjs --findings <file> --list-invalid` printed nothing for any of the six files); the three drops above are dedup-only, not correctness rulings.
- **No static-analysis scanner ran**: every one of the six department reports states plainly that `semgrep` (or any other pattern-matching scanner) was not invoked in that department's pass. Every finding in this program, and therefore in this report, comes from a language model reading source code directly and citing exact lines, checked afterward by the mechanical examiner — not from scanner output.
- **No dynamic testing**: no department stood up a running instance of dvja or sent it a live HTTP request (no exploit was executed for the SQL injection, command injection, XSS, CSRF, or reset-token findings); every finding is a static source-to-sink trace.
- **Git history was not inspected** by any department (no `git log -p`, no secret-scanning of historical blobs): only the working tree at the commit `target.json` locks was read, so an earlier, different value for the committed MySQL password (or a secret since removed) would not be found here.
- **Transitive dependency versions were not resolved**: `mvn dependency:tree` was not run (it would write a `target/` directory into the read-only target tree), so exact transitive coordinates — for example the specific `log4j:log4j` 1.x version `slf4j-log4j12` pulls in, or Hibernate 3.x's own transitive Javassist/dom4j versions — were not individually checked against OSV.
- **Compiled third-party jars were not opened**: Struts2/XWork internals, the Log4j2 internals, and the Hibernate 3.x internals are not among the 174 tracked source files and were not decompiled; this is why the devMode console (`platform-001`), the config-browser plugin's exact route (`platform-002`), the Log4j2-vs-Log4j-1.x call-site question (`dependencies-log4j-core`), and Jetty's actual default cookie flags (`platform-004`) are all `likely`/`possible` rather than `confirmed`.
- **Vendored front-end assets were not audited for their own CVEs**: `src/main/webapp/assets/jquery-3.2.1.min.js`, `showdown.min.js`, and the Font Awesome `assets/fa/**` tree were grepped for obvious DOM-sink patterns (`postMessage`, `innerHTML`, `document.write`, `eval`) with no application-authored hits, but the project has no manifest (`package.json`) declaring these versions, so they were not turned into dependency findings and their own known advisories (if any) were not queried.
- **Documentation and IDE metadata were not treated as reviewable code**: `docs/**` (the project's own OWASP-training walkthroughs), `README.md`, and `.idea/**` project files were opened only far enough to confirm they hold no embedded credential or executable logic; they were not otherwise assessed for content (e.g. a documented example reset-key URL in `docs/solution/a2-broken-authentication-and-session-management.md` is training prose, not a value the running service reads, and is not cited as a finding here).
- **Database schema and container runtime hardening were only partially checked**: `db/schema.sql` was read to confirm the credentials trace to a real `users` table, but was not itself assessed for schema-level weaknesses (missing constraints, column-level encryption); actual deployed container/network configuration (reverse proxy, TLS termination, WAF, firewall rules) is outside this repository and could not be assessed statically.
- **Classes of defect no department's skill claims to own**: business-logic/race-condition abuse (for example, concurrent use of the same reset key before it would be re-derived), broader weak-randomness findings beyond the one reset-token case already reported (`access-reset-password-predictable-token`), and a systematic horizontal-authorization sweep across every entity type beyond the specific routes examined (the `editUser` IDOR was checked and found closed by the code as read, but not every entity/action pair in the app was re-derived from first principles) were not the subject of any department's pass and are not represented among the 40 findings above.
- **Runtime/network transport** (whether TLS terminates in front of this app via a reverse proxy) is infrastructure outside the locked source tree and cannot be confirmed by a static read either way; no finding above claims a transport-security conclusion.
