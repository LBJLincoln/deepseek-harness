## Executive summary

This review covered OWASP NodeGoat (`/root/targets/NodeGoat`, 111 files locked in `target.json`, sha256 `78ac112b7bd5083bb065086c4642dcd8a3932a8d3052f9405503124c90a70fe3`). Six specialist departments (access, data, dependencies, injection, platform, secrets) plus one generalist department each read the repository independently — entry points first, then request-controlled data traced from source to sink — grounded by `semgrep` (the program's local rule pack plus `p/owasp-top-ten`) and by `npm audit` for dependency advisories; the integration then merged their 49 findings (none was rejected by the mechanical examiner) without dropping any for duplication, since no two share `file`, `line`, and `cwe` at once. Breakdown: 9 critical, 18 high, 12 medium, 10 low, 0 info. The three most important findings: (1) three `eval()` calls on `/contributions` form fields (`app/routes/contributions.js:32-34`) give any authenticated user server-side remote code execution; (2) an admin account with the plaintext password `Admin_123` is reseeded into the production database on every Heroku one-click deploy and every container start (`artifacts/db-reset.js:18`, `app.json:13`); (3) several production dependencies (`underscore`, `swig`, `mongodb`) carry critical advisories, including an arbitrary-code-execution advisory and an arbitrary-file-read advisory in `swig` that has no fix because the package is abandoned upstream.

The method combines a language-model-driven read, a static scanner, and the repository's own mechanical examiner (`verify-safety-report.mjs`), which re-checks every `file`+`line` against the locked tree. This review did not exercise the running application, did not test a real deployed instance, did not examine git history, and did not open vendored front-end libraries as shipped (`app/assets/vendor/**`); "What was not covered" details these limits and every control class that did not run. This review makes no claim about the target's overall security posture: nothing this program did could support such a claim, only the presence of the specific findings listed below.

## Scope and method

Target: `/root/targets/NodeGoat` (OWASP NodeGoat), 111 files locked in `target.json`, sha256 `78ac112b7bd5083bb065086c4642dcd8a3932a8d3052f9405503124c90a70fe3`. The target was read-only throughout; nothing was written into it by any department or by this integration.

Seven department branches ran and each committed `findings/<department>.json` plus `report/<department>.md`, merged into this worktree: **access** (authentication, session management, authorization, CSRF), **data** (sensitive-data exposure, cryptography, logging), **dependencies** (manifest/lockfile advisory audit), **generalist** (cross-cutting reads spanning multiple file kinds at once), **injection** (SQL/NoSQL/code injection, XSS, SSRF, ReDoS, open redirect), **platform** (security headers, cookies, error handling, rate limiting, TLS), and **secrets** (hard-coded credentials and keys). Every department reports `semgrep 1.177.0` as available and ran it over the target (`--config <local pack> --config p/owasp-top-ten --metrics off --json`), scanning 72 git-tracked files with up to 113 applicable rules for 29 raw hits; every department treated a semgrep hit as a lead to read in context, never as a finding on its own — several departments explicitly state that none of their filed findings came from a semgrep hit directly. The dependencies department additionally ran `npm audit --json` against the live npm registry (145 vulnerable packages across 1,479 resolved packages: 38 critical, 66 high, 33 moderate, 8 low) and `npm view <pkg>@<version> deprecated`/`time.modified` for maintenance status, and grouped its 13 findings one per direct dependency rather than one per transitive package. This integration ran the program's own examiner, `verify-safety-report.mjs`, in two modes: `--findings <file> --list-invalid` against every one of the seven `findings/*.json` files (no id was printed as invalid by any run — see "What was not covered" for what that does and does not mean), and `--findings findings.json` against the merged union (49/49 verified).

Files each department reports reading directly (not sampled) include, across all seven: `server.js` end to end; every file under `app/routes/` and `app/data/`; the server-rendered templates under `app/views/` that those routes render (`benefits.html`, `profile.html`, `dashboard.html`, `error-template.html`, `layout.html`, `login.html`, `memos.html`); `config/config.js` and all four files under `config/env/`; `package.json` and `package-lock.json`; the deployment surface `app.json`, `Dockerfile`, `docker-compose.yml`, `Procfile`; `artifacts/db-reset.js` and `artifacts/cert/{server.key,server.crt}`; `.github/workflows/*.yml` and `.travis.yml`; and `test/security/profile-test.js`. `findings.json` is the union of all seven `findings/<department>.json` files, deduplicated by `file`+`line`+`cwe` (no duplicate key was found across the 49 entries, so none was dropped for that reason); each entry is copied whole from its department's committed file, snippet included verbatim, so the examiner's line-text comparison against the target continues to pass.

## Findings

### critical

- `dep-underscore-rce` — underscore resolves to a version with a critical arbitrary-code-execution advisory (`package.json:23`, CWE-94, confirmed) — underscore ships in the production dependency tree (package.json 'dependencies', not devDependencies). An attacker who can influence input into underscore's template compiler can execute arbitrary code in the Node process serving the whole application; deeply nested or circular input into _.isEqual/_.flatten can crash the process. Fix: Bump the declared range to "^1.13.8" (the first published version clear of both advisory ranges) and regenerate package-lock.json.
- `dep-swig-file-read` — swig template engine has an unpatched arbitrary local file read advisory and is abandoned upstream (`package.json:22`, CWE-22, confirmed) — swig is the view-rendering engine wired through `consolidate` for NodeGoat's HTML templates; a template-rendering path that reaches this advisory lets an attacker read arbitrary files off the server filesystem, and because the package is abandoned there is no upgrade path that removes the bug short of replacing the engine. Fix: Migrate off swig to a maintained engine reachable through the same `consolidate` abstraction (e.g. Nunjucks or EJS); no version bump within the swig package fixes this.
- `dep-mongodb-driver-outdated` — mongodb driver is 5+ major versions behind, with its own DoS advisory and a critical deserialization advisory in bundled bson (`package.json:18`, CWE-400, confirmed) — mongodb is the application's database driver (used throughout app/data/*-dao.js). A malformed BSON document reaching the deserializer, or a crafted request that triggers the driver's own DoS path, can crash the process or corrupt in-memory state for every request being served. Fix: Upgrade the mongodb driver; at minimum move past 3.1.13 to clear the driver's own advisory, but given the API and dependency changes accumulated since 2.x, plan the upgrade to a current 6.x/7.x release and update app/data/*-dao.js call sites for the new driver API.
- `dep-forever-prototype-pollution-chain` — forever, the process supervisor Procfile starts the app with, carries a critical prototype-pollution chain (`package.json:15`, CWE-1321, likely) — If forever's config-loading path (nconf) or its argument parsing (optimist/minimist) ever parses attacker-influenced input, prototype pollution in the process that supervises and restarts the whole application is a critical-blast-radius bug: it can affect every request handled after pollution occurs. Fix: Upgrade forever to 4.0.3 (a semver-major bump, per `npm audit`'s own `fixAvailable` suggestion), which drops the vulnerable flatiron/nconf/optimist chain; re-verify the Procfile invocation still works with the new major's CLI.
- `inj-eval-pretax` — Server-side code injection via eval() on the contributions pre-tax field (`app/routes/contributions.js:32`, CWE-95, confirmed) — An authenticated user can submit a payload such as `require('child_process').execSync('id')` (or any JS expression) as the preTax form field; it executes in the Node.js server process with full access to the process, filesystem and network, giving full remote code execution. Fix: Replace eval(req.body.preTax) with Number(req.body.preTax) or parseInt(req.body.preTax, 10), then validate the parsed number as the existing isNaN/range checks already attempt to do.
- `inj-eval-aftertax` — Server-side code injection via eval() on the contributions after-tax field (`app/routes/contributions.js:33`, CWE-95, confirmed) — Same as the preTax sink: an authenticated user can supply arbitrary JavaScript in the afterTax field and have it executed server-side, yielding remote code execution. Fix: Replace eval(req.body.afterTax) with Number(req.body.afterTax) or parseInt(req.body.afterTax, 10) before the numeric validation.
- `inj-eval-roth` — Server-side code injection via eval() on the contributions roth field (`app/routes/contributions.js:34`, CWE-95, confirmed) — Same as the other two sinks: an authenticated user can supply arbitrary JavaScript in the roth field and have it executed server-side, yielding remote code execution. Fix: Replace eval(req.body.roth) with Number(req.body.roth) or parseInt(req.body.roth, 10) before the numeric validation.
- `inj-nosql-where-allocations` — NoSQL $where injection in the allocations threshold filter (`app/data/allocations-dao.js:78`, CWE-943, confirmed) — Any authenticated user can send e.g. `?threshold=0'; return true; var x='` or `?threshold=0';while(true){}` to make MongoDB evaluate attacker-supplied JavaScript inside its $where clause: this can bypass the intended filter to dump other users' allocation records, or hang the shared mongod process in an infinite loop, denying the database to every other user of the application. Fix: Never build $where from request input. Parse threshold with parseInt and validate it is within an expected numeric range (0-99), then express the comparison as a normal query operator, e.g. { userId: parsedUserId, stocks: { $gt: parsedThreshold } }, so MongoDB never executes attacker-controlled JavaScript.
- `secrets-admin-plaintext-password` — Admin account is seeded with a hard-coded plaintext password on every deploy and start (`artifacts/db-reset.js:18`, CWE-798, confirmed) — Anyone with the repository or who has seen this well-known admin/Admin_123 pair can log in remotely to any deployment that used this seed script as an administrator (isAdmin: true), gaining access to admin-only routes such as /benefits (confirmed in app/routes/benefits.js) with no other precondition. Fix: Never seed a working admin password from source. Generate a random password (or none, forcing an out-of-band admin bootstrap) at first deploy, store only a salted hash (uncomment and use the bcrypt.hashSync path already present), and change comparePassword in user-dao.js to bcrypt.compareSync instead of plaintext equality.

### high

- `access-001-idor-allocations` — Allocations page is an IDOR: userId is taken from the URL and never checked against the caller's session (`app/routes/index.js:63`, CWE-639, confirmed) — Any logged-in user can read any other user's financial allocation data (stocks, funds, bonds, and the target's name) simply by walking through small integer user ids in the URL. Fix: Drop the :userId route parameter and read the id from req.session.userId (the commented-out fix in allocations.js is correct), or, if an id parameter must stay, verify it equals req.session.userId (or the caller is an admin) before querying.
- `access-002-benefits-missing-admin-check` — Benefits update route lets any authenticated user change any other user's benefit start date; the admin-check middleware exists but is never applied here (`app/routes/index.js:56`, CWE-862, confirmed) — Any authenticated, non-admin user can rewrite the benefitStartDate of any other user account by posting an arbitrary userId, and can view every non-admin user's benefits listing -- a vertical privilege escalation into an administrative function with no role check at all. Fix: Add the existing isAdmin middleware to both routes: app.get("/benefits", isLoggedIn, isAdmin, ...) and app.post("/benefits", isLoggedIn, isAdmin, ...).
- `data-plaintext-password-storage` — User passwords are stored in MongoDB in plaintext, and login compares them with a bare string equality (`app/data/user-dao.js:25-30`, CWE-256, confirmed) — Anyone who can read the `users` collection — a database admin, a backup, a restored snapshot, or an attacker who reaches Mongo through any other flaw (e.g. the NoSQL query issues in allocations-dao.js) — obtains every user's real login password in plaintext, not a hash. Because users commonly reuse passwords, this also gives an attacker working credentials on other, unrelated services for the same individuals. Fix: Hash on write with a memory-hard or heavily iterated algorithm (bcrypt with cost >= 12, or argon2id) as the commented-out code already shows, and compare with the corresponding constant-time verify function (`bcrypt.compareSync`) instead of `===`.
- `data-plaintext-ssn-bank-storage` — Social Security number, date of birth, and bank account/routing numbers are written to MongoDB unencrypted (`app/data/profile-dao.js:55-66`, CWE-312, confirmed) — Anyone with read access to the `users` collection — a DBA, a database backup, a restored snapshot, or an attacker who reaches Mongo through another flaw — gets each user's SSN, date of birth, and bank account and routing numbers in the clear, enough for identity theft and unauthorized ACH transfers against that user. Fix: Re-enable the commented encryption path (or replace it with a maintained AEAD library call, e.g. AES-256-GCM with a per-field random IV and a key from a KMS/secrets manager, not a hardcoded config value) before the `$set` write, and decrypt only when rendering back to the owning user.
- `data-cleartext-http-transport` — The application only ever listens on plain HTTP; the HTTPS server setup is fully commented out (`server.js:145`, CWE-319, confirmed) — Anyone able to observe network traffic between a client and this server (a shared network, a compromised router, an on-path proxy) can read login credentials, the session cookie, and the SSN/bank fields submitted on the profile form, and can tamper with responses in transit. Fix: Uncomment and use the `https.createServer(httpsOptions, app)` block with the existing certificate/key, redirect any plain-HTTP listener to HTTPS, and add `Strict-Transport-Security` once HTTPS is live.
- `dep-express-outdated` — express carries its own open-redirect/XSS advisories plus six transitive advisories in bundled middleware (`package.json:13`, CWE-601, confirmed) — express is the web framework handling every route in app/routes/*.js. `response.redirect()` calls anywhere in the app can be turned into an open redirect or reflected XSS by an attacker-controlled redirect target, and the bundled path-to-regexp ReDoS is reachable by any request whose path matches a route with multiple parameters. Fix: Upgrade express to the latest 4.x (>=4.21.3) to clear the two advisories on express itself; the six transitive advisories are only fully cleared by moving to express 5.x or by overriding body-parser, cookie, path-to-regexp, qs, send and serve-static to patched versions in package-lock.json.
- `dep-body-parser-dos` — body-parser (declared directly and pulled in again via express) has two DoS advisories at the resolved version (`package.json:9`, CWE-405, confirmed) — body-parser sits in front of every route that accepts a request body (used directly by server.js and again inside express). A request with url-encoded data or a crafted limit value can silently bypass size enforcement or block the event loop, denying service to the whole application. Fix: Bump body-parser to >=1.20.6 (clears both own advisories); pin qs to >=6.14.1 in the resulting lockfile to also clear the bundled prototype-pollution/DoS advisories.
- `dep-marked-redos` — marked is pinned to an exact version with multiple ReDoS and XSS advisories (`package.json:17`, CWE-1333, confirmed) — marked renders Markdown content into HTML in the application. Attacker-controlled Markdown reaching it can trigger a regex backtracking DoS or, via the sanitization-bypass advisories, stored XSS in rendered output. Fix: Do not stop at the minor-version 0.3.19 fix; upgrade marked to >=4.0.10 (a semver-major jump) to clear the two Inefficient-Regular-Expression-Complexity advisories, and update any code that depends on marked's 0.x API surface.
- `dep-helmet-outdated-chain` — helmet is six major versions out of date and bundles a ReDoS-vulnerable connect/debug/ms chain (`package.json:16`, CWE-1104, likely) — helmet is the module responsible for setting security response headers on every request. A ReDoS in a dependency it loads at startup can block the event loop for the whole app, and helmet-csp's configuration-override advisory can silently weaken the Content-Security-Policy the application believes it is sending. Fix: Upgrade helmet to a current 7.x/8.x release; note this is a semver-major change (helmet dropped the `connect`/`helmet-csp` dependency chain entirely in later majors and exposes CSP as its own sub-module), so header-configuration code in config/ will need to be updated alongside the bump.
- `generalist-heroku-postdeploy-admin-seed` — Heroku one-click deploy automatically seeds a live admin account with a hard-coded plaintext password into the production database (`app.json:13`, CWE-798, confirmed) — Anyone who deploys the app via the documented Heroku button ships a production database with a known admin/Admin_123 account already active. A remote, unauthenticated attacker who simply reads this public repository can log in as that administrator on any such deployment and reach every isAdmin-gated capability. Fix: Do not run a data-seeding script with hard-coded credentials from a production deployment hook; generate a random admin password at deploy time (e.g. from a Heroku config var) and hash it with bcrypt before insertion, or remove postdeploy seeding entirely for production and require an explicit, out-of-band admin bootstrap step.
- `inj-nosql-operator-login` — NoSQL operator injection in the login username lookup (`app/data/user-dao.js:91-93`, CWE-943, confirmed) — An unauthenticated attacker can manipulate which user document the lookup returns (e.g. matching any/every username with $ne or $regex), enabling user enumeration and query-logic bypass of the intended exact-username match; combined with any future weakening of the password check this becomes a full authentication bypass. Fix: Reject the request (or coerce/validate) unless typeof userName === 'string' (and similarly for password) before building the query, or use a schema validator (e.g. Joi) on req.body ahead of the DAO call so operator objects can never reach findOne().
- `inj-ssrf-research` — SSRF via unvalidated URL and symbol query parameters in the research stock-lookup (`app/routes/research.js:15-16`, CWE-918, confirmed) — Any authenticated user can point url at an internal-only address (e.g. http://169.254.169.254/latest/meta-data/, http://localhost:<admin-port>/, or any RFC1918 host) and have the server fetch it on their behalf; the response body is echoed back in the page (line 25), so this can also be used to read internal service responses that would otherwise be unreachable from outside the network. Fix: Do not accept an arbitrary destination URL from the client. Validate req.query.url against an allowlist of stock-data hosts, or better, keep the target host fixed server-side and accept only the symbol as a request parameter; additionally block requests whose resolved IP is private/link-local/loopback before the request is issued.
- `inj-redos-profile-bankrouting` — Catastrophic-backtracking regular expression applied to the bank routing field (`app/routes/profile.js:59-61`, CWE-1333, confirmed) — An authenticated user can submit a long string of digits with no trailing '#' (e.g. 40+ '1' characters) as bankRouting; matching it against this pattern takes exponential time on Node's single-threaded event loop, freezing the entire application for every user for as long as the match runs. Fix: Remove the redundant outer quantifier so the pattern cannot backtrack ambiguously, e.g. /^[0-9]+#$/, and/or cap the input length before running the regex.
- `inj-xss-benefits-lastname` — Stored XSS: unescaped user.lastName/firstName rendered on the shared benefits page (`app/views/benefits.html:52`, CWE-79, confirmed) — Any authenticated user can set their own lastName to an HTML/JavaScript payload via POST /profile; the next time any other logged-in user (not just the attacker) opens /benefits, the payload executes in that victim's browser session, allowing session-cookie theft or full account takeover of whoever views the page. The same unescaped field also renders in app/views/profile.html and app/views/allocations.html. Fix: Re-enable swig's default autoescaping (remove the `autoescape: false` override in server.js, or set it to true) so all template output is HTML-encoded by default, and additionally validate/sanitize firstName/lastName server-side (e.g. reject or strip HTML-significant characters) before they are stored.
- `platform-002` — Session cookie is issued without the HttpOnly flag (`server.js:78-102`, CWE-1004, confirmed) — Any script running on the page, including through the disabled-autoescape XSS surface in this same app, can read document.cookie and exfiltrate the session id, taking over the victim's session. Fix: Pass cookie: { httpOnly: true, secure: true, sameSite: 'lax' } to the session() call.
- `platform-003` — Session cookie is issued without the Secure flag while the server only listens on plain HTTP (`server.js:78-102`, CWE-614, confirmed) — The session cookie is sent in cleartext over every request; anyone able to observe network traffic (shared Wi-Fi, a compromised router, a proxy) can capture it and impersonate the logged-in user. Fix: Set cookie: { secure: true } once the app terminates TLS, and enforce HTTPS (see the http.createServer finding for the missing TLS listener).
- `platform-008` — No rate limiting or lockout on the login endpoint (`app/routes/index.js:34`, CWE-307, confirmed) — An attacker can submit unlimited login attempts against any known or guessed username with no throttling, enabling credential stuffing and password brute-forcing at network speed. Fix: Add a rate limiter (express-rate-limit or equivalent) keyed by IP and by username on /login, and add a per-account lockout or exponential backoff after repeated failures.
- `secrets-cookie-secret` — express-session secret is a hard-coded literal with no environment override (`config/env/all.js:8`, CWE-798, confirmed) — Anyone who reads the repository (it is public) knows the express-session signing secret used by every deployment that does not override this file. With the secret, an attacker can forge the signature on an arbitrary express-session cookie (cookie-signature HMAC), tamper with or fabricate session cookies accepted by the server, and combine this with any predictable or leaked session id to hijack or fabricate authenticated sessions. Fix: Read cookieSecret from an environment variable with no working literal fallback (e.g. `cookieSecret: process.env.COOKIE_SECRET` and fail startup if unset), generate a strong random value per deployment, and rotate the current committed value.

### medium

- `access-003-session-fixation-login` — Login does not regenerate the session id, so a pre-login session id survives authentication (session fixation) (`app/routes/session.js:116`, CWE-384, confirmed) — An attacker who can set a victim's session cookie before login (session fixation) inherits the victim's authenticated session once the victim signs in, without ever knowing the victim's password. Fix: Call req.session.regenerate() before setting req.session.userId in handleLoginRequest, mirroring what handleSignup already does.
- `access-004-csrf-missing-on-state-changing-routes` — No CSRF protection on any state-changing route: csurf is a dependency but is never mounted (`app/routes/index.js:48`, CWE-352, confirmed) — A page visited by a logged-in victim can silently submit a cross-site POST to /profile (or any of the other POST routes) that rewrites the victim's bank account, routing number, SSN, contributions or benefits, since the browser will attach the session cookie automatically and the server has no token or origin check to reject it. Fix: Uncomment and mount csurf() before the routes (server.js:104-113), expose the token to templates, and add a hidden csrf token field to every state-changing form; alternatively set the session cookie to SameSite=Strict/Lax and check the Origin/Referer header on state-changing requests.
- `data-seed-script-logs-plaintext-passwords` — The database seed script prints every seed user's plaintext password to stdout (`artifacts/db-reset.js:99`, CWE-532, confirmed) — Whoever can read the CI job output, container logs, or terminal history for a `db:seed`/`grunt db-reset` run obtains the plaintext admin and test-user passwords, including the `admin` account's `Admin_123` password. Fix: Do not log full user documents; log only non-sensitive identifiers (e.g. `userName`), or redact the `password` key before calling `console.log`/`JSON.stringify`.
- `dep-grunt-devtooling` — grunt (build tooling) carries three own advisories including arbitrary code execution (`package.json:45`, CWE-1188, likely) — A malicious or compromised grunt plugin, or a crafted file processed by a vulnerable grunt task, can execute arbitrary code or traverse the filesystem on a developer's machine or in CI at build/test time. It does not affect the running production application directly. Fix: Upgrade grunt to >=1.6.1 (the latest published 1.x) to clear the three own advisories, and audit the grunt-legacy-util/js-yaml/minimatch chain separately.
- `dep-cypress-devtooling-chain` — cypress (e2e test runner) pulls in eight transitive packages with advisories, worst a critical prototype pollution (`package.json:44`, CWE-1321, likely) — Running the e2e test suite (locally or in CI) executes this dependency chain; a crafted fixture or a compromised transitive package (extract-zip's zip-handling, minimist's argument parsing) can achieve prototype pollution or arbitrary file writes in the CI environment, not in production. Fix: Upgrade cypress to a current major (the audit suggests 16.1.0 as the nearest fix) to pick up patched debug/extract-zip/lodash/minimost/moment/request/tmp versions; treat this as CI/supply-chain hardening rather than an application vulnerability.
- `generalist-profile-href-reflected-xss` — Unescaped first name is rendered as an href attribute value, giving a javascript:/attribute-breakout XSS distinct from the developer's own (mis-targeted) fix comment (`app/views/profile.html:78`, CWE-79, confirmed) — Since csurf is commented out in server.js (line 7) and no CSRF token is enforced, an attacker can host a page that auto-submits a cross-site POST to /profile with a malicious firstName and a bankRouting value chosen to fail the routing-number regex; the victim's authenticated browser then renders and executes the attacker's markup/script in the profile page, enabling session and data theft. Fix: Escape firstNameSafeString for HTML-attribute context before rendering it (or re-enable swig autoescape and remove ad-hoc unescaped interpolation), and add CSRF protection to state-changing POST routes.
- `inj-open-redirect-learn` — Open redirect via unvalidated url query parameter on /learn (`app/routes/index.js:72`, CWE-601, confirmed) — An attacker can craft a link such as https://victim-app/learn?url=https://evil.example.com/phish that appears to originate from the trusted NodeGoat domain but redirects the authenticated victim to an attacker-controlled site, aiding phishing or OAuth-token-theft style attacks. Fix: Validate the destination against a fixed allowlist of learning-resource hosts before redirecting, or resolve it to a relative path only and reject absolute/external URLs.
- `platform-001` — No security headers are mounted: helmet is required, configured and commented out entirely (`server.js:10`, CWE-693, confirmed) — Responses carry no clickjacking protection (framing is possible), no CSP to contain any XSS the app does have (autoescape is separately disabled, see swig config), no HSTS to force HTTPS, and the X-Powered-By header fingerprints the framework for attackers. Fix: Uncomment and mount helmet() (or its modern app.use(helmet()) equivalent) before the routes are registered, and enable frameguard, contentSecurityPolicy, hsts, and app.disable("x-powered-by") explicitly.
- `platform-004` — Server only listens over plain HTTP; the HTTPS listener is written but commented out (`server.js:144-147`, CWE-319, confirmed) — Credentials submitted at /login, the session cookie, and all response content are exposed to network eavesdropping and man-in-the-middle tampering. Fix: Terminate TLS (either in the app via https.createServer with real certificates, or at a reverse proxy in front of it) and redirect plain HTTP to HTTPS.
- `platform-005` — The global error handler renders the raw error object straight into the HTML response (`app/views/error-template.html:11`, CWE-209, confirmed) — Any unhandled error (a database failure, a thrown validation exception, a library error containing internal file paths or a query fragment) is rendered to the requesting client instead of a generic message, and because autoescape is off the error text is also a potential reflected-content injection point. Fix: In the error handler, render a generic message and a correlation id, and log the full error (message and stack) only server-side; never pass the raw Error object into the template context.
- `platform-006` — The full application config, including the session-signing and crypto secrets, is logged to the console on every startup (`config/config.js:12-13`, CWE-532, confirmed) — Anyone with read access to the server's stdout/log aggregation (a shared log pipeline, a misconfigured logging sink, a support engineer) obtains the cookie-signing secret and the crypto key, letting them forge session cookies or decrypt data protected by cryptoKey. Fix: Remove the console.log of the full config object, or redact secret-bearing keys (cookieSecret, cryptoKey) before logging.
- `secrets-committed-rsa-private-key` — RSA TLS private key is committed to the repository (`artifacts/cert/server.key:1-15`, CWE-321, confirmed) — Anyone with the repository holds the private key matching server.crt. If a deployment follows the tutorial's own instructions and uncomments the HTTPS block in server.js without replacing this key pair, an attacker who has cloned the repository can decrypt captured TLS traffic or impersonate the server in a man-in-the-middle attack against any client that trusts the certificate. Fix: Remove the committed key and certificate from the repository and its history, generate a fresh key pair per deployment (or via a CA/ACME), and load it only from a secret store or mounted volume, never from a path inside the source tree.

### low

- `access-005-non-constant-time-password-compare` — Login compares passwords with a plain === instead of a constant-time or hash-verify comparison (`app/data/user-dao.js:61`, CWE-208, confirmed) — An attacker with low-latency network access to the login endpoint could, in principle, use response-time differences to narrow down a victim's password character by character faster than blind brute force, though this requires a very clean timing channel to be practical. Fix: Store passwords hashed with bcrypt (bcrypt.hashSync on signup) and verify with bcrypt.compareSync, which is constant-time with respect to the secret, instead of ===.
- `access-006-session-no-absolute-expiry` — Session cookie is configured with no maxAge/expiry and no Secure flag, so sessions never expire server-side (`server.js:78`, CWE-613, confirmed) — A session id, once obtained (e.g. via network capture, XSS, or a shared machine), remains valid indefinitely with no absolute expiration, extending the window an attacker can reuse a stolen session. Fix: Set an explicit cookie.maxAge (and re-issue/rotate the id periodically), and once the app serves over HTTPS, set cookie.secure: true so the session cookie is never sent in the clear.
- `dep-express-session-cookie-onheaders` — express-session bundles low-severity cookie and on-headers advisories (`package.json:14`, CWE-241, confirmed) — express-session issues the application's session cookie on every authenticated request; the bundled cookie/on-headers advisories allow malformed cookie attributes or header manipulation at the edges of what the library validates, which is low severity on its own but sits directly on the session-management path. Fix: Upgrade express-session to a current 1.19.x release so it pulls cookie >=0.7.0 and on-headers >=1.1.0.
- `dep-csurf-archived` — csurf is archived and no longer maintained upstream, and bundles a low-severity cookie advisory (`package.json:11`, CWE-1104, confirmed) — csurf is the CSRF-protection middleware in this app. It is not currently the target of an open CVE, but with the package archived, any future CSRF-bypass finding against it will never be patched upstream; the immediate cookie advisory is low severity. Fix: Plan a migration off csurf to a maintained CSRF library before relying on it long-term (the deprecation notice itself points to Express's own discussion board for current recommendations); in the meantime bump the resolved cookie dependency to >=0.7.0.
- `dep-bcrypt-nodejs-unmaintained` — bcrypt-nodejs, the password-hashing dependency, is explicitly deprecated with no active CVE found (`package.json:8`, CWE-1104, confirmed) — No known exploit exists in the code as read. The risk is that bcrypt-nodejs, being unmaintained, will not receive a fix if one is ever found in its hashing or salt-generation code, on a package that directly protects stored user passwords. Fix: Migrate to the actively maintained `bcrypt` (native binding) or `bcryptjs` (pure JS) package the deprecation notice itself recommends; verify the hash format is compatible or plan a rehash-on-login migration.
- `generalist-grunt-if-floating-git-tarball` — Build dependency is installed from a mutable GitHub branch tarball instead of a versioned, integrity-checked npm release (`package.json:51`, CWE-829, likely) — A compromise of the upstream branch (or a MITM without TLS pinning at install time) lets an attacker run arbitrary code in the build/CI environment the next time dependencies are installed, potentially exfiltrating CI secrets or poisoning the published artifact. Fix: Pin grunt-if to a specific commit SHA (e.g. `git+https://github.com/binarymist/grunt-if.git#<commit>`) or vendor/replace it with a registry-published, version-locked alternative, and verify the lockfile records that fixed reference.
- `platform-007` — Environment defaults to "development", which injects a live-reload debug script, unescaped, into every rendered page (`config/config.js:5`, CWE-489, confirmed) — A deployment that forgets to set NODE_ENV=production ships development tooling (and the unescaped-interpolation pattern it depends on) to real users, and signals to an attacker that verbose/dev behavior may be reachable elsewhere in the app. Fix: Fail closed instead of defaulting to "development" (e.g. require NODE_ENV to be set, or default to "production"), and never interpolate config-driven script tags without escaping.
- `secrets-zap-api-key-dev` — OWASP ZAP API key hard-coded in development and test configuration (`config/env/development.js:6`, CWE-798, confirmed) — Limited: this key only grants control of a local OWASP ZAP proxy instance used for the project's own security regression testing on a private IP; it does not grant access to the NodeGoat application or its data. Anyone who can already reach that private ZAP instance would not need this key to be meaningfully more dangerous, but the key is still committed in cleartext and reused verbatim in config/env/test.js. Fix: Read the ZAP API key from an environment variable or local, gitignored file instead of committing it, even for development/test tooling.
- `secrets-zap-api-key-test` — OWASP ZAP API key hard-coded again in the test environment configuration (`config/env/test.js:6`, CWE-798, confirmed) — Same as the development.js instance: limited to controlling a local ZAP proxy instance on a private network used for this project's own security scans. Fix: Read the ZAP API key from an environment variable or gitignored local file in both development.js and test.js rather than duplicating the literal.
- `secrets-crypto-key-dead-code` — Hard-coded AES key shipped in config for a currently-disabled encryption feature (`config/env/all.js:9`, CWE-321, possible) — No impact today, because the encryption path that would use this key is disabled (dead code). If a developer follows the tutorial's own suggested fix and uncomments profile-dao.js without first replacing cryptoKey, this exact hard-coded key would become the key used to encrypt SSNs, dates of birth and bank account/routing numbers for every user, and anyone with the repository would be able to decrypt that data. Fix: If the encryption feature in profile-dao.js is ever enabled, generate cryptoKey from an environment-provided secret or a KMS-managed key rather than this literal, and rotate/remove the literal from config/env/all.js regardless.
