## Executive summary

This review covered the locked OWASP NodeGoat tree (`/root/targets/NodeGoat`, 111 files, SHA-256 `78ac112b7bd5083bb065086c4642dcd8a3932a8d3052f9405503124c90a70fe3`), read by seven departments working in parallel over the same read-only copy: access/authentication, sensitive data, dependencies, a cross-cutting generalist pass, injection, platform/configuration, and secrets. After union and deduplication (same file, same line, same CWE), 44 distinct findings remain. The three most important: (1) server-side arbitrary code execution via `eval()` on contribution percentages (`app/routes/contributions.js:32`), giving any authenticated user command execution on the server; (2) a hard-coded, plaintext admin password that is re-seeded on every container start (`artifacts/db-reset.js:18`), giving full admin access with no credentials; (3) a fully open server-side request forgery (SSRF) in the research page, where the destination URL is entirely caller-controlled (`app/routes/research.js:15`). The review covered every HTTP entry point, the MongoDB DAOs, session and transport configuration, the template engine, and the dependency manifest and lockfile; it did not cover Git history, vendored third-party packages, real deployment behavior, or any dynamic testing (see "What was not covered"). Method: entry points read first, one finding per sink, the exact line quoted and mechanically re-verified by the examiner (`verify-safety-report.mjs`), a stated confidence level per finding, `semgrep` (v1.177.0) and `npm audit` used as lead generators rather than as proof.

## Scope and method

Target: `/root/targets/NodeGoat` (OWASP NodeGoat, an intentionally vulnerable Express.js/MongoDB training application), locked in `target.json` to 111 files under a root SHA-256 of `78ac112b7bd5083bb065086c4642dcd8a3932a8d3052f9405503124c90a70fe3`; the tree is read-only, and `verify-safety-report.mjs` re-hashed every locked file before this report was written, confirming nothing in it had changed.

Seven departments ran and each committed its own `findings/<department>.json` and `report/<department>.md` on its own branch, merged into this worktree: **access** (authentication, session handling, authorization), **data** (sensitive data exposure, logging, cryptography), **dependencies** (manifest/lockfile audit), **generalist** (a cross-cutting full-tree pass for defects that fall outside the other departments' named subjects), **injection** (SQL/NoSQL/command/template injection, XSS, SSRF, open redirects), **platform** (security headers, cookies, CSRF, rate limiting, error handling, environment defaults), and **secrets** (hard-coded credentials and leaked configuration).

Tools that ran: `semgrep` v1.177.0, run by access, data, generalist, injection, platform and secrets with the code-safety pack's local rules plus the registry pack `p/owasp-top-ten` (`--metrics off --json`), each run producing 29 hits over 72 tracked files that were used only as pointers to code worth reading, never quoted as findings on their own; `npm audit --json`, run by the dependencies department directly inside the read-only target with the npm registry reachable (145 raw advisory entries returned, split `critical: 38, high: 66, moderate: 33, low: 8` before grouping by direct dependency), plus read-only `npm view` registry queries to check package maintenance status; and `node verify-safety-report.mjs`, run by every department against its own `findings/<department>.json` before commit, and run again here against the union `findings.json` and against this report.

Every finding below reflects a file a department's session actually opened and read line by line, not a file that merely exists in the target. Files that were read in full or in the cited section across the seven departments include: `server.js`; `config/config.js` and `config/env/{all,development,production,test}.js`; every route handler under `app/routes/` (`index.js`, `session.js`, `profile.js`, `contributions.js`, `allocations.js`, `benefits.js`, `memos.js`, `research.js`, `error.js`, `tutorial.js`); every DAO under `app/data/` (`user-dao.js`, `profile-dao.js`, `contributions-dao.js`, `allocations-dao.js`, `benefits-dao.js`, `memos-dao.js`, `research-dao.js`); the views that render request-derived data (`app/views/login.html`, `signup.html`, `profile.html`, `memos.html`, `error-template.html`, `dashboard.html`); `package.json` and `package-lock.json`; `artifacts/db-reset.js` and `artifacts/cert/server.key`; `Dockerfile`, `docker-compose.yml`, `Procfile`, `app.json`, `nodemon.json`, `cypress.json`; and `test/security/profile-test.js` together with the e2e fixtures under `test/e2e/fixtures/users/`. This report is a review by a language model, grounded by that static scanner (`semgrep`), by the advisory source (`npm audit` against the live registry), and by this program's own mechanical examiner (`verify-safety-report.mjs`), not a claim about what exists in files no session opened.

## Findings

### critical

- `access-missing-role-benefits-post` — Any authenticated user can modify another user's benefit start date via an unguarded admin route (`app/routes/index.js:56`, CWE-862, confirmed) — the `isAdmin` middleware defined two lines above is never attached to `POST /benefits`, and the handler takes its target `userId` from the request body, so any logged-in user can overwrite any other employee's benefit start date; add `isAdmin` to the route's middleware chain and validate `userId` server-side.
- `dependencies-underscore-rce` — underscore is pinned to a version with a known arbitrary-code-execution advisory (`package.json:23`, CWE-94, confirmed) — the resolved 1.9.1 falls inside GHSA-cf4h-3jhx-xvhq's affected range, letting a template-compiler call execute attacker-supplied code; upgrade to `underscore@>=1.13.8`.
- `dependencies-swig-file-read-abandoned` — swig has an unpatched arbitrary local file read and has had no release since 2014 (`package.json:22`, CWE-22, confirmed) — GHSA-2rq5-699j-x7p6 has no fix available and the package is registry-marked no longer maintained; replace swig with a maintained template engine.
- `dependencies-forever-outdated` — forever's process-supervision chain carries a critical prototype-pollution advisory (`package.json:15`, CWE-1104, confirmed) — the resolved 2.0.0 pulls in a vulnerable `nconf` via `flatiron`/`forever-monitor`; the audit's own fix is the major-version jump to `forever@4.0.3`.
- `injection-eval-contributions` — Server-side code injection via `eval()` on contribution percentages (`app/routes/contributions.js:32`, CWE-95, confirmed) — `req.body.preTax`/`afterTax`/`roth` are evaluated as JavaScript before any validation runs, giving any logged-in user remote code execution on the server; replace `eval()` with `Number()`/`parseInt()`.
- `injection-ssrf-research` — Server-side request forgery: the research endpoint fetches an attacker-supplied URL (`app/routes/research.js:15`, CWE-918, confirmed) — `req.query.url` is concatenated and handed straight to `needle.get()` with the response echoed back to the caller, enabling internal network reconnaissance and cloud-metadata reads; resolve symbols against a fixed server-side endpoint or allowlist and revalidate the resolved host.
- `secrets-002-admin-password` — Default admin account is seeded with a hard-coded plaintext password on every deploy (`artifacts/db-reset.js:18`, CWE-798, confirmed) — `docker-compose` and the Heroku postdeploy hook both run this seed script, and the login check compares passwords with plain `===`, so `admin`/`Admin_123` is a working unauthenticated path to full admin access on any default deployment; stop shipping a fixed default credential and hash stored passwords with bcrypt.

### high

- `access-idor-allocations` — Allocations route trusts the `:userId` path parameter with no ownership check (IDOR) (`app/routes/index.js:63`, CWE-639, confirmed) — only `isLoggedIn` guards `GET /allocations/:userId`, so any authenticated user can read any other user's financial allocation record by changing the URL; derive the target user from `req.session.userId` instead of the path parameter.
- `access-csrf-profile-update` — State-changing profile update, including bank account and SSN, has no CSRF protection (`app/routes/index.js:48`, CWE-352, confirmed) — the `csurf` middleware that would populate and check a token is entirely commented out in `server.js`, so a forged cross-site POST from a page the victim merely visits changes their bank/SSN data; mount `csrf()` and verify the token on every state-changing route.
- `data-plaintext-password-storage` — User passwords are stored and compared in plaintext (`app/data/user-dao.js:25`, CWE-256, confirmed) — signup stores the raw password and login compares with `===`; the bcrypt hashing call exists only as a comment. A database compromise recovers every user's real password; hash with bcrypt/argon2id and compare with the corresponding verify function.
- `data-ssn-dob-bank-stored-unencrypted` — SSN and date of birth are written to the database unencrypted; the encryption code exists but is disabled (`app/data/profile-dao.js:62`, CWE-311, confirmed) — the AES/PBKDF2 encrypt/decrypt helpers built for this purpose are commented out, so SSNs, DOBs and bank details sit in plaintext in MongoDB; re-enable field-level encryption with a key that is not the one hard-coded in config.
- `dependencies-mongodb-driver-dos` — mongodb driver is pinned to a version vulnerable to a denial-of-service advisory (`package.json:18`, CWE-400, confirmed) — the resolved 2.2.36 falls inside GHSA-mh5c-679w-hh4r's range plus two further advisories via `mongodb-core`; the audit's fix path is a major upgrade to `mongodb@7.6.0`.
- `dependencies-marked-redos` — marked is pinned to a 2015-era version with six distinct XSS and ReDoS advisories (`package.json:17`, CWE-1333, confirmed) — the exact-pinned `0.3.5` falls inside every one of six advisory ranges; move to a current maintained release and re-check the 4.x API.
- `dependencies-body-parser-dos` — body-parser is pinned to a version vulnerable to a URL-encoding denial-of-service (`package.json:9`, CWE-405, confirmed) — the resolved 1.18.3 falls inside GHSA-qwcr-r2fm-qrc7's range, plus six further advisories via `qs`; upgrade to `body-parser@>=1.20.6`.
- `dependencies-express-outdated` — express is pinned to an outdated 4.16.x line carrying 16 distinct advisories across its own code and bundled dependencies (`package.json:13`, CWE-1104, confirmed) — includes an open redirect and a reflected-XSS-via-redirect on express itself plus advisories in six bundled packages; track `npm audit fix`'s remediation graph rather than bumping express alone.
- `dependencies-helmet-outdated` — helmet is pinned to a version that pulls in a ReDoS advisory (`debug`) and a CSP configuration-override advisory (`helmet-csp`) (`package.json:16`, CWE-1104, confirmed) — 4 distinct advisories reachable through this one dependency; upgrade to a current major release (helmet's API was restructured across majors).
- `injection-nosql-where-allocations` — NoSQL injection via unsanitized threshold in a MongoDB `$where` clause (`app/data/allocations-dao.js:77`, CWE-943, confirmed) — `req.query.threshold` is interpolated verbatim into server-executed JavaScript, letting an attacker pin the database on an infinite loop or extract other users' data; replace the `$where` clause with a plain query operator on a validated numeric value.
- `injection-xss-stored-memos` — Stored XSS: memo body is rendered as raw HTML to every user (`app/views/memos.html:31`, CWE-79, confirmed) — memos are rendered through `marked()` with autoescape globally disabled, so any authenticated user can post script that executes in every other viewer's browser, including admins'; sanitize the rendered HTML with an allowlist sanitizer and re-enable autoescape.
- `platform-insecure-http-transport` — The server listens on plain HTTP; the session cookie and all credentials travel in cleartext (`server.js:145`, CWE-319, confirmed) — the working `https.createServer` block is fully commented out and no route redirects HTTP to HTTPS; terminate TLS at the app or at a reverse proxy and redirect all traffic to HTTPS.
- `platform-session-cookie-flags-missing` — Session cookie is issued with no httpOnly, secure or sameSite flag and the default cookie name (`server.js:78`, CWE-1004, confirmed) — the `session()` call has no `cookie` option at all, so express-session's insecure defaults apply; set `cookie: { httpOnly: true, secure: true, sameSite: 'lax', maxAge: ... }` and a non-default cookie name.
- `platform-swig-autoescape-disabled` — The template engine's autoescape is globally disabled (`server.js:137`, CWE-79, confirmed) — `swig.setDefaults({ autoescape: false })` turns every reflected value in every view into a potential XSS sink; remove the override so swig's documented default (`true`) applies.
- `secrets-001-cookie-secret` — Session-signing secret is hard-coded in committed config with no override path (`config/env/all.js:8`, CWE-798, confirmed) — no environment variable overrides this literal in any of the four config files, so it is used unmodified by every default deployment, letting anyone with the source forge a valid session cookie for any user; read it from an environment variable or secrets manager and rotate the exposed value.

### medium

- `access-missing-role-benefits-get` — Benefits listing is reachable by any logged-in user, not only admins (`app/routes/index.js:55`, CWE-862, confirmed) — the `isAdmin` middleware defined in the same file is never applied to `GET /benefits`; add it to the route.
- `access-session-fixation-login` — Session id is not regenerated after successful login, enabling session fixation (`app/routes/index.js:34`, CWE-384, confirmed) — `handleLoginRequest` sets `req.session.userId` without first calling `req.session.regenerate()`, unlike the signup handler in the same file; wrap the post-login state change in `req.session.regenerate()`.
- `access-no-rate-limit-login` — Login endpoint has no attempt limiting or lockout (`app/routes/index.js:34`, CWE-307, confirmed) — no rate-limiting or account-lockout middleware is mounted anywhere in the request path, making online brute-force practical; add a per-account/per-IP limiter with backoff.
- `generalist-session-memorystore-dos` — express-session is mounted with the default in-memory store, `saveUninitialized:true`, and no cookie expiry, so every visit leaks a session that is never pruned (`server.js:78`, CWE-770, likely) — an unauthenticated attacker can repeatedly hit any public route to grow the in-memory session store without bound, exhausting server memory; configure a bounded external session store with TTL eviction, set `saveUninitialized: false`, and set `cookie.maxAge`.
- `injection-open-redirect-learn` — Open redirect via unvalidated `url` query parameter (`app/routes/index.js:72`, CWE-601, confirmed) — `GET /learn` passes `req.query.url` straight into `res.redirect()`, letting an attacker phish a victim through the trusted origin; validate the destination against a fixed allowlist before redirecting.
- `injection-xss-reflected-profile-href` — Reflected XSS: unescaped `firstName` echoed into an `href` attribute on validation error (`app/views/profile.html:78`, CWE-79, confirmed) — `firstNameSafeString` is set from `req.body.firstName` with no encoding and rendered with autoescape disabled; encode the value for its attribute context before rendering.
- `injection-xss-reflected-login-username` — Reflected XSS: unvalidated username echoed unescaped on failed login (`app/views/login.html:110`, CWE-79, confirmed) — a failed login re-renders the submitted `userName` verbatim into a form field with autoescape disabled; encode the value before rendering, or apply the same validation login performs on other fields.
- `platform-security-headers-not-mounted` — No security-header middleware is mounted; CSP, frame options, HSTS and MIME-sniffing protection are absent (`server.js:68`, CWE-693, confirmed) — the entire `helmet` block is commented out, so responses carry no `X-Frame-Options`, `X-Content-Type-Options`, CSP or HSTS, and disclose `X-Powered-By: Express`; uncomment and mount `helmet()` and disable `x-powered-by`.
- `platform-csrf-protection-not-mounted` — CSRF protection is never mounted; all state-changing POST routes accept cross-site requests (`server.js:132`, CWE-352, confirmed) — the `csurf` require and its mounting block are both commented out in `server.js`, so no route registered afterward ever checks a token; mount `csrf()` after the session middleware and before route registration.
- `platform-error-handler-exposes-error-object` — The global error handler renders the raw caught error object into the HTML response (`app/routes/error.js:10`, CWE-209, confirmed) — with autoescape disabled, whatever the internal error's `toString()` produces reaches the client unescaped, aiding reconnaissance and enabling reflected XSS from certain error paths; log the full error server-side only and render a generic message.
- `platform-default-env-is-development` — The application defaults to the development configuration whenever `NODE_ENV` is unset, including in the shipped Docker Compose deployment (`config/config.js:5`, CWE-489, confirmed) — Compose declares `NODE_ENV:` with no value, which falls back to `"development"`, injecting a live-reload script tag and exposing a hard-coded ZAP API key into every rendered page; default to `"production"` or refuse to start without an explicit `NODE_ENV`.
- `secrets-004-committed-private-key` — RSA private key committed to the repository for a currently-disabled HTTPS listener (`artifacts/cert/server.key:1`, CWE-321, confirmed) — the key is unused by the running server today but is shipped in this public repository and would be immediately reusable if the commented-out HTTPS block is re-enabled without rotating it; remove it from source control and issue a fresh keypair per deployment.
- `secrets-005-config-logged-to-stdout` — Full config object, including the session secret and crypto key, is logged to stdout on every start (`config/config.js:12`, CWE-532, confirmed) — the merged config, including `cookieSecret` and `cryptoKey`, is written unconditionally to stdout on every process start, widening exposure to anyone with log access; remove the log line or redact the known-sensitive keys before logging.

### low

- `access-timing-unsafe-password-compare` — Login password check uses a non-constant-time string comparison (`app/data/user-dao.js:61`, CWE-208, confirmed) — `fromDB === fromUser` leaks timing information about partial matches; compare with `bcrypt.compareSync`/`bcrypt.compare` after hashing at signup.
- `access-session-no-absolute-expiry` — Session cookie has no `maxAge`, so authenticated sessions never expire on their own (`server.js:78`, CWE-613, confirmed) — the `session()` call has no `cookie` block at all, so only an explicit logout ends a session; set an explicit `cookie.maxAge`.
- `data-hardcoded-crypto-key` — Encryption key for PII fields is hard-coded in the committed configuration (`config/env/all.js:9`, CWE-798, confirmed) — the key is currently dead code (the encryption path that would use it is disabled) but would defeat re-enabled encryption if not rotated; never commit encryption keys, load from a secrets manager.
- `dependencies-bcrypt-nodejs-abandoned` — Password hashing depends on `bcrypt-nodejs`, a package the registry itself marks no longer maintained (`package.json:8`, CWE-1104, confirmed) — no advisory is open today, but the registry's own deprecation notice names `bcrypt`/`bcryptjs` as the replacement for this security-sensitive dependency; migrate to one of them.
- `secrets-003-crypto-key-dead-code` — Hard-coded AES key shipped in config for a currently-disabled encryption path (`config/env/all.js:9`, CWE-321, possible) — no live code path reaches this key today (SSN/DOB are stored in plaintext instead), but it would make any re-enabled encryption trivially reversible; remove the literal and derive any future key from a secrets manager with a fresh IV per operation.
- `secrets-006-zap-api-key` — Hard-coded OWASP ZAP API key used by the security-test harness (`config/env/development.js:6`, CWE-798, confirmed) — a live credential to a private (RFC1918) ZAP proxy instance, bounded impact since it is dev/test tooling on a non-internet-reachable host; read it from an environment variable on the test runner instead.

### info

- `dependencies-node-esapi-abandoned` — `node-esapi` has had exactly one release in its entire history, 11+ years ago (`package.json:20`, CWE-1104, confirmed) — a maintenance finding, not a vulnerability finding; confirm what it is used for and replace it with a maintained equivalent.
- `dependencies-devdependencies-outdated-bundle` — 14 devDependencies are pinned to versions with a combined 105 distinct advisories in their transitive trees (`package.json:41`, CWE-1104, confirmed) — none ship in the production runtime tree, so this is a build/CI supply-chain risk, not a direct application-runtime one; treat as routine dev-tooling maintenance.
- `secrets-007-e2e-fixture-admin-password` — Test fixture duplicates the live default admin password (`test/e2e/fixtures/users/admin.json:3`, CWE-798, confirmed) — this fixture only matters to whoever runs the e2e suite; the primary exposure is `secrets-002-admin-password`. Apply the same fix there.

## What was not covered

**File kinds nobody opened line by line:** vendored third-party client-side bundles (`app/assets/vendor/**` — jQuery, Bootstrap, Raphael, Morris, Font Awesome) and binary/image assets (favicon, PNGs, font files) were located but treated as unmodified upstream code, not first-party attack surface. `node_modules` was not walked; only `npm audit`'s advisory feed and targeted `npm view` metadata queries were used to assess dependency risk. `package-lock.json` was not read line by line for embedded registry tokens (a targeted grep found none). CI/CD workflow files (`.github/workflows/*.yml`, `.travis.yml`) were grepped for hard-coded-secret and mutable-action-tag patterns but not fully read or filed as platform/dependency findings.

**Classes of defect no department owns in this run:** typosquatting of dependency names was not systematically checked, only impressionistically reviewed while reading the manifest. Full manual tracing of every Swig `{{ }}` interpolation in every view was not performed; only the request-tainted sinks named above were traced end-to-end. JWT handling and MFA were not exercised because this codebase has no JWT issuance/verification code path and no MFA/OTP flow — the corresponding checks in the access skill do not apply here. `.git` history was not scanned for secrets rotated out of the current tree (no full-history gitleaks/trufflehog-style pass); only the files as locked in `target.json` were read. Cryptographic verification that `artifacts/cert/server.key` and `server.crt` are a matching pair was not attempted.

**Checks that did not run:** no dynamic testing or exploitation attempt was made against a running instance of NodeGoat; every finding above is from a static read of the locked tree. Runtime/deployment behavior — the actual `NODE_ENV`, environment variables, a reverse proxy or WAF in front of the app, or which log aggregator really captures container stdout in a given deployment — cannot be confirmed from static reading alone, and several findings' real-world impact (e.g. `secrets-005-config-logged-to-stdout`, `platform-default-env-is-development`) depends on that unconfirmed deployment detail. No native/mobile code exists in this tree, so no memory-safety class of defect was in scope.
