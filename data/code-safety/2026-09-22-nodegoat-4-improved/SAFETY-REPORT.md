## Executive summary

This review covered the OWASP NodeGoat repository (`/root/targets/NodeGoat`, 111 files locked by SHA-256, per `target.json`). Six departments each ran a static, language-model-assisted review over their own scope — access (authentication, session, authorization), data (exposure, cryptography, logging), dependencies (components and advisories), injection (SQL/NoSQL/command, XSS, SSRF, open redirect), platform (headers, cookies, rate limiting, errors) and secrets (hard-coded credentials and keys) — each grounded by semgrep 1.177.0 (the local pack plus p/owasp-top-ten) and, for dependencies, by npm audit --json / npm view. The deduplicated union (by file, line and CWE, keeping the higher-confidence entry) holds 44 findings out of 50 the departments reported: 6 critical, 18 high, 12 medium, 7 low, 1 info. The most important: (1) three server-side code-injection sinks via eval() on the contribution percentage (`app/routes/contributions.js:32-34`), letting any authenticated user run arbitrary JavaScript on the server; (2) passwords stored in plaintext in MongoDB (`app/data/user-dao.js:25`), exposing every user's real password to anyone who reads the database; (3) an admin account seeded with the plaintext credential admin/Admin_123 and compared by string equality (`artifacts/db-reset.js:18`), directly exploitable remotely. The review covered HTTP entry points, authentication and session handling, sensitive data, declared dependencies, injection sinks, and platform configuration, over the files each department actually read (see "Scope and method"). ## Scope and method

## Findings

### critical

- `data-plaintext-password-storage` — User passwords are stored in MongoDB as plaintext, not hashed (`app/data/user-dao.js:25`, CWE-256, confirmed) — Anyone who reads the users collection - a database backup, an admin, a NoSQL-injection read, or a compromised DB credential - obtains every user's real login password in cleartext, directly reusable against this and any other site the user reused it on. Hash the password with bcrypt (or argon2id) before insert, e.g. `password: bcrypt.hashSync(password, bcrypt.genSaltSync(12))`, and compare with bcrypt.compareSync in validateLogin instead of `===`.
- `dependencies-swig-unmaintained-file-read` — swig, the active template engine, is deprecated/unmaintained and has an unfixed arbitrary local file read advisory (`package.json:22`, CWE-22, confirmed) — Combined with any template-injection path, an attacker can read arbitrary files on the server filesystem; there is no upstream fix and the maintainers have stopped shipping one, so this risk is permanent as long as swig stays in the dependency tree. Replace swig with a maintained template engine (the project already loads templates through `consolidate`, which supports several current engines), and re-enable autoescaping in whatever engine replaces it.
- `dependencies-underscore-rce` — underscore is pinned to a range resolving to a version with a known arbitrary-code-execution advisory (`package.json:23`, CWE-94, confirmed) — If `_.template` is ever called with attacker-influenced template source or options, an attacker can execute arbitrary code in the Node.js process; independently, a crafted deeply-nested object handed to `_.flatten` or `_.isEqual` can crash the process via stack exhaustion. Update underscore to >=1.13.8 and confirm no code path in the application passes attacker-controlled strings into `_.template`.
- `injection-eval-pretax` — Server-side JavaScript injection via eval() on contribution percentage (preTax) (`app/routes/contributions.js:32`, CWE-95, confirmed) — Any authenticated user can submit a POST /contributions request with preTax set to arbitrary JavaScript (e.g. `require('child_process').execSync('id')` or a process-crashing payload) and have it executed in the Node process, giving full server-side code execution under the application's privileges. Never eval request data. Parse the value with Number()/parseInt() and reject non-numeric input, as the commented-out fix in the same file (lines 37-40) already shows.
- `injection-eval-aftertax` — Server-side JavaScript injection via eval() on contribution percentage (afterTax) (`app/routes/contributions.js:33`, CWE-95, confirmed) — Any authenticated user can execute arbitrary JavaScript on the server by setting afterTax to a malicious expression, achieving remote code execution. Replace eval(req.body.afterTax) with Number(req.body.afterTax) or parseInt(req.body.afterTax, 10) plus a NaN check before use.
- `injection-eval-roth` — Server-side JavaScript injection via eval() on contribution percentage (roth) (`app/routes/contributions.js:34`, CWE-95, confirmed) — Any authenticated user can execute arbitrary JavaScript on the server by setting roth to a malicious expression, achieving remote code execution. Replace eval(req.body.roth) with Number(req.body.roth) or parseInt(req.body.roth, 10) plus a NaN check before use.

### high

- `access-idor-allocations-userid` — Allocations route is an IDOR: any logged-in user can read any other user's allocation data by editing the URL (`app/routes/index.js:63`, CWE-639, confirmed) — Any authenticated low-privilege user can walk the numeric :userId path segment (e.g. /allocations/1, /allocations/2, ...) and receive another user's stock/fund/bond allocation data. Ignore the :userId route parameter and load allocations for req.session.userId only, or verify req.session.userId === req.params.userId (or that the caller is admin) before calling the DAO.
- `access-missing-admin-check-benefits` — Admin-only benefits routes have no role check; any logged-in user can view and overwrite any other user's benefit start date (`app/routes/index.js:56`, CWE-862, confirmed) — Any authenticated non-admin user can POST an arbitrary userId and benefitStartDate to overwrite another employee's benefits record, and can view the admin benefits roster of all non-admin users -- a full vertical privilege escalation on a state-changing route. Add the existing isAdmin middleware to both routes exactly as the commented-out code shows: app.get("/benefits", isLoggedIn, isAdmin, ...) and app.post("/benefits", isLoggedIn, isAdmin, ...).
- `access-password-compare-not-constant-time` — Login compares passwords with plain string equality on plaintext-stored passwords instead of a constant-time hash verify (`app/data/user-dao.js:61`, CWE-916, confirmed) — The === comparison leaks timing information proportional to the number of matching leading characters, letting an attacker who can measure response time recover a valid password character-by-character; independently, because passwords are stored in plaintext, any read access to the users collection discloses every user's real password in the clear, not a hash. Hash passwords on signup with bcrypt (bcrypt.hashSync(password, bcrypt.genSaltSync())) and verify with the library's constant-time bcrypt.compareSync(password, user.password) instead of ===.
- `access-csrf-missing-profile-update` — No CSRF protection anywhere in the app: profile update (bank account, SSN, address) is forgeable from a cookie-authenticated session (`app/routes/index.js:48`, CWE-352, confirmed) — A page on another origin that auto-submits a form to POST /profile (the victim's session cookie is attached automatically by the browser) can silently overwrite the victim's bank account number, routing number, SSN, address, and name. Re-enable csurf() (or an equivalent double-submit/SameSite=Strict scheme) mounted before the routes in server.js, and include the token in every state-changing form (profile, benefits, contributions, memos, login).
- `data-config-logged-at-startup` — Full application config, including session secret and crypto key, is dumped to stdout on every start (`config/config.js:12-13`, CWE-532, confirmed) — Anyone who can read the process's stdout/log files - container logs, a log-aggregation pipeline, a support engineer, or an attacker with log read access - obtains the session-signing secret, the crypto key, and the database credentials in one line, enough to forge sessions for any user and to connect to the database directly. Remove the startup config dump, or log an explicit allowlist of non-secret fields (e.g. port, hostName) instead of the whole object.
- `data-cleartext-pii-storage` — SSN, date of birth and bank account/routing numbers are stored in MongoDB unencrypted (`app/data/profile-dao.js:55-66`, CWE-312, confirmed) — Anyone who reads the users collection - a database backup, an admin, an SSRF/NoSQL-injection read path, or a stolen DB credential - obtains every user's real SSN, date of birth and bank account/routing numbers in cleartext. Re-enable field-level encryption (AES-256-GCM with a random IV per record, key from a vault) before writing ssn/dob/bankAcc/bankRouting, and decrypt only when displaying to the owning user.
- `data-cleartext-http-transport` — Application only listens over plain HTTP; TLS is fully disabled (`server.js:145`, CWE-319, confirmed) — Any attacker positioned on the network path (shared Wi-Fi, a compromised router, an ISP, or a man-in-the-middle) can read or modify login credentials, session cookies and all submitted PII in transit. Terminate TLS at the app or a reverse proxy in front of it, redirect all HTTP to HTTPS, and set the session cookie's `secure` flag once TLS is in place.
- `dependencies-express-outdated-vulnerable` — express is a vulnerable 4.x release pulling six vulnerable transitive packages (`package.json:13`, CWE-1104, confirmed) — An attacker can redirect users to attacker-controlled hosts, inject markup via response.redirect(), or trigger denial-of-service through the vulnerable transitive qs/path-to-regexp parsers -- reachable on every request the framework handles, unauthenticated. Update express to >=4.21.2 (still within the declared ^4.13.4 range; `npm audit fix` reports a fix is available without a manifest change) and regenerate package-lock.json so the transitive body-parser/cookie/qs/send/serve-static versions are refreshed too.
- `dependencies-body-parser-dos` — body-parser is pinned to a range that resolves to a version with two denial-of-service advisories (`package.json:9`, CWE-405, confirmed) — An unauthenticated remote attacker can send a crafted request body to exhaust event-loop time or bypass the configured body-size limit, denying service to the whole application. Update body-parser to >=1.20.6 (within the declared ^1.15.1 range; npm audit reports a non-breaking fix is available) and regenerate the lockfile.
- `dependencies-marked-xss-redos` — marked is pinned to an exact, years-old version with active XSS and ReDoS advisories, and is wired into templates (`package.json:17`, CWE-79, confirmed) — A user who can submit markdown content (e.g. via the memos feature) can bypass marked's sanitize option and inject script that executes in another user's session, or trigger a ReDoS that stalls the single Node.js event loop for every request. At minimum update to marked@0.3.19 (the non-major fix npm audit resolves within this branch); for a durable fix, migrate off the deprecated `sanitize` option entirely and run output through a maintained HTML sanitizer (e.g. DOMPurify) on a current marked major version.
- `dependencies-mongodb-driver-outdated` — mongodb driver is pinned to an ancient 2.x range with a DoS advisory and an unmaintained transitive driver-core (`package.json:18`, CWE-1104, confirmed) — A malformed server response or crafted query result can crash or hang the database connection layer that every route in the application depends on; the 2.x driver also predates years of TLS, authentication and query-hardening fixes shipped in later majors. At minimum update to mongodb >=3.1.13 to clear the known DoS; plan a migration to a current major (7.x) since the 2.x line is long past any security support window.
- `injection-nosql-where-allocations` — NoSQL injection via unsanitized threshold in MongoDB $where clause (`app/data/allocations-dao.js:78`, CWE-943, confirmed) — An attacker can submit GET /allocations/<userId>?threshold=' ; while(true){} // or an operator such as 0' ; return true; var x='0 to run arbitrary JavaScript inside the MongoDB server, causing denial of service or bypassing the intended filter to read every user's allocation data. Never build a $where clause from request input. Validate `threshold` as a bounded integer (parseInt with a 0-99 range check, as the commented-out original fix does) and use a plain query object such as { userId: parsedUserId, stocks: { $gt: parsedThreshold } } instead of a $where string.
- `injection-ssrf-research` — Server-side request forgery via unvalidated url/symbol query parameters (`app/routes/research.js:16`, CWE-918, confirmed) — An authenticated user can set url to an internal or cloud-metadata address (e.g. http://169.254.169.254/ or http://localhost:<internal-port>/) and have the server fetch it on their behalf, exfiltrating internal service responses or cloud credentials back through the reflected response body. Validate and allowlist the destination host (e.g. restrict to finance.yahoo.com) before calling needle.get, resolve and re-check the IP to block private/link-local/metadata ranges, and never let the request supply the full request URL.
- `injection-xss-memos-marked` — Stored XSS: unescaped markdown-rendered memo output with autoescape disabled (`app/views/memos.html:31`, CWE-79, confirmed) — Any logged-in user can submit a memo containing HTML/script content (e.g. via a markdown construct marked's sanitizer fails to strip, or raw HTML since sanitize is not a full parser-level guarantee) that executes in every other user's browser when they view /memos, enabling session/cookie theft or actions performed as another user. Re-enable swig's default autoescaping (remove autoescape: false in server.js) and, for the deliberately-raw markdown output, sanitize the rendered HTML with an allowlist library (e.g. DOMPurify server-side) immediately before rendering rather than relying on marked's sanitize option alone.
- `platform-missing-security-headers` — No security response headers are set anywhere in the middleware stack (`server.js:68`, CWE-693, confirmed) — Clickjacking (no frame-ancestors/X-Frame-Options), unrestricted script/style sources for any injected content (no CSP), MIME-type confusion attacks (no X-Content-Type-Options: nosniff), no forced HTTPS upgrade (no HSTS), and easy fingerprinting of the framework/version via X-Powered-By to target known Express/Node CVEs. Require and mount helmet() as the first middleware in the stack, before favicon/body-parser/session: `app.use(helmet());` plus an explicit `contentSecurityPolicy` policy, `app.disable("x-powered-by")`, and `helmet.hsts()` once the app is served over HTTPS.
- `platform-no-rate-limiting-auth` — Login and signup routes have no rate limiting or lockout (`app/routes/index.js:34`, CWE-307, confirmed) — An attacker can script unlimited username/password guesses against /login (and account-enumeration or spam signups against /signup at app/routes/index.js:38) at whatever rate the network allows, making credential stuffing and brute force practical against any account. Mount a limiter (e.g. express-rate-limit) keyed by IP and by username/account on /login, /signup, and any password-reset route, with a lockout or exponential backoff after repeated failures.
- `secrets-cookie-secret` — Express session signing secret is hard-coded in the committed default configuration (`config/env/all.js:8`, CWE-798, confirmed) — Anyone who has read the (public, OWASP-published) source tree knows the exact HMAC key express-session uses to sign the session-id cookie. They can craft or tamper with a session cookie's signature for any session id, which is the building block for session fixation/hijacking against any user of a deployment that has not overridden this default. Read the secret from a required environment variable (fail startup if unset) and generate a unique, random value per deployment; rotate the committed value since it must now be treated as burned.
- `secrets-admin-default-credential` — Admin account is seeded with a hard-coded plaintext password that the running app compares in cleartext (`artifacts/db-reset.js:18`, CWE-798, confirmed) — Anyone who has read this source (a public OWASP training repo) can log in as `admin`/`Admin_123` on any deployment that used the default seed, reaching the admin-only `/benefits` route (gated by `isAdminUserMiddleware` in app/routes/session.js) and every other authenticated user's data. Remove the hard-coded seed password from source; generate a random admin password at first-run time (or require an operator-supplied one via environment variable) and store only its bcrypt hash, using the already-present but commented-out bcrypt path.

### medium

- `access-login-no-session-regenerate` — Login does not regenerate the session id, allowing session fixation (`app/routes/session.js:116`, CWE-384, confirmed) — An attacker who fixes a victim's pre-login session id (trivial here since sessions exist for unauthenticated visitors too) inherits the victim's authenticated session once the victim logs in with that id, without ever seeing the victim's credentials. Call req.session.regenerate() before setting req.session.userId in handleLoginRequest, exactly as handleSignup already does.
- `access-session-cookie-insecure-config` — Session cookie is configured with no httpOnly, no secure flag, and no maxAge (never expires) (`server.js:78-102`, CWE-614, confirmed) — The session cookie is readable by any script injected via XSS (no httpOnly), is sent in the clear (no secure flag, plain HTTP server), and carries no explicit bound on its lifetime, so a stolen or fixed session id remains usable for as long as the session store keeps it alive. Set cookie: { httpOnly: true, secure: true, maxAge: <a bounded value>, sameSite: 'lax' } in the session() call and serve over HTTPS.
- `data-hardcoded-crypto-key` — AES encryption key for PII is a hard-coded literal committed to source (`config/env/all.js:9`, CWE-798, confirmed) — If the intended SSN/DOB encryption were turned on, anyone with this committed key could decrypt every user's stored SSN and date of birth; today it also confirms the AES key an operator would need to reuse for any other encryption using this config. Load cryptoKey from environment/secret storage per deployment, generate it with a CSPRNG, and rotate the committed value.
- `data-pii-rendered-cleartext-to-client` — Profile page renders SSN, DOB and bank account/routing numbers in cleartext in the HTML response (`app/views/profile.html:49-61`, CWE-200, confirmed) — The user's SSN, date of birth and full bank account/routing numbers appear in plain text in the page's HTML source on every profile view - visible in browser history/cache, any proxy or corporate web-filter log, and to anyone positioned to read the unencrypted HTTP response (see data-cleartext-http-transport). Mask sensitive fields in the UI (e.g. show only the last 4 digits) and require a fresh, explicit reveal action; never place full SSN/bank numbers in a rendered form value.
- `dependencies-forever-transitive-prototype-pollution` — forever, a production dependency, pulls four vulnerable transitive packages including a prototype-pollution advisory in nconf (`package.json:15`, CWE-1321, confirmed) — forever itself is not on the HTTP request path, so the realistic exploitation route is through whatever configuration files or environment forever's own tooling parses via nconf; a prototype-pollution there could corrupt process-wide object behavior for anything else sharing the process. Bump the declared range to forever@^4.0.3 (a major upgrade, per npm audit's fixAvailable) or, given forever predates modern process supervisors, replace it with a maintained alternative such as pm2 or a systemd unit.
- `dependencies-bcrypt-nodejs-abandoned` — bcrypt-nodejs, the password-hashing library, is an npm-flagged deprecated package with no further releases (`package.json:8`, CWE-1104, confirmed) — The single component responsible for password hashing has no maintainer watching for weaknesses in its bcrypt implementation or new algorithmic guidance; any future flaw found in it will never receive an upstream patch. Migrate to the maintained `bcrypt` (native binding) or `bcryptjs` (pure JS) package, as the deprecation notice itself recommends.
- `dependencies-grunt-env-floating-latest` — grunt-env is declared with the floating range "latest" instead of a pinned version (`package.json:50`, CWE-1357, confirmed) — A future malicious or simply breaking publish of grunt-env is installed automatically and silently, with no version bump or diff for reviewers to see in package.json; this is a supply-chain integrity gap independent of any currently known CVE. Pin grunt-env to an exact resolved version (matching what package-lock.json currently locks it to) and let dependabot/renovate propose bumps explicitly instead of floating to "latest".
- `dependencies-grunt-if-unpinned-git-tarball` — grunt-if is installed from a GitHub branch tarball with no tag or commit pin (`package.json:51`, CWE-829, confirmed) — Whatever the `master` branch of that third-party repository contains at install time runs in the build/test pipeline with no version pin or independent review step, and package-lock.json cannot meaningfully pin its content the way it does for registry packages. Replace the branch tarball reference with a pinned commit SHA or, preferably, a published, versioned release of grunt-if (or a maintained alternative) resolved through the npm registry.
- `injection-open-redirect-learn` — Open redirect via unvalidated url query parameter (`app/routes/index.js:72`, CWE-601, confirmed) — An attacker can craft a link such as /learn?url=https://evil.example/phish that, once clicked by a logged-in victim, redirects them from a trusted NodeGoat URL to an attacker-controlled site for phishing or credential harvesting. Validate the target against an allowlist of known learning-resource hosts/paths, or only allow relative paths within the application, before calling res.redirect().
- `injection-xss-profile-firstname-value` — Reflected XSS: unescaped firstName echoed into input value attribute (`app/views/profile.html:41`, CWE-79, confirmed) — A user can submit firstName containing `"><script>...</script>` in a POST /profile request with an intentionally-invalid bankRouting value, breaking out of the value attribute and executing arbitrary script in their own (or, if combined with another stored path, another user's) browser session. Enable swig's default autoescaping, or explicitly HTML-attribute-encode firstName (e.g. via node-esapi's encodeForHTMLAttribute, matching the pattern already used for `website` at app/routes/profile.js:28) before assigning it to firstNameSafeString.
- `injection-xss-profile-firstname-href` — Reflected XSS: unescaped firstName echoed into href attribute (javascript: URI) (`app/views/profile.html:78`, CWE-79, confirmed) — A user can set firstName to `javascript:alert(document.cookie)` so that clicking the rendered 'Google search this profile by name' link executes arbitrary script in the victim's browser session, since the value lands directly in an href with no URL-context encoding or scheme allowlist. HTML/URL-encode firstName for this specific context (e.g. ESAPI.encoder().encodeForURL(...) into a separate firstNameSafeURLString field, as the code's own annotation at app/routes/profile.js:29-31 describes) and reject non-http(s) schemes before placing any value in an href.
- `platform-error-handler-discloses-error` — Global error handler renders the raw error object into the HTML response with auto-escaping disabled (`app/views/error-template.html:11`, CWE-209, confirmed) — Any unhandled error anywhere in the request pipeline (DB errors, thrown exceptions from route handlers) is echoed to the client, leaking internal error text (library names, query context, file paths) that helps an attacker map the backend, and — because auto-escaping is off — any HTML/script characters the error text happens to contain would also be rendered unescaped. In errorHandler, render only a generic message and a correlation id to the client (`res.render("error-template", { error: "Something went wrong. Reference: " + reqId })`), keep the full message/stack in server-side logs only, and re-enable swig auto-escaping.

### low
