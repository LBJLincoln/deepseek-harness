# Enterprise roster

English | [中文](README.zh.md)

`roster.json` in this directory is a generated roster of 147 seat definitions for the enterprise proof of concept, a composition of role x division x specialization built from sources this repository actually defines, and each seat carries the evidence the committed session records and the ledger give it. [`scripts/enterprise-roster.ts`](../../scripts/enterprise-roster.ts) generates it (`pnpm run roster`); [`scripts/harness-feed.ts`](../../scripts/harness-feed.ts) serves it with live session status recomputed (`pnpm run feed`). The roster is not the organisation of record: that is [the ledger](#the-ledger), `ledger.jsonl` beside it, one line per deliverable, and the program runs the feed serves on `GET /programs`. The work queue the stewards draw from is [tickets/](tickets/README.md), which [shifts](#shifts) work; the divisions that need no ticket perform their [functions](#functions) on a schedule.

## Reading the counts

No count here is a headcount of agents. The roster states three counts, each dated by its `generatedAt`: seats **defined** (`counts.defined`, the roles this repository defines), seats **occupied** with evidence (`counts.occupied`, seats a recorded deliverable names), and seats **active** in the 24 hours before the stamp (`counts.active`). `counts.work` splits the occupied and the active seats by what their deliverables were: model-driven (a model did the work), automated checks (a `verify-*` gate, a Branch CI verdict, a fold), and tickets halted before any model ran. The roster stamped 2026-09-29 07:07 UTC over 141 ledger lines reads 147 defined; 53 occupied, of which 27 model-driven, 22 automated checks and 4 only halted before any model ran; and 44 active, of which 18 model-driven, 22 automated checks and 4 halted before any model ran. What the enterprise delivered in that window, `outcomes` in the deck's `enterprise.json`, is 3 tickets shipped, 3 tickets a model worked that shipped nothing, 4 halted before any model ran, 7 of 7 code-safety review seats and 2 of 2 intake coordinators passed, and 105 of 114 automated checks passed. The command deck leads with those outcomes and shows the current counts with their age.

## The honesty rule

147 is the count of seats this repository **defines** — every entry's `source` field names a real, existing repository path (a package README, a `verify-*.ts` script, a CI gate name, an Agent Note, a skill directory, a Proving Ground bench task environment, or a code-safety review knowledge pack), checked against disk when the roster is generated. Each division's count is a fixed quota (summing to 147); a division built from a variable pool takes exactly its quota from the pool, sorted, and the generator throws naming the division and the shortfall if the tree ever defines fewer sources than that. A definition is neither a running agent nor evidence that one ever ran: every seat composes from one of the two test-fixture presets (`coding`, `reviewing`) and names the route it is defined for, whether or not a session ever ran there.

## Evidence

Each seat carries `evidence: { sessions, lastSeen?, routesSeen }`, computed from the committed records under `data/proving-ground/*/sessions` and `data/code-safety/*/sessions` by the attribution rules in [`scripts/roster-evidence.ts`](../../scripts/roster-evidence.ts), the module the feed also uses, so the file and the feed agree over the same records:

- a program session in a code-safety review occupies the code-safety seat its id names: a department's session its department's integrator seat, the program's own session and its integration session the program lead;
- a session whose `environment/run` names a bench environment occupies the Proving Ground bench operator seat specialized in that environment;
- a delegated session occupies what its delegating session occupies.

A route a session shares with a seat is not evidence. `routesSeen` names the provider routes a seat's sessions ran on beside the `route` it is defined for, so a seat defined for `deepseek-official` whose sessions all ran on `claude-code` says exactly that. The top-level `evidence` names the records read (`records`), their session count (`sessions`), and the sessions per route across every session, attributed or not (`routes`). `unattributed` counts the sessions no rule places on a seat, by reason: `environment-not-seated`, `program-not-code-safety`, `program-member-not-seated`, `parent-not-recorded`, `no-seat-evidence`. No session is placed on a seat by default.

Each seat also carries `ledger: { lines, lastAt? }`: the ticket and function lines of `ledger.jsonl` naming its id, counted exactly by seat id and nothing looser. The top-level `ledger` names the file, the lines read, and the lines naming no roster seat (`unseated`). The committed file covers exactly the records `evidence.records` names and the first `ledger.lines` lines of the ledger, so it still reproduces from those inputs after more records are committed or more lines appended; `pnpm run roster` extends it to everything committed. The [roster-evidence Agent Note](../../.agents/notes/proposed/architecture/2026-09-22-roster-evidence-and-org-of-record.md) records the attribution decision and the audit behind it.

## Occupancy

A seat is occupied only by a recorded deliverable — a shipped or reviewed ticket, a gate run on a commit, a CI verdict, a published snapshot, a recorded session attributed to it — and nothing else counts: not its definition, its route, its skills, an edge, or a mention in a task. [`scripts/enterprise-ledger.ts`](../../scripts/enterprise-ledger.ts) is the one implementation of the rule, read by the roster generator, the functions runner and the deck's published data:

- `counts.occupied` counts the seats with at least one attributed session or one ledger line;
- `counts.active` counts the seats whose newest deliverable — a ledger line by its `at`, or an attributed session by the newest time its record logged — falls inside `activeWindow`, the 24 hours ending at `generatedAt`, both ends inclusive;
- a seat's `status` is `"active"` for exactly those seats and `"defined"` for every other one; live session status is the feed's, never written here;
- a deliverable is **model-driven** when a model did the work: an attributed session, a ticket line whose department or review ran a session, that shipped, or that records model tokens, and a function line outside the check divisions (the code-safety `review`, the `intake`); an **automated check** is a function line of Verification, Judging, Observatory or Curation & Data, which run a script, read a CI verdict or fold records and call no model; any other ticket line is **halted before any model ran**;
- an occupied seat's `work.occupied` is the strongest of those kinds among all its deliverables (model-driven, then automated check, then halted), and an active seat's `work.active` the strongest among those inside the window; `counts.work.occupied` and `counts.work.active` count the seats per kind and sum to `counts.occupied` and `counts.active`.

The window is measured at `generatedAt` rather than at the moment of reading, so the file is a snapshot with a stated time: regenerated over unchanged inputs it is byte-identical, and every new ledger line or record changes the content, which restamps it and measures the window afresh. The [enterprise operating model Agent Note](../../.agents/notes/implemented/architecture/2026-09-28-enterprise-functions-and-occupancy.md) records why the rule counts deliverables and nothing else.

## The ledger

`ledger.jsonl` is append-only, one JSON object per line. Two line types share it; a line without `type` is read as a ticket line, and a line that lacks a field its readers rely on (`at`, `seat`, `division`, and the type's own required fields) is skipped and reported by line number rather than guessed at.

- A **ticket line** is one ticket worked in one shift, appended by the [engine](#shifts) (`pnpm run enterprise -- shift`): `{ "type": "ticket", "at", "shift", "ticket", "seat", "division", "programId", "implementer", "model", "department": { "outcome", "sessionId" }, "checks": [{ "id", "ok" }], "review": { "verdict", "sessionId" }, "reviewer"?: { "sessionId", "route", "model", "verdict" }, "integration": { "outcome" }, "shipped": { "commit" } | null, "reason", "tokens", "seconds" }`. `department.outcome` is `certified`, `failed`, `blocked`, `abandoned`, `pending` or `halted`; `review.verdict` is `approve`, `reject` or `none`; `reviewer`, on every line a review decided since the engine recorded it, names the reviewer's session, the route and model it ran on, and its verdict; `integration.outcome` is `merged`, `skipped`, `conflict`, `checks-failed`, `digest-mismatch` or `not-shipped`; `shipped.commit` is the commit on the branch that carries the ticket's change. A ticket is `shipped` once any of its lines names a commit in `shipped`, whatever the order of its lines, because nothing takes a shipped commit off the branch and a later line can record an attempt that began before the shipping line reached the branch (shift `041341-222d` failed `T-0007` at 04:14Z, while the line that shipped it as `cba8e4682`, dated 02:04Z, reached the branch with its shift's push at 06:45Z). Otherwise its status is its latest line's: `rejected` when the review verdict is `reject`, and `halted` otherwise — a department that failed its acceptance, a change the integration could not assemble, or a shift the route's usage limit stopped (`halted: limit (resets at <instant>)` as the reason) — and a ticket with no line is `queued`. A ticket is closed once it is `shipped` or `rejected`; a `halted` ticket stays open, and a later shift works it again.
- A **function line** is one seat performing its function on one commit, appended by `pnpm run enterprise:functions`: `{ "type": "function", "at", "shift", "seat", "division", "function", "target": { "commit", "via"?, "requested"? }, "outcome": "pass" | "fail" | "error", "evidence": { "path" } | { "url" }, "seconds" }`. `at` is the deliverable's own time — when the gate finished, or when the CI verdict was rendered — `outcome` is the gate's or the verdict's, `error` meaning no verdict could be obtained, and `evidence` is the output the seat wrote or the page it read the verdict from.

**Append-only.** A commit may only add lines at the end of the file, and a merge keeps each parent's lines in order, as the `merge=union` driver in `.gitattributes` joins two writers' appends. Every commit a line names (a ticket line's `shipped.commit`; a function line's `target.commit`, `target.requested` and `target.via`) must be a full commit id that is an ancestor of the commit that added the line, so no line cites work the branch does not carry. A writer that rebases before it pushes rewrites its own unpushed lines around the new hashes, as the [engine](#shifts) does; recovering a clone's unpushed commits must do the same, or merge that history so every commit its lines name stays on the branch. [`scripts/verify-enterprise-ledger.ts`](../../scripts/verify-enterprise-ledger.ts) checks both rules: `pnpm run verify-enterprise-ledger -- --base <rev> [--head <rev>]` walks every commit in `base..head` that changes the file and fails on a line inserted before the end, deleted or changed, a merge that drops a parent's line, an added line that does not parse, or a reference that is abbreviated, missing, or not on the adding commit's ancestry; a base the head no longer contains fails as a rewritten branch. Branch CI's static lane runs it over each push from the push's `github.event.before`. A manual run, or a push that created the branch, has no base, and the gate then checks only that every line parses. GitHub keeps only the newest pending run of the workflow, so a push whose run was superseded is checked by no run of its own; one run with `--base` at the start of any stretch covers all of it.

**Lines written after the fact.** A line its run's own writer did not append is recorded later by a line that carries `"recordedBy"` and `"recordedAt"`, both or neither. `recordedBy` is one of a closed set, `supervisor`: the session that operates the enterprise, which writes such a line only from evidence on the branch and cites that evidence in the line's `reason` or in the commit that adds it. On such a line `at` is when the event happened, or the earliest moment the evidence establishes it, and `recordedAt`, never earlier than `at`, is when the line was written. It carries only what its evidence states: a line that completes an engine run whose push failed is the engine's own line with the hashes of the rebased commits, and a line rebuilt from a lost or partial record leaves `checks` empty and omits `model`, `tokens` and `seconds`. It counts as an attempt in the queue order like any line, and the status rule (`ticketStandings` in [`scripts/enterprise-ledger.ts`](../../scripts/enterprise-ledger.ts), which the engine, the deck's data, the briefing and the report all read) places it among its ticket's lines by `at`, so recording an old shift never reopens or recloses a ticket a later line settled. The first six, all written on 2026-09-29, are shift `171951-516d`'s T-0012 (approved, then the driver crashed in the assembly) and T-0019 (rejected by its review), from that shift's partial record under [`shifts/2026-09-28-171951-516d/`](shifts/2026-09-28-171951-516d/result.json); shift `201448-94fd`'s T-0001 and T-0005, abandoned when the container reset of 2026-09-28 destroyed the shift, from [the transcript losses](../transcripts/LOSSES.md) and the restored orchestrator log; and shift `101309-c95c`'s T-0020 and T-0021, the engine's own lines, whose push the supervisor completed after the agent proxy's port moved under the running cycle.

## Shifts

A shift is one run of the [enterprise-shift engine](../../examples/headless-agent/tests/fixtures/enterprise-shift/README.md) (`pnpm run enterprise -- shift --next <n> --push`): it clones the development branch tip, works the selected open tickets through the program workflow in their own worktrees, has an independent reviewer decide on each certified change, assembles the approved ones as one commit per ticket, recertifies them, and pushes them fast-forward to the branch together with the shift's own commit. That commit carries the shift's ledger lines and its record, so the branch is the only place a shift reports to. A human release gate is not in place for unattended shifts or intakes: no person reviews what they ship, their programs run without `requireSignoff`, and their records name the spec freeze and the release as decisions of a machine principal (`daliesk-enterprise-shift`, `daliesk-enterprise-intake`) whose `decidedBy` names the engine and the shift or intake run; what a person reviews is the branch afterwards.

`shifts/<UTC date>-<shift id>/` is the shift's record: `result.json` (the shift, the program report, the engine's `decisions`, every ticket's line with the reviewer's rationale, the halt), `manifest.json` (the base revision, the branch, the composition, every file's SHA-256) and `sessions/<session id>.jsonl` for every session the shift ran — the program ledger, each department, each review, the integration — with credential- and personal-data-shaped strings, e-mail addresses included, masked by the shared patterns of `data/transcripts/tools/secret-patterns.mjs` and counted; a record in which a re-scan still finds a match is never committed. The record is written by the shift that ran it and never rewritten. `shift-starts.jsonl` holds one start line per shift, `{ type: "shift-start", at, shift, tickets, base, host, pid, implementer }`, which the shift pushes before any department runs; a start whose shift left no ticket line was cut off by a container reset, and the next shift closes each of its tickets with an `abandoned: container reset` ticket line that counts as an attempt. The file is append-only and merges by line union.

## Functions

`pnpm run enterprise:functions -- [--commit <sha>] [--shift <id>] [--branch <name>] [--only <divisions>] [--gate-timeout-ms <ms>] [--lock <file>]` ([`scripts/enterprise-functions.ts`](../../scripts/enterprise-functions.ts)) runs the functions of the divisions that need no ticket on the checked-out commit and appends one function line per seat whose function really ran. `--commit` must name the checkout, because the gates run on it; the shift defaults to the minute the run started (`2026-09-28T17-20Z`); `--only` narrows the run to some of `verification`, `judging`, `observatory`, `curation-data`; `--lock` names the file every heavy command on a shared machine takes through util-linux `flock`, and each gate then waits for it, holds it while it runs and releases it before the next gate, so a run on such a machine is started unwrapped with `--lock` rather than under an outer `flock`, which the gates could never acquire.

| Division | What runs | Evidence |
|---|---|---|
| Verification | Each of the 14 verifier seats runs the root package script its `source` names (`scripts/verify-md-links.ts` runs `pnpm run verify-md-links`), one after another; a gate that judges nothing without a build runs the script that builds and then verifies, as CI's static lane does (`verify-doc-site-fragments` runs `pnpm run docs:build:mpa`), and a script the root `package.json` lacks fails the run before anything is recorded. `pass` is exit 0, `fail` any other exit, `error` a spawn failure or the timeout (15 minutes unless `--gate-timeout-ms` says otherwise). | `functions/<shift>/<seat>.log`: the command, the commit, the outcome, and the last 12 KB of the gate's output with terminal styling and trailing whitespace removed. |
| Judging | The Branch CI run of the commit (`LBJLincoln/deepseek-harness`, `branch-ci.yml`, read from GitHub's REST API without credentials, through the proxy `HTTPS_PROXY` names when the environment names one — Node's `fetch` honours it only under `NODE_USE_ENV_PROXY=1`, which the package script sets, and a read that bypasses the proxy leaves the judges vacant with that hint; Node prints one `UNDICI-EHPA` experimental warning per process started under that variable, and the gates run without it): the newest completed run whose lanes rendered a verdict, so a run a later push superseded while it waited is passed over; when the commit has none, the first later such run whose head contains the commit (GitHub's comparison of the two answers `ahead` or `identical`), its head named in `target.via`, the branch's runs compared newest first until one's head is older than the commit; and when no such run exists yet, the branch's newest such run, a verdict on another commit, whose commit then stands in `target.commit` with the asked-for commit in `target.requested`. Each job maps to the seat of the gate mode its log opens with (`run-gates: ci-static running …`); a job's `success` is `pass`, `failure` is `fail`, anything else `error`. A gate group a job's log shows by name maps to that group's seat: `ci-lint-contracts-ready` from the `lint and duplication` gate, `ci-snapshot` from `build` and `test:snapshot`, `ci-artifacts` from `build`, `publint`, `node-next types`, `built package invariants` and `built-bin smoke`, each `pass` when every gate passed, `fail` when one failed, `error` when one was skipped after a failed dependency, and no line when the log does not show them all. | Curation & Data | The scorekeeper folds `foldSessionFacts` and `foldScoreboard` from `@deepseek-ai/dsh-scorekeeper` over the same sessions and refreshes [`scoreboard.json`](#telemetry-and-scoreboard). | `scoreboard.json`. |

If the API cannot be read, every judge stays vacant with the failure as its reason and the other divisions still run; the command exits non-zero only for a misconfiguration it cannot record — a missing roster, a commit that is not the checkout, an unknown flag.

## Telemetry and scoreboard

`telemetry.json` is the enterprise's own telemetry snapshot: `publishedAt`, the `shift` and `commit`, the `window` (the 24 hours before publication), the `records` read, `inWindow` and `total` figures — sessions, tokens (`input`, `output`, `cacheRead`, `cacheWrite`, `reasoning`, summed from the scorekeeper's efficiency facts) and the session-stats unit's `turns`, `steps`, `llmMs`, `toolMs` — `sessionsByTree`, `seats` (occupied and active in all and per division, by the occupancy rule over the ledger as it stands at publication, this run's earlier lines included), and `skipped`, the sessions the scorekeeper fold could not read. A session is in the window when its newest event is. `scoreboard.json` is the scorekeeper's fold over the same sessions: `computedAt`, `rows` (one per model route, attempt ladder, environment, isolation, implementer, preset, held-out split and district, with pass@1), `excluded`, `unstamped` (sessions no `environment/run` stamp names a cell for) and `skipped`. Both files are rewritten whole on every run.

## Live status

`GET /roster` on the running feed (`pnpm run feed`) recomputes every seat's session evidence, `evidence` and `unattributed` over every run the feed discovers, live runs included, and sets each seat's `status` from those sessions alone: `active` while a session attributed to it belongs to a run still running, `certified` once one of its sessions logged a certificate event, and `failed` when its sessions ended without one. A seat no discovered session occupies reads `"defined"` on the feed whatever the file says. The feed keeps the file's `counts`, which the file's `generatedAt` dates, and adds `counts.running`, the seats a session is running on now; the deck labels that count "running now" and never as active. A fresh checkout with no runtime data reports the committed records' evidence and `running: 0` on the feed, which is the correct answer.

## Intake

When the [ticket queue](tickets/README.md) holds fewer open tickets than its minimum, the Program Departments coordinators refill it: `pnpm run enterprise:intake` runs one program whose departments are coordinators, each proposing tickets for its own package group, and files only the proposals its deterministic admission accepts. Every run first answers the owner's [requests](#requests), writes a record under `intake/`, and appends to `ledger.jsonl` one function line per department that ran, naming the coordinator who staffed it. The [enterprise-intake fixture](../../examples/headless-agent/tests/fixtures/enterprise-intake/README.md) documents the command, admission, and the record; the [Agent Note](../../.agents/notes/implemented/architecture/2026-09-28-coordinators-intake.md) records the decision.

## Requests

The owner gives the enterprise work by committing a request, `requests/<name>.md`: a first line `# <title>` and free text, nothing else. Every [intake](#intake) run, before and independently of its refill, has a coordinator's department turn each request no ticket answers yet, up to `--max-requests` (default 2) in file-name order, into exactly one ticket whose source is the request's file and title line; a request admission refuses is recorded with the reason in the intake record and taken up again by the next run. A ticket answers a request when its `source.path` is the request's file; such a ticket, and no other, may take priority `0`, which the [shift's](#shifts) queue order takes before every untried ticket. `pnpm run enterprise:requests` ([`scripts/enterprise-requests.ts`](../../scripts/enterprise-requests.ts)) prints each request's file, title and state — `waiting`, `refused`, `queued`, `halted`, `shipped` or `rejected` — derived from the queue, the ledger and the intake records alone. The [requests README](requests/README.md) says how to write one and what each state means; the [Agent Note](../../.agents/notes/implemented/architecture/2026-09-28-owner-requests.md) records the decision.

## Code-safety specializations name a target, not an implemented scanner

This repository is TypeScript/JavaScript and ships no Java, Go, PHP, or mobile static-analysis tooling. Every department x specialization reviewer seat — including the four languages this repository does not implement a scanner for — cites its department's real review knowledge pack at `data/knowledge/code-safety/<department>/SKILL.md`; the specialization records what the seat is *for*, not a claim that a matching scanner already runs. Every reviewer, integrator, and the program lead also draws on that pack (and, for the lead, the cross-cutting review-method and severity-and-evidence packs) as a `code-safety/<id>` skill. Reviewers route to `openrouter`, cycling through the free-tier model ids this repository's own Proving Ground bench composes (`examples/headless-agent/tests/fixtures/proving-ground-bench/overlays/with-openrouter.cordis.yml`), extracted by the generator rather than hardcoded. Read [`scripts/enterprise-roster.ts`](../../scripts/enterprise-roster.ts) for exactly which source grounds each department, and the [Agent Note](../../.agents/notes/implemented/architecture/2026-09-19-enterprise-roster-and-harness-feed.md) for the full rationale.

## Publishing the deck

`pnpm run enterprise:publish` ([`scripts/enterprise-publish.ts`](../../scripts/enterprise-publish.ts)) regenerates the Command Deck's static enterprise data from the roster, the ledger and the ticket queue: `apps/command-deck/public/fixtures/roster.json`, a byte copy of `roster.json`, and `apps/command-deck/public/fixtures/enterprise.json`, the Enterprise view's lead and its Ledger tab — `asOf` (the newer of the roster's stamp and the last ledger line), the window, `outcomes` (tickets with a line in the window that shipped a commit; tickets a model worked there that shipped nothing; tickets whose every line there halted before any model ran; the model-driven function runs per function; the automated checks by outcome), seats occupied and active per division with the active ones split by `work`, the day's tickets by status (queued from the queue, the rest from each ticket's newest line inside the window), the day's function runs newest first, and the ten latest shipped commits with the CI verdicts recorded on them, matched by commit prefix. It also writes `apps/command-deck/public/fixtures/enterprise-day.json`, the deck's 24 hours tab: the [report](#the-report) over the roster's window, the 24 hours ending at its `generatedAt`, which reads the cycle records, HEAD's git history and Branch CI as the report does (the package script sets `NODE_USE_ENV_PROXY=1`); the cycle publishes before it writes its own record, so that report lists the publishing cycle as one without a record. Each file is a pure function of its inputs, GitHub's answers included for the third. Its last step runs `pnpm run enterprise:briefing` ([`scripts/enterprise-briefing.ts`](../../scripts/enterprise-briefing.ts)), which writes `apps/command-deck/public/fixtures/briefing.json`, the data of the deck's client briefing at `/briefing`: every figure the page shows with the repository paths or URLs it was read from and its computation, over the roster, the ledger, the queue, the shift and intake records, the cycle records and the enterprise's cycle commits, the cycle and scheduler logs the [live transcript capture](../transcripts/README.md#live-capture) holds, the Proving Ground and code-safety records, and, from GitHub's REST API, the branch's Branch CI runs and the repository's visibility; an unreadable API leaves those figures unknown instead of failing the step. Every fixture is rewritten only when its bytes change, and [`deck-pages.yml`](../../.github/workflows/deck-pages.yml) republishes <https://lbjlincoln.github.io/deepseek-harness/> on every push of the deck's branch that touches `apps/command-deck/**`, which a changed fixture does.

## Regenerating

```sh
pnpm run enterprise:functions   # the functions of the ticketless divisions, appended to the ledger
pnpm run roster                 # the roster over every record and every ledger line
pnpm run enterprise:publish     # the deck's fixtures from the roster and the ledger, then the briefing's
```

Each command is idempotent and safe on any later commit: the functions runner appends and never rewrites, records a CI verdict once, and leaves the judges vacant rather than failing when the API cannot be read; the generator reproduces `roster.json` byte for byte over unchanged inputs and restamps it only when a record, a source or a ledger line changed, a moved source failing it with its name before anything is written; the publisher rewrites a fixture only when its bytes change. The engine runs the three in this order after every shift.

## The cycle

[`scripts/enterprise-cycle.sh`](../../scripts/enterprise-cycle.sh) runs the enterprise once, in order: the coordinators' [intake](#intake), which answers the owner's [requests](#requests) and refills the queue when fewer than `ENTERPRISE_MIN_OPEN` tickets (default 8) are open, committed and pushed first so the shift's clone sees the new tickets; one [shift](#shifts) over the next `ENTERPRISE_TICKETS` (default 2) open tickets in the engine's queue order with `--push`, to which the cycle exports `ENTERPRISE_HEAVY_LOCK` (default `/tmp/dsh-heavy.lock`) so that each of its heavy acceptance runs takes that lock only while it runs; the ticketless [functions](#functions) on the new tip, each heavy gate taking the same lock only while it runs; `pnpm run roster` and `pnpm run enterprise:publish`; its [record](#the-cycle-record); and one commit of the functions' lines and evidence, the roster, the deck data and the record, pushed. Every step runs whatever an earlier step's outcome was, except that an intake the usage limit stopped (exit 3) skips the shift, and a record that cannot be written is the failed step `record`, after which the push still runs. The cycle exits 2 when `ENTERPRISE_PUSH_LOCK_WAIT` is not a whole number of seconds, 4 when another cycle holds its lock, 5 when the checkout has uncommitted changes to tracked files, and otherwise with the first failing step's code; its own commits carry `ENTERPRISE_COMMIT_TRAILERS` when set. The cycle's commits and pushes carry machine-written data only and pass `--no-verify`, as the shift and the transcript capture loop do: the repository's pre-push hook typechecks the workspace for about three minutes, in which the capture loop's pushes move the tip and a push that ran the hook is refused. Each push rebases onto the remote tip first and is retried after 2, 4, 8 and 16 seconds, a rebase that failed being aborted before the next try. Each attempt holds the push lock `ENTERPRISE_PUSH_LOCK` (default `/tmp/dsh-push.lock`) around its pull and push, waiting up to `ENTERPRISE_PUSH_LOCK_WAIT` seconds (default 1800), and a lock not taken in time fails the push; the cycle exports both to the shift, whose engine holds the same lock from its fetch through its recertification to its push, and the transcript capture loop holds it around its pull, commit and push. A push whose rebase conflicts, as the roster, the scoreboard, the telemetry and the deck data that other writers also regenerate make it, is rebuilt on the remote tip: the unpushed commits' new files under `data/enterprise/` (function logs, intake and cycle records, admitted tickets) and their new ledger lines are saved under `TMPDIR`, the checkout is reset to the tip, both are restored (a line the tip already carries is not appended twice), `pnpm run roster` and `pnpm run enterprise:publish` regenerate the rest, and the rebuilt commit is pushed. A checkout that starts a cycle with unpushed commits pushes them the same way before its pull instead of failing the fast-forward. Only a dedicated linked worktree is ever reset; in any other checkout the rebuild fails and the commits stay. The enterprise runs it every two hours from a dedicated checkout of the development branch, so no operator's working tree is written to.

[`scripts/enterprise-scheduler.sh`](../../scripts/enterprise-scheduler.sh) keeps the cycle's times without an operator session. Started once, detached, in that checkout, it runs the cycle at `ENTERPRISE_SCHEDULE_MINUTE` (default 13) past every UTC hour divisible by `ENTERPRISE_SCHEDULE_HOURS` (default 2), writes each cycle's output to `<ENTERPRISE_CYCLE_LOGS>/cycle-<UTC stamp>.log` (default `/home/user/enterprise-cycles`), passes its environment to every cycle, and waits for each cycle it starts; at a slot where a cycle started by hand still runs, it waits for that cycle and then starts its own, so a long cycle delays the next one instead of skipping it. A second scheduler exits 4, and a schedule outside whole hours from 1 to 24 or minutes from 0 to 59 exits 2. A container restart ends it, so the scheduled Routine that watches the enterprise starts it again when it is not running.

## The cycle record

`cycles/<cycle id>.json` is what one cycle did, written by `pnpm run enterprise:cycle-record` ([`scripts/enterprise-cycle-record.ts`](../../scripts/enterprise-cycle-record.ts)) after the cycle's publish step and committed in its final commit, so the branch holds every cycle whose final push reached it, whatever became of the container-local log. The cycle script appends one `<name> <exit code> <UTC time>` line per step to a temporary file; the command reads that file and the checkout, validates the record, and never overwrites one. A record holds:

- `cycle`, `startedAt` (the moment the id stamps), `endedAt` (when the record was built) and `startedBy`, `scheduler` when `scripts/enterprise-scheduler.sh` is the cycle's parent process and `operator` otherwise (absent from a record whose cycle script predates it);
- `commits`: `start`, the checkout's commit when the cycle began, whose cycle script ran; `pulled`, the commit after the initial pull, whose ledger the cycle's lines are counted against; `end`, the commit the record was built on, the parent of the cycle's final commit;
- `steps`: every step that ran before the record, in order, as `{ name, exit, at }` — `pull`, `intake`, `intake-push`, `shift` (absent when an intake stopped at the usage limit skipped it), `pull-after-shift`, `functions`, `roster`, `publish`;
- `shifts`, `tickets` and `functions`: the shift ids of the ticket lines the ledger gained during the cycle, those ticket lines by status, and the function lines it gained by outcome, the ledger rows compared as a multiset so a rebase that reorders them counts each once; `unreadable` counts the gained rows no reader could use;
- `firstFailure`: the first step that exited non-zero, as `{ step, exit }`, or `null`;
- `previous`: the newest earlier record in the checkout, and `recordOnRemote`, whether the remote branch held it when this cycle's initial pull fetched it (`null` when the checkout has no remote-tracking ref).

A record cannot state its own final push: the next cycle's `previous.recordOnRemote` does, `true` when that push delivered it and `false` when it had not reached the remote branch by the next cycle's start, in which case the next cycle pushes the commits the checkout kept before its pull. A cycle that exited 4 or 5 before its first step, whose record could not be written, or that a container reset ended mid-run has no record; the branch shows such a cycle, and every cycle before the record existed, only by the commits it pushed, `chore(enterprise): <cycle id> intake` and `chore(enterprise): <cycle id> functions, roster and deck`, and the [report](#the-report) counts it as seen only in git history.

## The report

`pnpm run enterprise:report -- [--since <ISO>] [--until <ISO>] [--write]` ([`scripts/enterprise-report.ts`](../../scripts/enterprise-report.ts)) prints as Markdown what the enterprise did in a window, both ends inclusive; `--until` defaults to now and `--since` to 24 hours before `--until`. It reads the checkout — the ledger, the [cycle records](#the-cycle-record), the shift and intake records, the loss register `data/transcripts/LOSSES.md`, the recorded sessions, HEAD's git history, the roster generator — and Branch CI's runs from GitHub's REST API without credentials, through the proxy as the [functions](#functions) runner reads them, so over a fixed window it is deterministic given the repository and those answers. `--write` also writes `reports/<until as YYYY-MM-DDTHHMMZ>.json` and `.md`. A one-sentence headline of the pilot's exact counts opens it, and it reports:

- the cycles that started in the window: counted, clean and failed from their records with the count of cycles each step failed in, who started each (its record's `startedBy`, or the operator for a cycle that began before `scripts/enterprise-scheduler.sh` was first committed), whether each record reached the remote branch as the next record states, and every cycle without a record counted from the commits naming it and labelled as seen only in git history, its outcome unknown;
- the shifts: each shift record that began in the window with its program outcome and halt, each shift only ledger lines in the window show, and each shift the loss register names that left neither, dated by its id's time of day on the day of the register's first mention;
- the ticket lines dated in the window by status and by division, their reviews as approved, rejected or not reached, and the distinct tickets shipped with their commits;
- each shipped commit's Branch CI verdict: the runs whose head is that exact commit when one of them rendered a verdict or is still queued or running, else the first run created after the commit that rendered a verdict and whose head contains it in the checkout's history, labelled as coming from that later run and naming the commit's own runs a later push superseded, else `no run`;
- the function lines dated in the window by division and outcome;
- the spend, one total per source, each labelled with what it covers and never summed because they overlap: the ticket lines' token counts and seconds, the intake coordinators' counts, the tokens and model time of the recorded sessions whose newest event falls in the window per record tree (shifts, intake, Proving Ground, code safety), the function lines' seconds, and the recorded cycles' wall time;
- seats defined, occupied and active by division, from the roster generator run at the window's end over the ledger lines and recorded sessions dated at or before it.

What the data does not show is listed under Unknown rather than inferred: a cycle seen only in git history or whose starter no record states, a lost shift's tickets and spend, an unreadable record or ledger row, a verdict the API could not give or whose run head the checkout lacks, a line or coordinator without a token count, a session the fold could not read, and a record whose push no later record has stated yet.

`pnpm run enterprise:verdicts` ([`scripts/enterprise-verdicts.ts`](../../scripts/enterprise-verdicts.ts)) prints as a Markdown table every commit the ledger's ticket lines shipped, from the ledger's first line to now, with the tickets it carries, its verdict, the basis (`exact`, `later`, `none` or `unknown`), which run that is, and the run's page, each answered as the report answers it.
