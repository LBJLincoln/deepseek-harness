## 证据表明什么

- **已交付的工作。** 2 张工单在由操作员启动的班次 182951-78a6 中交付：T-0012 (`1d6a5d343`) 与 T-0019 (`cfe0a75f7`)。每张都通过了全部 6 项检查，并由一位没有调用任何工具的审阅者批准。没有任何 Branch CI 运行单独测试过其中任何一个确切提交。携带它们的推送的包含运行失败：它引入了 `translation pairing` 的失败，而 `test:snapshot` 与 `web browser snapshot` 在该班次之前已经失败；第一次包含它们的完全成功运行在推送 35 分钟后、于 19:40 UTC 结束。
- **无人值守的周期。** `cycle-20260928T201148Z` 的班次没有在分支上留下任何记录：[LOSSES.md](../../data/transcripts/LOSSES.md) 记载它在 22:07Z 的容器重置中丢失。调度器启动的周期尚未交付任何工单。
- **基准测试。** 在 44 个内部编写的环境上，更大的模型在第 5 层级上胜过中间模型（16 个单元中 16 对 13，+0.19，区间 [0.13, 0.25]）；harness 循环与产品自身的循环持平（16 个中 15 对 14，无定论）；把尝试次数从三次减到一次会降低认证率（−0.38，区间 [−0.56, −0.19]）。尚无冻结配对实验推动过 harness 的改动。
- **安全审查。** 在 NodeGoat 同一修订版上的三层对比中（每层各运行一次），扫描器、单个模型的单次审查与本企业记录 `2026-09-21-nodegoat-3`分别找到 18 个已记录问题中的 4 个、15 个 与 13 个，均以发现落在问题行范围三行以内为准；单次审查的发现未经行级验证，其运行间波动也未测量。依据对本企业在该应用上漏报的诊断编写检查清单后，两次运行分别找到 18 与 18 个，未使用时为 14 与 15 个；这是样本内读数，这些清单能否迁移到其他代码库尚未验证。在 dvja 上找到 14 个中的 13 个。

## 数据流向

- **模型请求。** 各部门、审阅者与受理协调员通过操作员的 Claude Code 登录运行：每次模型请求，连同部门读取的每个文件的内容，都在该账户下发送到 Anthropic 的模型 API。
- **发布的记录。** 班次记录提交每个会话日志，实时捕获每五分钟把操作员与各部门的对话记录提交到本仓库；该仓库在 GitHub 上的可见性为 public。
- **客户合作的要求。** 在读取任何客户代码之前：一个签有数据处理协议（DPA）并启用零数据保留的 Anthropic API 组织，以及一个存放记录的私有仓库。
- **完整说明。** [数据处理](data-handling.md)列出每一个去向、各自的条款，以及仍待操作员作出的决定。

## 控制措施

- **隔离。** 基准单元在 Linux 上的沙箱（bubblewrap，然后 Landlock）中运行；班次部门尚未在沙箱中运行，而是在无法推送的临时克隆的独立 worktree 中运行。
- **职责分离。** 审阅者是一个没有父会话、工作目录为空的新会话，只阅读差异、提交说明与检查输出；班次 171951-516d 的审阅会话仍调用了 6 次工具，此后引擎移除了审阅者的全部工具，班次 182951-78a6 与 001527-881f 的审阅会话没有调用工具。代码安全发现由已提交的检查器逐行核对（14 份记录中 14 份退出码为 0）。
- **签署。** 在推送之前，没有任何人员签署变更。引擎自行决定班次的规格冻结与发布。5 份记录中的签署事件由引擎在程序启动时写入，间隔不超过 2 毫秒，主体为 `enterprise-operator` 与 `enterprise-intake-operator`，类型标为 `human`。3 份记录以机器主体 `daliesk-enterprise-shift` 载有引擎的决定。

## 局限与风险

- **规模。** 试点共交付 2 张工单，另有 39 张未关闭；7 个班次记录。
- **CI。** 自 2026 年 9 月 27 日 15:36 UTC 以来，71 次已完成的 Branch CI 运行中有 13 次成功，最近一次有结论的运行失败。
- **数据使用条款。** 1,798 个基准会话中有 1,688 个固定了数据使用条款；代码安全会话 114 个中有 0 个、班次会话 19 个中有 0 个与受理会话 4 个中有 0 个。
- **单一供应商。** 已记录会话按供应商路由统计：claude-code 1,283、openrouter 29。

## 合作方式

先满足上述数据流向要求，并在每个会话上固定写明客户、协议、用途、驻留地与保留期限的数据使用条款；然后对客户选定的代码库做一次代码安全审查，由客户自己的工程师核对每一项发现；再在一个一致认可的队列上运行受监督的班次，每次发布由一位人员签署；最后依据测得的记录决定是否继续。目前记录在案的代码安全审查对象是 OWASP NodeGoat、Damn Vulnerable Java Application (dvja) 与 本仓库自身的代码。
